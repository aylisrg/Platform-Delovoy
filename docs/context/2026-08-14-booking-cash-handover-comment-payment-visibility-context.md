# Context: Передача кассы в бухгалтерию, заметка оператора, явный статус оплаты

**RUN_ID**: `2026-08-14-booking-cash-handover-comment-payment-visibility`

**Инициатор**: владелец парка «Деловой», три улучшения в бронях одним запросом
**PRD**: `docs/requirements/2026-08-14-booking-cash-handover-comment-payment-visibility-prd.md`

## PO — Ключевые решения

### R1: «Касса» — не новая сущность, а один недостающий шаг поверх уже существующей

Владелец прямо попросил «создать сущность Кассы». Проверено по коду: денежный журнал по каждой операции уже есть и не требует пересборки — `prisma.FinancialTransaction` (иммутабельный леджер: кто принял, сколько нал/карта, когда, привязка к брони). Плюс у Плей Парка уже есть дневная смена `ShiftHandover` (открыть/закрыть смену, авторасчёт кассы/карты из журнала). У Беседок такой смены нет — только сам журнал операций.

Единственный реальный пробел — шаг «менеджер закрыл смену → физически передал наличные бухгалтеру → зафиксировал, сколько отдал, кому и сошлось ли с расчётом». Это не новый факт, требующий новой модели — это несколько дополнительных полей к уже существующей `ShiftHandover` (переданная сумма, получатель, комментарий расхождения) плюс экран. PO отклоняет буквальное «создать сущность Кассы» по той же логике, что в PRD 2026-08-13 отклонялось буквальное превращение оплаты в enum-статус (см. R7 контекста от 2026-08-13): дать владельцу то, что он видит на экране («передал кассу в бухгалтерию, указал сумму»), не значит реализовывать это дословно как отдельную новую сущность, если существующие данные это уже покрывают почти полностью.

### R2: Асимметрия между модулями — Плей Парк почти готов, Беседки с нуля

По коду подтверждено: `getDayReport`/`openShift`/`closeShift` (`src/modules/ps-park/service.ts`) целиком завязаны на `MODULE_SLUG = "ps-park"`, у Беседок эквивалента нет вообще (ни экрана смены, ни открытия/закрытия дня — только период-агрегированная аналитика). Модель `ShiftHandover` в схеме уже module-slug-агностична (`@@unique([moduleSlug, date])`, дефолт `"ps-park"` — не хардкод), но сервисный слой — нет. Отсюда решение о фазировании: US-1 (передача в бухгалтерию) — Фаза 1 только для Плей Парка, как дешёвое расширение готового; US-3 (вся смена целиком для Беседок) — Фаза 3, потому что объём работы кратно больше. Это не игнорирование запроса по Беседкам, а осознанная последовательность по эффекту/усилию.

### R3: Нет роли «Бухгалтер» — получатель передачи как свободный текст, не как учётная запись

`Role` enum в схеме — только `SUPERADMIN | MANAGER | USER`, никакой связки «кто принимает деньги на стороне бухгалтерии» не существует. Добавлять новую роль — самостоятельное RBAC-решение с более широким влиянием (модульные права, `AdminPermission`, section-доступ), выходящее за рамки одного PRD про брони. PO сознательно не предлагает новую роль в этой итерации: получатель фиксируется как свободный текст («кому передано»), подтверждение с его стороны через систему — явно вынесено в «Вне скоупа» и в «Открытые вопросы» для владельца, а не решено явочным порядком.

### R4: Расхождение кассы — обязательный комментарий при любом ненулевом отличии, порог не настраиваем

Решение сознательно строгое: любое расхождение между расчётной и переданной суммой (даже 50 ₽) требует текстового объяснения перед сохранением (US-1 AC-2). Настраиваемый владельцем порог «предупреждать только если больше N ₽» не делаем в этой итерации — это отдельная настройка, которая сама по себе может подождать, пока не появится практика использования и реальное понимание, какие расхождения типичны (мелкие округления кассы vs реальная недостача).

### R5: Заметка оператора — разделяем по источнику, не пытаемся атрибутировать задним числом legacy-данные

Ключевая находка по коду: `metadata.comment` у брони заполняется **и** гостем на публичной форме бронирования (`booking-flow.tsx`, подпись «Комментарий», плейсхолдер «Пожелания, особые условия...»), **и** оператором в форме брони по звонку (`admin-booking-form.tsx`, подпись «Комментарий», плейсхолдер «Доп. информация») — в одно и то же поле, без указания автора. Карточка брони показывает оба одинаково. Это и есть источник путаницы, на которую жалуется владелец.

Решение — развести поля на уровне продукта (US-4): «Пожелание гостя» (гость пишет, только для чтения персоналом) и «Заметка администратора» (пишет и редактирует персонал, не видна гостю). Для уже существующих броней с заполненным старым общим полем — PO явно запрещает угадывать автора задним числом (AC-5): текст сохраняется, но показывается нейтрально, без ложной атрибуции «это гость» или «это оператор», которую система не может знать наверняка.

### R6: Заметка администратора — редактируемая и с историей факта изменения, не diff текста

В отличие от текущего `comment` (пишется один раз при создании, не редактируется), заметка администратора должна быть редактируемой (менеджер уточняет информацию по ходу общения с клиентом). Изменение логируется как событие в уже существующей ленте истории брони (`AuditLog`, выпущено вчера/сегодня, 2026-08-13) — PO намеренно требует только факт и время правки, не полнотекстовый diff «было/стало», чтобы не плодить более тяжёлую функциональность, чем нужно для заявленной ценности («легко читалось», а не «полный аудит правок текста»).

### R7: Статус оплаты — десктоп уже частично решён, мобильные экраны почти пусты

При проверке кода обнаружено расхождение по готовности между экранами внутри одного и того же вчерашнего релиза:

- Десктопная таблица истории броней (`booking-history-table.tsx`, оба модуля) уже показывает `PaymentBadge` (касса+карта+онлайн) и вдобавок узкоспециальный `BookingPaymentBadge` (только для состояний «возврат»/«ожидание онлайн-оплаты», которые общая сумма не показывает) — это уже правильный, продуманный паттерн, задокументированный прямо в коде.
- Мобильный список броней Беседок (`booking-list-mobile.tsx`) показывает **только** `BookingPaymentBadge` (статус именно онлайн-платежа) — бронь, оплаченная наличными или картой на месте (то есть подавляющее большинство броней по телефону), не получает вообще никакого индикатора оплаты на этом экране.
- Мобильный список Плей Парка не показывает индикатор оплаты вообще, в любом виде.
- Мобильная лента дня (вертикальный список слотов, `mobile-timeline.tsx`) в обоих модулях не показывает ни статус оплаты, ни признак заметки — вообще никакой дополнительной информации, кроме имени и статуса жизненного цикла.

Это меняет масштаб проблемы: заявленная владельцем «плохая читаемость серого кружка» — это верхушка; на мобильных экранах, которыми, по его словам, реально пользуются менеджеры на смене, индикатора часто нет вовсе. US-7 сформулирована так, чтобы закрыть именно это, а не только перекрасить кружок из US-6.

### R8: US-6 (доработка сегодняшнего значка) и US-7 (мобильные экраны) — Must have, наравне с US-1

PO намеренно ставит эти две user story в Фазу 1 вместе с кассовой передачей, а не в «Should have» вместе с остальной частью 2/3. Обоснование: обе — это фактически недоделанная часть уже выпущенной сегодня функции (значок оплаты), а не новая фича с нуля; риск — гость, с которого повторно требуют оплату, или неоплаченная бронь, принятая менеджером за оплаченную из-за низкой контрастности/отсутствия индикатора на телефоне. Это прямой риск для денег и для доверия гостя, что соответствует критерию Must have в этом проекте.

## Открытые вопросы для Architect

1. Схема хранения передачи в бухгалтерию (US-1) — дополнительные поля в `ShiftHandover` или отдельная дочерняя запись (на случай нескольких частичных передач за одну смену).
2. Перенос `getDayReport`/`openShift`/`closeShift` из `ps-park/service.ts` в общий `booking`-модуль до реализации US-3 (Беседки) — чтобы не дублировать логику между модулями второй раз подряд (та же ловушка, что уже было решено не повторять для истории брони 2026-08-13).
3. Точный визуальный язык признака «не оплачено» в сетке (US-6, AC-1) — PO требует различимость не только по цвету (доступность), конкретную реализацию (иконка/форма) оставляет на усмотрение Architect/Developer.
4. Именование/хранение отдельных полей «пожелание гостя» и «заметка администратора» (US-4) взамен общего `metadata.comment`, включая обратную совместимость с уже существующими бронями (см. R5, AC-5).

## Открытый вопрос для владельца

Нужна ли уже сейчас возможность подтверждения получения денег бухгалтером через систему (то есть доступ бухгалтера к платформе), или на первой итерации достаточно, что передачу фиксирует сам менеджер (см. «Вне скоупа» в PRD, R3)? Если нужна — PO пересмотрит приоритет и вынесет это отдельным вопросом к Architect по RBAC.
