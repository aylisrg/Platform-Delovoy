## PO — Ключевые решения

### Решение 1: Критерий `isExpired` — `now >= endTime`, а не `remainingMinutes === 0`

**Вопрос**: как определить момент перехода в красное состояние?

**Решение**: `isExpired = Date.now() >= new Date(session.endTime).getTime()`, вычисляется непосредственно в `updateProgress()` в миллисекундах, независимо от округлённого `remainingMinutes`.

**Обоснование**: `remainingMinutes` вычисляется через `Math.round()`, что создаёт неоднозначность в граничный момент: при `remaining = 0.3 мин` код выдаёт `remainingMinutes = 0`, но `now < endTime`. Вычисление напрямую из `Date.now()` и `endTime` устраняет эту двусмысленность. Граничный момент `now === endTime` — красный.

---

### Решение 2: Формат overrun-таймера — минуты до 59, затем «ч мин»

**Вопрос**: как отображать время просрочки? Только минуты или переключаться на часы?

**Решение**: «Просрочено: +X мин» при `X < 60`; «Просрочено: +Y ч Z мин» (или «+Y ч» при нулевых минутах) при `X >= 60`. Без верхнего ограничения.

**Обоснование**: просрочка более часа — аварийный сигнал. Усечение до «99 мин» или «99+» скрывает реальный масштаб проблемы. Формат с часами аналогичен уже существующей логике форматирования длительности сессии в строках 81–85 компонента — разработчику не нужно изобретать новую функцию.

---

### Решение 3: Пульсирующая точка в красном состоянии — `bg-red-500`

**Вопрос**: что делать с индикатором `animate-pulse bg-emerald-500` в шапке карточки при красном состоянии?

**Решение**: заменить на `bg-red-500` при `isExpired === true`. Анимацию `animate-pulse` сохранить.

**Обоснование**: зелёная пульсирующая точка на красной карточке создаёт визуальный диссонанс и обесценивает красный сигнал. Замена на красную точку входит в скоуп F2 (тот же файл) и не требует отдельного тикета. Альтернатива — убрать точку вовсе — отклонена: анимация усиливает срочность.

---

### Решение 4: Кнопки действий при просрочке — оставить активными

**Вопрос**: нужно ли блокировать «Продлить сессию» на просроченной карточке?

**Решение**: все три кнопки («Добавить позиции», «Продлить», «Завершить») остаются активными в красном состоянии. Изменение их поведения — вне скоупа F2.

**Обоснование**: блокировка «Продлить» при просрочке имеет смысл бизнесово (зачем продлевать истёкшую сессию?), но является отдельной product-decision. F2 — только визуальный сигнал. Добавление блокировки кнопок без отдельного PRD — scope creep. Менеджер технически может «продлить» просроченную сессию уже сейчас через UI — это останется возможным до отдельного решения.

---

### Решение 5: MoSCoW — «Should have», не «Must have»

**Вопрос**: почему F2 не «Must have», если F1 без неё теряет половину ценности?

**Решение**: «Should have». F1 (запрет завершения без оплаты) — Must have, потому что напрямую блокирует потерю выручки. F2 (красный цвет) — Should have, потому что менеджер может выполнить задачу (закрыть сессию с оплатой) даже без красного сигнала — просто медленнее и с большим риском пропустить просроченную карточку. Красный цвет ускоряет реакцию, но не является операционным блокером.

**Следствие для планирования**: F2 может войти в тот же релиз, что и F1, но не блокирует его.

---

### Решение 6: Тесты — 5 тест-кейсов, не snapshot

**Вопрос**: snapshot-тесты или explicit assertions на CSS-классы?

**Решение**: explicit assertions на наличие конкретных CSS-классов (`expect(card).toHaveClass('border-red-500')` и т.д.) через Testing Library. Snapshot-тесты не рекомендуются для компонентов с Tailwind — они хрупкие к косметическим изменениям классов, которые не влияют на поведение.

**Тест-кейсы**: зелёное состояние, жёлтое состояние, красное состояние, граничный случай `endTime === now`, приоритет `isExpired` над `isEnding`.

## Architect — Ключевые решения

### Решение A1: `isExpired` хранить в `useState`, не вычислять inline

`useEffect → updateProgress()` обновляет два **новых** state-поля одновременно с существующими `remainingMinutes` и `progressPercent`:

```ts
const [isExpired, setIsExpired] = useState(false);
const [overrunMinutes, setOverrunMinutes] = useState(0);
```

Альтернатива (inline `Date.now() >= endMs` при каждом рендере) отклонена: создаёт рассинхрон с `remainingMinutes` (он из state, обновляется раз в 30 сек), что в граничный момент даёт визуальный конфликт «контейнер красный, бейдж говорит "0 мин"» и делает тесты недетерминированными.

### Решение A2: Тернарная каскадная классификация без `cn`/`clsx`

В проекте нет `clsx`/`cn` — соседние компоненты в `src/components/admin/ps-park/` используют шаблонные литералы. Не вводим новую зависимость ради одного места. Каскадная тернарная (`isExpired ? red : isEnding ? amber : emerald`) выносится в локальные `const cardClass`, `const badgeClass`, `const progressBarClass` перед `return` — JSX остаётся плоским.

### Решение A3: Сужение `isEnding` для приоритета `isExpired > isEnding`

`isEnding = !isExpired && remainingMinutes <= 10 && remainingMinutes > 0`. Это закрывает PRD AC US-1 #8 (взаимоисключение трёх состояний). Старый текст бейджа `remainingMinutes > 0 ? "${X} мин" : "Время вышло"` удаляется — кейс `remainingMinutes === 0` теперь покрывается `isExpired` через `formatOverrun()`.

### Решение A4: `formatOverrun` — локальная функция в файле, не общий хелпер

Новый формат «Просрочено: +X мин / +Y ч Z мин» используется только здесь. Существующий IIFE строк 81–85 форматирует `durationMin` без префикса в формате «Yч Zмин» (без пробелов) — другая семантика, переиспользование сломает читаемость. Вынос в `@/lib/format` через параметризованный `formatDuration({ prefix, sep })` — over-engineering для одного места (нарушает «не переусложняй» из CLAUDE.md). Если позже появится третий формат — отдельный refactor-тикет. Функцию делаем `export function formatOverrun(min: number)` — для unit-тестируемости даже без jsdom.

### Решение A5: Тесты — два уровня в зависимости от наличия jsdom-инфры

В репозитории `vitest.config.ts` использует `environment: "node"`, нет `@testing-library/react`/`jsdom` в devDeps, нет ни одного теста React-компонента в `src/components/`. **F2 — потенциально первый компонентный тест в проекте.**
