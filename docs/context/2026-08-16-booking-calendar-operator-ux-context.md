## PO — Ключевые решения

### R1: Текст issue частично неточен по факту кода — PRD исправляет, а не копирует формулировки

Issue #442 описывает 7 пунктов как имеющиеся факты о коде («API принимает reason», «POST /api/gazebos есть»). Проверка кода перед написанием PRD (обязательный шаг из `agents/po.md`, п.5) показала два расхождения:
- «Причина отмены» (пункт 6) — на самом деле уже полностью реализована (см. R2).
- «UI создания ресурса» (пункт 7) — заявлено «POST /api/gazebos есть, кнопки нет»; по факту `POST` роута нет вовсе (только `GET`), сервисная функция `createResource()` — мёртвый код без единого вызова. Пробел больше, чем описан в issue: нужен и роут, и UI, не только UI.

PRD зафиксировал это явно в разделе «Что уже реализовано», чтобы Architect/Developer не унаследовали неверную оценку объёма работы из текста issue.

### R2: Пункт «причина отмены» снят со скоупа — уже сделано другим PRD

Между датой issue (2026-08-10) и сегодня (2026-08-16) фича была независимо доставлена через `docs/requirements/2026-08-13-gazebos-booking-safety-history-paid-prd.md` (US-2: подтверждение перед отменой с полем причины). Подтверждено в коде: `ConfirmDialog` (`src/components/admin/shared/confirm-dialog.tsx`) с полем `reason`, подключено в обеих карточках брони (`gazebos`, `ps-park`), причина доходит до `Booking.cancelReason` через PATCH-роут и `cancelBooking()`. Решение: явно исключить из PRD и из будущей декомпозиции — только пометка «уже сделано» и рекомендация регрессионного QA-чека, без нового PR. Без этого решения `/plan-epic` рисковал завести дублирующую задачу на уже закрытый пробел.

### R3: Формат — один PRD на пару модулей, а не 12 параллельных user story

Правило `agents/po.md` п.4 («Один PRD — один модуль, для cross-module фичи — отдельная story на модуль») применено по прецеденту `2026-08-13-...-prd.md`: беседки и Плей Парк намеренно построены на одной модели `Booking` и одном FSM переходов статусов, поэтому 6 итоговых story в этом PRD пишут явные общие AC («поведение идентично для беседок и Плей Парка») вместо дублирования на 12 почти одинаковых story. Точечные различия (например, drag-and-drop только для беседок в v1) вынесены в отдельные AC внутри той же story, а не в отдельную story.

### R4: Месяц явно вне скоупа — только неделя

Issue перечисляет «недельный/месячный» через слэш. PO трактует это как альтернативы, не как двойное требование, и явно ограничивает v1 недельным видом: месячная детализация нечитаема на часовом уровне текущей сетки, а отдельного запроса на месяц от владельца не зафиксировано. Решение зафиксировано в PRD как «Вне скоупа», чтобы decomposition не расширила US-5 на месяц по умолчанию.

### R5: Drag-and-drop сознательно урезан для v1 — десктоп, только беседки

Два независимых основания:
1. Задокументированный профиль операторов («часто на телефоне», прецедент PRD 2026-08-13) — drag-жест на мелкой сенсорной сетке менее надёжен, чем контролируемая форма редактирования, и это не гипотеза, а уже отмеченный в проекте факт о том, как реально работают операторы.
2. Перенос через drag и перенос через форму используют один и тот же серверный путь (`rescheduleBooking` с конфликт-чеком и advisory-lock, доработанным в P0-7/#429) — drag-and-drop не открывает новую зону риска по данным, поэтому урезание скоупа v1 — вопрос экономии усилий разработки и снижения UX-шума на touch, а не вопрос безопасности.

### R6: Автокомплит гостя (US-2) — архитектурная развилка зафиксирована, решение не предрешено

При чтении кода обнаружено: очевидный источник данных для автокомплита (`/api/admin/clients`) закрыт RBAC-гейтом `requireAdminSection(session, "clients")`, который типичный MANAGER беседок/Плей Парка не проходит (он назначен только на свой модуль, не на `clients`). Это не мелочь UI — без решения фича не заработает для целевой персоны. PO нашёл и задокументировал альтернативу без этой проблемы: у каждого модуля уже есть свой RBAC-чистый поиск по броням (`bookingFilterSchema.search`, сделано в P1-9), который можно использовать вместо CRM-эндпоинта. PO намеренно не выбирает между «расширить RBAC CRM-эндпоинта» и «строить автокомплит на данных модуля» — оставляет это Architect, но требует (жёсткий AC, не пожелание), чтобы выбранное решение действительно работало для оператора без доступа к разделу «Клиенты».

### R7: Общий календарный компонент vs дублирование по модулю — вопрос поднят, не решён

Найдено, что `TimelineBooking` в `src/modules/gazebos/types.ts` и `src/modules/ps-park/types.ts` сегодня побайтово идентичен. `TimelineData` той же формы, но не буквально идентичен: `resources` в нём ссылается на `GazeboResource`/`TimelineResource` соответственно, а эти типы расходятся не косметически — `GazeboResource.pricePerHour` остаётся сырым Prisma `Decimal | null` (`Pick<Resource, ...>`), у ps-park `TimelineResource.pricePerHour` уже нормализован до `number | null`. Вынос общего `TimelineData` потребует сначала свести эту нормализацию, а не «бесплатен» в буквальном смысле — при этом весь остальной доменный UI календаря дублируется по модулю по устоявшейся в проекте конвенции. Этот эпик — третье по счёту крупное наращивание одной и той же дублированной сетки. PO не предписывает Architect'у выносить общий компонент — это решение о стоимости владения, не о продуктовой ценности — но требует явного, задокументированного решения вместо продолжения дублирования по умолчанию/инерции.

### R8: Ни один пункт не поднят до Must

Все 6 актуальных story — операционные улучшения поверх уже работающего инструмента: у каждого пункта есть работающий сегодня fallback (ручной ввод, форма редактирования, бумажный журнал). Это соответствует собственной классификации эпика владельцем как P2 («бэклог после стабилизации перезапуска») — PO не поднимает приоритет искусственно вопреки этой классификации.

## Architect — Ключевые решения

**Дата:** 2026-08-23 · **Issue:** #669 (architecture spike) · **ADR:** `docs/architecture/2026-08-23-booking-calendar-week-view-drag-drop-adr.md`

Spike закрывает открытые вопросы 2, 3 и 4 (вопрос 1 закрыт по факту реализацией
#666 — автокомплит построен на `searchGuestsByPhone(moduleSlug, …)` по броням
модуля, без доступа к CRM; вопрос 5 закрыт: US-1…US-4 доставлены как #665–#668).

### A1: Недельный вид берёт данные одним диапазонным запросом, а не семью дневными

Отвергнуты и «N параллельных вызовов `/api/{module}/timeline`» (7 round-trip'ов,
≈28 запросов в БД вместо ≈4, «рваная неделя» при частичном отказе — пустая
ячейка неотличима от свободного слота, что для замены журнала худший вид отказа,
плюс лимит `authenticated` расходуется в 7 раз быстрее), и «расширить
`timelineQuerySchema` до `dateTo`» (мутация горячего пути, от которого зависят
4 UI-поверхности и 2 server-компонента; условный тип возврата; неограниченный
диапазонный скан). Принято: новый sibling-эндпоинт
`GET /api/{gazebos|ps-park}/week-timeline?weekStart=` поверх общей
`getWeekTimeline(moduleSlug, weekStart)` в `src/modules/booking/week-timeline.ts`.
Окно жёстко 7 дней, `weekStart` нормализуется сервером к понедельнику — клиент
не может запросить произвольный диапазон. Индекс `@@index([moduleSlug, date])`
уже есть, миграции не нужны. Тот же приём, что в #668 (`print-schedule`
сделан соседней функцией, а не расширением `getTimeline`).

### A2: Макет недели — матрица «ресурс × день», а не 7 колонок текущей сетки

Расширить процентную геометрию на 7 дней нельзя арифметически: сегодня 100 %
ширины дорожки = 15 часов при `min-w-[900px]` (~60 px/час); неделя в той же
геометрии — 105 часовых колонок (~4200 px при читаемом масштабе), а каждая
строка ресурса уже имеет собственный `overflow-x-auto`. Сжать в 900 px —
8.5 px/час, где часовая геометрия перестаёт нести информацию. Принято:
7 колонок-дней × N строк-ресурсов, в ячейке — чипы броней `10:00–14:00 · Иванов`,
статус цветом, оплата существующим `PaymentDot`, в подвале «занято X из Y ч».
Клик по чипу → существующая карточка брони (AC-3), клик по пустой ячейке →
переключение в дневной вид на эту дату (AC-6, минимально допустимый вариант).
Дневная сетка не переписывается — к ней добавляется только переключатель
«День / Неделя» (локальное состояние, без `?view=` в URL, чтобы не трогать
контракт deep-link `?date=&booking=`).

### A3: Общим делается только новая поверхность — дневная сетка остаётся дублированной (ответ на R7)

Явное решение, а не инерция. Ключевой факт: вся модуль-специфика двух
`timeline-grid.tsx` сидит в **пути создания брони** (pricing выходного дня у
беседок, `guestCount` vs `playerCount`, свои quick-формы) — а в недельном виде
пути создания нет вовсе (AC-6 отправляет в дневной вид). Остаётся ровно две
точки различия: подписи и компонент карточки брони. Поэтому: общий
`getWeekTimeline(moduleSlug, …)` в `booking`, общая
`weekTimelineQuerySchema` в `booking/validation.ts`, общий
`src/components/admin/shared/week-schedule-grid.tsx` с пропсами `moduleSlug` +
подписи и колбэками `onBookingClick`/`onEmptyCellClick`; карточку рендерит
модуль-обёртка. Big-bang-вынос дневной сетки отвергнут: он требует сначала
свести `Decimal` vs `number` у `pricePerHour` (тронуть тип, которым пользуется
весь модуль беседок) и параметризовать общий компонент двумя quick-формами —
крупный рефакторинг двух ежедневных production-поверхностей с нулевой
пользовательской ценностью, уезжающий в прод деплой-трейном вместе с фичей.
`pricePerHour` в новых недельных типах нормализуется к `number` сразу (#614);
`GazeboResource` не трогается — это отдельный техдолг, не нужный ни US-5, ни US-6.

### A4: Drag-and-drop делаем — серверная часть уже оплачена, отказ не обоснован

PRD допускал отказ «с обоснованием», но факты против: `PATCH
/api/gazebos/bookings/:id` **без** `status` уже уходит в `rescheduleBooking()`,
где есть `lockSlot()` (#429), конфликт-чек в той же транзакции, EXCLUDE-бэкстоп
`booking_no_overlap`, `AuditLog booking.reschedule`, `metadata.edits`,
синхронизация Google Calendar (включая перенос события между календарями при
смене беседки) и `enqueueNotification("booking.rescheduled")` — то есть AC-3 и
AC-4 выполняются буквально тем же HTTP-вызовом, что делает форма редактирования.
Серверных изменений — ноль, новых зависимостей — ноль (`@dnd-kit` в `package.json`).

Техника интеграции с абсолютным процентным позиционированием: **гибрид** —
`useDroppable` на строку ресурса (5 зон вместо 75 часовых), а время из
`event.delta.x` через измеренную `getBoundingClientRect()` ширину дорожки со
snap'ом в 30 минут; отсчёт от сдвига блока, а не позиции курсора. Растяжение —
отдельный `useDraggable` на ручке правого края (`resize:<id>`). Единственный
по-настоящему нетривиальный кусок — `DragOverlay`: строки ресурсов имеют
собственный `overflow-x-auto`, и без портала блок обрезается при переносе на
соседнюю строку. Чистые функции перевода координат выносятся в
`src/lib/timeline-drag.ts` — тестируются без DOM. Оценка: ~250–350 строк
фронтенда. Обязательное правило: при нулевом смещении после snap запрос не
отправляется вовсе — иначе дрожание мышью стоило бы гостю уведомления.

### A5: US-6 не зависит от US-5 функционально, но идёт после него по порядку правок

Drag ограничен дневным видом (PRD AC-1), в недельной матрице не вводится.
Но обе задачи правят `src/components/admin/gazebos/timeline-grid.tsx`, поэтому
рекомендуемый порядок — US-5, затем US-6 поверх; при взятии одной сессией их
правильно скомпоновать в один PR (Scope guard #3). Скоуп US-6 остаётся строго
по PRD: только беседки, только десктоп, одна бронь за операцию;
`mobile-timeline.tsx` обоих модулей не меняется ни строкой.

### A6: RBAC нового эндпоинта копирует гейт дневного, а не вводит новую ось доступа

`auth()` → `hasRole(session.user, "MANAGER")` → `requireAdminSection(session, slug)`
+ `rateLimit(request, "authenticated", session.user.id)`. `hasModuleAccess`
(ось `ModuleAssignment`) сознательно не используется: все админские роуты
`/api/gazebos/*` и `/api/ps-park/*` гейтятся `AdminPermission`-осью, и смешение
дало бы «дневное расписание видно, недельное — 403» при одном наборе прав.
Данные в выдаче — те же поля, что уже отдаёт `/timeline`, только за 7 дней;
новых PII и внутренних идентификаторов не появляется. Мутаций у эндпоинта нет,
поэтому `AuditLog` не трогаем; мутация drag'а логируется существующей записью
`booking.reschedule` (второй записью история брони задвоилась бы).
