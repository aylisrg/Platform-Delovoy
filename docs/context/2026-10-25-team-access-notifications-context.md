## Исследование (координатор, до PO)

### Почему пользователь не удаляется
- `DELETE /api/users/[id]` → `deleteUser` (`src/modules/users/service.ts:199`): жёсткий
  `prisma.user.delete`. Пре-чек только `Subscription`. Иначе P2003 → 409
  `USER_HAS_DEPENDENCIES` «Нельзя удалить пользователя: на него ссылаются другие записи.»,
  UI — `alert()` (`src/components/admin/users/users-list.tsx:173-189`).
- RESTRICT-FK на `User`: `AuditLog.userId` (каждый вход пишет строку — `src/lib/auth.ts:130`,
  бот `bot/handlers/auth-deeplink.ts:349`), `ModuleAssignment` (сидер
  `scripts/seeds/nedelovoy-grants.ts` даёт всем SUPERADMIN на каждом деплое), `TaskAssignee`,
  `FeedbackItem`, `Subscription`, `MergeCandidate.*`, `Chat.createdByUserId`,
  `ChatParticipant`, `ChatMessage.senderUserId`, `ChatMessageReceipt`; косвенно
  `OutgoingNotification.channelId → UserNotificationChannel` (каскад канала упирается в RESTRICT).
- «Команда» = `role IN (SUPERADMIN, ADMIN, MANAGER)` (`users/service.ts:81-83`).
- Действия «исключить из команды» нет. Смена роли на USER (`updateUser`) меняет только
  `role` — `AdminPermission`, `ModuleAssignment`, `Module.config.notificationRecipients`
  (рассылается без перепроверки роли), подписки и Telegram-канал остаются.
- JWT: `token.role`/`adminSections` обновляются только при логине или `trigger==="update"`
  (`src/lib/auth.config.ts:92-108`, `src/lib/auth.ts:79-115`) — понижённый сохраняет доступ
  до перелогина. Отзыва сессий нет.
- Модалка «Права» для SUPERADMIN не сохраняется: GET отдаёт все нестрогие разделы, PUT
  отвечает 400 `INVALID_ROLE` (`src/app/api/admin/permissions/[userId]/route.ts:100-106`).
- `/admin/users/[id]` не существует. `/admin/clients/[id]` — только `role: USER`.
- `SUPERADMIN_TELEGRAM_ID` в `scripts/seeds/core.ts:63-66` повышает до SUPERADMIN на каждом деплое.

- Подписки — `NotificationEventPreference` (opt-in: строка `enabled=true`), Центр в Mini App
  `src/modules/notifications/webapp-center.ts`, видимость категорий —

- Резолв получателей `notifyAdmin` (`src/modules/notifications/service.ts:303-409`):
  список модуля `Module.config.notificationRecipients` (`recipients.ts:42-49`) +
  самоподписанные (`subscribers.ts:50-80`) + групповой чат модуля/системный.
  `dispatch()` (`dispatch/dispatcher.ts`) → `OutgoingNotification` → cron `process-outgoing`.
- Расхождения: получатель из списка модуля видит в Центре «выкл»; `avito.lead.new` шлётся
  по роли (`src/app/api/avito/webhook/messenger/route.ts:301-349`), «вкл» никого не добавляет;

- Админского управления чужими подписками нет (кроме `PATCH /api/users/[id]/notify-releases`).

### Статистика
- `OutgoingNotification` (status, sentAt, failureReason, readAt, attempts), `InAppNotification.readAt`,

- Единственный stats-эндпоинт `src/app/api/admin/notifications/routing-map/stats/route.ts` —

### Email + Telegram
- `User` имеет `email` и `telegramId` в одной строке, но:
  - `processDeepLink` (`src/modules/telegram-link/service.ts:265`) — 409 «Этот Telegram уже
    привязан к другому аккаунту», если человек раньше входил через бота (бот создаёт
    отдельный аккаунт, `bot/handlers/auth-deeplink.ts:220`, `source: "telegram_bot"`);
  - OTP-привязка (`requestLink`) код не отправляет — только `console.log`;
  - `previewMerge`/`mergeClients` (`src/modules/clients/service.ts:1023/1112`) — только `role: USER`.
- Признака «запустил бота / заблокировал бота» нет. Без `/start` бот не может писать
  пользователю — Telegram-доставка падает.

## Решения владельца (AskUserQuestion, 2026-10-25)
1. Удаление → **только «Исключить из команды»** (offboarding, аккаунт остаётся клиентом,
   история цела). Жёсткое удаление/обезличивание — вне scope. Кнопка «Удалить» объясняет,
   что мешает, и предлагает исключение.
2. Реакция → **прочтение + клики** (трекинг-ссылки, время до реакции), по сотруднику и по типу события.
3. Управление → **админ ставит, сотрудник может менять** (та же `NotificationEventPreference`,
   AuditLog с актором). Замка «обязательное» нет.
4. Email+TG → **объединение аккаунтов сотрудников + починка самопривязки**; галочка
   «бот запущен» с датой и признак «бот заблокирован».

## PO — Ключевые решения

PRD: `docs/requirements/2026-10-25-team-access-notifications-prd.md`. Четыре решения владельца приняты без пересмотра. Ниже — решения PO внутри них, дополнения к исследованию и то, что передано Architect.

### Рамки
- **Новых модулей нет.** Расширяются `users`, `notifications`, `telegram-link`, `clients` (+ сессии/авторизация, бот, админ-UI, `permissions`). Новые таблицы (клики, пропуски, признак бота, запросы на объединение) допустимы внутри существующих модулей — решает Architect. Синк таблицы модулей в CLAUDE.md в том же PR (Scope guard п.4).
- **Волны, не микро-PR** (Scope guard п.3): 1) блок A + раннее начало записи кликов/пропусков/признака бота (данные не восстановить задним числом); 2) блоки B, C, E1; 3) блок D и E2–E4. Нарезку определяет Architect.
- **Персональные данные:** адрес сотрудника из запроса владельца в PRD не воспроизводится (правило `agents/po.md`); в PRD он указан ссылкой на этот контекст-лог. Примеры в тестах — заглушки.

### Блок A: исключение
- «Исключить из команды» — **операция, не удаление**; атомарная (всё или ничего); идемпотентная (повтор/двойной клик/два админа — одно выполнение, без повторного журнала).
- Подписки при исключении **удаляются, а не выключаются**: ключ подписки (пользователь + тип события) общий с клиентскими уведомлениями (`booking.*`, `order.*`); «выкл» мог бы заглушить человеку его собственные брони. Вынесено Architect (вопрос 8).
- **Telegram-канал, брони, заказы, абонементы остаются** — человек становится клиентом, не «пустым» аккаунтом.
- Смена роли на USER через дропдаун = та же операция (владелец явно просил «без хвостов»). **Любое понижение** роли прекращает старые сессии — тот же класс уязвимости, иначе SUPERADMIN → MANAGER сохранял бы доступ до перелогина.
- Сидированный суперадмин (`SUPERADMIN_TELEGRAM_ID`): **предупреждение + отдельное подтверждение**, не запрет (так сказал владелец). При объединении такой аккаунт **нельзя вливать как вторичный** — сидер ищет суперадмина по Telegram ID и создал бы нового.
- Срок отзыва доступа: **цель — со следующего запроса, допуск ≤ 60 с**; механизм — Architect (вопрос 1; вход на JWT, edge-прокси без базы).
- Гарды: себя, последний суперадмин («последний» = единственный действующий, не влитый, не системный), повторное исключение, не-сотрудник.
- «Удалить»: окно с типами связей и счётчиками; для сотрудника — предложение исключения; для клиента — только объяснение. Аккаунты с историей не удаляются никогда.
- «Права»: суперадмин — Must (чиним 400); **ADMIN — Should**: при чтении кода выяснилось, что сервер отклоняет любые стандартные разделы и для ADMIN, хотя политика (`permissions.ts`, miniapp PRD) выдаёт ADMIN разделы явными правами. Это расхождение вне прямой просьбы владельца; оставлено Should с возвратом вопроса PO, если ограничение намеренное.

### Блок B/C: страница, права, «кто что получает»
- Страница `/admin/users/[id]` — **SUPERADMIN-only даже при выданной секции «Пользователи»** (так сегодня все `/api/users/*`). Открывается и для USER (нужно для вторичного ботового аккаунта при объединении).
- Статус доставки двухуровневый: **«Получает» (маршрут есть)** и **«Подписан, но не дойдёт» (канал заблокирован)**. Без этого админ видит «вкл» там, где сообщение теряется.
- **Один тумблер управляет всеми путями**: «выкл» перекрывает список раздела и роль (Авито), «вкл» добавляет получателя без членства в списке. Это снимает три найденных расхождения (список раздела = «выкл», Авито мимо тумблера, «суперадмины всегда»). Механика — Architect (вопрос 7); обязательная проверка — автотест «экран = реальные получатели» (AC-C1.6).
- Без замка (решение №3): сотрудник может перекрыть решение админа; видно «Изменено: кто, когда»; журнал с актором и источником (админка / Mini App).
- Админ **не создаёт канал за сотрудника** (владение Telegram подтверждает только сам человек); включение без канала разрешено с предупреждением.
- Матрица «сотрудники × события»: просмотр — Must, управление ячейкой — Should; подсвечивает события, которых лично не получает никто.
- Центр в Mini App: правда про список раздела и Авито — Must; расширение категорий ADMIN, подсказки про бота, заметка о прозрачности для сотрудников — Should.

### Блок D: статистика
- **Реакция = первое из: прочтение (лента) или клик**, максимум одна на уведомление. Для Telegram и Web Push прочтения нет технически — это написано в интерфейсе постоянной подписью; «доли прочтения» по Telegram не рисуем.
- **Честный знаменатель:** доля реакции считается только по доставленным измеримым (есть кнопка/ссылка или лента); Telegram без ссылки считается отдельной строкой «реакцию измерить нельзя»; ошибки и пропуски в знаменатель не входят.
- Статистика **только по команде**; клиентские уведомления и рассылки вне скоупа. Групповые чаты (legacy-журнал) — отдельной строкой без привязки к человеку.
- В списках «последние уведомления» **нет текстов сообщений** (могут содержать данные клиентов).
- Трекинг-ссылка: адрес назначения берётся только из значения, сохранённого при отправке; нельзя передать адрес в ссылке (open redirect закрыт AC-D3.3); сбой записи не ломает переход; кнопки в старых сообщениях живут ≥ 12 месяцев (дольше срока хранения статистики); автопредпросмотры ссылок не считаются кликом.
- Обязательная подсветка: «бот не запущен/заблокирован → N неудачных доставок» (Must); «подписан без канала», «событие без личных получателей», фиксация пропусков с причиной — Should; график и CSV — Could.
- Для периода, частично предшествующего запуску измерений, показываем «данных нет», а не нули.

### Блок E: один аккаунт
- Признак бота — **четыре состояния** (нет Telegram / не запущен / запущен ✓ дата / заблокирован); дата первого обращения не перезаписывается; обращение **до привязки** аккаунта сохраняется; бэкфилл: была успешная Telegram-доставка или вход через бота → «Запущен (дата неизвестна)». Хранится только факт и дата, без текстов.
- Объединение: основной аккаунт определяет **роль и права**; права вторичного автоматически не переносятся (список «Не будут перенесены»); по умолчанию основной — с более высокой ролью; конфликт подписок — побеждает основной; конфликт контактов — основной, вторичный в журнал, конфликт Telegram — отдельное подтверждение; нельзя вливать аккаунт текущего пользователя; нельзя оставить систему без суперадмина; обязательное превью; откат в интерфейсе не предусмотрен. **Списки получателей модулей (JSON с id пользователей) должны переписываться на основной аккаунт** — иначе после объединения получатель указывает на скрытый аккаунт (найдено при чтении `mergeClients`; он этого не делает, потому что сегодня объединяет только клиентов).
- OTP: письмо реально уходит; код не в логах; ответ не раскрывает существование аккаунта; лимиты на адрес и Telegram; вариант «по телефону» не предлагается без SMS. **Предложение PO:** OTP-привязку к аккаунту SUPERADMIN запретить (бот намеренно не дополняет аккаунты сотрудников, `bot/handlers/auth-deeplink.ts` — `ADMIN_NO_BOT_LOGIN`); для ADMIN/MANAGER разрешить с записью в журнал. Требует подтверждения (вопрос 9).
- Конфликт «Telegram уже привязан» → понятное сообщение без данных чужого аккаунта + **запрос на объединение** для SUPERADMIN (одна открытая запись на пару; кнопки «Объединить» / «Это разные люди»). Очередь кандидатов в модели есть, экрана нет — используем её, не заводим параллельную.

Где базового значения нет — снимок в день релиза.

## Architect — Ключевые решения

ADR: `docs/architecture/2026-10-25-team-access-notifications-adr.md`. Ответы на все 12 вопросов PO — там, §1 (Q1–Q12). Кратко:

### Дополнения к исследованию (найдено при чтении кода)
- **OTP-самопривязка недостижима в принципе**, а не только «код не отправляется»: `/api/webapp/auth` при первом открытии Mini App создаёт USER-аккаунт с этим `telegramId`, после чего `requestLink` всегда отвечает 409 «Этот Telegram уже привязан к аккаунту».
- `mergeClients` пишет в основной `email/phone/telegramId` вторичного **до** их обнуления у вторичного → `P2002` при заполнении пустого поля; переносит права вторичного; удаляет `OutgoingNotification` дублирующих каналов (теряется история); не трогает `Subscription`, чаты, `InAppNotification`.
- `WebPushChannel` не кладёт `url`, а `public/sw.js` открывает `data.url` → клик по push всегда ведёт на `/admin/dashboard`.
- `dispatch()` уже блокирует доставку при явном `enabled=false` (дефолт `true` без строки) — «выкл побеждает» почти правда; врёт расчёт экрана и роль-путь Авито «вкл».
- Клиентские уведомления идут через легаси `NotificationPreference.enable*`, а не через `NotificationEventPreference` — ключи сотрудника и клиента фактически не пересекаются.
- Лента Mini App показывает все `OutgoingNotification` пользователя любого канала → прочтение в ленте — реакция для любого канала.
- `getUserAdminSections(ADMIN)` не включает разделы, которыми ADMIN владеет по роли на уровне API (gazebos, ps-park, inventory); `auth.ts` дублирует логику разделов.

### Решения
1. **Отзыв сессий:** `User.sessionVersion` + claim `sv` в токене; проверка в полном `jwt`-callback через Redis-кэш `auth:state:{id}` (TTL 60 с), несовпадение → перечитать роль/разделы, влитый → `null`; `SessionWatcher` в админке опрашивает `/api/auth/session` каждые 30 с; Mini App сверяет `sv`, клиент перевыпускает токен по 401; прокси не трогаем. Bump — исключение, любое понижение, снятие раздела, вливание вторичным.
2. **Списки получателей** — новая таблица `ModuleNotificationRecipient` (FK CASCADE), перенос JSON в миграции; исключение — одна транзакция с `FOR UPDATE`; ключ JSON не удаляется в этом релизе (blue-green).
3. **Реакции:** `clickedAt/clickCount/readVia` на `OutgoingNotification` (корень цепочки) и `InAppNotification`; `failureCode/externalId`; таблицы `NotificationLink` (400 дней) и `NotificationDeliverySkip` (180 дней); «Прочитать всё» реакцией не считается; статистика — SQL на лету.
4. **Трекинг-ссылки** `/r/{code}` (128 бит), цель только в БД, белый список (свой origin + `t.me/<бот>`) при записи и при редиректе, query-параметры не читаются, всегда `302`, HEAD/боты/prefetch не считаются, лимит `public` с `302` на главную. Лента Mini App — через авторизованный `POST /api/webapp/feed/open`, без редиректа.

6. **Слияние** — новый движок `clients/merge.ts`: роль и права основного, права вторичного удаляются, списки получателей переписываются, сидированный SUPERADMIN не может быть вторичным (сидер не меняем), порядок «освободить → заполнить», перенос чатов/абонементов/уведомлений; `mergeClients` — обёртка.

8. **Ключи подписок не разводим** — инвариант + тест; при исключении строки по типам каталога удаляются.
9. **Самопривязка:** OTP к SUPERADMIN запрещён (вместо кода — информационное письмо, ответ без раскрытия); после верного кода «пустой» TG-аккаунт вливается в email-аккаунт (`self_link`), иначе — запрос на объединение; deep-link из сессии разрешён всем ролям.
