## PO — Ключевые решения

### R1: Скоуп — беседки И Плей Парк, не только беседки

Баг-репорт пришёл со скриншота карточки бронирования беседок, но `booking-actions.tsx` / `booking-detail-card.tsx` / `gazebo(session)-bill-modal.tsx` у Плей Парка — параллельная, независимо продублированная реализация той же модели `Booking` и того же общего `src/modules/booking/state-machine.ts` (тот же паттерн, что уже был у F1/F3 payment-gate: PS Park первым, gazebos — зеркально). Отсутствие диалога подтверждения — это баг общего паттерна, а не только беседок. Хотфикс обязан закрыть оба модуля в одном PR, иначе через неделю придёт точно такой же репорт с Плей Парка.

### R2: «Бронь вылетает из календаря» — это не баг сам по себе

Проверено по коду и комментариям в `state-machine.ts`: `ACTIVE_BOOKING_STATUSES = [PENDING, CONFIRMED, CHECKED_IN]` — `COMPLETED`/`CANCELLED` намеренно не занимают слот и не рисуются в сетке. Это осознанное поведение (см. историю бага #424 про `CHECKED_IN`, выпавший из фильтров). Реальная проблема — отсутствие предупреждения перед необратимым действием и отсутствие пути назад, а не сам факт исчезновения из сетки. PRD явно не переоткрывает вопрос «активных статусов» — это вне скоупа, чтобы Architect не тратил время на пересмотр уже устоявшегося решения.

### R3: История — переиспользуем существующий журнал действий, не создаём новую модель

`AuditLog` (`userId, action, entity, entityId, metadata, createdAt`) уже пишется для части событий брони (`booking.complete`, `booking.discount_applied`, `booking.reschedule`), уже используется как единый источник для похожего просмотра действий в другом разделе админки. Проверено: простая отмена / подтверждение сейчас **не** пишут туда запись (только ветка `COMPLETED` в `updateBookingStatus` содержит явные `tx.auditLog.create`). Рекомендация — дописать недостающие точки логирования до полноты, а не заводить параллельную модель `BookingEvent`. Обоснование: ровно та же ловушка, что уже случалась в проекте (см. комментарий в `state-machine.ts` про «семнадцать мест вместо одного» для `ACTIVE_BOOKING_STATUSES`) — два параллельных источника правды по одному и тому же факту неизбежно разъедутся. Финальное архитектурное решение (расширять `AuditLog` как есть vs добавить индекс/вьюху для быстрой выборки по брони) — за Architect, но отправная точка зафиксирована.

### R4: Восстановление — SUPERADMIN-only, с обязательным re-check слота

Прямая ссылка на уже известную дыру #478 (`NO_SHOW → CHECKED_IN` без конфликт-чека, что может создать двойную бронь, если слот успели пересдать). US-4 явно требует от Architect/Developer не повторить эту ошибку: реактивация в `CONFIRMED` обязана прогонять тот же конфликт-чек, что и создание новой брони. Это не предложение, а жёсткий AC (US-4 AC-3), потому что прецедент дыры в проекте уже задокументирован и её повторение в новой фиче недопустимо.

Восстановление сознательно ограничено ролью SUPERADMIN (не MANAGER) и снабжено требованием повторного ввода пароля — по аналогии с существующим гейтом деструктивных действий (`src/lib/deletion.ts`, `authorizeSuperadminDeletion`). Логика та же: действие с высоким блаcт-радиусом (деньги + расписание) заслуживает того же уровня строгости, что и удаление, даже если технически это не удаление, а смена статуса.

### R5: Восстановление НЕ требует снепшот-модели по образцу `DeletionLog`

Важное упрощение, обнаруженное при чтении схемы: переход брони в `COMPLETED`/`CANCELLED` не трогает `deletedAt` и не удаляет строку — вся информация о ресурсе, времени, клиенте и деньгах остаётся в той же записи `Booking`. Поэтому «восстановление» — это чистый обратный FSM-переход с конфликт-чеком, а не восстановление из снепшота (в отличие от `DeletionLog`, который существует именно потому, что там строка физически исчезает/помечается). Не путать эти два механизма при реализации — они похожи по строгости гейта, но принципиально разные по хранимым данным.

### R6: Деньги при восстановлении — не откатываем автоматически

- Онлайн-предоплата, которая уже была автоматически возвращена при отмене (`autoRefundOnCancellation`) — не может быть технически «отменена» через провайдера обратно. US-4 требует явного предупреждения администратору в диалоге восстановления, а не тихого умолчания.
- `FinancialTransaction` — иммутабельный леджер (см. комментарий в схеме: «No updatedAt — immutable financial audit log»). Восстановление завершённой брони не может задним числом стирать уже созданную запись о выручке. PO требует, чтобы отчётность не «тихо» меняла прошлые цифры — техническое решение (новый тип транзакции / пометка) оставлено Architect, но инвариант зафиксирован как AC (US-4 AC-6).

### R7: «ОПЛАЧЕНО» — намеренно НЕ новое значение `BookingStatus`

Владелец прямым текстом просил «статус, самый высший». PO отклоняет буквальную реализацию (добавление enum-значения в `BookingStatus`) и рекомендует независимый признак оплаты поверх текущего статуса жизненного цикла. Причина: `BookingStatus` кодирует **этап** брони (взаимоисключающие состояния с разными правилами переходов), а оплата — независимая ось, которая может быть истинна на разных этапах одновременно (оплачено онлайн при ещё `PENDING`, оплачено на месте при `CHECKED_IN`, и т.д.). Если оплату сделать значением того же enum, теряется информация об этапе — и придётся заново решать, какие переходы разрешены из «Оплачено» в диспетчер `state-machine.ts` для каждого прежнего этапа. Это дороже и хрупче, чем отдельный флаг, а с точки зрения UI (что владелец реально увидит на экране) разница нулевая — оба статуса показываются рядом.

Уже существующая инфраструктура подтверждает верность этого пути: `metadata.onlinePaidAmount` и связка `cashAmount + cardAmount` уже используются как раз для проверки «набрана ли полная сумма» в шлюзе завершения брони (см. `PAYMENT_REQUIRED` gate в `gazebos/service.ts`). Признак оплаты для UI — это, по сути, та же самая проверка, вынесенная наружу и показанная визуально, а не новая концепция.

### R8: Данные представления «оплачено» — Architect выбирает вычисляемое значение vs хранимое поле

PO намеренно не предписывает, персистить ли признак оплаты отдельным полем в БД или вычислять на лету из `cashAmount + cardAmount + metadata.onlinePaidAmount` относительно `metadata.totalPrice`. Рекомендация в PRD — вычислять, чтобы не заводить ещё один источник правды, который придётся синхронизировать (см. R3/R7 — сквозная тема этого PRD: не плодить дублирующиеся источники истины). Если производительность списка/сетки потребует кэш-поля — решение и обоснование остаются за Architect.

### R9: Порядок поставки — хотфикс отделён от остального физически, не только по приоритету

US-1/US-2 идут отдельным PR сегодня. US-3/US-4/US-5 намеренно не блокируют хотфикс и не должны с ним смешиваться в одной ветке/PR — иначе критический фикс задержится ради более сложной и рискованной функциональности (особенно US-4 с деньгами и конфликтами слотов).
