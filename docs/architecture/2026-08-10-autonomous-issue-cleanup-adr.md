# ADR: автономная разгрузка бэклога issues

- **Дата:** 2026-08-10
- **Статус:** принят, внедряется
- **Контекст:** 49 открытых issues, из них 11 P0 в проде; владелец требует разгрузку без своего участия

---

## Проблема

К 10.08.2026 в репозитории 49 открытых issues. Разбор показал три разных болезни,
которые лечатся по-разному:

1. **Мёртвый груз.** 12 issues (#61–#72) заведены 14.04 под три продуктовых
   направления — лояльность, резиденты, дашборд владельца. За четыре месяца ни
   одного коммита. Ни для одного нет PRD, ни один модуль не значится в таблице
   модулей CLAUDE.md, то есть по scope guard проекта они не могут быть взяты в
   работу в принципе. При этом они неотличимы в списке от настоящих P0 и создают
   иллюзию, что бэклог больше и безнадёжнее, чем он есть.

2. **Настоящая работа без порядка.** 25 issues от QA-аудита 10.08 (#423–#445) и
   epic доступности (#451–#458) — конкретные баги с указанием файлов и строк.
   Порядка между ними нет: ничто не говорит, что чинить первым — двойное
   бронирование или неработающую кнопку в админке.

3. **Отсутствие исполнителя.** Даже с идеальным порядком нужен кто-то, кто
   каждый день берёт верхнюю задачу и доводит до мержа. Владелец этим заниматься
   не будет — это и есть исходное требование.

Дополнительное ограничение: попытка построить такого исполнителя уже была и
провалилась. Standalone-агент в `agent/` (Telegram-управляемый Claude Code на
Hetzner) удалён 10.08 — Anthropic OAuth не проходит с российских IP, а прод-VPS
в ru-1. Новое решение не должно зависеть от собственного хостинга.

## Решение

Три слоя, каждый работает при отказе остальных.

### Слой 1 — состояние очереди в лейблах GitHub

Отдельной БД, файла состояния или внешнего сервиса нет. Очередь — это лейблы:

| Лейбл | Значение |
|---|---|
| `prio:P0` / `P1` / `P2` | Что важнее |
| `auto:ready` | Воркер может брать |
| `auto:wip` | Взято; лок от параллельных сессий |
| `auto:review` | PR открыт, гейт не пропустил в авто-мерж — ждёт владельца |
| `auto:blocked` | Нужны доступы или решение владельца |
| `auto:prod-apply` | Код автоматизируем, финальный apply трогает прод |
| `auto:epic` / `auto:parked` | Вне очереди |

Почему так: состояние видно владельцу в обычном интерфейсе issues, правится
руками в один клик, переживает потерю любой сессии агента и не требует ни одного
нового сервиса. Цена — порядок нельзя выразить точнее, чем «приоритет + номер»;
для этого есть `pinned` в конфиге.

### Слой 2 — детерминированная логика, без AI

`scripts/lib/issue-queue.ts` — чистые функции: разбор лейблов, порядок очереди,
выбор следующей задачи, поиск протухших локов, классификация merge-гейта, разбор
состояния CI. Ни одного сетевого вызова, 53 юнит-теста.

`scripts/issue-queue.ts` — CLI поверх них. Очередь: `next`, `claim`, `release`,
`park`, `reconcile`, `report`. Жизненный цикл PR: `pr-open`, `pr-wait`,
`pr-status`, `gate`, `pr-ready`, `pr-merge`.

Весь цикл PR живёт в CLI не случайно: сессии, которые будит Routine, стартуют
**без MCP-инструментов** — `mcp__github__*` там нет, есть только Bash. CLI ходит
в GitHub через curl (в Actions — с `Authorization: Bearer $GH_TOKEN`, в сессии
Claude Code заголовок не нужен, учётку подставляет agent-proxy; `node fetch`
прокси игнорирует и получает 401 — отсюда curl).

`pr-merge` — последний предохранитель перед прод-деплоем: перепроверяет и гейт,
и зелёный CI сам, а не верит вызывающему, и отказывается мержить черновик.

Отсюда же следует, что `pr-open` создаёт PR **не черновиком**. Снять draft умеет
только мутация GraphQL — в REST такой операции нет, — а agent-proxy сессий
воркера GraphQL не отдаёт. PR, открытый черновиком, воркер уже никогда бы не
домержил. Гейт от этого не слабеет: черновик тут был украшением, а решение
принимает `pr-merge`.

`.github/workflows/issue-queue.yml` — ежечасный крон, который гоняет `reconcile`
и `report`. **AI в нём нет.** Это принципиально: уборка и учёт обязаны работать
и тогда, когда воркер сломан. Крон снимает локи с задач, чьи сессии умерли, и
перерисовывает issue-дашборд.

### Слой 3 — воркер

Routine Claude Code (внешний планировщик) будит свежую сессию каждые 4 часа —
`trig_01UVwFjedpTGeww6291VYeJn`, уведомления владельцу выключены. Сессия
выполняет `.claude/commands/next-issue.md`: берёт верхнюю задачу, ставит лок,
реализует по правилам CLAUDE.md, прогоняет `code-reviewer` и `qa-engineer`,
открывает PR и опросом (`pr-wait`) дожидается CI, починяя красное, пока не
позеленеет.

Почему Routine, а не GitHub Actions: в репозитории нет секрета `ANTHROPIC_API_KEY`
и заводить его не требуется — Routine работает от учётки владельца во внешней
среде. Заодно снимается ограничение, которое убило агента на Hetzner: среда не
привязана к российскому IP.

#### Чего у сессии воркера нет (проверено, стоило суток простоя)

Сессия, которую заводит Routine, — не копия интерактивной сессии. Отличия
неочевидные, и на них система встала намертво в первые сутки: воркер исправно
просыпался каждые 4 часа, ничего не делал и уходил спать, а бэклог не двигался.

1. **Репозиторий не примонтирован.** У интерактивной сессии в `session_context`
   есть `sources` с git-репозиторием; у сессии Routine его нет. `git checkout main`
   падает, и бутстрап-проверка честно завершает сессию — формально правильно,
   практически бесполезно. Лечится клоном в ШАГЕ 0 промпта: прокси окружения
   подставляет учётку сам, ни токен, ни `add_repo` не нужны.
2. **MCP-инструментов нет вообще.** Ни `mcp__github__*`, ни `add_repo`,
   ни `subscribe_pr_activity`. Отсюда весь цикл PR в CLI и опрос CI через
   `pr-wait` вместо вебхуков.
3. **Права наследуются от создателя.** Сессия унаследовала `permission_mode: auto`
   от интерактивной сессии, где Routine заводили. Это единственное отличие,
   которое сыграло в плюс: в `default` она бы встала на первом же запросе
   разрешения, как встали более ранние дочерние сессии
   (`add_repo`, `send_later` — обе висели, пока их не заархивировали).

Что при этом есть и работает: Bash, `git clone`/`push` через прокси,
преднастроенная git-identity, субагенты (`Task`) и `npx tsx` без `npm install` —
npx сам подтягивает tsx, а CLI очереди не импортирует зависимости проекта.

Мораль на будущее: **не считать сессию Routine эквивалентом своей.** Всё, на что
она опирается, должно либо создаваться в ШАГЕ 0, либо жить в репозитории.

## Merge gate — главное решение этого ADR

Мерж в `main` запускает CI, а `deploy.yml` по `workflow_run` от CI выкатывает
прод. Значит «включить авто-мерж» буквально означает «выкатывать в прод без
человека». Отсюда деление на два класса.

**Мержится автоматически** (после зелёного CI и PASS от обоих ревью-агентов):
код приложения в `src/`, `bot/`, тесты, документация, сиды. Изменение обратимо
откатом коммита, деплой защищён blue-green, снапшотом VPS, бэкапом БД,
smoke-тестами и автооткатом.

**Ждёт владельца** (`tier: hold`, PR остаётся черновиком с лейблом `needs-owner`):

- `prisma/migrations/**`, `prisma/schema.prisma` — деплой прогоняет `migrate deploy`;
- `infra/**`, `docker-compose*.yml`, `Dockerfile*` — меняет саму инфраструктуру;
- `.github/workflows/deploy*|ops-*|timeweb-*|release*` — меняет то, как катится прод;
- `.github/workflows/issue-queue.yml`, `.github/issue-queue.json` — автоматизация
  не мержит сама себя без присмотра;
- `scripts/deploy-*|restore-*|backup-*|pre-migration-*|apply-nginx-*`;
- PR, затрагивающий 5+ модулей — правило scope creep из CLAUDE.md #5.

Список — `HOLD_PATTERNS` в `scripts/lib/issue-queue.ts`, покрыт тестами.

## Рубильники

`.github/issue-queue.json`:

```json
{ "enabled": true, "autoMerge": true, "maxOpenPrs": 2,
  "staleWipHours": 6, "maxAttempts": 3, "pinned": [...] }
```

- `enabled: false` — воркер просыпается, видит флаг, уходит спать. Полная остановка.
- `autoMerge: false` — работа идёт, но каждый PR ждёт ручного мержа.
- `maxOpenPrs` — backpressure: не даёт накопить пачку PR-ов, которые
  конфликтуют друг с другом быстрее, чем мержатся.
- `staleWipHours` — через сколько часов молчания лок считается протухшим.
- `maxAttempts` — сколько раз задачу можно подобрать и бросить. Исчерпав лимит,
  `reconcile` уводит её в `auto:blocked` с объяснением, вместо того чтобы вечно
  скармливать её новым сессиям.

Плюс аварийная остановка снаружи репозитория: выключить сам Routine.

## Последствия

**Хорошее.** Бэклог перестаёт быть свалкой: 49 issues → 37 рабочих с явным
порядком + 12 честно замороженных. P0-баги в проде чинятся по одному без участия
владельца. Дашборд показывает состояние без чтения истории.

**Плохое.** Правило CLAUDE.md «No auto-merge для `claude/**`» ослаблено — это
осознанный размен, зафиксированный merge-гейтом выше. Автономный мерж кода
приложения означает автономный деплой; защита — CI, два ревью-агента,
blue-green и автооткат, но не человеческий взгляд.

**Риски и что их держит.**

| Риск | Защита |
|---|---|
| Воркер сломает прод | merge gate + blue-green + автооткат + `enabled:false` |
| Сессия умрёт с локом | `reconcile` снимает лок через `staleWipHours` |
| Две сессии возьмут одну issue | `auto:wip` проверяется до начала работы; при конфликте лейблов `wip` побеждает |
| PR-ы накопятся и разъедутся | `maxOpenPrs` + существующий `auto-rebase.yml` |
| Непросмотренный PR уровня hold остановит очередь | задача уезжает в `auto:review` (`park`), лок освобождается; `reconcile` делает это же по лейблу `needs-owner` |
| Агент придумает себе задачу | Берёт только `auto:ready`; новый модуль без PRD → `release` и выход |
| Неподъёмная задача крутится вечно и жжёт бюджет | `maxAttempts`: после трёх брошенных попыток `reconcile` уводит её в `auto:blocked` |
| Воркер молча ничего не делает, а выглядит живым | Дашборд показывает дату обновления и «что дальше»; если очередь не движется сутки при непустом `auto:ready` — воркер сломан, смотреть промпт Routine |

## Альтернативы

**GitHub Action с Claude Code** — требует `ANTHROPIC_API_KEY` в секретах репозитория
и упирается в те же лимиты, что убили Hetzner-агента. Отклонено.

**Свой воркер на прод-VPS** — Anthropic OAuth не проходит с российских IP
(причина удаления `agent/` 10.08). Отклонено как заведомо неработающее.

**GitHub Projects вместо лейблов** — богаче по полям, но состояние уезжает в
отдельную сущность, хуже видно из CLI и не переживает смену проекта. Отклонено:
лейблов достаточно.
