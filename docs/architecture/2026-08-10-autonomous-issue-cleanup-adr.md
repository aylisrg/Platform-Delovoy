# ADR: автономная разгрузка бэклога issues

- **Дата:** 2026-08-10
- **Статус:** принят, внедряется
- **Контекст:** 49 открытых issues, из них 11 P0 в проде; владелец требует разгрузку без своего участия

---

## Проблема

К 10.08.2026 в репозитории 49 открытых issues. Разбор показал три разных болезни,
которые лечатся по-разному:

1. **Мёртвый груз.** 12 issues (#61–#72) заведены 14.04 под три продуктовых
   направления — лояльность, резиденты, дашборд владельца. За четыре месяца ни
   одного коммита. Ни для одного нет PRD, ни один модуль не значится в таблице
   модулей CLAUDE.md, то есть по scope guard проекта они не могут быть взяты в
   работу в принципе. При этом они неотличимы в списке от настоящих P0 и создают
   иллюзию, что бэклог больше и безнадёжнее, чем он есть.

2. **Настоящая работа без порядка.** 25 issues от QA-аудита 10.08 (#423–#445) и
   epic доступности (#451–#458) — конкретные баги с указанием файлов и строк.
   Порядка между ними нет: ничто не говорит, что чинить первым — двойное
   бронирование или неработающую кнопку в админке.

3. **Отсутствие исполнителя.** Даже с идеальным порядком нужен кто-то, кто
   каждый день берёт верхнюю задачу и доводит до мержа. Владелец этим заниматься
   не будет — это и есть исходное требование.

Дополнительное ограничение: попытка построить такого исполнителя уже была и
провалилась. Standalone-агент в `agent/` (Telegram-управляемый Claude Code на
Hetzner) удалён 10.08 — Anthropic OAuth не проходит с российских IP, а прод-VPS
в ru-1. Новое решение не должно зависеть от собственного хостинга.

## Решение

Три слоя, каждый работает при отказе остальных.

### Слой 1 — состояние очереди в лейблах GitHub

Отдельной БД, файла состояния или внешнего сервиса нет. Очередь — это лейблы:

| Лейбл | Значение |
|---|---|
| `prio:P0` / `P1` / `P2` | Что важнее |
| `auto:ready` | Воркер может брать |
| `auto:wip` | Взято; лок от параллельных сессий |
| `auto:review` | PR открыт, гейт не пропустил в авто-мерж — ждёт владельца |
| `auto:blocked` | Нужны доступы или решение владельца |
| `auto:prod-apply` | Код автоматизируем, финальный apply трогает прод |
| `auto:epic` / `auto:parked` | Вне очереди |

Почему так: состояние видно владельцу в обычном интерфейсе issues, правится
руками в один клик, переживает потерю любой сессии агента и не требует ни одного
нового сервиса. Цена — порядок нельзя выразить точнее, чем «приоритет + номер»;
для этого есть `pinned` в конфиге.

### Слой 2 — детерминированная логика, без AI

`scripts/lib/issue-queue.ts` — чистые функции: разбор лейблов, порядок очереди,
выбор следующей задачи, поиск протухших локов, классификация merge-гейта, разбор
состояния CI. Ни одного сетевого вызова, 53 юнит-теста.

`scripts/issue-queue.ts` — CLI поверх них. Очередь: `next`, `claim`, `release`,
`park`, `reconcile`, `report`. Жизненный цикл PR: `pr-open`, `pr-wait`,
`pr-status`, `gate`, `pr-ready`, `pr-merge`.

Весь цикл PR живёт в CLI, а не в MCP-инструментах: так он одинаково работает и в
GitHub Actions, и в интерактивной сессии, и не зависит от того, какой набор
инструментов достался исполнителю. CLI ходит в GitHub через curl — в Actions с
`Authorization: Bearer $GH_TOKEN`, в сессии Claude Code заголовок не нужен,
учётку подставляет agent-proxy. Именно curl, а не `node fetch`: fetch игнорирует
`HTTPS_PROXY` и получает 401.

`pr-merge` — последний предохранитель перед прод-деплоем: перепроверяет и гейт,
и зелёный CI сам, а не верит вызывающему, и отказывается мержить черновик.
Пустой список чеков он считает не «всё прошло», а «CI ещё не стартовал» — иначе
сразу после push можно было бы замержить непроверенный код.

`pr-open` создаёт PR **не черновиком**: снять draft умеет только мутация GraphQL
(в REST такой операции нет), и там, где GraphQL недоступен, черновик стал бы
ловушкой — домержить его было бы уже нельзя. Гейт от этого не слабеет: черновик
был украшением, решение принимает `pr-merge`.

`.github/workflows/issue-queue.yml` — ежечасный крон, который гоняет `reconcile`
и `report`. **AI в нём нет.** Это принципиально: уборка и учёт обязаны работать
и тогда, когда воркер сломан. Крон снимает локи с задач, чьи сессии умерли, и
перерисовывает issue-дашборд.

### Слой 3 — исполнитель

**Обычная интерактивная сессия Claude Code**, работающая по
`.claude/commands/next-issue.md`: берёт верхнюю задачу, ставит лок, чинит по
правилам CLAUDE.md, прогоняет `code-reviewer` и `qa-engineer`, открывает PR,
доводит CI до зелёного, мержит — и сразу берётся за следующую.

Непрерывность держится на двух вещах:

- **вебхук о мерже PR** будит сессию и запускает следующую итерацию — основной
  триггер, ждать команды владельца не нужно;
- **`send_later` минут на 30** как страховка, если вебхук не дошёл или PR завис.
  Проснулся, ничего не изменилось — перевзвёл молча.

Ключевое свойство: **состояние очереди живёт вне диалога** — в лейблах GitHub и
дашборде. Поэтому сжатие контекста, рестарт контейнера или потеря сессии не
ломают разбор: `next` восстанавливает картину с нуля, а ежечасный `reconcile`
снимает протухшие локи.

#### Два отвергнутых варианта исполнителя

Оба испробованы на живой системе, оба стоили простоя. Записаны, чтобы к ним
не возвращались.

**1. Внешний планировщик (Routine), 10–11.08.** Планировщик будил свежую сессию
каждые 4 часа. Сутки простоя, три независимые причины:

- у сессии планировщика нет примонтированного репозитория (`sources` пуст),
  и бутстрап честно завершал её, не найдя файлов;
- без репозитория нет и доступа к GitHub API — он привязан к сконфигурированным
  репозиториям сессии (`sessions are bound to their configured repositories`);
- решающее: `git clone`, `curl` и `add_repo` требуют интерактивного
  подтверждения. Диагностическая сессия даже в режиме `auto` упёрлась в него —
  а подтвердить некому, в том и смысл автономности.

Вывод: сессия, заведённая планировщиком, **не эквивалентна интерактивной** и
исполнителем быть не может.

**2. GitHub Actions + `anthropics/claude-code-action`, 11.08.** Технически
работает — репозиторий на месте, `GITHUB_TOKEN` выдан, подтверждений не
требуется. Но нужен `ANTHROPIC_API_KEY` в секретах репозитория. **Отвергнуто
владельцем:** «через API строить разработку не будем, однозначно нет». Workflow
удалён, чтобы не шуметь пустыми прогонами.

Диагностика сохранена: сессии `DIAG` и `DIAG-2` от 2026-08-11.

### Обновление 2026-08-12 — владелец выпал из цикла

Через сутки работы выяснилось, что слой 3 отдаёт владельцу два шага, которые
формально были «частью исполнителя», а на деле — ручной работой человека.

**Симптом 1: мерж держался на живой сессии.** `pr-merge` вызывался шагом 7
`/next-issue`. Сессия смертна, и смерть между `pr-open` и `pr-merge` оставляла PR
с зелёным CI и гейтом `auto` висеть навсегда: `reconcile` через `staleWipHours`
уводил задачу в `auto:review`, то есть в инбокс владельца. Так был смержен PR #483 —
руками владельца, через 14 часов после того, как всё сошлось. Туда же попадали
черновики: сессии Claude Code на вебе обязаны открывать PR черновиком, а снять флаг
мог только человек (PR #491).

**Симптом 2: очередь никто не запускал.** Heartbeat из `issue-queue.yml` слал
владельцу «Запусти сессию и скажи ей `/next-issue`». Это и есть единственный
механизм старта — то есть автономность заканчивалась ровно там, где начиналась.

Оба шага вынесены из сессии:

- **Мерж → крон.** `.github/workflows/issue-queue-merge.yml` каждые 15 минут и по
  событию завершения CI обходит открытые PR-ы и домерживает те, где гейт вернул
  `auto`, CI зелёный, нет `needs-owner` и PR не трогали `automergeQuietMinutes`
  (20) минут. AI не нужен по той же причине, что и в слое 2: решение полностью
  детерминировано. Окно тишины защищает от мержа середины чужой работы; черновик
  снимается только после того, как гейт и CI уже сказали «да». PR уровня `hold`
  получает `needs-owner` сразу, а не через шесть часов протухания лока.
- **Старт сессий → Routine.** Отвергнутый вариант 1 реанимирован, но в другой роли:
  Routine больше не исполнитель, а только *стартер* — она заводит свежую сессию
  раз в 2 часа, а вся работа идёт по `/next-issue` внутри неё. Три причины отказа
  сняты: Routine создана **из сессии с примонтированным репозиторием** и наследует
  её `environment_id`, поэтому фиксы `sources` и доступа к GitHub API отпадают, а
  `git clone`/`add_repo` не нужны вовсе — клонировать нечего.

  Это остаётся самым хрупким местом схемы: наследование монтирования проверяется
  только фактическим запуском. Промпт Routine начинается с проверки
  `ls /home/user/Platform-Delovoy/CLAUDE.md` и при отсутствии репозитория завершает
  сессию одной строкой, ничего не создавая, — неудача стоит одного пустого запуска,
  а не суток простоя, как 10–11.08. Если монтирование не наследуется, Routine
  бесполезна и её надо выключить; тогда стартера у очереди снова нет, а мерж
  остаётся автономным в любом случае.

Heartbeat переформулирован: он больше не просит владельца запустить сессию, а
сообщает, что **сломался планировщик** — очередь стоит вопреки расписанию.

Заодно расширена зона авто-мержа: с `claude/issue-*` на все `claude/**`. Сессия,
заведённая не через `/next-issue` (разбор инцидента, задача от владельца в чате),
проходит тот же CI и тот же гейт, а её PR оседал у владельца только из-за имени
ветки — ровно случай PR #491.

### Обновление 2026-08-13 — гейт одобрения CI, третий ручной шаг

Первая же версия автономного мержа вскрыла шаг, который не считался ручным вообще,
потому что появился на стороне GitHub, а не у нас.

**Симптом: у ребейзнутого PR пропадает CI.** С 11.06.2026 GitHub паркует прогоны,
приписанные `github-actions[bot]`, в состоянии `action_required` — они не стартуют,
пока человек с write-доступом не нажмёт «Approve and run»
([changelog](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)).
Это защита от того, чтобы сгенерированный код сам запускал workflow с доступом к
секретам, и выключаемой настройки у неё нет.

Единственный источник таких прогонов у нас — `auto-rebase.yml`: он форс-пушит ветки
под `GITHUB_TOKEN`. Замер на PR #493: три ребейза подряд — три ручных одобрения;
пуши `claude[bot]` и владельца при этом стартуют CI сами. То есть цикл был такой:
подметальщик мержит → main двигается → auto-rebase толкает остальные PR → их CI
паркуется → владелец жмёт кнопку. Автономный мерж заменил один ручной шаг другим.

**Почему это встаёт молча.** Запаркованный прогон не создаёт даже check-run:
`GET /commits/{sha}/check-runs` возвращает пусто. Подметальщик читает именно этот
эндпоинт, а `summarizeChecks([])` по конструкции даёт «чеки ещё не появились» →
`pending`, не `red`. Ждать при этом нечего — без человека прогон не стартует.
Дальше PR уезжает по худшему пути: heartbeat молчит, пока issue в `auto:wip`, а
через `staleWipHours` `reconcile` переводит её в `auto:review`, то есть владельцу.

**Решение: единый PAT автоматики.** `auto-rebase.yml`, `issue-queue-merge.yml` и
`release.yml` читают `secrets.AUTOMATION_TOKEN` (исторические синонимы
`QUEUE_MERGE_TOKEN` и `RELEASE_PLEASE_TOKEN` продолжают работать). Пуш под PAT
приписывается человеку — гейт не срабатывает вовсе. Побочно чинится и то, ради
чего PAT задумывался в `release.yml` изначально: мерж начинает порождать
настоящие события, поэтому `deploy.yml` и `auto-rebase.yml` запускаются сами, а
костыль с явным `workflow_dispatch` в подметальщике становится запасным путём.

Секрет необязателен: без него всё работает как раньше, а `auto-rebase` честно
пишет в step summary, что CI ребейзнутых веток запаркуется. Отвергнутая
альтернатива — расталкивать запаркованные прогоны через `POST /actions/runs/{id}/rerun`
из самого workflow: вручную с токеном человека это работает (проверено на #493),
но одобрять по правилу GitHub должен пользователь с write-доступом, а
`GITHUB_TOKEN` им не является — rerun из-под него, по всей вероятности,
запаркуется снова. Вторая альтернатива — убрать сплошной ребейз на каждый мерж —
осталась в резерве: она не требует секретов, но теряет раннее обнаружение
семантических конфликтов, ради которого `auto-rebase.yml` и заводился.

## Merge gate — главное решение этого ADR

Мерж в `main` запускает CI, а `deploy.yml` по `workflow_run` от CI выкатывает
прод. Значит «включить авто-мерж» буквально означает «выкатывать в прод без
человека». Отсюда деление на два класса.

**Мержится автоматически** (после зелёного CI и PASS от обоих ревью-агентов):
код приложения в `src/`, `bot/`, тесты, документация, сиды. Изменение обратимо
откатом коммита, деплой защищён blue-green, снапшотом VPS, бэкапом БД,
smoke-тестами и автооткатом.

**Ждёт владельца** (`tier: hold`, на PR вешается лейбл `needs-owner`, issue уезжает
в `auto:review`, чтобы очередь не встала) — по решению владельца от 11.08 осталось
ровно два класса, и оба про необратимость:

- **рубильники самой автоматики** — `.github/issue-queue.json`,
  `.github/workflows/issue-queue.yml`, а также реализация гейта
  (`scripts/lib/issue-queue.ts`, `scripts/issue-queue.ts`). Без последних двух
  защита циклична: агент мог бы ослабить правило и тем же прогоном замержить
  своё ослабление. Тесты очереди сюда не входят — их правит кто угодно;
- **деструктивные миграции** — `prisma/migrations/**`, в диффе которых есть
  `DROP TABLE`, `DROP COLUMN`, `DROP CONSTRAINT`, `TRUNCATE`, `DELETE FROM`,
  `ALTER TYPE` или `SET NOT NULL`. Код откатывается коммитом, а потерянные данные —
  только восстановлением бэкапа, то есть с окном потерь. Аддитивные миграции
  (`CREATE TABLE`, `ADD COLUMN`, `CREATE INDEX`) мержатся сами;
- PR, затрагивающий 5+ модулей — правило scope creep из CLAUDE.md #5.

Всё остальное — `infra/**`, `docker-compose*`, `Dockerfile*`, деплой- и
ops-workflow'ы, `prisma/schema.prisma`, скрипты деплоя — **мержится
автоматически**. Раньше держалось; снято сознательно, потому что владелец
попросил катить без его участия, а защита и без того многослойная: CI, два
ревью-агента, blue-green, снапшот VPS, бэкап БД, smoke-тесты, автооткат.

Реализация — `HOLD_PATTERNS` и `destructiveSqlIn()` в
`scripts/lib/issue-queue.ts`, обе покрыты тестами. Дифф гейт берёт из поля
`patch` ответа `/pulls/{n}/files`; если GitHub его не отдал (слишком большой
файл), миграция считается безопасной — ронять на этом очередь неправильно,
CI и ревью-агенты остаются на месте.

## Рубильники

`.github/issue-queue.json`:

```json
{ "enabled": true, "autoMerge": true, "maxOpenPrs": 2,
  "staleWipHours": 6, "maxAttempts": 3, "pinned": [...] }
```

- `enabled: false` — воркер просыпается, видит флаг, уходит спать. Полная остановка.
- `autoMerge: false` — работа идёт, но каждый PR ждёт ручного мержа.
- `maxOpenPrs` — backpressure: не даёт накопить пачку PR-ов, которые
  конфликтуют друг с другом быстрее, чем мержатся.
- `staleWipHours` — через сколько часов молчания лок считается протухшим.
- `maxAttempts` — сколько раз задачу можно подобрать и бросить. Исчерпав лимит,
  `reconcile` уводит её в `auto:blocked` с объяснением, вместо того чтобы вечно
  скармливать её новым сессиям.

Плюс аварийная остановка на ходу: сказать сессии «стоп». Исполнитель — живой
диалог, а не демон; это его слабость по части непрерывности и одновременно самый
надёжный рубильник.

После 2026-08-12 рубильников стало три, и «сказать сессии стоп» больше не
останавливает цикл целиком — сессию заведут снова по расписанию. Полная остановка:

| Что выключить | Как | Что перестаёт работать |
|---|---|---|
| Разбор задач | выключить Routine «Автоочередь: разбор бэклога» | новые сессии не заводятся; открытые PR всё ещё домержатся |
| Авто-мерж | `autoMerge: false` в `.github/issue-queue.json` | подметальщик выходит сразу и молча, ничего не переклеивая |
| Всё сразу | `enabled: false` там же | встаёт и `pickNext`, и подметальщик |
| Один PR | лейбл `needs-owner` на PR | этот PR ждёт владельца, очередь идёт дальше |

## Последствия

**Хорошее.** Бэклог перестаёт быть свалкой: 49 issues → 37 рабочих с явным
порядком + 12 честно замороженных. P0-баги в проде чинятся по одному без участия
владельца. Дашборд показывает состояние без чтения истории.

**Плохое.** Правило CLAUDE.md «No auto-merge для `claude/**`» ослаблено — это
осознанный размен, зафиксированный merge-гейтом выше. Автономный мерж кода
приложения означает автономный деплой; защита — CI, два ревью-агента,
blue-green и автооткат, но не человеческий взгляд.

**Риски и что их держит.**

| Риск | Защита |
|---|---|
| Воркер сломает прод | merge gate + blue-green + автооткат + `enabled:false` |
| Сессия умрёт с локом | `reconcile` снимает лок через `staleWipHours` |
| Две сессии возьмут одну issue | `auto:wip` проверяется до начала работы; при конфликте лейблов `wip` побеждает |
| PR-ы накопятся и разъедутся | `maxOpenPrs` + существующий `auto-rebase.yml` |
| Непросмотренный PR уровня hold остановит очередь | задача уезжает в `auto:review` (`park`), лок освобождается; `reconcile` делает это же по лейблу `needs-owner` |
| Агент придумает себе задачу | Берёт только `auto:ready`; новый модуль без PRD → `release` и выход |
| Неподъёмная задача крутится вечно и жжёт бюджет | `maxAttempts`: после трёх брошенных попыток `reconcile` уводит её в `auto:blocked` |
| Воркер молча ничего не делает, а выглядит живым | Дашборд показывает дату обновления и «что дальше»; прогоны воркера видны в Actions; если очередь не движется сутки при непустом `auto:ready` — смотреть последний прогон `issue-worker` |

## Альтернативы

**GitHub Action с Claude Code** — требует `ANTHROPIC_API_KEY` в секретах репозитория
и упирается в те же лимиты, что убили Hetzner-агента. Отклонено.

**Свой воркер на прод-VPS** — Anthropic OAuth не проходит с российских IP
(причина удаления `agent/` 10.08). Отклонено как заведомо неработающее.

**GitHub Projects вместо лейблов** — богаче по полям, но состояние уезжает в
отдельную сущность, хуже видно из CLI и не переживает смену проекта. Отклонено:
лейблов достаточно.
