# План интеграции онлайн-оплаты ЮKassa (YooKassa)

- **Статус:** DRAFT — на согласовании с владельцем продукта
- **Дата:** 2026-07-08
- **Тип:** интеграционный план (перед реализацией будет разбит на PRD + ADR по фазам)

---

## 1. Контекст и цель

Ключи ЮKassa (shopId + secret key) получены и лежат в GitHub Secrets. Задача — принять
онлайн-оплату во всех местах платформы, где сегодня формируется потребность платить,
сделав это «как в лучших сервисах»: платёжная ссылка/страница, автоматическое
подтверждение по вебхуку, возвраты, чеки 54-ФЗ, учёт и системные уведомления.

## 2. Текущее состояние: где деньги считаются, но онлайн не принимаются

Аудит кодовой базы показал: **онлайн-платежей в сервисе нет вообще**. Ни SDK, ни env-переменных,
ни модели платёжной сессии. Все денежные потоки:

| Поток | Сумма считается | Как «оплачивается» сейчас |
|---|---|---|
| **rental / nedelovoy** (аренда B2B) | `RentalPayment.amount` — график платежей по контракту | Арендатор платит по банковским реквизитам (`bankDetails` в email-напоминаниях), менеджер вручную жмёт «Оплачено» (`paidAt` + `markedPaidById`) |
| **subscriptions** (абонементы PS Park) | `Subscription.pricePaid` | Менеджер выписывает пасс, факт приёма денег нигде не проводится |
| **ps-park** (сессии) | `getBookingBill()` → `FinancialTransaction` | POS-модель: менеджер вводит наличные/карту при завершении, гейт `PAYMENT_REQUIRED` (HTTP 402) |
| **gazebos** (беседки) | `Booking.metadata.totalPrice` → `FinancialTransaction` | POS при завершении; предоплаты при бронировании нет |
| **cafe** (заказы) | `Order.totalAmount` | Оплата не отслеживается вообще (нет ни поля, ни статуса); суммы вливаются в чек ps-park-сессии через `OrderBooking` |
| **management** (управленка) | — | Только расходы; доходная часть отсутствует |

Что уже есть и будет переиспользовано:

- **Иммутабельный леджер** `FinancialTransaction` (type: `SESSION_PAYMENT | REFUND | ADJUSTMENT`, split cash/card) — правильная модель для проведения денег; расширяется онлайн-каналом.
- **Два образца входящих вебхуков**: Novofon (HMAC, fail-secure 503) и Avito (secret-token в URL, `timingSafeEqual`, **всегда HTTP 200**, чтобы провайдер не штормил ретраями).
- **Диспетчер уведомлений** `src/modules/notifications/` (очередь `OutgoingNotification`, каналы telegram/email/web-push, `dedupKey`).
- **Аудит и мониторинг**: `logAudit()` → `AuditLog`, `SystemEvent` (INFO…CRITICAL), `telegram-alert.ts`.
- **Cron-паттерн** с `CRON_SECRET` (`/api/cron/*`).

## 3. Что можем и что не можем через API ЮKassa

### Можем

- **Платёж по ссылке** (`confirmation.type = redirect`) — страница ЮKassa со всеми способами оплаты (карты, СБП, SberPay, T-Pay, ЮMoney). Самый быстрый старт. Есть и виджет (`embedded`) для оплаты без ухода с сайта — этап полировки.
- **Счета (Invoices API)** — готовая страница-счёт со сроком жизни **до 30 дней** (против ~1 часа у обычного платежа). Идеально для ежемесячной аренды B2B: ссылку можно отправить в email-напоминании.
- **Двухстадийная оплата** (`capture: false`): холд до **7 дней** (карты/SberPay/T-Pay/ЮMoney) → `capture` (можно частичный) или бесплатный `cancel`. Подходит для бронирований, требующих подтверждения менеджером.
- **Возвраты**: полный и частичный (`POST /refunds`), несколько частичных на один платёж, минимум 1 ₽. Для захолдированного платежа — бесплатная отмена холда вместо возврата.
- **Сохранение способа оплаты** (`save_payment_method`) → автосписания по `payment_method_id` без участия клиента (автопродление аренды/абонементов). ⚠️ На боевом магазине включается менеджером ЮKassa по запросу.
- **Чеки 54-ФЗ**: объект `receipt` в платеже; фискализация либо через «Чеки от ЮKassa», либо через свою онлайн-кассу (Атол и др.).
- **Тестовый магазин**: отдельная пара shopId/ключ, тестовые карты, `test: true` на всех объектах. Переключение test/prod = подмена env-переменных.

### Не можем / ограничения

- **Вебхуки не подписаны.** Верификация — только по IP-диапазонам ЮKassa + обязательный re-fetch `GET /payments/{id}` перед принятием решения. Это ложится в основу архитектуры (§ 4.4).
- **`pending` живёт ~1 час** — бронь «в ожидании оплаты» нельзя держать дольше; нужен TTL и автоотмена.
- **b2b_sberbank** (платёжка юрлица через СберБизнес): не работает в Invoices API, возвраты по нему не делаются через API, плательщик должен быть клиентом СберБизнес. Для аренды B2B реалистичный путь: счёт ЮKassa (оплата картой/СБП) **плюс** сохранение текущего пути «по реквизитам» как ручного варианта.
- **Возвраты невозможны** для способов `cash` (терминалы), `mobile_balance`; по картам эквайер может отклонить возврат старше 15 месяцев.
- **Только RUB**; минимальная сумма ~1 ₽.
- **Комиссия ЮKassa не возвращается** при возврате платежа (ориентиры: карты ~2.8–3.5 %, СБП ~0.4–0.7 %).
- **return_url ≠ подтверждение оплаты** — пользователь может не вернуться на сайт. Источник истины: вебхук + поллинг API, никогда UI-редирект.
- **Вебхук-ретраи идут только 24 часа** — обязателен reconciliation-cron, добивающий зависшие статусы.
- **HTTP 500/таймаут от API ≠ провал операции** — ретраи строго с тем же `Idempotence-Key`, иначе риск двойного списания.

## 4. Целевая архитектура

### 4.1 Размещение кода

ЮKassa — **интеграция, не модуль** (по прецеденту Avito, ADR `2026-04-28-delovoy-avito-adr.md`):

```
src/lib/yookassa/
├── client.ts        # тонкий клиент на нативном fetch: Basic auth, Idempotence-Key (UUID),
│                    # ретраи с тем же ключом, Zod-валидация ответов
├── types.ts         # типы API (Payment, Refund, Invoice, Receipt, Amount, ...)
└── receipts.ts      # сборка объекта receipt (54-ФЗ) из доменных позиций

src/modules/payments/          # бизнес-логика платежей (модуль — попадёт в CLAUDE.md)
├── service.ts                 # createPaymentFor(subject), applySucceededPayment(), refund(), ...
├── validation.ts              # Zod-схемы входов
├── types.ts
└── __tests__/

src/app/api/payments/
├── yookassa/webhook/route.ts  # приём уведомлений
├── [id]/route.ts              # GET статус платежа (для страницы «ожидание оплаты»)
└── [id]/refund/route.ts       # POST возврат (admin)

src/app/api/cron/payments-reconcile/route.ts   # добивание зависших статусов
```

Официального Node.js SDK у ЮKassa нет (community-пакет `@a2seven/yoo-checkout` устарел,
не покрывает Invoices) — пишем свой тонкий клиент на `fetch`: API маленький (6–8 эндпоинтов),
это соответствует strict-TS-конвенциям проекта и убирает неподдерживаемую зависимость.

### 4.2 Модель данных (Prisma)

Новая модель `Payment` — платёжная сессия с внешним провайдером, полиморфно привязанная
к доменной сущности:

```prisma
enum PaymentStatus {
  PENDING              // создан, ждёт оплаты
  WAITING_FOR_CAPTURE  // деньги захолдированы (двухстадийка)
  SUCCEEDED            // оплачен
  CANCELED             // не оплачен / отменён / холд истёк
  REFUNDED             // возвращён полностью
  PARTIALLY_REFUNDED   // возвращён частично
}

enum PaymentSubjectType {
  RENTAL_PAYMENT   // RentalPayment.id  — аренда B2B
  SUBSCRIPTION     // Subscription.id   — абонемент PS Park
  BOOKING          // Booking.id        — беседки / PS Park
  ORDER            // Order.id          — кафе
}

model Payment {
  id                 String        @id @default(cuid())
  provider           String        @default("yookassa")
  providerPaymentId  String?       @unique   // id платежа в ЮKassa
  providerInvoiceId  String?       @unique   // id счёта (Invoices API), если платёж по счёту
  status             PaymentStatus @default(PENDING)
  amount             Decimal       @db.Decimal(10, 2)
  refundedAmount     Decimal       @default(0) @db.Decimal(10, 2)
  currency           String        @default("RUB")
  subjectType        PaymentSubjectType
  subjectId          String
  userId             String?       // плательщик (если известен)
  createdById        String?       // менеджер, инициировавший ссылку/счёт
  confirmationUrl    String?       // ссылка на оплату / счёт
  description        String
  idempotenceKey     String        @unique
  paymentMethodType  String?       // bank_card / sbp / ... (из ответа ЮKassa)
  cancellationReason String?
  isTest             Boolean       @default(false)
  metadata           Json?         // снапшот позиций чека и пр.
  paidAt             DateTime?
  expiresAt          DateTime?     // TTL pending / срок холда / срок счёта
  createdAt          DateTime      @default(now())
  updatedAt          DateTime      @updatedAt

  refunds PaymentRefund[]
  @@index([subjectType, subjectId])
  @@index([status])
}

model PaymentRefund {
  id                String   @id @default(cuid())
  paymentId         String
  providerRefundId  String   @unique
  amount            Decimal  @db.Decimal(10, 2)
  status            String   // pending / succeeded / canceled
  reason            String?
  createdById       String   // кто оформил возврат
  createdAt         DateTime @default(now())

  payment Payment @relation(fields: [paymentId], references: [id])
}
```

Дополнительно:

- `FinancialTxType` расширяется значением `ONLINE_PAYMENT` (и возвраты онлайн идут type
  `REFUND` с `metadata.paymentId`) — онлайн-выручка попадает в тот же иммутабельный леджер,
  что и POS, а значит и в сверку смен/аналитику.
- `OrderStatus`/`Order` — добавить поле оплаты только в фазе «кафе» (не сейчас).

### 4.3 Клиент API — правила

- `Idempotence-Key` = UUID, сохраняется в `Payment.idempotenceKey` **до** запроса; при
  500/таймауте — ретрай с тем же ключом (окно идемпотентности ЮKassa — 24 ч).
- `amount.value` — строка с 2 знаками (`"1500.00"`), конвертация из `Decimal` централизована.
- Все ответы валидируются Zod; неожиданные поля не роняют обработку.
- Ключи: `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` (env). Тест/прод различаются только парой
  ключей. ⚠️ GitHub Secrets доступны только CI — для прод-VPS ключи нужно завести в env
  docker-compose (как `NOVOFON_WEBHOOK_SECRET`).

### 4.4 Вебхук (критическая часть)

`POST /api/payments/yookassa/webhook/{secret}` — по образцу Avito:

1. **Секретный сегмент URL** из env (`YOOKASSA_WEBHOOK_SECRET`), сравнение `timingSafeEqual`,
   fail-secure (503 без секрета) — первая линия защиты.
2. **IP-фильтр** по официальным диапазонам ЮKassa (185.71.76.0/27, 185.71.77.0/27,
   77.75.153.0/25, 77.75.154.128/25, 77.75.156.11, 77.75.156.35, 2a02:5180::/32) — вторая линия
   (за nginx — real IP из `X-Forwarded-For` с `set_real_ip_from`).
3. **Телу уведомления не доверяем**: берём `object.id` → `GET /v3/payments/{id}` → решение
   принимается **только** по свежему статусу из API. Это закрывает и подделку, и гонки,
   и дубли событий.
4. **Идемпотентная обработка**: переход `Payment.status` — конечный автомат; повторное
   событие с тем же статусом = no-op.
5. **Всегда HTTP 200** (кроме проваленной аутентификации), тяжёлая работа — внутри, но быстро;
   ошибка обработки → `SystemEvent` ERROR + Telegram-алерт, ЮKassa доретраит 24 часа.

События, которые слушаем: `payment.succeeded`, `payment.waiting_for_capture`,
`payment.canceled`, `refund.succeeded`. Настройка URL — в личном кабинете ЮKassa
(API настройки вебхуков при Basic auth недоступен).

### 4.5 Reconciliation-cron

`GET /api/cron/payments-reconcile` (авторизация `CRON_SECRET`, запуск каждые ~10 минут):

- все `Payment` в нефинальных статусах старше N минут → `GET /payments/{id}` → синхронизация;
- `PENDING` старше TTL без объекта в ЮKassa → `CANCELED` + освобождение брони;
- страховка от потери вебхука (ретраи ЮKassa живут только 24 ч).

### 4.6 Проведение успешного платежа

Единая точка `applySucceededPayment(payment)` в `src/modules/payments/service.ts`, всё в
`prisma.$transaction`:

1. `Payment.status → SUCCEEDED`, `paidAt`, `paymentMethodType`.
2. Доменный эффект по `subjectType`:
   - `RENTAL_PAYMENT` → `RentalPayment.paidAt = paidAt` (авто-«Оплачено», без ручной кнопки);
   - `SUBSCRIPTION` → активация пасса (пасс создаётся в статусе «ожидает оплаты» и активируется здесь);
   - `BOOKING` → пометка предоплаты в `Booking` (+ запись в `FinancialTransaction` type `ONLINE_PAYMENT`);
   - `ORDER` → пометка заказа оплаченным (фаза «кафе»).
3. `FinancialTransaction` (`ONLINE_PAYMENT`) — в общий леджер.
4. `logAudit(...)` → `AuditLog`.
5. `enqueueNotification(...)` — клиенту и админам (§ 4.7).

### 4.7 Уведомления и системные сообщения

Новые события в реестре `src/modules/notifications/events.ts`:

| Событие | Кому | Каналы |
|---|---|---|
| `payment.link.created` | клиент | email/telegram — ссылка на оплату/счёт |
| `payment.succeeded` | клиент + админ-группа | подтверждение оплаты, чек придёт от ЮKassa |
| `payment.canceled` | клиент (+ менеджер, если бронь слетела) | «оплата не прошла», причина из `cancellation_details` |
| `payment.refund.succeeded` | клиент + админ | подтверждение возврата |
| `payment.expiring` (счета аренды) | клиент | напоминание до истечения счёта |

Мониторинг: ошибки вебхука/клиента API → `SystemEvent` ERROR (Telegram-группа админов);
недоступность API ЮKassa в reconciliation → WARNING; расхождение сумм при сверке → CRITICAL.
Health-check `GET /api/payments/health` по конвенции модулей.

### 4.8 Безопасность

- Секреты только в env; ключи никогда не попадают в ответы API и логи.
- Вебхук — вне общего public-rate-limit (или отдельный tier), защита секрет-сегментом + IP.
- Возвраты — только SUPERADMIN или менеджер с правом секции (`requireAdminSection`),
  каждая операция в `AuditLog`.
- Никаких `providerPaymentId`/`confirmationUrl` чужих платежей в публичных ответах — клиент
  видит только свои `Payment` (проверка `userId`).

## 5. Продуктовые потоки по модулям

### 5.1 Аренда B2B (rental / nedelovoy) — фаза 1, максимальная отдача

Сейчас: email-напоминание с банковскими реквизитами → арендатор платит платёжкой → менеджер вручную жмёт «Оплачено».

Станет:

1. Кнопка **«Выставить счёт»** на строке `RentalPayment` в админке (`/admin/rental/payments`,
   `/admin/nedelovoy/payments`) → `POST /v3/invoices` (срок жизни = due date + грейс, до 30 дней)
   → ссылка сохраняется в `Payment.confirmationUrl`.
2. Ссылка на оплату автоматически включается в существующие email-напоминания
   (`rental/notifications.ts`) рядом с реквизитами — арендатор сам выбирает: карта/СБП онлайн
   или платёжка по реквизитам.
3. Оплата → вебхук → `RentalPayment.paidAt` проставляется автоматически; кнопка «Оплачено»
   остаётся для оплат по реквизитам.
4. Эскалации и `ManagerTask OVERDUE_PAYMENT` продолжают работать без изменений — они смотрят
   на `paidAt`.

Опционально (после включения автоплатежей менеджером ЮKassa): сохранённая карта арендатора
→ автосписание в due date с уведомлением за 3 дня — как в лучших SaaS-подписках.

### 5.2 Абонементы PS Park (subscriptions) — фаза 2

Сейчас: менеджер выписывает пасс, `pricePaid` — просто цифра.

Станет: пасс создаётся в состоянии «ожидает оплаты» → клиенту уходит платёжная ссылка
(или QR СБП на стойке) → оплата → вебхук активирует пасс и пишет `FinancialTransaction`.
Ручная активация (наличные на стойке) остаётся как POS-путь — тогда менеджер, как и сейчас,
проводит оплату вручную.

### 5.3 Беседки (gazebos) — фаза 3, предоплата с холдом

Лучшая практика для бронирований с подтверждением — **двухстадийная оплата**:

1. Гость бронирует → создаётся платёж `capture: false` → редирект на оплату.
2. Деньги холдируются (до 7 дней для карт); бронь в `PENDING` с TTL ~1 час на оплату
   (окно pending у ЮKassa), не оплачено → автоотмена и слот освобождается.
3. Менеджер подтверждает бронь → `capture` (списание); отклоняет → `cancel`
   (бесплатно, деньги мгновенно разблокируются — не возврат!).
4. Гость отменил после списания → возврат по политике отмены (полный/частичный
   в зависимости от срока до брони — политику зафиксируем в PRD фазы).

Существующий POS-гейт `PAYMENT_REQUIRED` при завершении учитывает предоплату: онлайн-часть
уже лежит в `FinancialTransaction`, доплата на месте — как сейчас.

⚠️ Решение «предоплата 100 % / частичная / опциональная» — продуктовый вопрос (§ 10).

### 5.4 PS Park сессии — фаза 3–4

Walk-in-модель почти не меняется (POS остаётся основной). Добавляем: оплату счёта сессии
по QR СБП/ссылке — менеджер в `session-bill-modal` жмёт «Оплатить онлайн», гость сканирует
QR, вебхук закрывает счёт третьим способом оплаты рядом с наличными/картой/абонементом.

### 5.5 Кафе — фаза 4 (последняя)

Требует самого большого доменного изменения (у `Order` вообще нет понятия оплаты).
Добавляем `Order.paidAt` + оплату при онлайн-заказе. Автономная ценность небольшая, пока
заказы вливаются в чек PS Park — делаем последним или по отдельному решению PO.

## 6. Возвраты

- Админ-действие «Оформить возврат» на карточке платежа: полный или частичный (Zod-валидация:
  0 < сумма ≤ `amount - refundedAmount`), причина обязательна.
- Развилка по статусу: `WAITING_FOR_CAPTURE` → `cancel` (бесплатно); `SUCCEEDED` → `refund`.
- `PaymentRefund` со статусом из API; `refund.succeeded` вебхук → финализация +
  `FinancialTransaction` type `REFUND` + чек возврата (54-ФЗ) + уведомление клиенту.
- Ошибка `insufficient_funds` (не хватает средств на балансе магазина ЮKassa) → понятное
  сообщение менеджеру + `SystemEvent` WARNING, ретрай позже.
- Права: возврат — SUPERADMIN или менеджер секции; всё в `AuditLog`.
- Автовозврат при отмене брони системой (не приехал/слот отменён) — политика в PRD фазы 3.

## 7. Чеки 54-ФЗ

Обязательная развилка **до первого боевого платежа** (§ 10, вопрос 2):

- **«Чеки от ЮKassa»** — без своей кассы, чек уходит на email покупателя. Минимум усилий,
  рекомендую как старт.
- **Своя онлайн-касса** (Атол Онлайн и др.) — если касса уже есть/планируется.

Технически в обоих случаях: при включённой фискализации объект `receipt` обязателен в каждом
платеже/capture/refund → нам **нужен email или телефон плательщика до создания платежа**
(для аренды есть в CRM; для гостей — поле на форме оплаты). Сборка `receipt` централизована
в `src/lib/yookassa/receipts.ts`: позиции, `vat_code` (по нашей СНО), `payment_subject:
"service"`. Пока фискализация в ЛК не включена — `receipt` не отправляем, флаг в env.

## 8. Паттерны «как в лучших сервисах»

- **Страница ожидания оплаты**: после возврата с `return_url` клиент попадает на
  `/payments/{id}/status`, которая поллит наш `GET /api/payments/{id}` до финального статуса —
  а не «спасибо за оплату» по факту редиректа (return_url не гарантирует оплату).
- **Один источник истины** — статус из API ЮKassa; UI и вебхук лишь триггеры проверки.
- **Иммутабельный леджер** — все деньги (POS + онлайн + возвраты) в `FinancialTransaction`,
  никакие суммы не перезаписываются.
- **Идемпотентность на всех уровнях**: Idempotence-Key наружу, конечный автомат статусов внутрь.
- **Graceful degradation**: ЮKassa недоступна → POS и «по реквизитам» продолжают работать,
  онлайн-кнопки показывают понятную ошибку.
- **Прозрачные письма**: ссылка на оплату, подтверждение, возврат — через существующий
  диспетчер уведомлений с дедупом.

## 10. Открытые вопросы (нужно решение владельца)

1. **Порядок фаз**: старт с аренды B2B (максимальная отдача: убирает ручную кнопку «Оплачено»

## 11. Подключение и env

```
YOOKASSA_SHOP_ID=         # ЛК → Настройки → Магазин
YOOKASSA_SECRET_KEY=      # ЛК → Интеграция → Ключи API (тест и прод — разные пары)
YOOKASSA_WEBHOOK_SECRET=  # наш случайный сегмент URL вебхука
YOOKASSA_RECEIPTS_ENABLED=false   # включить после настройки фискализации в ЛК
```

Шаги вне кода (владелец/админ ЛК ЮKassa):

1. Создать **тестовый магазин** в ЛК, выдать тестовые ключи (для разработки фазы 0).
2. В ЛК настроить **HTTP-уведомления** на `https://<домен>/api/payments/yookassa/webhook/<secret>`
   (события: payment.succeeded, payment.waiting_for_capture, payment.canceled, refund.succeeded) —
   при Basic auth это делается только в ЛК, не через API.
3. Определиться с фискализацией (§ 10.2).
4. Прод-ключи — в env VPS (docker-compose), GitHub Secrets достаточно только для CI.
5. (Позже) запросить у менеджера ЮKassa включение автоплатежей, если решим (§ 10.5).
