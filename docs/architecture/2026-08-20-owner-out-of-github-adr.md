# ADR: владелец вне GitHub — зонтики мелочи, деплой-трейн, решения в Telegram

- **Дата:** 2026-08-20
- **Статус:** принят
- **Связан с:** `2026-08-10-autonomous-issue-cleanup-adr.md` (очередь, гейт,
  свипер), `2026-08-11-backlog-intake-adr.md` (интейк),
  `2026-08-14-autonomous-dev-pipeline-audit.md` (карта узких мест B1–B8/F1–F7)

## Контекст

Автономная очередь работала, но владелец вместо продукта занимался GitHub.
Замер 15–17.08: ~20 смерженных PR за двое суток, открытых issues стабильно ~27 —
приток равен оттоку. Причины, подтверждённые кодом и живым API:

1. **Мелочь дробилась на issues, а деплой дорогой.** Единица работы = 1 мелкая
   issue = 1 PR = полный CI (~15–20 мин) + деплой. `deploy.yml` имел
   concurrency-группу ПО SHA: пять мержей подряд = пять параллельных полных
   деплоев (каждый со снапшотом, pg_dump, миграциями и рестартом бота на один
   VPS). Мерж release-please PR добавлял ещё один деплой без единой строчки кода.
2. **Интейк плодил дубли.** `escalate-incidents` дедупил только по открытым
   issues: очередь закрывала root-cause, ночной крон создавал её заново — 6
   копий «notifications-down» за 6 суток (#487→#506→#535→#603→#637→#678).
   Вдобавок watchdog-и закрывали root-cause через минуты после создания (#678 —
   через 14 минут): лейбл инцидента на root-cause попадал под их авто-закрытие.
3. **Владелец был вшит в GitHub шестью каналами:** терминальный `needs-owner`
   (снимается только руками), `auto:blocked`, восемь висящих dependabot-PR
   (автомерж покрывал только patch, и то мёртвой джобой), ручной мерж
   release-PR, «Approve and run» на запаркованных CI (мёртвый
   `AUTOMATION_TOKEN`, #499), heartbeat-алерты.

Требование владельца: «Я не хочу возиться с GitHub вообще. Мелкие issues
убивают работу из-за долгого деплоя. Направьте меня на работу с пользователями,
деплой — обязанность автоматики».

## Решение

Пять блоков. Очередь, гейт, свипер и интейк остаются прежней архитектуры
(лейблы-как-состояние, детерминированный TS без AI) — меняется гранулярность
потока и поверхность контакта с владельцем.

### 1. Зонтики: мелочь перестаёт быть issues

P2-мелочь живёт **пунктами-комментариями** «зонтика» области — issue с лейблом
`batch` и маркером `<!-- batch:<area> -->`; пункты добавляет `issue-queue.ts
batch-add` (append-only комментарии с маркером `batch-item:<key>` — гонка
read-modify-write тела исключена по построению). Зонтик для механики очереди —
обычная issue: лок/staleWip/maxAttempts не менялись. Воркер закрывает зонтик
целиком одним PR, перед PR отчитывается `batch-result` (сделано/перенесено);
`reconcile` сверяет закрытые зонтики с отчётом и механически спасает забытые
пункты в новый зонтик — молчаливых потерь сигналов нет. Отдельной issue достойны
P0/P1, security, миграции, prod-apply и фичи. Источники мелочи переключены на
`batch-add`: P2-паттерны и всплески интейка, perf-регрессии, триаж-мелочь,
попутные находки сессий. Чистые функции — `scripts/lib/issue-batch.ts` (вне
HOLD_PATTERNS — прецедент `queue-watch.ts`: на решение о мерже не влияет).

Отвергнут вариант «area-лейблы + мульти-`pickNext`»: не снижает видимое число
issues (цель владельца) и требует глубокой правки механики с 53 тестами.

### 2. Интейк: дедуп переживает закрытие

Все анализаторы дедупят по `state=all` в окне ретроспективы (14 дней — ширина
базлайна fingerprint'а; «закрыли вечером → пересоздали ночью» невозможно).
`escalate-incidents` при живом инциденте **реоткрывает** закрытую root-cause
(история диагностики в одной ветке), а watchdog-и (`site-watchdog`,
`ci-watchdog`) больше не закрывают issues с лейблом `root-cause` — они живут
циклом бэклога, а не «упало-поднялось». `create` получил дедуп: отказ по точному
совпадению title с открытой issue (exit 3, `--force`) и опциональный
`--dedup-key` (маркер, окно 14 дней). Fuzzy-похожесть отвергнута: механика — без
AI и без ложных срабатываний.

### 3. Деплой-трейн: пачка мержей = 1–2 деплоя

`deploy.yml` — фиксированная concurrency-группа `deploy-production-train`
(`cancel-in-progress: false`): GitHub держит максимум «1 бегущий + 1 pending»,
промежуточные pending отменяет сам (отменённый pending не исполняет шагов —
ложных «Deploy FAILED» нет). Ключевое — **resolve-to-HEAD**: любой не-dispatch
ран деплоит текущий HEAD `main`, а не SHA своего события. Это закрывает две
гонки разом: (а) события приходят out-of-order (workflow_run старого коммита
создаётся позже push-рана нового и вытесняет его из pending), (б) «у новейшего
коммита красный CI → никто ничего не задеплоил молча». Не слабее прежнего:
push-путь и раньше деплоил, не дожидаясь CI; блокирующие smoke, blue-green и
error-budget-автооткат остаются последней линией. Guard скипает ран за ~10с,
если HEAD уже задеплоен (`DEPLOYED_SHA_CURRENT`). `workflow_dispatch` с явным
`sha` (hotfix, авто-откат) — своя группа, вне трейна.
`deploy-error-budget.yml` — фиксированная группа с `cancel-in-progress: true`:
окно наблюдения всегда достаётся итоговому SHA трейна.

Release-please PR мержит свипер — только в ночное окно (00–02 UTC = 03–05 МСК;
мерж release-PR — это деплой без кода, ему не место в трафик-часы) и только при
диффе целиком из `{CHANGELOG.md, package.json, package-lock.json}` (проверено по
#649/#611); что-то сверх — обычный путь через гейт. Вердикты ревью на release-PR
не требуются: их не было и при ручном мерже, whitelist строже. Dependabot
пересобран в недельные ночные группы (`npm-minor-patch`, `actions-all`) — их
мержит свипер при зелёном CI (мерж под PAT рождает события — deploy стартует
сам); majors конвертируются в задачи очереди с настоящим ревью. Мёртвая джоба
автомержа release-PR удалена (не срабатывала по конструкции: PR от
`GITHUB_TOKEN` не рождает `pull_request`-событий, с PAT актор — человек).

### 4. Контур owner-decisions: решения — кнопками в Telegram

`needs-owner` больше не GitHub-инбокс. Контур: **свипер** (Actions,
`decisions-sync` каждые 15 минут) reconcile'ом заводит запросы решений на сайте
(`POST /api/admin/owner-decisions`, секрет `OWNER_DECISIONS_SECRET` — паттерн
release-notify): для каждого открытого needs-owner PR — `merge-hold` под его
текущий head SHA, для каждой открытой issue в `auto:blocked`/`auto:prod-apply` —
`blocked-question` (один живой вопрос на issue, дедуп по-субъектный);
**сайт** шлёт владельцу личное Telegram-сообщение с кнопками
«Мержить/Отклонить/Позже»; **бот** записывает ответ (двухшаговый confirm,
авторизация строго по `TELEGRAM_OWNER_CHAT_ID` и повторно на сервере, AuditLog,
команда `/decisions`, реплай — детали ответа, «идея: …» — поручение → issue);
**свипер** исполняет: аппрув мержит hold-PR через `attemptMerge` с **пином к
head SHA** (`sha` в `PUT /merge` — атомарный 409 при гонке), после grace-окна
15 минут с кнопкой «Отменить», при обязательном зелёном CI; reject закрывает PR
и уводит issue в `auto:blocked`; approve blocked-question возвращает issue в
очередь и при `payload.dispatchWorkflow` диспатчит ops-workflow (закрывает класс
`auto:prod-apply`). Reconcile-паттерн вместо «POST один раз»: лежащий сайт или
ещё не заведённый секрет ничего не теряют — запросы доотправятся следующим
проходом; тот же механизм даёт бекфилл уже висящих PR. `auto-rebase` пропускает
needs-owner PR — иначе каждый мерж менял бы head под ждущим решением и аппрувы
вечно устаревали бы.

GitHub-креды остаются только у Actions: сайт и бот лишь хранят решение.
Единственное действие владельца в самом GitHub — перевыпуск fine-grained PAT раз
в ~90 дней; инструкция приходит decision-сообщением с кнопкой «Готово»
(ops-watch следит за живостью и сам заводит запрос).

### 5. Владелец получает продукт, а не процесс

Вечерний дайджест (`owner-digest.yml`, 21:00 МСК, личный чат): что уехало в прод
за сутки (merged PR + `DEPLOYED_SHA_CURRENT` — Releases не годятся, трейн
выкатывает и между ночными релизами), дельта бэклога, ждущие решения
(PENDING+DEFERRED с возрастом), фидбек пользователей. Кнопок в дайджесте нет —
действия живут в decision-сообщениях и `/decisions`. Старый суточный
needs-owner-дайджест из `issue-queue.yml` удалён вместе с его кодом
(`buildNeedsOwnerDigest`); heartbeat («сломался планировщик») и алерт мёртвого
PAT остаются.

### Гейт: расширение HOLD и правило ширины

`HOLD_PATTERNS` += `issue-queue-merge.yml` (свипер не мержит правку самого
себя — та же циклическая дыра, что у файлов гейта), `auto-rebase.yml`
(форс-пуш чужих веток под PAT с человеческой атрибуцией), все файлы контура
owner-decisions (канал мержа мимо гейта не расширяет себя сам) и
`.claude/commands/next-issue.md` (промпт — программа агента, ведущая к
вердиктам #580). **Осознанная асимметрия:** CLAUDE.md в HOLD не входит — он
правится на порядок чаще (каждый синк модулей), механику мержа не задаёт, и
каждая его правка стоила бы владельцу кнопки; `next-issue.md` правится ~1 раз в
неделю и напрямую управляет тем, кто ставит вердикты.

Правило «≥5 модулей → hold» заменено: ≥8 модулей → hold всегда (новый жёсткий
потолок, которого не было); 5–7 модулей → hold только при диффе >400 строк или
>25 файлов, либо когда метрики диффа недоступны (консервативно); <5 — как
раньше. Коридор открыт ровно для зонтичных батчей (5–7 областей × 20–50 строк),
взамен появились стопы на широкие свалки, которые раньше проходили (4 модуля ×
3000 строк ехали в auto).

## Остаточные риски (приняты владельцем)

1. **Корень доверия owner-decisions — прод-БД**, куда пишет код, задеплоенный
   самим конвейером: авто-tier PR теоретически может добавить код, флипающий
   PENDING→APPROVED. Раньше needs-owner был строго терминален (мержил только
   человек в GitHub). Смягчения: файлы контура в HOLD (автоматика не правит
   контур сама), grace-окно 15 мин с «Отменить» + подтверждение владельцу до
   исполнения (форджа видима), SHA-пиннинг, обязательный зелёный CI, AuditLog,
   исполнение только на стороне Actions. Владелец выбрал «кнопки в Telegram»
   с этим trade-off явно.
2. **Трейн при красном CI финального HEAD** не деплоит ничего до следующего
   мержа/ночного релиза — сигналом остаётся ci-watchdog «CI FAILED на main»
   (push-путь и раньше вёз непроверенный HEAD, так что это строго не хуже).
3. **Мёртвый бот** = кнопки не работают: решения лежат PENDING в БД, дайджест
   напоминает, очередь не стоит (park-механика не менялась).

## Отвергнутые альтернативы

- **GitHub-токен боту/VPS** для мгновенного исполнения решений — нарушает
  принцип «GitHub-мутации только у Actions и сессий»; 15 минут латентности
  свипера дешевле нового класса секретов на проде.
- **Webhook сайт→Actions** (`workflow_dispatch` с прода) — тот же токен на VPS.
- **Кнопки прямо в дайджесте** — дублирование decision-механизма.
- **Fuzzy-дедуп в `create`** — недетерминированно; точный title + маркеры
  закрывают наблюдавшиеся дубли.
- **HOLD на deploy.yml и все `.claude/commands/`** — против решения владельца от
  2026-08-11 «катить без участия» и против цели «меньше кнопок»; deploy защищён
  своими слоями (снапшот, миграции до подмены, блокирующие smoke, error-budget,
  авто-откат).
- **Автомерж dependabot-majors** — им нужно ревью; вместо этого конверсия в
  задачи очереди.

## Что остаётся владельцу

| Действие | Канал | Частота |
|---|---|---|
| Кнопки решений (merge-hold, blocked-вопросы) | Telegram | по событию, редко |
| «идея: …» / «ответ: …» реплаем | Telegram | по желанию |
| Вечерняя сводка | Telegram | ежедневно, читать |
| Перевыпуск PAT + (разово) секрет `OWNER_DECISIONS_SECRET` | GitHub Settings | ~2 мин раз в 90 дней |

GitHub (issues, PR, Actions) владелец не открывает.
