# ADR: ежедневная сводка звонков в ленте Mini App

Статус: принято. Основание: [PRD](../requirements/2026-10-24-telephony-daily-summary-prd.md).

## Контекст

Пользователь заказал ежедневное сообщение внутри Telegram Mini App: всего звонков, принято и пропущено. `/webapp/notifications` управляет настройками; сообщения отображаются в ленте `/webapp`. Существующий `OutgoingNotification` требует внешнего канала и обслуживается очередью Telegram/email/push. Его пяти­минутный dedup не гарантирует одну сводку за день, а фиктивная запись `SENT` в Telegram неверно описывала бы фактическую доставку.

## Решение и данные

Используется отдельная `InAppNotification`: `id`, `userId`, `eventType`, `payload`, `readAt`, `createdAt`. Добавление модели и индексов оформляется отдельной инфраструктурной зависимостью; бизнес-логика остаётся в существующем `telephony`, новых модулей и пакетов нет.

Тип события — `telephony.daily_summary`. Primary key `telephony-daily:<YYYY-MM-DD>:<userId>` детерминирован и не зависит от текста, времени попытки и последующих уточнений провайдера. В одной транзакции создаются уведомление и `AuditLog`; при P2002 повтор считается уже обработанным. Ошибка аудита откатывает уведомление. После частичного сбоя новые попытки создают только отсутствующих получателей, существующие payload не переписываются.

Лента получает третий персональный источник с префиксом `ia:`; отметка прочтения и счётчик относятся к той же строке. Строки не попадают в dispatcher, `OutgoingNotification`, бота, email или push. Наличие Telegram-канала не требуется. Настройки отдельно показывают доставку «В ленте Mini App».

## Расписание и подтверждение отчёта

Существующий `/api/cron/notifications`, зарегистрированный каждые пять минут, вызывает `processTelephonyDailySummaries`. До 09:00 МСК работа пропускается. После 09:00 формируется предыдущий завершённый календарный день МСК. Константа расписания — `TELEPHONY_DAILY_HOUR_MSK = 9` (10:00 по времени Dubai); текущие неполные сутки никогда не публикуются. После длительного простоя восстанавливается сводка за вчера, без лавины исторических уведомлений.

Перед сетевым запросом выбираются действующие владельцы и уже созданные id; если все получатели покрыты, API Novofon не вызывается. Затем `get.calls_report` запрашивается за точные границы вчера: `00:00:00` — `23:59:59` МСК. Все страницы загружаются до короткой последней страницы. Общий AbortSignal ограничивает запрос отчёта 45 секундами, сохраняются ограниченные повторы rate-limit из существующего клиента и предел offset Novofon.

Если интеграция не настроена, задача тихо возвращает `reason: not_configured`, не создаёт сообщения и не пишет повторяющийся error каждые пять минут. Ошибки уже настроенного провайдера остаются ошибками с последующей плановой повторной попыткой. Аудит создания появляется только в транзакции публикации после полностью проверенного отчёта; пропуск, неподтверждённый ноль и неудачный запрос не являются опубликованной сводкой.

Успешный HTTP сам по себе не достаточен: `result.data` обязан быть массивом. Проверяются id, дата внутри отчётного дня, направление, булев `is_lost`, конечная неотрицательная длительность. Повторяющиеся id, выход за дату, сломанная оболочка, слишком большая страница или превышение пагинации отменяют всю публикацию. При таймауте/ошибке не создаются ни уведомления, ни marker успеха; следующий плановый вызов повторяет попытку. Действительно пустой подтверждённый отчёт даёт честное сообщение «По отчёту Novofon за этот день звонков не было».

API-проверка выполняется для публикации, а чтение уже созданной карточки не требует сети. Late webhook или изменения отчёта не меняют сохранённую сводку; время формирования показывается отдельно от отчётного дня.

## Метрики и клиентский контракт

Семантика совпадает с дашбордом: пропущенные — только `INBOUND && isLost`; принятые — `INBOUND && !isLost && talkDuration > 0`; прочие входящие — `pending`. Исходящие без ответа не входят в пропущенные. Доля ответов считается среди известных входящих исходов; при нулевом знаменателе `null`.

Клиент-безопасный контракт и валидатор — `daily-summary-types.ts`:

```text
payload: {
  title, body,
  telephonySummary: {
    reportDate: YYYY-MM-DD,
    timeZone: Europe/Moscow,
    generatedAt: ISO timestamp,
    total, inbound, answered, missed, outbound, pending,
    answerRate: number | null
  }
}
```

В payload нет телефонных номеров, записей, имён сотрудников и необработанных строк провайдера. Валидатор проверяет неотрицательные числа и равенства `total = inbound + outbound`, `inbound = answered + missed + pending`. Повреждённые расширенные payload не становятся визуально убедительными KPI-карточками; остаётся безопасный общий текст уведомления.

«Подробнее» раскрывает тот же snapshot внутри Mini App. Перехода в `/admin/telephony` с другой датой и отдельной NextAuth-сессией нет.

## Права и подписка

Получатели — только `SUPERADMIN` с `mergedIntoUserId = null`. Сводка включена по умолчанию, поскольку пользователь прямо заказал ежедневную функцию; явное `NotificationEventPreference(enabled=false)` отключает её. Роль и предпочтение повторно проверяются после API-запроса перед вставкой.

Категория имеет жёсткое `superadminOnly`, существующее правило grandfather по старой подписке на неё не распространяется. Лента, unread count и mark-read дополнительно проверяют актуальную роль через БД: разжалованный владелец не видит старые глобальные данные Novofon, даже если помнит id сообщения. DND внешних каналов не требуется для тихой внутренней ленты.

## Проверки

Тесты покрывают границу 09:00 МСК и переход года, полный вчерашний интервал, 3 принятых + 2 пропущенных + 1 уточняемый входящий + 2 исходящих = 8 всего и 60%, подтверждённый ноль, некорректный ответ/строку, дубли id, пагинацию/усечение, таймаут, повтор после ошибки, PK-конфликт, отмену доступа после fetch, пропуск уже опубликованных получателей, транзакционную запись аудита и включение задачи в существующий scheduler. Все сетевые ответы в тестах мокируются, реальные сообщения не отправляются.
