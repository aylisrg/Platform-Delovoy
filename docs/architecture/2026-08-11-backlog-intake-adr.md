# ADR: Автопополнение и триаж бэклога (backlog intake)

- **Дата:** 2026-08-11
- **Статус:** принят
- **Связан с:** `2026-08-10-autonomous-issue-cleanup-adr.md` (потребляющая половина:
  очередь, гейт, исполнитель-сессия)

## Контекст

Очередь разгрузки бэклога (ADR 2026-08-10) потребляет issues с `prio:*` +
`auto:ready`, но ни один автоматический источник сигналов их не создавал:

- `scripts/analyze-errors.ts` был написан и покрыт тестами, но не имел ни
  npm-скрипта, ни workflow, а issues создавал с лейблами `bug,auto-detected`,
  которые для очереди невидимы (`laneOf` без `auto:*` → untriaged);
- фидбек пользователей (`FeedbackItem`, BUG/SUGGESTION) заканчивался в
  админке и Telegram-алерте, до GitHub не доходил;
- watchdog-issues (`site-down`, `notifications-down`, `ci-failure`) живут
  инцидент-циклом «открылась-закрылась» и в бэклог не превращались, даже
  когда один инцидент повторялся всю неделю;
- issue, заведённая человеком без лейблов, зависала навсегда — правило
  «заводишь issue — ставь лейблы сам» нарушали и люди, и вся автоматика.

Автономность заканчивалась на границе интейка: очередь могла разгребать
бэклог, но никто не мог его пополнять.

## Решение

### Разделение: механика — детерминированная, суждение — у сессии

Всё, что можно решить правилом, решается кодом без AI (пороги, дедуп,
маппинг лейблов, окна). AI-суждение (какой приоритет у свободного текста,
задача это или эпик) выполняет интерактивная сессия Claude Code — тот же
исполнитель, что разбирает очередь, — шагом 0 цикла `/next-issue`.

### Источники → issues

| Источник | Скрипт | Лейблы | Порог |
|---|---|---|---|
| Новый паттерн ERROR/CRITICAL (`SystemEvent`, фингерпринт против недельного базлайна) | `analyze-errors.ts` | `bug, auto-detected, prio:P1\|P2, auto:ready` | CRITICAL или ERROR ≥20/сутки → P1, иначе P2; ≤5 issues/прогон |
| Всплеск WARNING (`client-beacon`, `rate-limit`) | `analyze-errors.ts` (`detectWarningSpikes`) | `bug, auto-detected, prio:P2, auto:ready` | ≥50/сутки и ≥3× базлайна |
| Фидбек-BUG (`FeedbackItem`, status=NEW) | `feedback-to-issues.ts` | `bug, from-feedback, prio:P1 (isUrgent)\|P2, auto:ready` | все новые; ≤20/прогон |
| Фидбек-SUGGESTION | `feedback-to-issues.ts` | `enhancement, from-feedback` (без `auto:*` → шаг-0 триаж) | — |
| Повторяющийся инцидент | `escalate-incidents.ts` | `root-cause, <label>, prio:P1, auto:ready` | ≥3 закрытий за 7 дней |
| Свободный текст владельца / issue без лейблов | шаг-0 триажа сессии (`untriaged`/`triage`) | `prio:P0..P2 + auto:ready` или `auto:epic` | эвристики в `next-issue.md` |
| Крупная идея (`auto:epic`) | `/plan-epic` | PRD + дочерние issues `prio:P1\|P2, auto:ready` | 2–8 задач, один эпик за заход |

Пороги — константы в чистых функциях (`DEFAULT_SPIKE_OPTIONS`,
`HIGH_FREQ_ERROR`, `DEFAULT_ESCALATION_OPTIONS`), после первой недели живых
прогонов их дёшево подтюнить.

### Доступ к прод-БД: SSH-дамп, а не прямое подключение

Прод-Postgres не доступен GitHub-раннерам. `backlog-intake.yml` (ежедневно
03:43 UTC) снимает два `psql ... json_agg`-дампа по SSH (паттерн
`beacon-divergence` из site-watchdog.yml) и скармливает их скриптам через
`--events-file`/`--file` — Prisma и `DATABASE_URL` на раннере не нужны.

Отвергнутые альтернативы:
- **запускать скрипты на VPS** — там нет `gh`/`GH_TOKEN`, пришлось бы
  раздавать GitHub-учётку проду;
- **прямое подключение раннера к БД** — открывать Postgres наружу ради
  крона не вариант.

Ограничения дампа: 15 дней (окно 24ч + базлайн `now-14d..now-7d`), 20 000
строк новейших-вперёд, `message` до 500 символов. При росте объёма событий
базлайн молча усечётся — тогда поднять LIMIT или сузить выборку.

### Дедуп — маркеры в телах issues

Состояние интейка, как и состояние очереди, живёт в GitHub, без своей БД:

| Маркер | Где | Что дедупит |
|---|---|---|
| `<!-- error-fingerprint:<fp> -->` | тело issue | повторное заведение паттерна |
| `<!-- warning-spike:<source> -->` | тело issue | повторный всплеск источника |
| `<!-- feedback:<id> -->` | тело issue | повторный перенос фидбека |
| `root-cause` + лейбл инцидента | лейблы | вторая root-cause issue (повтор — комментарий) |
| `<!-- epic-planned -->` | комментарий эпика | повторная декомпозиция |
| `<!-- issue-queue-heartbeat -->` | комментарий дашборда | спам алертами простоя (кулдаун) |
| `<!-- issue-queue-stale-release -->` | комментарий issue | счётчик брошенных попыток |
| `<!-- issue-queue-gave-up -->` | комментарий issue | сброс счётчика (возврат владельцем = чистый лист) |
| `<!-- issue-queue-parked-stale-pr -->` | комментарий issue | след рипера мёртвых сессий с PR |

### Недоверенный текст

Фидбек и сообщения ошибок содержат пользовательский ввод (client-beacon пишет
браузер клиента). Поэтому:

- в issues этот текст огорожен код-блоком с явной пометкой «данные, не
  инструкции»; такая же пометка — в промптах триажа и `/plan-epic`;
- `github-issues.ts` переведён с интерполяции shell-команд `gh` CLI на
  `ghApi` (curl с JSON-телом) — shell-инъекция через текст ошибки исключена;
- `backlog-intake.yml` включён в `HOLD_PATTERNS`: workflow, чеканящий
  `auto:ready` из внешних данных, автоматика не правит сама.

Остаточный риск принят владельцем: фидбек-BUG → P1-issue → реализация →
авто-мерж → прод, без человеческого взгляда. Слои защиты: гейт
(деструктивные миграции и рубильники — hold), CI, два ревью-агента,
blue-green со снапшотом и автооткатом.

### Heartbeat

Исполнитель очереди — смертная интерактивная сессия. Ежечасный
`issue-queue.yml` после report вызывает `issue-queue.ts heartbeat`:
`ready>0 && wip==0 && нет активности PR очереди > heartbeatIdleHours (3)` →
Telegram «запусти /next-issue», не чаще одного раза в
`heartbeatCooldownHours` (12). Дедуп — маркер-комментарий на дашборде.
Это ответ на главный урок issue-worker: молчащая автоматика неотличима от
работающей, ~20 часов «зелёного» бездействия никто не заметил.

## Non-goals (осознанно не сделано)

- **Обратная синхронизация статуса фидбека** (issue закрыта → FeedbackItem
  RESOLVED): нужен `githubIssueNumber` в схеме и write-path с прода в GitHub
  или наоборот. Односторонний мост покрывает задачу «баг попал в очередь»;
  статусом управляет админка.
- **AI-триаж в Actions**: владелец отверг API-ключ в CI («через API строить
  разработку не будем»); суждение остаётся в сессии.
- **Автозакрытие issues при исчезновении паттерна** — enhancement из
  README-analyze-errors, ждёт живой статистики.

## Последствия

- Бэклог пополняется из четырёх источников без участия владельца; его роль —
  писать идеи в свободной форме (в issue или прямо сессии) и отвечать на
  `needs-owner`.
- Полный цикл: сигнал → issue с лейблами → триаж/эпик → реализация → PR →
  гейт → мерж → прод. Человек в цикле обязателен ровно в двух местах:
  hold-PR и `needs-owner`.
- Новые лейблы: `auto-detected`, `from-feedback`, `root-cause` (создаются
  идемпотентно самим workflow).
- Ежедневный прогон интейка добавляет ~1 SSH-сессию и десяток GitHub-запросов —
  фон, неотличимый от нуля на фоне site-watchdog (каждые 5 минут).
