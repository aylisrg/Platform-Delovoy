# ADR: статистика и журнал звонков Novofon в админке

Статус: принято. Основание: [PRD](../requirements/2026-10-24-telephony-dashboard-prd.md).

## Контекст и проверенные факты

Интеграция уже реализована: `calls-sync.ts` получает `get.calls_report` через Novofon Data API, первый запуск загружает 90 дней, далее использует перекрывающееся окно. Deploy workflow устанавливает cron раз в 10 минут. `call-journal.ts` обрабатывает завершение звонка и запись разговора из аутентифицированного webhook. Оба источника обновляют `NovofonCall` по одному идентификатору сессии.

Существующий `CallLog` отражает операции платформы и события webhook. Его нельзя суммировать с `NovofonCall`: один звонок может присутствовать в обеих таблицах. Старый `/api/telephony/calls` читает `CallLog`; интерфейса чтения полного журнала Novofon до этой задачи нет.

Это факты кода, а не проверка живого кабинета. Наличие ключа не доказывает доступность API, запись в журнале не является heartbeat синхронизации. В модели нет сведений об успешном последнем запуске cron.

## Варианты

1. Статистика из `CallLog`: проще переиспользовать существующий API, но неполный охват и риск ошибочного подсчёта событий вместо сессий.
2. Запрос Novofon при каждом открытии: актуальность зависит от провайдера, задержки и лимиты влияют на админку, уже имеющаяся синхронизация дублируется.
3. Чтение `NovofonCall`: полный существующий источник, идемпотентные сессии, быстрые агрегаты и независимость чтения от доступности провайдера. Выбран этот вариант.

## Решение

Добавляется `/admin/telephony` и `GET /api/telephony/dashboard`. Доменные файлы `dashboard-service.ts`, `dashboard-validation.ts`, `dashboard-types.ts` остаются внутри существующего модуля `telephony`. Миграций, новых зависимостей и изменений внешних рассылок нет.

Глобальные звонки не имеют надёжной атрибуции к бизнес-модулю. Поэтому страница, карточка главного дашборда и API доступны только `SUPERADMIN`. Сервер проверяет сессию и роль до валидации запроса и чтения БД. Выдача разрешения на раздел менеджеру сама по себе не открывает глобальные данные.

Периоды `today`, `7d`, `30d` включают текущий день. Границы и группировка используют `Europe/Moscow` (фиксированный UTC+03:00), как существующий Novofon sync. Интервал запроса полуоткрытый: начало первого дня включительно, начало следующего за последним дня исключительно. Нулевые дни дополняются на сервере.

Статистика агрегируется в PostgreSQL параметризованным `Prisma.sql` / `$queryRaw`, наружу выходят только дневные суммы. Журнал выбирается отдельно с явной проекцией и пагинацией 25 записей; сортировка по `startedAt desc, id desc` стабильна при одинаковом времени. Полный журнал не загружается в память. Чтения используют существующий паттерн параллельных запросов; при входящем webhook между запросами возможна кратковременная разница счётчика и страницы, следующее обновление её устраняет.

## Семантика

- Всего — количество сессий `NovofonCall` в периоде, не количество уникальных клиентов.
- Входящие — `direction = INBOUND`.
- Принятые — входящие с `isLost = false` и положительным `talkDuration`.
- Пропущенные — входящие с `isLost = true`; исходящий без ответа сюда не входит.
- Уточняется — остальные входящие. Уведомление только о записи может создать строку с `isLost = false`, но без длительности; это не подтверждённый ответ.
- Исходящие — все `OUTBOUND`; журнал дополнительно показывает `isLost` для исходящих без ответа.
- Доля ответов — `answered / (answered + missed) × 100`, до одного десятичного знака. При нулевом знаменателе `null`, а не 0 или 100.
- Средний разговор — среднее положительных `talkDuration` по входящим и исходящим; без разговоров `null`.

Карточки и график зависят только от периода. Фильтр журнала не изменяет их, что сохраняет контекст при просмотре пропущенных.

## API-контракт

`GET /api/telephony/dashboard?period=today|7d|30d&filter=all|inbound|answered|missed|outbound&page=1`

Значения по умолчанию: `today`, `all`, `1`. Страница — целое от 1 до 100000. Неверные значения дают 422 без чтения данных; гость получает 401, остальные роли — 403.

Ответ `{ success: true, data: TelephonyDashboard }`; точный контракт — `src/modules/telephony/dashboard-types.ts`:

- `dateFrom`, `dateTo` — включительные календарные даты `YYYY-MM-DD`; `timeZone` — `Europe/Moscow`.
- `summary` — `total`, `inbound`, `answered`, `missed`, `outbound`, `pending`, `answerRate`, `avgTalkSeconds`.
- `daily` — те же счётчики без доли и среднего, плюс `date`.
- `calls` — время, направление, результат, маска контакта, имя сотрудника, длительности и `isLost`.
- `pagination` — `page`, `perPage`, `total`, `totalPages`.
- `source` — `dataApiConfigured`, `webhookConfigured`, `lastCallAt`, `lastJournalUpdate`.

`lastJournalUpdate` — последнее изменение любой сохранённой строки, не время гарантированно успешной синхронизации. Кнопка обновления перечитывает БД и не запускает синхронизацию. Ошибка БД возвращает безопасное сообщение без деталей. Успешный ответ имеет `Cache-Control: private, no-store`.

## Защита данных и сопутствующее исправление

Телефон маскируется на сервере, видны только последние четыре цифры; короткий номер скрыт целиком. API не выбирает `recordUrl`, `recordId`, `employeeId`, metadata и не возвращает исходный номер. Записи разговоров и обратный звонок в этот scope не входят.

Во время проверки существующего API обнаружена ветка неверного фильтра в `/api/telephony/calls`, которая до проверки роли возвращала общий журнал. Она заменена на 422; доступ роли USER отклоняется до разбора фильтра. Валидные запросы сохраняют существующие проверки секции и обязательный `moduleSlug` для не-владельца. Регрессионный тест фиксирует отсутствие вызова сервиса для обходящих запросов.

В обработке завершения звонка исправлено сохранение результата при неполном повторном уведомлении: отсутствие `talk_time_duration` больше не сбрасывает ранее установленный `isLost`. Явное событие `lost_call` по-прежнему устанавливает пропуск, известная длительность уточняет исход. Это предотвращает исчезновение подтверждённых пропущенных из новой статистики до следующей синхронизации; поведение покрыто регрессией.

## Проверка

Тесты покрывают границу суток МСК, все нулевые дни, неизвестный результат, исходящий без ответа, маску и проекцию, независимость итогов от фильтра журнала, пагинацию, 401/403/422, безопасную ошибку БД и обход прав старого журнала. Контрольный пример PRD: 3 принятых + 2 пропущенных + 1 уточняемый входящий + 2 исходящих = 8 всего, 6 входящих, доля ответов 60%.
