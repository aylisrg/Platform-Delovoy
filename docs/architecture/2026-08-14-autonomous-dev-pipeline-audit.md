# Аудит автономного dev-конвейера и целевая архитектура Closed-Loop Flywheel

- **Дата:** 2026-08-14
- **Статус:** отчёт-аудит (не ADR; решения по рекомендациям — за владельцем)
- **Метод:** фактический аудит репозитория — 29 workflow, `scripts/issue-queue.ts` + `scripts/lib/`, `.claude/commands/` + `agents/`, `src/modules/monitoring`, prisma-схема, ADR `2026-08-10` / `2026-08-11`, DEPLOYMENT.md. Все утверждения ниже проверены по коду, а не по документации.

---

## Резюме

Platform Delovoy — это **уже работающая автономная фабрика разработки**, а не «процесс с AI-ассистентом». Полный цикл «сигнал из прода → issue → реализация → ревью двумя агентами → авто-мерж → деплой в прод → watchdog» замкнут и работает без владельца. Это состояние, до которого большинство команд, обсуждающих «autonomous multi-agent factory», не доходит.

Поэтому целевая архитектура — **не перестройка, а закрытие шести конкретных дыр**, ранжированных по риску:

1. **Верификация — самое слабое звено.** E2E/скриншот-тестов нет вообще (Playwright заявлен в `.mcp.json`, но ни разу не запускается в CI). Smoke-тесты после деплоя **не валят деплой** — при `FAILED > 0` печатается warning и деплой отчитывается зелёным (`deploy.yml`, шаг Verify). Автономный мерж в прод опирается на unit-тесты и два LLM-ревью.
2. **Событийного алертинга нет.** `routeAlert` в `bot/handlers/alerts.ts` — мёртвый код (ни одного вызова). CRITICAL в `SystemEvent` сам по себе никому ничего не шлёт; все алерты — внешние кроны (watchdog-и). Задержка обнаружения инцидента, который не роняет `/api/health`, — до суток (до следующего `backlog-intake`).
3. **Перфоманс-телеметрии не существует.** Нет request-duration, нет учёта HTTP-статусов (5xx-спайк детектировать нечем), `access_log off` в nginx, `src/middleware.ts` отсутствует (хотя задокументирован в CLAUDE.md — drift).
4. **Продуктовой петли нет.** Первичной воронки (шаги бронирования/чекаута) нет ни в своей БД, ни в аналитике; `src/modules/analytics` — read-through к Метрике/Директу (ad-attribution, не product analytics). Падение конверсии не порождает ничего.
5. **Автономия имеет внешние SPOF без надзора:** Routine на claude.ai (единственный источник воркер-сессий), fine-grained PAT `AUTOMATION_TOKEN` с ограниченным сроком жизни (протухнет — CI ребейзнутых веток тихо паркуется в `action_required`), лейбл `needs-owner` без SLA/напоминаний.
6. **«Самообучение» реализовано наполовину.** `collect-qa-feedback.sh` копит только счётчики по категориям; секции «Частые ошибки» в `.claude/feedback/qa-patterns.md` — пустые заглушки, т.е. Developer читает статистику, а не паттерны.

Рекомендуемая стратегия: **Phase 1 (неделя)** — сделать верификацию блокирующей и алертинг событийным; **Phase 2 (2–4 недели)** — телеметрия запросов/ошибок и упрочнение контура Error-to-Fix; **Phase 3 (1–2 месяца)** — продуктовая петля Performance/Product-to-Code. Без LangGraph/CrewAI/внешних оркестраторов — текущая архитектура «интерактивные Claude Code-сессии + детерминированные Actions + состояние в лейблах» выстрадана двумя провалившимися альтернативами (ADR 2026-08-10) и является правильной базой.

## Часть 0. Аудит текущего состояния (ответы на 5 блоков по факту кода)

### Блок 1 — Входная точка и оркестрация

**Как формулируются задачи.** Шесть путей входа, по убыванию автоматизации:

| Путь | Механизм | AI |
|---|---|---|
| Ошибки прода | `backlog-intake.yml` (ежедн. 03:43 UTC) → `analyze-errors.ts`: fingerprint новых ERROR/CRITICAL-паттернов (24ч vs baseline недельной давности) → issue `auto:ready`, ≤5/прогон | нет |
| Фидбек пользователей | `feedback-to-issues.ts`: BUG → `prio:P1\|P2` + `auto:ready` (сразу в очередь), SUGGESTION → на триаж | нет |
| Повторные инциденты | `escalate-incidents.ts`: ≥3 закрытий `site-down`/`notifications-down`/`ci-failure` за 7 дней → root-cause issue P1 | нет |
| Владелец, свободный текст | любая сессия → `issue-queue.ts create`; шаблоны issue запрещают ставить `prio:*`/`auto:*` руками | сессия |
| Триаж входящих | шаг 0 `/next-issue`: непомеченные issue → `prio:*` + `auto:ready`/`auto:epic` | сессия |
| Эпики | `/plan-epic`: PRD (PO-агент) + декомпозиция на 2–8 дочерних задач | сессия |

**Оркестрация.** Исполнитель — обычная интерактивная Claude Code-сессия по `.claude/commands/next-issue.md`; запускает её Routine claude.ai каждые 2 часа. Состояние очереди — **только лейблы GitHub** (без БД/файла — осознанно, ADR 2026-08-10); вся механика (pick, lock, gate, reconcile, sweeper) — детерминированный TypeScript без AI (53 unit-теста на чистые функции). Два отвергнутых на живой системе варианта задокументированы: внешний планировщик-как-исполнитель (сутки простоя: нет mounted-репо, интерактивные подтверждения) и GitHub Actions с `claude-code-action` (вето владельца на `ANTHROPIC_API_KEY`: «через API строить разработку не будем»).

**Изоляция контекстов и память.** Четыре механизма изоляции: субагенты в отдельных контекстах; tool-allowlist по ролям (PO/Architect — без Bash/Edit; Reviewer/QA — Bash, но без Edit; Edit только у Developer); file-based handoff (каждая роль читает артефакты, не транскрипты); общий контекст-лог `docs/context/{RUN_ID}-context.md`. Память проекта: CLAUDE.md (source of truth), AGENTS.md (зеркало для сторонних инструментов), `.claude/feedback/qa-patterns.md` (единственный автоматически пишущийся файл памяти), артефакты в `docs/`. MEMORY.md/векторной памяти нет. Синк CLAUDE.md — только правилом «drift = bug», автоматической проверки нет.

### Блок 2 — Генерация и кодовая база

Стек: Next.js 15 (App Router) + Prisma + PostgreSQL 16 + Redis 7 + NextAuth v5, деплой Docker Compose на Timeweb VPS (**2 CPU / 4 GB RAM / 48 GB NVMe** — это жёсткое ограничение для любых рекомендаций по observability). Доступ агентов к коду: полный mounted-репозиторий сессии + Grep/Glob (RAG/AST-индексации нет — для ~30 модулей это адекватно и не является узким местом). MCP: `postgres` (read-only пользователь), `filesystem` (scoped), `playwright` (**заявлен для QA, фактически не используется нигде**), `github-actions` (PAT, dispatch workflow'ов — прод-диагностика без владельца).

### Блок 3 — QA, верификация, безопасность

- **CI (на каждый PR):** ESLint, lockfile-чек, Vitest (~1500 тестов), `tsc --noEmit`, Docker build. `npm audit` и Trivy — **advisory** (не блокируют, `continue-on-error` / `exit-code: 0`).
- **LLM-ревью:** `code-reviewer` (чеклист: AC, scope creep, RBAC, секреты, «сомневаешься → NEEDS_CHANGES», обязательная секция Security) → `qa-engineer` (каждый AC по отдельности, RBAC под каждой ролью включая анонима, rate limiting, инъекции; один security-FAIL = общий FAIL). Максимум 3 итерации, потом `needs-owner`.
- **Кто жмёт merge:** для `auto`-tier — **никто**. Sweeper `issue-queue-merge.yml` (каждые 15 мин) мержит PR с зелёным CI, гейтом `auto`, тишиной 20 мин. `hold` (ручной мерж): рубильники самой автоматики, деструктивные миграции, 5+ модулей. Мерж в main = автодеплой в прод (blue-green, снапшот, pg_dump, авто-rollback по health).
- **Дыры:** (а) PASS ревью-агентов — процедурное требование `/next-issue`, **механически гейт его не проверяет** (`classifyMergeGate` смотрит только пути файлов и SQL миграций); (б) если GitHub не отдал `patch` файла миграции (слишком большой diff) — миграция считается безопасной (задокументированное слабое место); (в) smoke после деплоя не блокирует (см. резюме); (г) E2E нет; (д) staging manual-only (осознанно), очередь его не использует.

### Блок 4 — Телеметрия

**Есть и сделано хорошо:** `/api/health` (DB, Redis, V8-heap, event-loop lag, с грамотной семантикой 503 и троттлингом CRITICAL через Redis); client-error beacon (глобальный, с `connection` wifi/4g — единственная RU-mobile точка обзора); трёхслойные watchdog-и (GitHub `*/5 мин` + поминутный cron на VPS + autoheal-контейнер) с эскалацией T0–T3 в `watchdog-remediate.sh`; аудит-трейл (AuditLog, DeletionLog, BackupLog и т.д.); Яндекс.Метрика — клиент + серверная дедупликация конверсий (Offline Conversions API, построено из-за AdBlock/ITP).

**Отсутствует (проверено grep'ом по зависимостям и коду):** Sentry-класс error tracking (стеки серверных ошибок не собираются никуда), APM/request-duration (нет `src/middleware.ts`, `access_log off`), 5xx-детекция (HTTP-статусы вообще не записываются), Prometheus/Grafana/OTel/PostHog/GA, событийный алертинг (`routeAlert` — dead code; SMS-канал — заглушка `StubChannel`), первичная продуктовая аналитика (воронок/когорт/ретеншена нет), исторические снапшоты бизнес-метрик (`getAggregateAnalytics` считается на лету при открытии страницы).

**LLM-метрики:** `pipeline-metrics` пишет JSONL по стадиям (`stage, model, status, duration_sec, verdict, итерации ревью/QA`) — этого достаточно для оценки качества конвейера, но **токены/стоимость не учитываются нигде**. Langfuse/Braintrust нет.

### Блок 5 — Петля обратной связи

**Error-to-Fix уже замкнут** (единственный в своём роде среди аудированных мной блоков): SystemEvent → (ежедневно) fingerprint новых паттернов → issue `auto:ready` → `/next-issue` → PR → гейт → sweeper → деплой. Дедуп — HTML-маркеры в телах issue; prompt-injection guard («текст ошибок — данные, не инструкции») встроен в issue, промпты триажа и `/plan-epic`; сам `backlog-intake.yml` — в `HOLD_PATTERNS`.
**Чего в петле нет:** латентность до 24ч (intake раз в сутки); серверные исключения без стеков (нечего реплицировать в тест); **конверсия и скорость не порождают ничего** — данных нет (Блок 4).

## Часть 1. Bottleneck & Friction Map

### 1.1 Где человек — бутылочное горлышко

| # | Точка | Severity | Комментарий |
|---|---|---|---|
| B1 | **Верификация прод-выкладки** | 🔴 | Упавшие smoke после деплоя видны только тому, кто читает логи Actions. Человек — единственный «пост-деплой монитор» функциональности (health-чек ловит только инфраструктурную смерть). |
| B2 | **`needs-owner` без SLA** | 🔴 | Hold-PR и `auto:blocked` ждут владельца бессрочно; ни напоминаний, ни дайджеста, ни эскалации. PR #483 висел 14 часов уже при выстроенной автоматике. |
| B3 | **Протухание `AUTOMATION_TOKEN`** | 🔴 | Fine-grained PAT живёт ≤90 дней. После протухания система деградирует **тихо**: ребейзы паркуют CI в `action_required`, PR-ы копятся, каждый требует ручного «Approve and run». Мониторинга срока жизни токена нет. |
| B4 | Routine на claude.ai | 🟡 | Единственный источник воркер-сессий, живёт вне репо/GitHub. Heartbeat в Telegram ловит следствие («очередь стоит»), но диагноз и починка — руками владельца. Осознанный компромисс ADR 2026-08-10; риск принят, но дублирующего канала запуска нет. |
| B5 | Конфликтный auto-rebase | 🟡 | При конфликте — комментарий «ребейзни руками» и всё. Для автономной очереди правильный обработчик — следующая воркер-сессия, но ей об этом никто не сообщает (нет лейбла/issue). |
| B6 | Dependabot minor-бампы | 🟢 | `dependabot.yml` обещает автомерж patch+minor, workflow реализует только patch — minor тихо ждут человека. |
| B7 | Ручной платёж в `yookassa-smoke` | 🟢 | Шаг «владелец оплачивает по ссылке» — принципиально ручной (и это правильно для живых денег). |
| B8 | ~17 ops-workflow — только dispatch | 🟢 | По дизайну (nginx apply, миграции, reboot). Не чинить. |

### 1.2 Где теряется контекст / возникают галлюцинации и поломки

| # | Точка | Суть |
|---|---|---|
| F1 | **CLAUDE.md drift** | CLAUDE.md описывает `src/middleware.ts` («Auth guard + request logging») — **файла не существует** (проверено). `DEVELOPMENT-RULES.md` до сих пор утверждает «Автомерж отключён», противореча действующей политике. Агент, доверившийся документации, строит выводы на несуществующей архитектуре — это готовый генератор галлюцинаций. |
| F2 | **`routeAlert` — мёртвый код** | Документированный контракт «CRITICAL → Telegram + SMS» (CLAUDE.md, таблица Monitoring) не реализован: функция ни разу не вызывается, SMS — заглушка. Документация обещает канал алертинга, которого нет. |
| F3 | **`qa-patterns.md` — полупустая память** | Скрипт копит счётчики (~29 строк статистики), но секции с самими паттернами — пустые HTML-комментарии. Developer «учится» на цифрах без содержания. |
| F4 | **`SystemEvent.source` — свободная строка** | Дрейф имён (`scheduler` vs `rental.scheduler`, `cron/inventory` vs `cron.notifications`, точки vs слэши) размывает и спайк-детекцию (она группирует по source), и читаемость. Реестра источников нет; ~20 колл-сайтов пишут в обход `logger.ts` (теряя console-fallback). |
| F5 | **Гейт не видит вердиктов ревью** | «PASS от code-reviewer и qa-engineer» — конвенция промпта, не машинная проверка. Сессия, пропустившая шаг 5, произведёт PR, неотличимый для sweeper'а от проверенного. |
| F6 | Слепое пятно миграций | Отсутствующий `patch` у файла миграции → «безопасно». Осознанно, но в сумме с F5 — два независимых отверстия в одном руле. |
| F7 | Наблюдаемость самих агентов | JSONL-метрики пишутся только у `pipeline.sh` (5-стадийный контур); у основного рабочего контура `/next-issue` — никакой телеметрии прогонов (сколько сессий умерло на каком шаге, сколько итераций CI-fix — неизвестно; диагноз только по косвенным следам в PR). |

## Часть 2. Целевая архитектура: четыре движка

Все четыре движка **уже существуют**. Ниже — состояние и дельта до целевого уровня.

### 2.1 Spec Engine (есть — укрепить)

**Сейчас:** PO-агент (самый детальный промпт в репо: персоны, MoSCoW, анти-паттерны, чеклист передачи) → PRD; Architect (обязательные ≥2 варианта, RBAC на каждый endpoint) → ADR; `/plan-epic` конвертирует эпики в PRD + 2–8 child-issues; `eval/` — структурные регрессионные проверки артефактов, включённые в CI (`agents-eval.yml`).

**Дельта:**
- **AC-трассируемость до теста.** Сейчас связь «AC → тест» держится на дисциплине QA-агента. Целевое: конвенция `// AC-3` в названиях тестов + структурная проверка в `eval/checks` «каждый AC из PRD упомянут хотя бы одним тестом» для PR, ссылающихся на PRD. Дёшево, детерминированно, в духе существующего eval-фреймворка.
- **Спецификация от сигнала.** Для issue из `analyze-errors` (есть fingerprint, но нет стека) PRD не нужен, но нужен воспроизводящий тест до фикса — правило уже есть в `/next-issue` («тест, падавший до фикса»); станет по-настоящему исполнимым после появления серверных стеков (Часть 3.1).

### 2.2 Coder Swarm (есть — не расширять)

**Сейчас:** роли с жёстким разделением инструментов; один worker в один момент (`auto:wip`-lock), backpressure `maxOpenPrs: 2`; `parallel-pipeline.sh` для параллельных фич; auto-rebase линеаризует мержи.

**Рекомендация — осознанно НЕ строить «рой».** Для одного продукта, одного владельца и VPS 2 CPU параллелизм агентов упирается не в генерацию кода, а в пропускную способность верификации и ревью человека для hold-PR. Текущее «одна задача в полёте, очередь как буфер» — правильная топология. Единственная оправданная параллель — отделение **инцидент-сессий** (реакция на алерт) от **очередных** (backlog): инцидентная ветка `claude/**` уже проходит тот же гейт (политика 2026-08-13).

### 2.3 QA & Sandbox Engine (главная стройка)

**Сейчас:** Vitest (мок DB/Redis) + tsc + lint + docker build. Изолированного запуска приложения нигде нет: ни E2E, ни скриншотов, ни smoke против живого инстанса до прода.

**Целевое (по нарастающей):**
1. **CI E2E job:** поднять в CI стек `app + postgres + redis` (compose уже есть; `docker-compose.yml` для локалки), прогнать seed, затем Playwright-suite из 5–7 критических флоу: главная, бронирование беседки (до создания записи в БД), PS-Park слот, cafe checkout до формирования заказа, `/admin` логин + RBAC-отказ для USER, `/api/health`. Job — **required check** наравне с `test`. Это единственное недостающее звено, которое видит то, чего не видят unit-тесты: роутинг, RSC-границы, реальные Prisma-запросы, битые клиентские бандлы.
2. **Скриншот-регрессии** тех же 5–7 страниц (Playwright `toHaveScreenshot`, маскировать динамику). Ловит CSS/layout-поломки, к которым LLM-ревью слепо.
3. **Фаззинг — не заводить отдельным движком.** Точечно достаточно: property-based тесты (fast-check) для Zod-схем и парсеров денег/дат в `booking`/`payments` — там, где инварианты дорогие. Полноценный фаззинг на этом стеке не окупается.
4. **«Авто-исправление до победного» уже есть** (`pr-wait` → red → чинить → пуш, «круг за кругом»); лимит — 3 раунда саморевью + park. Менять не нужно; после появления E2E тот же контур будет чинить и E2E-падения.

### 2.4 Release Engine (есть — довести до блокирующего)

**Сейчас:** гейт → sweeper → CI на main → `deploy.yml`: снапшот VPS, pg_dump, миграции **до** подмены контейнера (провал = прод не тронут), blue-green с health-гейтом и даунтайм-метром (>10 с не-200 = провал), rollback на legacy-пути, Gemini-релизноуты с grounding-проверкой.

**Дельта:**
1. **Smoke-тесты — блокирующими** (`deploy.yml` Verify): `FAILED > 0` → `exit 1` + откат (в blue-green — flip upstream обратно, слот ещё жив 30 с дренажа; продлить дренаж до завершения smoke). Это правка на десятки строк, закрывающая B1.
2. **Post-deploy error-budget watch вместо canary.** Canary на одном VPS с одним инстансом БД — карго-культ; правильный эквивалент: 15 минут после flip сравнивать `SystemEvent` ERROR/CRITICAL + client-beacon rate с тем же окном до деплоя (запрос уже тривиален — паттерн `beacon-divergence` готов); превышение ×3 → автоматический `force_legacy_deploy`-откат либо P0-issue + Telegram. Реализация — job в `deploy.yml` или отдельный workflow по `workflow_run`.
3. **Rollback-паритет:** на blue-green-пути после дренажа старого слота отката нет — держать предыдущий образ в слоте B «тёплым» до конца error-budget окна.

## Часть 3. Контуры самооптимизации (Closed-Loop Telemetry → Code)

### 3.1 Error-to-Fix Loop v2 (усилить существующий)

Текущий контур: `SystemEvent → (24ч) analyze-errors → issue → сессия → PR → sweeper → прод`. Три усиления:

1. **Серверные стеки.** Next.js 15 даёт хук `onRequestError` в `instrumentation.ts` (файл уже существует с process-guard'ами). Писать в `SystemEvent` `source: server-error` с `digest`, роутом, стеком (обрезанным), статусом. Это превращает issue из «есть паттерн строки» в «есть стек → можно реплицировать в тесте» — предусловие честного шага «Репликация в тестах» из целевого контура. Sentry не нужен: та же fingerprint-машина `pattern-extractor.ts` заработает по цифровому `digest`.
2. **Латентность CRITICAL: сутки → минуты.** Не трогая дневной intake, добавить событийный путь: `log.critical()` → прямой `sendAlert()` (в `src/lib/notifications.ts` уже есть самодостаточная реализация) — это оживление контракта, который CLAUDE.md уже обещает (F2). Мёртвый `routeAlert` — удалить либо сделать этой самой точкой. SMS-канал: либо реализовать (SMSC/SMS.RU — RU-доступные), либо честно вычеркнуть из таблицы Monitoring.
3. **Гейт-гигиена контура:** `analyze-errors` создаёт ≤5 issue/день — при всплеске разнотипных ошибок хвост ждёт завтра; после появления `server-error`-источника поднять до ≤10 с дедупом по digest.

### 3.2 Performance Loop (построить)

Принцип: **сначала данные, потом агенты**. Сейчас петля невозможна физически — нечего анализировать.

1. **Источник данных — nginx, не приложение.** Включить `access_log` с JSON `log_format` (`$request_time`, `$upstream_response_time`, `$status`, путь, `$http_x_real_ip` не писать — PII), logrotate 7 дней (48 GB NVMe позволяют). Нулевая нагрузка на Node, статусы 5xx — бесплатно. Вариант «middleware в Next» отвергнут: edge-runtime ограничения и лишние миллисекунды на 2 CPU.
2. **Дневной разбор — в существующий `backlog-intake.yml`:** тем же SSH-паттерном забрать агрегат за сутки (awk/jq на VPS: p50/p95/число 5xx по топ-20 роутов), сравнить с 7-дневным baseline тем же `detectWarningSpikes`-механизмом → issue `perf-regression, prio:P2, auto:ready` при p95 ×2 или 5xx-спайке. **5xx-спайк ×3 — также немедленный Telegram** через локальный watchdog (он уже поминутный — добавить grep свежего лога).
3. **Замыкание на код:** issue формата «роут X: p95 вырос с A до B после деплоя SHA» содержит достаточно контекста для `/next-issue`; сессия проверяет diff деплоя из issue — типовые исходы: N+1 в Prisma, отсутствующий индекс, тяжёлый RSC.

### 3.3 Product Loop (построить — единственный принципиально новый контур)

1. **Первичные события воронки.** Таблица `ProductEvent (id, funnel, step, sessionKey, moduleSlug, metadata, createdAt)` + server-side запись в существующих точках: бронирование беседок/PS-Park (просмотр → выбор слота → сабмит → оплата), cafe checkout (меню → корзина → заказ → оплата), rental (страница → заявка). Точки записи уже размечены — это те же 4 роута, где стоит серверная Метрика-конверсия (`metrika-server.ts`). PII не писать; `sessionKey` — анонимный хэш.
2. **Еженедельная аналитическая сессия.** Routine (раз в неделю) запускает сессию с задачей: `product-analyst`-агент (уже существует, read-only SQL через postgres-MCP) строит отчёт в `docs/analytics/`: конверсия по шагам воронок, дельта к прошлой неделе, drop-off точки, корреляция с деплоями недели; формулирует ≤3 гипотезы; **каждая гипотеза — issue** через `issue-queue.ts create` (`enhancement` на триаж — не `auto:ready`: продуктовые изменения без владельца в прод не едут — это осознанная граница автономии).
3. **Метрика как ранний детектор.** В `backlog-intake.yml` — ежедневный чек через существующий `metrika-client.ts`: конверсия целевого goal упала ×2 к 7-дневному baseline → Telegram + issue. A/B-тестирование в Phase 3 **не строить** — на текущем трафике мощности эксперимента не будет; гипотезы проверять до/после с baseline (правило `product-analyst` «baseline mandatory» уже есть).

### 3.4 Телеметрия самого конвейера

1. **Метрики `/next-issue`-прогонов:** сессия в конце (шаг 8) дописывает JSONL-строку в стиле `pipeline-metrics` (issue, исход: merged/parked/blocked, раунды CI-fix, раунды ревью, длительность). Смотреть в уже существующем `/admin/monitoring/pipelines`.
2. **Токены/стоимость:** учитывать по-простому — счётчик сессий/день из Routine + JSONL выше; полноценный LLM-tracing (Langfuse и т.п.) **не разворачивать**: на подписочной модели (без API-ключей — политика владельца) трассировать нечего, а self-hosted Langfuse v3 (ClickHouse) не помещается в 4 GB рядом с продом.
3. **Watchdog автономии** (закрывает B3, B2, частично B4) — в почасовой `issue-queue.yml` добавить: (а) проверка живости `AUTOMATION_TOKEN` (`GET /user`; ошибка или ≤14 дней до истечения → Telegram); (б) дайджест `needs-owner`: PR-ы старше 48ч — раз в сутки списком в Telegram; (в) счётчик пустых запусков Routine (сессия стартовала, но ни одного PR/лейбла за N часов при непустой очереди — уже частично покрыто heartbeat'ом; добавить явный признак «сессии стартуют, но умирают до первого действия»).

## Часть 4. Рекомендуемый стек

Ограничения, которые дисквалифицируют «дефолтные» рекомендации: (1) вето владельца на API-ключи в CI; (2) Anthropic OAuth не работает с RU IP → self-hosted воркеры невозможны; (3) VPS 2 CPU / 4 GB, уже занятый app+bot+postgres+redis+nginx+autoheal; (4) санкционные риски SaaS (Sentry.io ограничивает RU-аккаунты); (5) один владелец — каждая новая система должна обслуживать себя сама.

| Слой | Оставить как есть | Добавить | Осознанно НЕ брать |
|---|---|---|---|
| Оркестрация | Claude Code сессии + Routine + лейблы-как-состояние + детерминированные Actions | телеметрию прогонов (3.4) | LangGraph/CrewAI/AutoGen — дублируют готовое, требуют API-ключей и хостинга; внешний воркер — OAuth/RU |
| Sandbox/E2E | GitHub-runner + docker compose | Playwright (@playwright/test) job в CI, screenshot-тесты | Modal/E2B — API-ключи, оплата, та же изоляция уже есть в runner-контейнерах |
| Error tracking | SystemEvent + client-beacon | `onRequestError` → SystemEvent (стеки, digest) | Sentry SaaS (санкционный риск), self-hosted Sentry (не влезет), GlitchTip — только при появлении второго VPS |
| APM/метрики | health-эндпоинты | nginx JSON access_log + дневной агрегат в intake | Prometheus+Grafana/OTel-стек — операционный оверхед выше ценности для соло-проекта |
| Продукт-аналитика | Яндекс.Метрика (клиент+сервер) | `ProductEvent` first-party + недельный product-analyst | PostHog (self-hosted требует ClickHouse; cloud — санкционный риск), GA4 (RU-доступность) |
| Алертинг | Telegram (watchdog-и) | событийный `log.critical → sendAlert`; SMS через SMSC/SMS.RU или вычеркнуть | — |
| Внешний обзор | site-watchdog (GitHub) + local-watchdog | **второй дешёвый RU-VPS** (~500–800 ₽/мес): внешняя проба (закрывает #452/#456 — независимый от GitHub-троттлинга канал) и, опционально, GlitchTip | Hetzner (изъят), UptimeRobot и пр. SaaS (внешние зависимости при RU-блокировках) |

## Открытые вопросы владельцу

Единственное, что аудит кода дать не может:

1. **Второй VPS (~500–800 ₽/мес)** — да/нет? Разблокирует #452/#455/#456 (внешняя проба, Telegram-транспорт) и даёт дом для GlitchTip. Без него внешний обзор остаётся на троттлящемся GitHub-cron.
2. **Бюджет сессий.** Routine каждые 2 часа ≈ до 12 сессий/день + недельный аналитик (Phase 3.2). Есть ли лимиты подписки, в которые надо вписаться? Это определяет, можно ли поднять частоту intake для CRITICAL.
3. **SMS для CRITICAL** — нужен ли канал вообще (SMSC/SMS.RU, ~платно), или Telegram + поминутный watchdog достаточны и строку про SMS честно убрать из CLAUDE.md?
4. **Приоритет воронки** для Phase 3.1: бронирования (беседки/PS-Park), cafe-checkout или rental-заявки — что инструментировать первым?
5. **`maxOpenPrs: 2`** — оставить (рекомендую) или поднять? Поднятие ускорит разбор бэклога, но увеличит частоту auto-rebase-конфликтов (B5) и нагрузку hold-ревью на владельца.
