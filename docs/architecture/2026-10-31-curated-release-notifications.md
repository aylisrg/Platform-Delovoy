# Явные анонсы обновлений и подтверждение очереди

Дополнение к ADR `2026-08-13-miniapp-role-rebuild-adr.md`, §6. Основание: пользователь запросил заметный центр уведомлений и сообщил, что не получил анонс нового раздела. При последнем деплое API вернул `already-announced`: номер пакета оставался 2.27.2. Инфраструктурные алерты, анонсы продукта и подтверждение личной доставки — разные контуры.

## Идентичность анонса

- Автоматически сгенерированные заметки сохраняют прежнюю политику: один анонс на номер версии. Исторические строки `ReleaseAnnouncement` не изменяются и не переотправляются.
- Непустой вручную написанный `docs/releases/current.md` явно обозначает содержательное обновление. Workflow удаляет строки заголовков, цитат-инструкций, пустые строки и пустые пункты; нормализует Unicode NFC, окончания строк и пробелы по краям каждой строки. Из итогового текста вычисляется `manual:<sha256>`.
- API принимает необязательный `updateId` строго в этом формате и проверяет совпадение хеша с непустым нормализованным `releaseNotes`. Версия ограничена SemVer-форматом; она не может занять пространство `manual:`.
- Ключ сохраняется в существующем PK `ReleaseAnnouncement.version`. Для старых/автоматических записей это номер версии, для явных анонсов — `manual:<hash>`. Отображаемая версия передаётся отдельно в payload. Миграции схемы не нужны; других читателей этого реестра в приложении нет.
- Одинаковые ручные заметки имеют один ключ при любом SHA/номере версии. Новая техническая выкладка сама по себе не разрешает новый анонс. Нет обхода по старым релизам, очистки claims, исторической рассылки или автоматической подписки новых получателей.

## Аудитория и очередь

Аудитория определяется прежним `resolveStaffRouting(system.release)` с текущими ролями, явными подписками и исключением объединённых пользователей. Изменения обычных уведомлений, ролей, финансового доступа и подписки на еженедельную аналитику в этом контуре отсутствуют. Dispatcher продолжает учитывать доступный подтверждённый канал, DND, тихие часы и персональное отключение события.

Новый claim создаётся атомарным INSERT до обращения к dispatcher. Ошибка claim теперь закрывает отправку; прежний fail-open мог создавать дубли. Состояние записывается в существующем строковом поле `source` с префиксом `manual:` или `deploy:`:

| Состояние | Поведение следующего вызова |
| --- | --- |
| `processing` | Повторная постановка запрещена; после 15 минут показывается неопределённый исход. Этот срок не является арендой и не разрешает захват. |
| `complete` | Повтор заблокирован. Claim означает обработку анонса, а не доставку. |
| `retryable` | Допускается атомарный CAS по ключу, состоянию и времени предыдущего claim. Только победитель продолжает. |
| `uncertain` | Повтор запрещён до диагностики оператором; автоматического удаления или сброса нет. |
| Историческое `deploy`/другое прежнее значение | Сохраняется прежняя блокировка дубля; строка не переписывается. |

Перед каждой обработкой загружаются все `OutgoingNotification` с этим ключом `Release/system.release`. Пользователь с любой такой строкой исключается из нового вызова dispatcher независимо от возраста и статуса строки, включая FAILED/SKIPPED и цепочки fallback. Дальнейшая доставка и повторы уже созданных записей принадлежат существующему dispatcher. Это долговечная защита сверх его пятиминутного dedup.

`retryable` разрешён только при известном отсутствии новой очереди: аудитория пуста, dispatcher явно вернул `skipped`, либо чтение до вызова dispatcher не удалось. При частичном успехе следующий проход исключит уже поставленных получателей и снова проверит текущую аудиторию. Новые получатели не добавляются к успешно завершённым анонсам. Любое исключение dispatcher может скрывать записанную очередь, поэтому весь claim становится `uncertain`. Сбой записи результата оставляет блокирующий claim. Нужна диагностика, а не предположение, что сообщения не было.

## Результат и наблюдаемость

API возвращает `status: queued | skipped | error`, точную `reason`, количество новых `queued`, подмножество `deferred`, `skipped`, `failed`, `previouslyQueued` и признак `retryable`. `announced` сохранён для совместимости и равен `queued > 0`. Он не означает доставку. `recipientCount` учитывает известные поставленные в очередь записи по уникальным получателям; источником истины при восстановлении остаются сами outgoing-записи.

Workflow печатает обезличенный результат. Очередь, дубли, пустая аудитория, явные пропуски и неопределённые исходы не превращаются в групповые анонсы. Частично поставленный анонс не дублируется через группу. Прежний инфраструктурный fallback остаётся для ошибок до подтверждённой очереди/ответа сервера; его сообщение подтверждает деплой, а не личный анонс. Ответы старого API поддерживаются при целевом откате.

Подтверждение личной Telegram-доставки проверяется отдельно: `OutgoingNotification.status = SENT`, `sentAt`, Telegram `externalId` и проверенная связь получателя. Health-check бота, успешный deploy, claim, `queued` и `already-announced` таким подтверждением не являются.

## Проверки

Unit/API: нормализация и соответствие хеша, независимость от версии/SHA, сохранение старых claims, закрытие при ошибке INSERT, zero audience/all skipped/all failed, частичный успех, неопределённая запись, CAS-конкуренция, долговечное исключение предыдущего получателя и валидация входа. Workflow: синтаксис shell, нормализация реального блока и выбор fallback по результатам. Реальных отправок при локальных проверках нет.
