## 1. Контекст

Эпик #442 — семь UX-пробелов админ-календаря беседок и Плей Парка. К моменту этого
ADR четыре из шести актуальных story уже доставлены отдельными PR:

| Story | Issue | Что появилось в коде |
|---|---|---|
| US-1 комментарий/email в quick-форме | #665 | `adminCreateBookingSchema.email`, поля в обеих формах обоих модулей |
| US-2 автокомплит гостя по телефону | #666 | `src/modules/booking/guest-search.ts` — `searchGuestsByPhone(moduleSlug, phone)`, роуты `/api/{module}/guests/search` |
| US-3 создание ресурса из панели | #667 | `POST /api/gazebos` (и аналог ps-park) |
| US-4 печатный лист дня | #668 | `src/modules/booking/print-schedule.ts` — `getPrintableDaySchedule(moduleSlug, …)`, роуты `/api/{module}/print-schedule`, общий UI `src/components/admin/shared/print-day-sheet.tsx` |

Остались US-5 (недельный вид) и US-6 (drag-and-drop) — обе PO пометил как требующие
предварительного архитектурного решения. Этот ADR закрывает вопросы 2–4 из PRD.

### 1.1 Факты о коде, на которых стоят решения

Проверено чтением исходников (не по документации):

1. **Бэкенд дневного таймлайна привязан к одной дате жёстко.**
   `getTimeline(date: string)` (`src/modules/gazebos/service.ts:1856`,
   `src/modules/ps-park/service.ts:1466`) делает `booking.findMany({ where: { …, date: bookingDate } })` —
   равенство, не диапазон. `timelineQuerySchema` в обоих модулях — ровно
   `{ date: z.string().regex(dateRegex) }`. Одна и та же функция обслуживает
   четыре production-поверхности: два десктопных грида, два мобильных таймлайна,
   плюс server-компоненты страниц `/admin/gazebos` и `/admin/ps-park`.

2. **Геометрия сетки принципиально дневная.** `getBookingStyle()` в обоих
   `timeline-grid.tsx` считает `left = ((startHour - openHour) / (closeHour - openHour)) * 100`,
   `width` — аналогично. То есть 100 % ширины дорожки = один рабочий день
   (`hours` приходят с бэкенда из `Module.config`, сейчас 08:00–23:00 = 15 часов).
   Каждая строка ресурса — собственный контейнер `overflow-x-auto` с
   `min-w-[900px]` внутри.

3. **`TimelineBooking` у двух модулей побайтово идентичен**, включая комментарии.
   `TimelineData` — той же формы, но `resources` ссылается на разные типы:
   `GazeboResource.pricePerHour` — сырой Prisma `Decimal | null`
   (`Pick<Resource, …>`), а `TimelineResource.pricePerHour` у ps-park уже
   нормализован до `number | null` — специально, чтобы Decimal не пересекал
   границу Server → Client Component (issue #614).

4. **Два `timeline-grid.tsx` совпадают примерно на 95 %.** Реально расходятся:
   импорт типов модуля, `getResourcePricing`/`pricing` (только беседки),
   `initialBookingId` deep-link (только беседки), подписи («Беседка»/«Стол»,
   «чел.»/«игр.»), компонент quick-формы и компонент карточки брони.
   Вся модуль-специфика сосредоточена в **пути создания брони**, не в отображении.

5. **Переносу брони не нужен ни один новый эндпоинт.**
   `PATCH /api/gazebos/bookings/:id` **без поля `status`** уходит в ветку правки:
   `rescheduleBookingSchema` → `rescheduleBooking(id, input, session.user.id)`.
   Внутри уже есть всё, чего требует US-6 AC-3/AC-4: `lockSlot()` (advisory-lock,
   #429) первым стейтментом транзакции, конфликт-чек по `ACTIVE_BOOKING_STATUSES`
   в той же транзакции, EXCLUDE-бэкстоп `booking_no_overlap`, `AuditLog
   booking.reschedule`, история правок в `metadata.edits`, синхронизация Google
   Calendar (включая перенос события между календарями при смене беседки) и
   `enqueueNotification({ type: "booking.rescheduled" })`. Календарь и уведомления
   срабатывают при `timeOrResourceChanged` — а drag меняет время и/или ресурс
   всегда. Форма редактирования (`booking-edit-form.tsx`) шлёт ровно такой же
   PATCH — то есть «тот же service-層 путь» из ограничения PRD достигается
   буквально тем же HTTP-вызовом.

6. **`@dnd-kit` уже в зависимостях** (`@dnd-kit/core ^6.3.1`, `sortable ^10`,
   `utilities ^3.2.2`), прецедент использования — `src/app/admin/tasks/kanban-board.tsx`
   и `src/components/admin/rental/deal-kanban.tsx`: `PointerSensor` с
   `activationConstraint: { distance: 5 }`, оптимистичное обновление состояния и
   откат на ошибке fetch.

7. **`Booking` уже проиндексирован под диапазонный запрос:**
   `@@index([moduleSlug, date])` (`prisma/schema.prisma:239`).

8. **Прецедент общего слоя из этого же эпика (три недели назад):**
   бизнес-логика, общая для двух модулей, кладётся в `src/modules/booking/*.ts`
   и параметризуется `moduleSlug`; Zod-схема — в `src/modules/booking/validation.ts`;
   тонкие роуты остаются у каждого модуля со своим RBAC-гейтом; общий UI —
   в `src/components/admin/shared/` с пропсами `moduleSlug` + подписи
   (`PrintDaySheet`). Ровно так сделаны #666 и #668.

## 2. Вопрос 1 (PRD №2, часть А): откуда недельный вид берёт данные

### Вариант A — N параллельных вызовов существующего `/api/{module}/timeline?date=`

Клиент делает 7 запросов `Promise.all`, склеивает результат.

- **Плюсы:** ноль изменений на бэкенде; переключение недель работает сразу.
- **Минусы:** 7 HTTP-round-trip'ов на каждое переключение недели. Каждый запрос
  независимо делает `auth()`, `requireAdminSection()` (запрос в БД),
  `resource.findMany`, `booking.findMany`, `getOpenCloseHours()` и
  `getMinBookingHours()` (ещё два чтения `Module.config`) — ≈28 запросов в БД
  вместо ≈4. Список ресурсов и `hours` едут по сети семь раз подряд.
  Частичный отказ даёт «рваную неделю»: три дня загрузились, четыре — нет, и
  оператор видит пустые ячейки как «свободно», хотя там могут быть брони —
  это худший из возможных отказов для инструмента, который заменяет журнал.
  Плюс лимит `authenticated` (240/мин на пользователя) расходуется в 7 раз
  быстрее: ~34 переключения недели в минуту упрутся в 429.

### Вариант B — новый sibling-эндпоинт `GET /api/{module}/week-timeline?weekStart=…`

Один запрос, один диапазонный `booking.findMany({ date: { gte, lt } })` по уже
существующему индексу `[moduleSlug, date]`, общая реализация
`getWeekTimeline(moduleSlug, weekStart)` в `src/modules/booking/week-timeline.ts`.

- **Плюсы:** один round-trip, ~4 запроса в БД на неделю, неделя приходит
  атомарно (нет «рваного» состояния). Дневной `getTimeline` не трогается вообще —
  нулевой риск регрессии на четырёх production-поверхностях. Реализация общая
  для двух модулей сразу (AC-5 «поведение идентично» выполняется по построению).
  Ровно тот же приём, что уже применён в #668: там `getTimeline()` намеренно
  не переиспользовали и не расширяли, а сделали соседнюю функцию под другую
  форму данных.
- **Минусы:** новый эндпоинт + тесты (по факту — ~80 строк сервиса и два
  восьмистрочных роут-хендлера по образцу `print-schedule`).

### Вариант C — расширить `timelineQuerySchema`/`getTimeline` до диапазона

Добавить необязательный `dateTo`, вернуть либо день, либо неделю.

- **Плюсы:** нет нового эндпоинта.
- **Минусы:** мутируем горячий путь, от которого зависят два десктопных грида,
  два мобильных таймлайна и два server-компонента страниц. Тип возврата
  становится условным (`date` vs `days`) — это union в каждом потребителе, то есть
  правки во всех шести местах ради P2-фичи. Свободный `dateTo` — это ещё и
  неограниченный диапазонный скан: клиент может попросить год одним запросом.
  Отклонено.

### Решение: **Вариант B**

Новый эндпоинт `GET /api/{gazebos|ps-park}/week-timeline?weekStart=YYYY-MM-DD`
поверх общей `getWeekTimeline(moduleSlug, weekStart)` в
`src/modules/booking/week-timeline.ts`. Окно фиксировано семью днями и
**не параметризуется** клиентом: приходит только `weekStart`, сервер сам
нормализует его к понедельнику той же недели и считает `dateTo = weekStart + 7d`.
Это и защита от произвольного тяжёлого диапазона, и гарантия, что клиент не
получит смещённую сетку из-за своего часового пояса.

## 3. Вопрос 2 (PRD №2, часть Б): макет недельного вида

Расширить текущую сетку «на 7 колонок дней» буквально — нельзя по арифметике,
а не по вкусу. Сегодня 100 % ширины дорожки = 15 часов одного дня при
`min-w-[900px]`, то есть ~60 px на час. Неделя в той же геометрии — это
7 × 15 = 105 часовых колонок; при читаемых 40 px/час дорожка становится ~4200 px
шириной, а каждая строка ресурса уже сейчас имеет **собственный**
`overflow-x-auto` (шапка часов скроллится отдельно от строк) — на такой ширине
это перестаёт быть мелким недочётом и делает вид неработоспособным.
Сжать неделю в те же 900 px — 8.5 px на час: блок брони на 2 часа = 17 px, имя
гостя не помещается, часовая геометрия перестаёт нести информацию.

### Вариант A — матрица «ресурс × день», ячейка = компактный список броней

7 колонок (дни недели) × N строк (ресурсы). В ячейке — чипы броней
`10:00–14:00 · Иванов` по возрастанию времени, статус — цветом (те же цвета, что
в дневной сетке), оплата — существующим `PaymentDot`.

- **Плюсы:** влезает на один экран при реальных 5 беседках / 4–5 столах (AC-2).
  Буквально выполняет «брони по каждому ресурсу». Прямо отвечает на заявленную
  задачу («оценить загрузку, спланировать смены/закупки»): в шапке дня можно
  дать «занято X из Y ч» без единого дополнительного запроса. Нулевая
  процентная геометрия — нечего ломать. Клик по чипу открывает **ту же**
  карточку брони (AC-3), клик по пустой ячейке — переключение в дневной вид на
  этот день (AC-6, минимально допустимый вариант из PRD).
- **Минусы:** теряется масштабная «полоска занятости» внутри дня — видно
  перечень, а не геометрию. Для планирования на неделю это приемлемо; для
  часовой работы остаётся дневной вид, который никуда не девается.

### Вариант B — семь дневных сеток стопкой

- **Плюсы:** максимальное переиспользование текущего компонента.
- **Минусы:** высота ≈ 7 × (N × 64 px + шапка) — это 2500+ px, то есть прямое
  нарушение AC-2 («за один экран»). Смысл фичи (одним взглядом) теряется.

### Вариант C — «гугл-календарь»: колонка = день, строка = час, ресурсы внутри ячейки

- **Плюсы:** сохраняет часовую геометрию, влезает по высоте.
- **Минусы:** при 5 ресурсах одновременные брони делят ширину колонки дня
  (~140 px / 5 ≈ 28 px) — имена нечитаемы, а «по каждому ресурсу» (AC-2)
  выполняется только формально. Плюс это самая дорогая по коду раскладка из трёх.

### Решение: **Вариант A** — матрица «ресурс × день»

```
             Пн 24.08     Вт 25.08     Ср 26.08    …   Вс 30.08
Беседка №1   10–14 Иванов  —           12–16 Пётр  …   11–15 Сидоров
             18–22 Пётр                                 16–20 Ким
Беседка №2   —            09–13 Ким    —           …   —
Беседка №3   14–18 Ким     —           10–14 Иванов…   12–23 Корп.
…
Итого/день   6 из 75 ч    4 из 75 ч    9 из 75 ч   …   14 из 75 ч
```

Строка «Итого/день» считается на клиенте из уже полученных данных (сумма часов
броней / (кол-во ресурсов × длина рабочего дня)) — отдельного API не нужно.

Существующий `timeline-grid.tsx` при этом **не переписывается**: он остаётся
дневным видом, к нему добавляется только переключатель «День / Неделя» рядом с
кнопкой «Печать» (там же, где сейчас индикатор «Загрузка…»). Состояние
переключателя — локальное состояние компонента, **без** `?view=` в URL: server-компонент
страницы `/admin/gazebos` уже держит контракт deep-link `?date=&booking=` из
«Истории бронирований», и трогать его ради P2-фичи незачем.

**Замер продуктовой метрики** («≥30 % визитов используют недельный вид») не
требует новой инструментализации: доля запросов `week-timeline` к `timeline`
видна в логах доступа.

## 4. Вопрос 3 (PRD №3 / R7): общий календарный компонент или дублирование по модулю

Это вопрос про стоимость владения, и он решается **не «всё вынести» и не
«всё дублировать»**, а по границе, которую уже провёл сам код.

Модуль-специфика двух `timeline-grid.tsx` (см. факт 1.1.4) целиком сидит
в **пути создания брони**: quick-форма беседок нуждается в `getResourcePricing()`
(будни/выходные), у ps-park её нет; `guestCount` против `playerCount`; свои
карточки брони. Именно поэтому дневная сетка и осталась дублированной — и
именно поэтому недельный вид от неё отличается: **в нём пути создания нет
вовсе** (AC-6 разрешает вместо inline-create просто переключить на дневной вид).
Значит модуль-специфики в недельном виде остаётся ровно две штуки: подписи
(«Беседка»/«Стол») и компонент карточки брони.

### Вариант A — продолжать дублировать: два `week-grid.tsx` по модулю

- **Плюсы:** соответствует конвенции дневной сетки; модули изолированы.
- **Минусы:** это уже третье наращивание одной и той же дублированной сетки;
  два независимых компонента без единой модульной причины расходиться. Каждая
  следующая правка недельного вида — двойная, и каждый расхождение между
  копиями — потенциальный баг вида «в Плей Парке починили, в беседках забыли».

### Вариант B — big-bang: вынести общий календарный примитив, переведя на него и дневную сетку

- **Плюсы:** одна реализация календаря на весь проект.
- **Минусы:** требует сначала свести `GazeboResource.pricePerHour`
  (`Decimal | null`) и `TimelineResource.pricePerHour` (`number | null`), то есть
  тронуть тип, которым пользуется весь модуль беседок; параметризовать общий
  компонент quick-формой, карточкой брони и pricing'ом обоих модулей. Итог —
  крупный рефакторинг двух ежедневно используемых production-поверхностей, с
  нулевой пользовательской ценностью, и он уезжает в прод деплой-трейном вместе
  с фичей. Классический «элегантно, но не просто» — против правила 7 из
  `agents/architect.md`.

### Вариант C — общим делается только новая поверхность (недельный вид), дневная не трогается

- Общая логика: `getWeekTimeline(moduleSlug, weekStart)` в `src/modules/booking/week-timeline.ts`.
- Общая схема: `weekTimelineQuerySchema` в `src/modules/booking/validation.ts`.
- Общий UI: `src/components/admin/shared/week-schedule-grid.tsx` с пропсами
  `moduleSlug`, `resourceLabel`, `unitLabel` и колбэками
  `onBookingClick(booking)` / `onEmptyCellClick(date, resourceId)` — карточку
  брони рендерит модуль-обёртка, как сейчас делает `timeline-grid.tsx`.
- Дневная сетка и типы `GazeboResource`/`TimelineResource` — без изменений.

### Решение: **Вариант C**

Это ровно тот паттерн, который проект уже выбрал в этом же эпике дважды
(`getPrintableDaySchedule` + `PrintDaySheet` в #668, `searchGuestsByPhone` в #666):
новая кросс-модульная функциональность пишется один раз в `booking`/`shared` и
параметризуется `moduleSlug`, а исторически дублированный дневной UI живёт как
есть, пока не появится задача, которая его действительно потребует.

**Про `pricePerHour` (R7 из PO-контекста) решение явное:** общий тип ресурса
для недели (`WeekTimelineResource`) с самого начала объявляется с
`pricePerHour: number | null`, а нормализация `Decimal → number` делается внутри
`getWeekTimeline` — так же, как это делает `getTimeline` у ps-park по причине
#614. Приводить к этому же виду `GazeboResource` **в этой задаче не надо**:
это самостоятельный технический долг, который не нужен ни US-5, ни US-6 (общий
недельный слой не импортирует типы модулей вообще — иначе `booking` зависел бы
от `gazebos`, что ломает изоляцию доменов).

**Побочный приятный факт, снимающий вопрос по AC-3:** `WeekTimelineBooking` —
структурный супертип `TimelineBooking` (те же поля + `date`), поэтому объект
недельного вида передаётся в существующие `GazeboBookingDetailCard` /
`BookingDetailCard` без адаптеров и без правки их пропсов.

## 5. Вопрос 4 (PRD №4): drag-and-drop поверх процентно-позиционированной сетки

### 5.1 Что уже не нужно делать

Серверная часть US-6 — **ноль строк**. Перенос идёт существующим
`PATCH /api/gazebos/bookings/:id` без `status` (факт 1.1.5): конфликт-чек под
advisory-lock, EXCLUDE-бэкстоп, `AuditLog`, `metadata.edits`, Google Calendar,
уведомление `booking.rescheduled` — всё уже там и вызывается сегодня формой
редактирования. Требование PRD «drag должен вызывать тот же service-путь, что
форма» выполняется буквально: тот же URL, то же тело, тот же обработчик.
Новых полей `Booking`, миграций и клиентской проверки конфликтов не появляется.

### 5.2 Что действительно нужно решить — перевод drag-события в «ресурс + время»

Сетка не состоит из ячеек-элементов: брони — абсолютно позиционированные блоки
в процентах, а часовые «ячейки» — декоративные `flex-1` div'ы. Поэтому drop
нельзя просто «поймать ячейкой».

**Вариант A — droppable на каждую часовую ячейку** (`res:<id>:h:<hour>`):
15 часов × 5 ресурсов = 75 droppable-зон на день. Работает «из коробки»
коллизиями dnd-kit, но даёт только часовую гранулярность (получасовой шаг —
уже 150 зон), и точка отсчёта — курсор, а не левый край блока, поэтому
двухчасовая бронь, взятая мышью за середину, поедет на час.

**Вариант B — гибрид (выбран):** droppable — **строка ресурса** (`res:<id>`,
5 зон), время — из `event.delta.x`:

```
deltaHours = (delta.x / trackWidthPx) * (closeHour - openHour)
snapped    = Math.round(deltaHours * (60 / STEP_MIN)) / (60 / STEP_MIN)   // STEP_MIN = 30
newStart   = oldStart + snapped;  newEnd = oldEnd + snapped               // длительность сохраняется
```

`trackWidthPx` берётся с `ref` на дорожку ресурса через `getBoundingClientRect()`
в момент `onDragStart` (не на каждый кадр). Смещение считается от **сдвига
блока**, а не от позиции курсора — поэтому «взял за середину» работает
корректно. Ресурс приходит из `over.id`, вертикаль руками не считается.
Результат клампится в `[openHour, closeHour]`; выход за границы всё равно
поймает сервер (`OUTSIDE_WORKING_HOURS`, 422).

**Растяжение (AC-2)** — отдельная зона `useDraggable` c id `resize:<bookingId>`
на правом крае блока (6–8 px, `cursor: ew-resize`, `stopPropagation` чтобы не
стартовал перенос всего блока). Тот же перевод `delta.x → часы`, но меняется
только `endTime`. Нижнюю границу (`minBookingHours`) не проверяем на клиенте —
сервер вернёт `DURATION_BELOW_MIN` (422) с готовым русским текстом.

### 5.3 Реальные технические сложности (оценка, а не общие слова)

| # | Сложность | Решение | Цена |
|---|---|---|---|
| 1 | Клик по брони открывает карточку — drag не должен её открывать | `PointerSensor` с `activationConstraint: { distance: 8 }` (прецедент канбана — 5) | 1 строка |
| 2 | Каждая строка ресурса — свой `overflow-x-auto`, перетаскиваемый блок обрезается при уходе на соседнюю строку | `DragOverlay` из `@dnd-kit/core` (портал на уровне body) + оригинал с `opacity-40` | ~25 строк, единственный по-настоящему нетривиальный кусок |
| 3 | Перевод px → часы и обратно | Чистые функции в `src/lib/timeline-drag.ts` (`pxDeltaToHours`, `snapHours`, `shiftBooking`, `clampToWorkingHours`) — тестируются юнит-тестами без DOM | ~60 строк + тесты |
| 4 | Ошибка сервера после оптимистичного сдвига | Откат состояния к сохранённому снимку + показ `error.message` строкой рядом с навигацией даты (место уже есть — там индикатор «Загрузка…») | ~20 строк |
| 5 | Микро-сдвиг мышью = реальный перенос = уведомление гостю | Если после snap смещение равно нулю **и** ресурс не изменился — запрос не отправляется вовсе (no-op) | 3 строки, обязательно |
| 6 | Параллельные drag'и | Блокировка блока на время in-flight PATCH (`draggingId`) | 5 строк |

**Итого:** ~250–350 строк нового/изменённого фронтенд-кода в одном компоненте
плюс тестируемый чистый модуль. Ни новой зависимости, ни эндпоинта, ни миграции,
ни изменения `Booking`.

### 5.4 Решение: US-6 делаем, в границах PRD

Отказ от US-6 (PRD допускает его «с обоснованием») **не обоснован фактами**:
дорогая часть — серверная безопасность переноса — уже оплачена (#429/#433/#439),
а оставшаяся работа — один фронтенд-компонент без инфраструктурных последствий.
При этом скоуп остаётся ровно тем, что зафиксировал PRD: **только беседки,
только десктопная сетка, только дневной вид, одна бронь за операцию**.
`mobile-timeline.tsx` (оба модуля) не меняется — проверено, это отдельный
компонент с собственной разметкой без абсолютного позиционирования, drag его
не касается ни одной строкой. Перенос между модулями невозможен по построению:
droppable-зоны создаются только для ресурсов текущего модуля (AC-5).

### 5.5 Зависимость US-6 от US-5

**Функциональной зависимости нет:** PRD AC-1 явно ограничивает drag дневным
видом («В дневном виде сетки…»), в недельной матрице drag не предусмотрен и
этим ADR не вводится (в раскладке «ресурс × день» перетаскивание меняло бы
дату, но не время — полуфункция, дороже пользы).

**Есть организационная зависимость:** обе задачи правят один файл
`src/components/admin/gazebos/timeline-grid.tsx` (US-5 добавляет переключатель
вида, US-6 оборачивает сетку в `DndContext`). Рекомендуемый порядок — US-5,
затем US-6 поверх. Если обе берутся одной сессией — их допустимо и правильно
скомпоновать в один PR (Scope guard #3), это остаётся в границах одного эпика
и одного PRD.

## 6. Схема данных

**Изменений в `prisma/schema.prisma` нет. Миграции не требуются.**

Обоснование по каждому требованию:

- Недельный вид читает те же `Booking` и `Resource`, только диапазоном дат;
  нужный индекс `@@index([moduleSlug, date])` уже есть (`schema.prisma:239`).
- Drag-and-drop пишет через существующий `rescheduleBooking()`, который уже
  обновляет `resourceId/date/startTime/endTime` и дописывает `metadata.edits`.
- Требование PRD «без изменений модели `Booking`/статус-машины сверх минимума»
  выполняется в строгой форме: минимум здесь — ноль.

Новые **типы** (TypeScript, не БД) — в `src/modules/booking/week-timeline.ts`:

```ts
export type WeekTimelineResource = {
  id: string;
  name: string;
  description: string | null;
  capacity: number | null;
  /** Decimal → number на границе Server → Client Component (#614). */
  pricePerHour: number | null;
  isActive: boolean;
};

export type WeekTimelineBooking = {
  id: string;
  resourceId: string;
  /** YYYY-MM-DD в МСК — ключ ячейки; клиент не выводит дату из ISO сам. */
  date: string;
  startTime: string; // ISO datetime
  endTime: string;   // ISO datetime
  status: "PENDING" | "CONFIRMED" | "CHECKED_IN";
  clientName: string | null;
  clientPhone: string | null;
  metadata: Record<string, unknown> | null;
  cashAmount: string | null;
  cardAmount: string | null;
};

export type WeekTimelineData = {
  weekStart: string;   // понедельник недели, YYYY-MM-DD
  days: string[];      // ровно 7 дат YYYY-MM-DD
  resources: WeekTimelineResource[];
  bookings: WeekTimelineBooking[];
  hours: string[];        // ["08:00", …] — как у дневного, для расчёта загрузки
  minBookingHours: number;
};
```

Брони отдаются плоским списком (а не вложенными в дни): одна форма данных,
группировка на клиенте одной `Map` — тот же приём, что в `getPrintableDaySchedule`.

```
                        "pricePerHour": 1500, "isActive": true, "description": null }],
        "bookings": [{ "id": "…", "resourceId": "…", "date": "2026-08-24",
                       "startTime": "2026-08-24T07:00:00.000Z",
                       "endTime":   "2026-08-24T11:00:00.000Z",
                       "status": "CONFIRMED", "clientName": "Иванов",
                       "clientPhone": "+7…", "metadata": { "guestCount": 8 },

                                   "message": "Формат даты: YYYY-MM-DD" } }
401 { "success": false, "error": { "code": "UNAUTHORIZED", … } }
403 { "success": false, "error": { "code": "FORBIDDEN", "message": "Нет доступа к этому разделу" } }

```

Роут-хендлер — тонкий, по образцу `src/app/api/gazebos/print-schedule/route.ts`:
парсинг query → Zod → вызов `getWeekTimeline("gazebos", …)` → `apiResponse(...)`,
всё в `try/catch → apiServerError()`.

**Zod-схема** (`src/modules/booking/validation.ts`, рядом с `printScheduleQuerySchema`):

```ts
export const weekTimelineQuerySchema = z.object({
  weekStart: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "Формат даты: YYYY-MM-DD"),
});
export type WeekTimelineQuery = z.infer<typeof weekTimelineQuerySchema>;
```

Валидируется ровно одно поле — `weekStart` (строка `YYYY-MM-DD`). Любая другая
дата недели нормализуется сервисом к понедельнику; произвольная длина окна
клиенту недоступна (нет `dateTo`/`days` параметров) — это осознанная защита от
неограниченного диапазонного скана. Неизвестные query-ключи Zod отбрасывает.

### 7.2 Существующий, используется drag'ом без изменений: `PATCH /api/gazebos/bookings/:id`

```
PATCH /api/gazebos/bookings/{id}
Content-Type: application/json

{ "resourceId": "<беседка-приёмник>", "date": "2026-08-24",
  "startTime": "12:00", "endTime": "16:00" }        // поля status НЕТ — это режим правки
```

Клиент при `success === false` откатывает оптимистичное состояние и показывает

Никакой собственной проверки конфликтов на клиенте не появляется (жёсткое
требование PRD AC-3).

### 7.3 RBAC — обязательный раздел для новых endpoint'ов

| Endpoint | USER | MANAGER | ADMIN | SUPERADMIN | Проверка в коде |
|---|---|---|---|---|---|
| `GET /api/gazebos/week-timeline` | ❌ 403 | ✅ только с `AdminPermission` на секцию `gazebos` | ✅ | ✅ | `auth()` → `hasRole(session.user,"MANAGER")` → `requireAdminSection(session,"gazebos")` |
| `GET /api/ps-park/week-timeline` | ❌ 403 | ✅ только с `AdminPermission` на секцию `ps-park` | ✅ | ✅ | то же с `"ps-park"` |
| `PATCH /api/gazebos/bookings/:id` (drag) | ❌ 403 | ✅ секция `gazebos` | ✅ | ✅ | уже реализовано в роуте, не меняется |

**Почему `requireAdminSection`, а не `hasModuleAccess`.** Это две разные оси
грантов: `hasModuleAccess` смотрит `ModuleAssignment`, `requireAdminSection` —
`AdminPermission` на секцию админки. Все админские роуты `/api/gazebos/*` и
`/api/ps-park/*` (включая `/timeline`, `/print-schedule`, `/guests/search`)
гейтятся вторым. Смешивать оси нельзя: получилась бы ситуация «оператор видит
дневное расписание, но получает 403 на недельное» (или наоборот) при одном и том
же наборе прав. Новый эндпоинт копирует гейт своего дневного собрата
один-в-один — это не новая поверхность доступа, а то же множество данных в
более широком временном окне.

**Утечки данных.** `week-timeline` отдаёт ровно те же поля, что уже отдаёт
`timeline` (`clientName`, `clientPhone`, `metadata`, суммы наличных/карты),
только за 7 дней. Ни паролей, ни токенов, ни `userId` в выдаче нет и не
добавляется; `Resource.googleCalendarId` в DTO не входит.

**Rate limiting.** `await rateLimit(request, "authenticated", session.user.id)`
сразу после RBAC-гейта — тир `authenticated` (240 req/min на пользователя,
`RATE_LIMIT_AUTH_PER_MIN`), по прецеденту `/api/ps-park/guests/search` (#666).
Для человека это недостижимый потолок (переключение недели — один запрос),
но защищает от зациклившегося клиента, который в отличие от дневного запроса
тянет семидневный диапазон. `PATCH /api/…/bookings/:id` дополнительным лимитом
не обкладываем — существующий эндпоинт не меняем, а от «дрожания мышью»
защищает no-op при нулевом смещении (§5.3, п.5) и блокировка блока на время
in-flight запроса.

**AuditLog.** Мутаций у нового эндпоинта нет (только чтение) — записи не нужны.
Мутация drag'а логируется существующим `logAudit(managerId, "booking.reschedule", …)`
внутри `rescheduleBooking()`, отдельного логирования не добавляем — иначе
история брони задвоится.

## 9. Технические edge cases для QA

Недельный вид:
1. `weekStart`, пришедший не понедельником (например, из ручного URL) —
   сервер нормализует; неделя всё равно понедельник–воскресенье.
2. Граница месяца/года внутри недели (напр. 29.12–04.01) — `days` считаются
   сдвигом UTC-даты, как в `DateNavigator.shiftDate`, без локальной TZ браузера.
3. Бронь, начавшаяся в один день и «висящая» до закрытия — по модели она
   всегда внутри одного `date`, но чипы всё равно сортируем по `startTime`.
4. Ресурс, деактивированный в середине недели (`isActive=false`) — как и у
   `getTimeline`, в выдачу не попадает; брони на нём остаются в `bookings`
   с `resourceId`, которого нет в `resources` → клиент не должен падать
   (прецедент бага: `getPrintableDaySchedule` подставляет `"—"`).
5. Пустая неделя (нет броней) — матрица рендерится с прочерками, не «Загрузка…».
6. MANAGER без `AdminPermission` на секцию → 403, а не пустая неделя.

Drag-and-drop:
7. Перенос `CHECKED_IN`-брони (идёт сеанс) — сервер разрешает (в `EDITABLE`),
   поведение должно совпадать с формой редактирования.
8. Перенос на занятое место → 409 `BOOKING_CONFLICT`, блок возвращается на
   исходную позицию, карточка брони не открывается.
9. Перетаскивание за 08:00 / после 23:00 → 422 `OUTSIDE_WORKING_HOURS`, откат.
10. Растяжение ниже `minBookingHours` → 422 `DURATION_BELOW_MIN`, откат.
11. Растяжение выше `maxBookingHours` → 422 `DURATION_ABOVE_MAX`, откат.
12. Микро-сдвиг (< полшага) — **никакого запроса**, гостю ничего не уходит.
13. Успешный перенос → в `AuditLog` одна запись `booking.reschedule`, в истории
    брони один пункт правки, у гостя одно уведомление `booking.rescheduled`,
    событие Google Calendar перенесено (при смене беседки — удалено в старом
    календаре и создано в новом).
14. Перенос брони с уже принятой оплатой пересчитывает `metadata.totalPrice` —
    это существующее поведение формы редактирования, drag его наследует
    намеренно; отдельного подтверждения PRD не требует, но регресс-чек нужен.
15. Клик (без движения) по брони по-прежнему открывает карточку; клик по
    свободному слоту по-прежнему открывает quick-форму.
16. Мобильный таймлайн беседок и обе поверхности Плей Парка — без изменений
    поведения (регресс-чек).

### Задача 2 — US-6

**Заголовок:** `feat(gazebos): drag-and-drop переноса и растяжения брони в дневной сетке (US-6, эпик #442)`

**Скоуп (входит):**
- `src/lib/timeline-drag.ts` — чистые функции `pxDeltaToHours`, `snapHours`,
  `shiftBooking`, `clampToWorkingHours` + юнит-тесты (без DOM).
- `src/components/admin/gazebos/timeline-grid.tsx`: `DndContext` +
  `PointerSensor{ distance: 8 }` + `DragOverlay`; `useDroppable` на строку
  ресурса; ручка растяжения правого края как отдельный `useDraggable`.
- Отправка `PATCH /api/gazebos/bookings/:id` **без** `status`
  (`{ resourceId, date, startTime, endTime }`), оптимистичное обновление,
  откат и показ `error.message` при `success:false`; no-op при нулевом смещении;
  блокировка повторного drag во время in-flight запроса.
- Тесты: happy path «drop → PATCH с ожидаемым телом», «409 → откат состояния и
  текст ошибки», «клик без движения открывает карточку, а не переносит».

**Не входит:** Плей Парк (PRD AC-7 — отдельная задача после подтверждения
ценности); мобильный/сенсорный таймлайн (AC-6); drag в недельном виде; bulk;
любые серверные изменения — эндпоинт, схема, `rescheduleBooking()`, миграции;
собственная клиентская проверка конфликтов.

**Зависимости:** функционально **не зависит** от Задачи 1 — drag живёт только
в дневном виде (PRD AC-1). Организационно: обе задачи правят
`src/components/admin/gazebos/timeline-grid.tsx`, поэтому брать **после**
Задачи 1 (или, если обе идут одной сессией, скомпоновать в один PR —
Scope guard #3).
