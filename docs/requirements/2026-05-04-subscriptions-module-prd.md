# PRD: F6 — Абонементы (Subscriptions) для PS Park

**Дата:** 2026-05-04
**Автор:** Product Owner
**Статус:** DRAFT — ожидает одобрения пользователя
**RUN_ID:** `2026-05-04-subscriptions-module-prd-only`

---

## Проблема

Сейчас администратор PS Park не может зафиксировать предоплаченный пакет часов для постоянного гостя. Каждый визит оплачивается отдельно: менеджер вынужден уточнять "оплачено или по абонементу?", вручную вести таблицу в Excel и рискует ошибиться при списании. Гость не видит остаток своих часов и не получает никакого подтверждения.

Результат: потеря доверия постоянных клиентов, ошибки в финансовом учёте, лишняя нагрузка на менеджера.

**Персона:** MANAGER PS Park (первичная), SUPERADMIN (вторичная).

---

## Решение

Добавить в раздел администрирования PS Park вкладку «Абонементы». Менеджер заводит карточку абонемента на конкретного гостя: сколько часов куплено, на какой срок, по какой цене. Система хранит остаток часов и ведёт неизменяемый журнал всех операций. В карточке гостя появляется отдельная вкладка с историей всех его абонементов.

Это MVP-итерация: охватывает только PS Park. Беседки, кафе и другие модули — следующие итерации по отдельным тикетам.

---

## Целевая аудитория

- **MANAGER PS Park** — ежедневная работа с абонементами гостей.
- **SUPERADMIN** — контроль, сводный просмотр, отмена абонементов.

## Бизнес-правила

1. **Один активный абонемент на гостя.** Нельзя создать второй абонемент со статусом ACTIVE для того же userId. При попытке — ошибка 409 `ACTIVE_SUBSCRIPTION_EXISTS`.

2. **Автоматический переход в EXPIRED.** Если текущая дата превысила `validTo` — абонемент истёк. Проверка происходит в момент чтения (`getActiveSubscriptionForUser`). Еженедельный фоновый процесс обновляет статусы для корректной фильтрации в списках.

3. **Автоматический переход в DEPLETED.** Если `remainingHours <= 0` — абонемент переходит в DEPLETED и недоступен для дальнейшего списания.

4. **Приоритет EXPIRED над DEPLETED.** Если срок истёк и часы исчерпаны одновременно — статус EXPIRED.

5. **Запрет ухода в минус.** Списание, делающее `remainingHours < 0`, отклоняется с ошибкой `INSUFFICIENT_HOURS`.

6. **Иммутабельность журнала транзакций.** Записи `SubscriptionTransaction` не редактируются и не удаляются — только создаются. Исправление ошибки = новая корректирующая транзакция.

7. **Гость — только USER.** Абонемент можно создать только для пользователя с ролью USER.

8. **Все мутации логируются.** Каждое создание, изменение, отмена и корректировка фиксируются в `AuditLog`.

## Модели данных (для Architect)

### Новые модели Prisma

**Subscription**
- `id` — идентификатор
- `userId` — FK к User (только role=USER)
- `totalHours` — куплено часов (Decimal, > 0)
- `remainingHours` — остаток (Decimal, >= 0)
- `validFrom` — дата начала действия
- `validTo` — дата окончания действия (> validFrom)
- `status` — SubscriptionStatus
- `pricePaid` — уплаченная сумма (Decimal, >= 0)
- `createdById` — FK к User (кто создал)
- `createdAt`, `updatedAt`

**SubscriptionTransaction** (иммутабельная, нет `updatedAt`)
- `id`
- `subscriptionId` — FK к Subscription
- `bookingId` — FK к Booking, nullable (заполняется при автосписании в F7)
- `hoursDelta` — Decimal (отрицательное = списание, положительное = пополнение)
- `reason` — SubscriptionTransactionReason
- `note` — текстовое примечание (обязательно для MANUAL_DEDUCT и MANUAL_TOPUP)
- `performedById`, `performedByName`
- `createdAt`

**Новые enum:**

`SubscriptionStatus`: `ACTIVE | EXPIRED | DEPLETED | CANCELLED`

`SubscriptionTransactionReason`: `CHARGE | REFUND | MANUAL_TOPUP | MANUAL_DEDUCT`

### Новый модуль

`src/modules/subscriptions/` — `service.ts`, `types.ts`, `validation.ts`, `__tests__/service.test.ts`

Ключевые функции сервиса (сигнатуры определяет Architect):
- `createSubscription` — создание с проверкой единственности ACTIVE
- `listSubscriptions` — список с фильтрацией и пагинацией
- `getSubscription` — детали + транзакции
- `adjustSubscriptionHours` — корректировка с записью в журнал
- `cancelSubscription` — отмена
- `getActiveSubscriptionForUser` — хелпер для F7 с lazy auto-status

## Acceptance Criteria (сводные, Given/When/Then)

1. **Given** гость с телефоном "+79991234567" существует в БД; **When** менеджер создаёт абонемент: 10 часов, срок 30 дней, цена 5 000 ₽; **Then** создаётся `Subscription` со `status=ACTIVE`, `remainingHours=10.00`, `pricePaid=5000.00`; в `AuditLog` появляется `action="subscription.create"`.

2. **Given** у гостя уже есть `Subscription` со `status=ACTIVE`; **When** менеджер создаёт второй абонемент для того же гостя; **Then** API возвращает 409 с `error.code="ACTIVE_SUBSCRIPTION_EXISTS"`.

3. **Given** `Subscription` с `validTo` в прошлом и `status=ACTIVE`; **When** вызывается `getActiveSubscriptionForUser(userId)`; **Then** статус обновляется до `EXPIRED`; функция возвращает `null`.

4. **Given** `Subscription` с `remainingHours=0.00` и `status=ACTIVE`; **When** вызывается `getActiveSubscriptionForUser(userId)`; **Then** статус обновляется до `DEPLETED`; функция возвращает `null`.

5. **Given** `Subscription` со `status=ACTIVE` и `remainingHours=3.00`; **When** менеджер отправляет PATCH с `hoursDelta=-2.00`, `reason="MANUAL_DEDUCT"`, `note="ошибка ввода прошлой смены"`; **Then** `remainingHours` становится `1.00`; создаётся `SubscriptionTransaction` (без `updatedAt`); в `AuditLog` появляется `action="subscription.update"`.

6. **Given** `Subscription` со `status=ACTIVE` и `remainingHours=1.00`; **When** менеджер отправляет PATCH с `hoursDelta=-2.00`; **Then** API возвращает 400 с `error.code="INSUFFICIENT_HOURS"`.

7. **Given** `Subscription` со `status=ACTIVE`; **When** SUPERADMIN отправляет POST на `/api/subscriptions/:id/cancel`; **Then** `status=CANCELLED`; `remainingHours` не изменяется; в `AuditLog` появляется `action="subscription.cancel"`; автоматического возврата денег не происходит.

8. **Given** открыта страница `/admin/ps-park/subscriptions`; **When** пользователь выбирает фильтр «Активные»; **Then** отображаются только записи со `status=ACTIVE`.

9. **Given** открыта карточка гостя в `/admin/clients/[id]`; **When** пользователь переключается на вкладку «Абонементы»; **Then** показываются все абонементы этого гостя в обратном хронологическом порядке.

10. **Given** форма создания абонемента открыта; **When** пользователь вводит `totalHours=0` или `validFrom` позже `validTo`; **Then** форма показывает inline-ошибку и запрос не отправляется.

## Edge Cases

| Ситуация | Ожидаемое поведение |
|----------|---------------------|
| Создание абонемента пользователю с `role != USER` | 400 `INVALID_USER_ROLE` |
| `validFrom > validTo` | 400 `INVALID_DATE_RANGE` |
| `totalHours <= 0` | 400 `INVALID_HOURS` |
| `pricePaid < 0` | 400 `INVALID_PRICE` |
| Второй ACTIVE абонемент для того же userId | 409 `ACTIVE_SUBSCRIPTION_EXISTS` |
| MANUAL_DEDUCT делает `remainingHours < 0` | 400 `INSUFFICIENT_HOURS` |
| Отмена уже CANCELLED абонемента | 409 `ALREADY_CANCELLED` |
| `getActiveSubscriptionForUser` при `validTo` в прошлом | Возвращает null, статус обновляется на EXPIRED |
| Race condition — одновременное создание двух ACTIVE | Защита транзакцией; детали — Architect |
| Перевод часов между абонементами | Не поддерживается |

## Приоритет (MoSCoW)

**Категория: Must have.**

Обоснование: постоянные клиенты с предоплаченными пакетами — один из ключевых источников выручки PS Park. Без этого инструмента менеджер работает в Excel или теряет учёт полностью. Прямые потери: либо недосписание (убыток), либо конфликты с гостями (отток). Заказчик явно подтвердил необходимость при уточнении требований.

**Зависимости:**
- F4 (клиентские карточки) — завершён: `User` с полями phone/name, `upsertClientByPhone`, `/api/admin/clients` search доступны.
- F7 (автосписание при завершении сессии) — зависит от F6; `getActiveSubscriptionForUser` экспортируется как public helper.

## Open Questions для Architect

1. **Lazy vs. cron для auto-status.** PO рекомендует lazy-проверку в `getActiveSubscriptionForUser` + еженедельный cron-cleanup для корректной фильтрации. Architect подтверждает или предлагает альтернативу.

2. **Точность `hoursDelta`.** PO рекомендует Decimal(10,2) — минимальный шаг 0.25 ч (15 мин), согласовано с `billedHours` PS Park. Int не подходит.

3. **Защита от race condition.** Варианты: partial unique index `WHERE status='ACTIVE'` на `(userId)`, SELECT FOR UPDATE в транзакции, optimistic lock. Architect выбирает.

4. **Продление validTo через PATCH.** PO считает это нормальной операцией (клиент доплатил за продление). Обязательный `reason`. Architect подтверждает или ограничивает.
