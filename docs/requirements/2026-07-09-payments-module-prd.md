# PRD: Модуль «Платежи» — онлайн-оплата через ЮKassa

**Дата:** 2026-07-09
**Автор:** Product Owner
**Статус:** DRAFT — ожидает одобрения пользователя
**RUN_ID:** `2026-07-09-payments-module-prd`
**Источник истины по архитектуре:** `docs/architecture/2026-07-08-yookassa-integration-plan.md` (согласован владельцем 2026-07-08, решения — § 10 этого документа)

---

## Проблема

Сегодня на платформе нигде не принимается онлайн-оплата — при том что деньги считаются
в пяти местах (`gazebos`, `ps-park`, `subscriptions`, `rental`, `cafe`). Гость не может
оплатить бронь беседки картой при бронировании — беседка «висит» неподтверждённой, пока
администратор не свяжется с гостем или не примет деньги на месте. Абонемент PS Park
выписывается менеджером «на веру» — факт оплаты нигде не фиксируется системой, только
в голове менеджера. Оплата счёта сессии PS Park возможна только физически на стойке
(наличные/карта через терминал POS) — гость не может закрыть счёт со своего телефона.

Следствия:
- Часть бронирований беседок срывается или требует ручного дозвона для подтверждения оплаты.
- Абонементы PS Park не защищены от ошибки «выписали, а не оплатили».
- Менеджер тратит время на POS-операции там, где гость мог бы оплатить сам за секунды.
- Нет единого финансового источника истины для онлайн-платежей — при возврате или споре
  администратор не может быстро посмотреть, что оплачено, чем и когда.

**Персоны:**
- **USER** (гость парка) — прямой выгодоприобретатель: оплачивает бронь/абонемент/счёт
  онлайн, без визита на ресепшн и без ожидания подтверждения по телефону.
- **MANAGER** (беседки / PS Park) — освобождается от части ручных POS-операций и телефонных
  подтверждений; получает третий способ приёма денег (онлайн) рядом с наличными и картой.
- **SUPERADMIN** — получает контроль над всеми онлайн-платежами: список, статус, возвраты,
  финансовый учёт в едином журнале (`FinancialTransaction`), не полагаясь на ручные отметки.

---

## Решение

Ввести новый модуль `payments`, который принимает онлайн-оплату через ЮKassa (эквайринг,
СБП, сохранённые карты) и служит единой точкой для платежей, возвратов и чеков 54-ФЗ для
всей платформы. В рамках этого релиза модуль подключается к трём точкам платформы:

1. **Беседки** — 100% предоплата при бронировании онлайн.
2. **Абонементы PS Park** — покупка пасса онлайн со ссылкой/QR на оплату.
3. **PS Park (сессии)** — оплата счёта сессии по QR/ссылке как третий способ рядом с
   наличными и картой на POS.

Плюс административная страница «Платежи» для SUPERADMIN — просмотр всех платежей и
ручное оформление возврата-исключения.

Источник истины по оплате — только статус, полученный напрямую от ЮKassa (через вебхук
и/или подстраховочную сверку), а не факт возврата пользователя на сайт. Все деньги —
и онлайн, и уже существующие POS-операции — попадают в один и тот же финансовый журнал
(`FinancialTransaction`), поэтому отчётность по выручке не расходится по источникам.

Аренда офисов (B2B) в эту итерацию **не входит** — решение владельца, аренда продолжает
оплачиваться по банковским реквизитам с ручной отметкой менеджера, как сейчас.

Технические детали (структура кода, конечный автомат статусов, вебхук, идемпотентность,
формат чеков) уже проработаны и согласованы в архитектурном плане — Architect использует
его как основу ADR, этот PRD фиксирует **что** и **зачем** видит и делает пользователь.

---

## Целевая аудитория

- **USER** — гость, бронирующий беседку; гость, покупающий абонемент PS Park; гость,
  оплачивающий счёт сессии PS Park.
- **MANAGER** (беседки, PS Park) — видит статус онлайн-оплаты в своих бронях/сессиях,
  инициирует оплату по QR на месте (Фаза 3).
- **SUPERADMIN** — видит все платежи и возвраты платформы, оформляет ручной возврат-исключение.

---

## Что уже есть (не делаем заново)

- **Иммутабельный финансовый журнал** `FinancialTransaction` — переиспользуется, добавляется
  новый тип операции для онлайн-платежей.
- **Диспетчер уведомлений** `src/modules/notifications/` — переиспользуется, добавляются
  новые события платежей (не создаём новый канал доставки).
- **Паттерны входящих вебхуков** (Novofon, Avito) — секрет в URL + `timingSafeEqual` +
  fail-secure — переиспользуются для вебхука ЮKassa.
- **Cron-инфраструктура** (`CRON_SECRET`, `/api/cron/*`) — переиспользуется для сверки
  зависших платежей.
- **POS-оплата** (наличные/карта на месте) для беседок и PS Park — не заменяется, а
  дополняется онлайн-каналом. Гейт «нельзя завершить бронь без полной оплаты»
  (PRD `2026-05-04-gazebos-payment-required-on-complete`, `2026-05-04-ps-park-payment-required-on-complete`)
  учитывает уже внесённую онлайн-предоплату — доплачивать нужно только разницу.
- Ключи ЮKassa (тестовый магазин) получены и лежат в GitHub Secrets — готовы для разработки.

## User Stories

### US-1: SUPERADMIN видит все онлайн-платежи и их статус

- **Как** владелец/управляющий парка (SUPERADMIN)
- **Я хочу** видеть единый список всех онлайн-платежей платформы с их статусом, суммой и
  привязкой к брони/абонементу/сессии
- **Чтобы** контролировать поступление денег и быстро разбираться в спорных ситуациях без
  захода в личный кабинет ЮKassa

**Acceptance Criteria:**
- [ ] AC-1.1: На странице «Платежи» в админке отображается таблица платежей: дата, сумма,
      статус («Ожидает оплаты», «Оплачен», «Отменён», «Возвращён», «Частично возвращён»),
      к чему относится платёж (бронь беседки / абонемент / сессия PS Park), плательщик
      (имя/телефон, если известен).
- [ ] AC-1.2: Список фильтруется по статусу и по типу («беседки», «абонементы», «PS Park»).
- [ ] AC-1.3: Открытие строки платежа показывает карточку с полной историей: когда создан,
      когда оплачен, способ оплаты (карта/СБП/…), связанные возвраты с их статусом и датой.
- [ ] AC-1.4: Страница доступна только SUPERADMIN; при заходе с ролью MANAGER или USER — 403.
- [ ] AC-1.5: Платёж со статусом «Оплачен» отображает ссылку на чек, если чек уже пришёл
      от ЮKassa (если нет — пометка «чек формируется»).

**Приоритет:** Must have.

### US-2: SUPERADMIN оформляет возврат-исключение вручную

- **Как** владелец/управляющий парка (SUPERADMIN)
- **Я хочу** вручную оформить полный возврат по конкретному платежу с указанием причины
- **Чтобы** иметь возможность пойти навстречу гостю в исключительной ситуации (например,
  отмена брони беседки менее чем за 24 часа по уважительной причине), не трогая базу данных
  напрямую

**Acceptance Criteria:**
- [ ] AC-2.1: На карточке оплаченного платежа есть кнопка «Оформить возврат», доступная
      только SUPERADMIN.
- [ ] AC-2.2: Возврат — всегда на полную сумму платежа; частичный возврат кнопкой не
      предлагается в этом релизе.
- [ ] AC-2.3: Форма требует обязательного комментария-причины (минимум 5 символов) перед
      подтверждением.
- [ ] AC-2.4: После подтверждения статус платежа меняется на «Возвращён» только после
      подтверждения от ЮKassa (не сразу по нажатию кнопки); до этого момента статус —
      «Возврат оформляется».
- [ ] AC-2.5: Если платёж уже был возвращён ранее (автоматически или вручную) — кнопка
      «Оформить возврат» недоступна, показывается сообщение «Уже возвращён».
- [ ] AC-2.6: Если ЮKassa отклоняет возврат (например, недостаточно средств на балансе
      магазина) — пользователь видит понятную ошибку и может повторить попытку позже.
- [ ] AC-2.7: Каждый ручной возврат фиксируется в журнале аудита с указанием, кто и когда
      его оформил и по какой причине.

**Приоритет:** Must have — без ручного возврата любое исключение из политики (US-4)
превращается в обращение в поддержку ЮKassa или прямую правку базы.

---

### US-3: Гость оплачивает бронь беседки онлайн при бронировании

- **Как** гость парка (USER)
- **Я хочу** оплатить бронь беседки картой или через СБП сразу при бронировании
- **Чтобы** не ехать в парк для предоплаты и быть уверенным, что беседка забронирована за мной

**Acceptance Criteria:**
- [ ] AC-3.1: После выбора даты, времени и подтверждения деталей брони гость видит кнопку
      «Оплатить» с итоговой суммой (100% стоимости брони).
- [ ] AC-3.2: Форма бронирования требует email или телефон гостя (для отправки чека); без
      заполнения хотя бы одного поля кнопка «Оплатить» неактивна. Для авторизованного
      гостя поле подставляется из профиля автоматически, если там уже есть email/телефон.
- [ ] AC-3.3: После нажатия «Оплатить» гость переходит на страницу оплаты ЮKassa (карта,
      СБП и другие доступные способы).
- [ ] AC-3.4: После успешной оплаты бронь автоматически получает статус «Подтверждена» —
      без участия менеджера.
- [ ] AC-3.5: После возврата со страницы оплаты (независимо от того, успел ли гость
      закрыть вкладку) гость видит страницу ожидания/результата, которая показывает
      актуальный статус оплаты, а не считает оплату успешной только по факту редиректа.
- [ ] AC-3.6: Гость получает подтверждение оплаты (Telegram/email — по доступным
      каналам) и электронный чек на указанный email от ЮKassa.
- [ ] AC-3.7: Менеджер беседок в списке броней видит отметку «Оплачено онлайн» на
      подтверждённых бронях.

**Приоритет:** Must have — первый и самый востребованный пользовательский поток,
явно запрошен владельцем.

### US-4: Неоплаченная бронь беседки не удерживает слот навсегда

- **Как** гость парка (USER), который передумал платить или у которого не прошла оплата
- **Я хочу**, чтобы система не держала слот забронированным бесконечно, если оплата не
  завершена
- **Чтобы** слот вовремя освобождался для других гостей, а мне было понятно, что бронь не
  подтверждена

**Acceptance Criteria:**
- [ ] AC-4.1: Если оплата не завершена в течение ~1 часа с момента создания брони, бронь
      автоматически отменяется, слот освобождается для новых бронирований.
- [ ] AC-4.2: Если гость закрыл страницу оплаты ЮKassa и вернулся позже (в пределах
      окна ~1 часа) и всё же оплатил — бронь подтверждается штатно, как в US-3.
- [ ] AC-4.3: Гость с неудавшейся/просроченной оплатой видит понятное сообщение
      («время на оплату истекло, забронируйте заново») и может создать новую бронь.
- [ ] AC-4.4: Освобождение просроченных неоплаченных броней происходит даже если
      уведомление от ЮKassa о неуспехе платежа не дошло (не полагаемся только на вебхук).

**Приоритет:** Must have — иначе неоплаченные брони блокируют слоты и создают путаницу
в доступности беседок.

---

### US-5: Возврат за отменённую бронь беседки — по чёткой политике

- **Как** гость парка (USER)
- **Я хочу** получить деньги обратно при отмене брони заранее и понимать, когда возврата
  не будет
- **Чтобы** доверять предоплате и не бояться потерять деньги при изменении планов

**Acceptance Criteria:**
- [ ] AC-5.1: Отмена оплаченной брони гостем более чем за 24 часа до начала — деньги
      возвращаются автоматически, в полном объёме, без участия менеджера. Гость получает
      уведомление о возврате.
- [ ] AC-5.2: Отмена оплаченной брони гостем менее чем за 24 часа до начала — деньги не
      возвращаются автоматически; гость видит это условие до подтверждения отмены.
- [ ] AC-5.3: Отмена брони со стороны парка (менеджер отменяет из-за форс-мажора,
      недоступности беседки и т.п.) — деньги возвращаются автоматически в полном объёме
      независимо от того, за сколько часов до начала это произошло.
- [ ] AC-5.4: Возврат-исключение для отмены менее чем за 24 часа возможен только вручную
      через SUPERADMIN (US-2), не через самостоятельную отмену гостем.
- [ ] AC-5.5: Статус возврата (в процессе / завершён / отклонён) виден гостю и в карточке
      платежа у SUPERADMIN.

**Приоритет:** Must have — без прозрачной политики возвратов предоплата вызывает
недоверие и жалобы.

### US-6: Гость покупает абонемент PS Park онлайн

- **Как** гость парка (USER), постоянный посетитель PS Park
- **Я хочу** оплатить абонемент (пакет часов) онлайн по ссылке или QR-коду
- **Чтобы** не приезжать заранее только ради оплаты и получить абонемент сразу после оплаты

**Acceptance Criteria:**
- [ ] AC-6.1: Менеджер PS Park при оформлении абонемента может выбрать способ оплаты
      «Онлайн» (в дополнение к текущему способу «Оплачено на месте»).
- [ ] AC-6.2: При выборе «Онлайн» абонемент создаётся в статусе «Ожидает оплаты» — часы
      недоступны для списания, пока оплата не подтверждена.
- [ ] AC-6.3: Гостю отправляется ссылка на оплату (и/или показывается QR-код на стойке
      для сканирования телефоном).
- [ ] AC-6.4: После успешной оплаты абонемент автоматически переходит в статус «Активен»
      без дополнительных действий менеджера.
- [ ] AC-6.5: Если оплата не происходит в разумный срок (несколько часов), менеджер видит
      абонемент как «Не оплачен» и может отменить его или создать заново.
- [ ] AC-6.6: Существующий способ «Оплачено на месте» (менеджер вручную подтверждает
      получение наличных) продолжает работать без изменений — это не замена, а
      дополнительный вариант.
- [ ] AC-6.7: Автопродление абонемента по сохранённой карте — в этом релизе **не
      делается** (см. «Вне скоупа»); при первой покупке карта не сохраняется.

**Приоритет:** Should have — заметная ценность (упрощает продажу абонементов
удалённо и снижает риск «выписали, но не оплатили»), но PS Park продолжает штатно
работать через ручное подтверждение оплаты, если оплата online недоступна.

### US-7: Гость оплачивает счёт сессии PS Park онлайн по QR

- **Как** гость PS Park, завершающий игровую сессию
- **Я хочу** оплатить счёт сессии со своего телефона, отсканировав QR-код, без похода к
  терминалу
- **Чтобы** быстрее закрыть сессию и не стоять в очереди к кассе

**Acceptance Criteria:**
- [ ] AC-7.1: В окне закрытия счёта сессии («Завершить сессию») менеджер видит третий
      способ оплаты — «Оплатить онлайн (QR)» — рядом с существующими «Наличные» и «Карта».
- [ ] AC-7.2: При выборе «Оплатить онлайн» на экране показывается QR-код (и/или ссылка)
      на сумму счёта; гость сканирует и оплачивает со своего телефона.
- [ ] AC-7.3: После успешной оплаты счёт сессии автоматически закрывается на нужную
      сумму — менеджеру не нужно вручную отмечать «оплачено».
- [ ] AC-7.4: Как и сейчас, менеджер может комбинировать способы оплаты (часть наличными,
      часть онлайн) для одного счёта, если сумма разбита.
- [ ] AC-7.5: Если гость не оплачивает по QR в течение нескольких минут, менеджер может
      отменить ожидание и принять оплату другим способом (наличные/карта) без блокировки
      завершения сессии.

**Приоритет:** Should have — удобство и снижение очереди на кассе, но существующий
POS-путь полностью покрывает завершение сессии уже сегодня.

## Бизнес-правила (сквозные, не привязаны к одной story)

1. **Единственный источник истины по статусу оплаты — подтверждение от ЮKassa**, не факт
   возврата пользователя на сайт после оплаты. Пользователь может закрыть вкладку раньше
   времени — платформа обязана всё равно узнать финальный статус (см. AC-3.5, AC-4.4).
2. **Чек 54-ФЗ обязателен для каждого платежа.** Фискализация — силами ЮKassa («Чеки от
   ЮKassa»); собственная касса не подключается. Email или телефон плательщика — обязательное
   условие для запуска любой оплаты (беседки, абонемент, счёт сессии).
3. **Возврат всегда полный, частичных возвратов в интерфейсе в этом релизе нет.**
4. **Аренда офисов (B2B) не участвует в онлайн-оплате в этом релизе** — решение владельца,
   пересмотру не подлежит в рамках этой итерации.
5. **Онлайн-оплата не заменяет POS**, а дополняет его — если ЮKassa временно недоступна,
   парк продолжает принимать наличные/карту на месте без сбоев в остальных модулях.
6. **Все платежи и возвраты — по одной денежной сумме, без двойного списания.** Повторные
   попытки оплаты/возврата при сбое сети должны приводить к тому же результату, а не к
   повторному списанию/возврату.

## Приоритет (MoSCoW)

| Компонент | Категория | Обоснование |
|---|---|---|
| Фундамент модуля `payments` (US-1, US-2) | Must have | Без него ни один из пользовательских потоков невозможен; SUPERADMIN не сможет разобраться в спорных платежах и оформить исключение из политики возвратов. |
| Беседки — предоплата и возвраты (US-3, US-4, US-5) | Must have | Явный запрос владельца, первый и самый частый пользовательский поток; сегодня брони теряются из-за отсутствия онлайн-предоплаты. |
| Абонементы PS Park (US-6) | Should have | Заметно снижает риск «выписали — не оплатили» и разгружает менеджера, но PS Park продолжает работать через ручное подтверждение, если отложить. |
| PS Park QR по счёту сессии (US-7) | Should have | Удобство и меньше очередей у кассы, но POS полностью закрывает эту потребность уже сегодня. |

Несмотря на разные категории MoSCoW, все четыре части поставляются в одном релизе одним
PR — решение владельца зафиксировано в архитектурном плане (§ 9–10): фундамент неотделим
от первого пользовательского потока, а абонементы и PS Park QR используют ту же
инфраструктуру и не требуют отдельного релизного цикла. Категории MoSCoW здесь объясняют
**почему** каждая часть нужна и в каком порядке её стоит откатывать, если потребуется
сократить скоуп — не являются признаком отсрочки.

**Зависимости:**
- `gazebos`, `subscriptions`, `ps-park` — существующие модули, в которые встраивается
  оплата; их текущая POS-логика не переписывается, а получает дополнительный источник
  оплаты.
- `notifications` — новые события платежей идут через существующий диспетчер.
- Ключи ЮKassa (тестовый магазин уже есть; боевой магазин, прод-ключи и включение «Чеков
  от ЮKassa» в личном кабинете — организационные шаги владельца/бухгалтерии вне разработки,
  см. § 11 архитектурного плана).

## Вне скоупа

- **Аренда офисов B2B (rental / nedelovoy)** — решение владельца; арендаторы продолжают
  платить по банковским реквизитам с ручной отметкой менеджера.
- **Автопродление абонементов по сохранённой карте** — одобрено владельцем концептуально,
  но переносится на следующую итерацию после включения опции менеджером ЮKassa; в этом
  релизе абонемент оплачивается только разово.
- **Самостоятельные заказы кафе и оплата заказа онлайн** — отдельная фаза (см.
  архитектурный план § 5.5), не в этой итерации.
- **Докупки из меню кафе во время аренды беседки («room service»)** — отдельный концепт
  (архитектурный план § 5.6), оформляется отдельным PRD по отдельной команде владельца.
- **Частичные возвраты в интерфейсе** — API ЮKassa их умеет, но кнопки/формы для частичного
  возврата в этом релизе нет; только полный возврат.
- **Встроенный виджет оплаты (без ухода со страницы)** — используется редирект на страницу
  ЮKassa; встраивание виджета — полировка следующих итераций.
- **Двухстадийная оплата (холд/подтверждение менеджером)** — для беседок выбрана
  одностадийная схема (см. архитектурный план § 5.2); холд остаётся возможным
  архитектурно, но не включается в этой итерации.
- **Оплата другими валютами кроме рубля** — ЮKassa поддерживает только RUB, не актуально.
- **Изменение работы POS (наличные/карта на месте)** — существующий процесс для беседок и
  PS Park не меняется, онлайн-оплата дополняет его.

## Открытые вопросы для Architect

1. **TTL брони беседки vs. TTL платежа ЮKassa (~1 час).** PO предлагает синхронизировать
   их напрямую (бронь протухает ровно тогда же, когда протухает возможность оплаты) —
   Architect подтверждает реализуемость через `expiresAt` и cron.
2. **Что видит гость, если оплата не прошла (declined) сразу на странице ЮKassa.** PO
   ожидает понятное сообщение с возможностью попробовать другой способ оплаты в пределах
   того же окна ~1 часа, без создания новой брони — Architect уточняет, насколько это
   покрывается штатным поведением ЮKassa (повторная попытка на той же confirmation-странице).
3. **QR-код для абонементов и счёта сессии PS Park** — рисуется на фронтенде из
   `confirmationUrl` (стандартный QR-от-ссылки) или используется отдельный SBP QR-объект
   API ЮKassa. Влияет на то, что видит менеджер на экране (US-6, US-7).
4. **Единообразие статуса «Оплачивается» в UI** для всех трёх потоков (беседки, абонементы,
   PS Park-счёт) — общий компонент ожидания оплаты или три независимых. PO предпочитает
   общий компонент ради единообразия UX, финальное решение — за Architect.
