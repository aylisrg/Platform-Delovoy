## Как читать этот документ

Epic #442 — сводка из 7 независимых UX-пробелов админ-календаря беседок и Плей Парка, обнаруженных при переходе операторов с бумажного журнала на компьютер. Владелец при переквалификации issue в `auto:epic` (2026-08-14) явно потребовал: «каждый пункт при взятии в работу — отдельный PRD-запрос к PO и отдельный PR» — эпик не закрывается одним PR.

Этот PRD — единый документ по требованию оркестрации (`/plan-epic` разбирает PRD на дочерние задачи после), но **каждый User Story ниже самодостаточен**: своя проблема, свои AC, свой приоритет, своя метрика. Это сделано специально, чтобы decomposition-шаг мог превратить каждый US в отдельную дочернюю задачу/PR без дополнительного уточнения скоупа — именно то, чего требовал владелец.

Формат «одна user story = обе модуля» (а не 12 параллельных story) — тот же, что уже использовался в PRD `2026-08-13-gazebos-booking-safety-history-paid-prd.md` для той же пары модулей: беседки и Плей Парк намеренно построены на одной модели `Booking` и одном движке переходов статусов (`src/modules/booking/state-machine.ts`), поэтому фичи этого календаря почти всегда идентичны по поведению в обоих модулях, с точечными различиями, которые явно оговорены в AC.

## Проблема

### Контекст

Администраторы беседок и Плей Парка переходят с бумажного журнала бронирований на админ-панель (см. `docs/runbooks/booking-operator-guide.md`, план перезапуска P0/P1). Публичное бронирование и основной жизненный цикл брони (создание, оплата, чек-ин, отмена, история, статус оплаты) уже реализованы и последовательно доводятся до продакшена волнами P0/P1. Но сам инструмент — админ-календарь — на нескольких участках заметно беднее бумажного журнала, который он должен заменить:

- Журнал показывал сразу неделю вперёд; в панели — только один день за раз, листать приходится по одному дню.
- В журнале можно было переставить бронь одной пометкой; в панели перенос — это открыть карточку → «Изменить» → выбрать новое время → сохранить.
- Журнал можно было унести на смену/распечатать; в панели печатной версии дня нет вовсе.
- В журнале администратор от руки писал заметку о госте («аллергия», «просил доп. стол») и помнил его номер по памяти или блокноту; в панели поле для заметки визуально не существует, а телефон постоянного гостя каждый раз вводится с нуля, даже если гость уже бронировал раньше.
- Расширение парка (новая беседка, новый стол Плей Парка) в журнале — просто новая строка; в панели — обращение к разработчику, потому что кнопки «добавить» нет.

### Для кого это боль

- **MANAGER беседок и Плей Парка** — администраторы на смене, часто отвечающие на телефонные брони параллельно с другими задачами (см. прецедент `docs/requirements/2026-08-13-gazebos-booking-safety-history-paid-prd.md`: «...часто на телефоне, между звонками»). Каждый лишний клик или повторный ввод данных, которые журнал давал бесплатно, — прямая потеря скорости на смене.
- **SUPERADMIN (владелец)** — не может сам добавить новый ресурс без обращения к разработчику; не видит загрузку на неделю вперёд для планирования смен и закупок одним взглядом.

### Последствия для бизнеса

- Риск, что операторы вернутся к параллельному бумажному учёту (то, от чего платформа должна избавлять) там, где панель объективно неудобнее журнала.
- Потерянные детали брони (пожелания гостя), которые раньше фиксировались на бумаге, а в панели негде записать.
- Дублирующиеся карточки клиента из-за опечаток при повторном ручном вводе телефона постоянного гостя.
- Зависимость от разработчика для рутинной операционной задачи (добавить ресурс).

## Что уже реализовано (проверено по коду, важные расхождения с текстом issue)

Проверка кода `src/modules/gazebos/`, `src/modules/ps-park/`, `src/components/admin/gazebos/`, `src/components/admin/ps-park/`, `src/app/api/gazebos/`, `src/app/api/ps-park/`, `src/app/api/admin/clients/` показала, что часть утверждений в тексте issue №442 неточна. Ниже — по каждому из 7 пунктов эпика: что есть на самом деле.

1. **Недельный/месячный вид — подтверждено, не реализовано.** И `GazeboTimelineGrid`/`GazeboMobileTimeline`, и их зеркала в `ps-park`, показывают строго один день. Бэкенд (`getTimeline(date)`, `timelineQuerySchema`) тоже принимает только одну дату — расширение на диапазон дат требует изменений и на бэкенде, и на фронтенде, не только UI.

2. **Drag-and-drop — подтверждено, не реализовано, но безопасно наращивать.** `@dnd-kit` — уже зависимость проекта, но используется только в канбане задач и сделках аренды (`kanban-board.tsx`, `deal-kanban.tsx`), не в календаре бронирований. Хорошая новость: перенос брони (`rescheduleBooking`) уже проходит через серверную проверку конфликтов и advisory-lock (доработано в рамках P0-7, #429) — drag-and-drop добавляет только способ *вызвать* уже безопасный перенос, а не новую зону риска по данным.

3. **Печатный лист дня — подтверждено, не реализовано.** У кафе есть `print-button.tsx` (печать чека/заказа), но это другой печатный документ (одна позиция, не сводная таблица дня) — переиспользовать как есть нельзя, это другой формат.

4. **Автокомплит гостя по телефону — источник данных есть, но с архитектурной проблемой доступа.** `/api/admin/clients` (поиск по имени/email/телефону, contains-insensitive) существует, и телефонные брони уже создают/обновляют карточку клиента через `upsertClientByPhone` (сделано в P1) — данные для автокомплита есть. Проблема: этот эндпоинт закрыт `requireAdminSection(session, "clients")` — MANAGER, назначенный только на `gazebos`/`ps-park` (обычный профиль оператора беседок), получит 403 без отдельного назначения на модуль `clients`. Также эндпоинт возвращает полную CRM-агрегацию (сумма трат, история по всем модулям) — тяжелее, чем нужно для подсказки при вводе. Альтернатива без этой проблемы: у каждого модуля уже есть собственный, RBAC-чистый поиск по своим броням (`GET /api/gazebos/bookings?search=`, `bookingFilterSchema.search`, сделано в P1-9) — можно строить автокомплит по истории броней модуля, не трогая CRM-доступ вовсе. Оба варианта и их компромиссы — в разделе «Открытые вопросы для Architect».

5. **Комментарий и email в квик-форме — подтверждено частично, УТОЧНЕНИЕ по факту.** `adminCreateBookingSchema` (беседки) действительно уже принимает `comment` (до 500 символов) на уровне схемы — но ни десктопная форма (`quick-booking-popover.tsx`), ни мобильная (`mobile-booking-sheet.tsx`) это поле физически не рендерят: там только имя, телефон и кол-во гостей. `email` в `adminCreateBookingSchema` нет вовсе (есть только в публичной гостевой `createBookingSchema`). У Плей Парка (`adminCreatePSBookingSchema`) `comment` тоже есть в схеме, `email` нет нигде — тот же UI-пробел в обеих quick-формах (десктоп и мобильная).

6. **Причина отмены в админ-UI — ФАКТИЧЕСКИ УЖЕ РЕАЛИЗОВАНО, вычеркнуть из скоупа.** Issue описывает это как открытый пробел, но между датой issue (2026-08-10) и сегодня фича была доставлена отдельным PRD `docs/requirements/2026-08-13-gazebos-booking-safety-history-paid-prd.md` (US-2). Подтверждено в коде: `ConfirmDialog` (`src/components/admin/shared/confirm-dialog.tsx`) уже рендерит необязательное поле «Причина отмены» при отмене брони, подключено и в `GazeboBookingDetailCard`, и в PS Park `booking-detail-card.tsx`; PATCH-роут передаёт `reason` в `cancelBooking()`, который пишет `Booking.cancelReason`. **Разработка не нужна.** Единственное действие — регрессионный QA-чек, что поле по-прежнему работает, без нового PRD/PR.

7. **UI создания ресурса — подтверждено, и пробел БОЛЬШЕ, чем указано в issue.** Текст issue утверждает «POST /api/gazebos есть, кнопки «добавить» нет» — это неточно. Проверено: `src/app/api/gazebos/route.ts` содержит только `GET`, POST-обработчика нет вовсе. Сервисная функция `createResource()` в `service.ts` существует, но не вызывается ни одним роутом и не покрыта тестами — мёртвый код. `ResourceEditor` умеет только редактировать существующий ресурс, кнопки создания нигде нет. То же самое у Плей Парка (`createTable()` аналогично не подключена). Значит пробел — это отсутствие и API-роута, и UI, а не только UI.

**Итог:** из 7 пунктов эпика один (причина отмены) уже полностью закрыт и снимается со скоупа; для одного (создание ресурса) реальный объём работы больше заявленного в issue (нужен ещё и API-роут); для одного (автокомплит) есть нерешённый архитектурный вопрос про RBAC, который не решается только фронтендом. Ниже — 6 актуальных user story.

## Общий архитектурный вопрос: общие компоненты или дублирование по модулю?

Устоявшийся в проекте паттерн: доменный UI календаря (`timeline-grid.tsx`, `quick-booking-popover.tsx`, `mobile-timeline.tsx`, `mobile-booking-sheet.tsx`, `booking-detail-card.tsx`, `resource-editor.tsx`) полностью продублирован по модулю — у беседок и Плей Парка отдельные, независимо поддерживаемые копии почти идентичной логики. Только по-настоящему общие примитивы (диалоги, статус-бейджи, навигация по дате: `src/components/admin/shared/*`) вынесены в общий слой. Подтверждено дополнительно: тип `TimelineBooking` в `src/modules/gazebos/types.ts` и `src/modules/ps-park/types.ts` сегодня побайтово идентичен, включая комментарии в коде. `TimelineData` той же формы, но ссылается на по-разному выведенные типы ресурсов: `GazeboResource.pricePerHour` — сырой Prisma `Decimal | null`, у ps-park `TimelineResource.pricePerHour` — уже нормализованный `number | null`.

Этот эпик — уже третье по счёту крупное наращивание одной и той же дублированной сетки (день → неделя → drag-drod → печать). PO не предписывает техническое решение (это зона Architect), но фиксирует наблюдение: продолжать копировать — соответствует текущей конвенции проекта и дешевле сегодня, но стоимость дублирования растёт с каждой новой фичей календаря, а `TimelineBooking` уже идентичен между модулями (вынос без потери гибкости), `TimelineData` — той же формы, но потребует сначала свести Decimal-vs-number нормализацию `pricePerHour` между `GazeboResource`/`TimelineResource`, то есть не буквально бесплатен, но и не архитектурная преграда. Architect должен явно принять и задокументировать решение (продолжать дублировать по конвенции, либо вынести общий, параметризуемый по модулю календарный примитив сейчас) — не оставлять по умолчанию из инерции.

## User Stories

### US-1: Комментарий и email в быстрой форме бронирования

- **Как** менеджер беседок или Плей Парка, принимающий бронь по телефону
- **Я хочу** указать комментарий и (опционально) email гостя прямо в форме создания брони
- **Чтобы** не терять важные детали брони (пожелания гостя, особые условия) и иметь контакт для чека, если позже потребуется дистанционная оплата

**Acceptance Criteria:**
- [ ] AC-1: В десктопной quick-форме (`quick-booking-popover.tsx`, оба модуля) появляется необязательное поле «Комментарий» (текст, до 500 символов).
- [ ] AC-2: То же поле появляется в мобильной форме (`mobile-booking-sheet.tsx`, оба модуля) — паритет desktop/mobile обязателен.
- [ ] AC-3: В обеих формах, в обоих модулях появляется необязательное поле email с проверкой формата (некорректный email блокирует отправку с понятной ошибкой, пустое поле — нет).
- [ ] AC-4: У Плей Парка `adminCreatePSBookingSchema` и у беседок `adminCreateBookingSchema` получают поле `email` (сейчас есть только в гостевой публичной схеме беседок).
- [ ] AC-5: Указанный комментарий сохраняется при брони и виден в карточке брони и в ленте «История» (см. `docs/requirements/2026-08-13-...`), как и прочие детали брони.
- [ ] AC-6: Email не создаёт учётную запись и не является способом входа — используется только как контакт/для чека, по аналогии с гостевой публичной бронью.
- [ ] AC-7: Оба поля необязательны — их отсутствие не блокирует создание брони.

**Приоритет (MoSCoW): Should have.** Обоснование: дешёвая доработка (поле `comment` уже частично готово на уровне схемы беседок), прямая польза оператору на смене — не требует новой инфраструктуры, но не блокирует создание брони без себя.

**Метрики успеха:**
- Базовое: 0% админ-броней содержат комментарий (поля физически нет в форме).
- Целевое: ≥15% новых админ-броней за 4 недели после запуска содержат заполненный комментарий (не каждая бронь требует заметки — целимся в устойчивое использование, а не в 100%).

### US-2: Автокомплит гостя по телефону в быстрой форме

- **Как** менеджер беседок или Плей Парка
- **Я хочу**, чтобы при вводе телефона в quick-форме система подсказывала совпадающего гостя из уже известных клиентов
- **Чтобы** не переспрашивать имя постоянного гостя заново и не плодить дублирующиеся карточки клиента из-за опечаток при повторном ручном вводе

**Acceptance Criteria:**
- [ ] AC-1: После ввода нескольких цифр номера телефона форма показывает всплывающий список совпадающих гостей (имя + номер) без блокировки дальнейшего ввода.
- [ ] AC-2: Выбор гостя из списка подставляет в форму его имя и телефон; после подстановки оператор может отредактировать имя вручную (например, бронь оформляется на другого человека с тем же номером — семья/компания).
- [ ] AC-3: Если совпадений нет — форма ведёт себя как сегодня, полностью ручной ввод.
- [ ] AC-4: Автокомплит доступен MANAGER'у, у которого есть доступ только к модулю бронирования (`gazebos` или `ps-park`), без отдельного назначения на модуль `clients` — сегодняшняя реализация `/api/admin/clients` этого не гарантирует (см. «Открытые вопросы для Architect»), и это жёсткое требование, а не пожелание: иначе фича не будет работать для типичного оператора беседок/Плей Парка, у которого нет доступа к разделу CRM.
- [ ] AC-5: Поведение идентично для беседок и Плей Парка, для десктопной и мобильной формы.

**Приоритет (MoSCoW): Should have.** Обоснование: заметная экономия времени и снижение дублей клиентских карточек на каждой телефонной брони — а таких броней большинство у операторов; не блокирует создание брони, ручной ввод остаётся рабочим fallback.

**Метрики успеха:**
- Базовое: функции нет; 0% телефонных броней используют подсказку.
- Целевое: ≥40% админ-броней за 4 недели создаются с выбором гостя из автокомплита (у беседок/Плей Парка много повторных гостей — компаний и постоянных посетителей).
- Вторичная метрика: снижение темпа появления новых дублирующихся карточек клиента (замеряется через существующий инструмент merge в разделе «Клиенты») относительно 4 недель до запуска.

### US-3: Самостоятельное создание ресурса (беседка / стол)

- **Как** SUPERADMIN или менеджер с правом редактирования модуля
- **Я хочу** добавить новую беседку (или игровой стол Плей Парка) прямо в панели
- **Чтобы** вводить в строй новые ресурсы сразу после их физического появления в парке, не дожидаясь разработчика

**Acceptance Criteria:**
- [ ] AC-1: На странице расписания/ресурсов модуля появляется кнопка «Добавить беседку» / «Добавить стол».
- [ ] AC-2: Форма создания запрашивает те же поля, что и существующая форма редактирования (название, описание, вместимость, прайс будни/выходные, час/день); обязательно — только название.
- [ ] AC-3: После сохранения новый ресурс сразу отображается в сетке расписания и доступен для бронирования (в т. ч. публичного, если публичная бронь модуля включена) без отдельного деплоя.
- [ ] AC-4: Кнопка/форма создания видна только пользователям с правом редактирования модуля — как сегодня у редактирования ресурса; MANAGER без доступа к модулю её не видит.
- [ ] AC-5: Создание ресурса пишется в журнал аудита, как и редактирование существующего.
- [ ] AC-6: Появляется недостающий `POST /api/gazebos` (и аналог для Плей Парка), подключённый к уже существующей, но сейчас не используемой сервисной функции создания ресурса — без него UI создавать нечего.
- [ ] AC-7: Поведение идентично для беседок и Плей Парка.

**Приоритет (MoSCoW): Should have.** Обоснование: снимает зависимость от разработчика при расширении парка — редкое, но реальное операционное событие; сервисная функция и форма редактирования почти готовы, стоимость реализации ниже похожих по ценности пунктов.

**Метрики успеха:**
- Базовое: добавление ресурса требует тикета разработчику (часы-дни ожидания).
- Целевое: администратор добавляет новый ресурс самостоятельно за < 5 минут; 0 тикетов разработчику на добавление ресурса за квартал после запуска.

### US-4: Печатный лист дня

- **Как** менеджер на смене
- **Я хочу** распечатать (или сохранить в PDF) расписание на выбранный день в табличном виде
- **Чтобы** иметь офлайн-копию расписания — на случай нестабильного интернета/устройства, для передачи смены или для использования там, где нет удобного экрана — как раньше давал бумажный журнал

**Acceptance Criteria:**
- [ ] AC-1: На странице расписания (десктоп) есть кнопка «Печать» для текущего выбранного дня.
- [ ] AC-2: Печатная версия — табличный список: время, ресурс, имя гостя, телефон, статус, кол-во гостей/игроков, комментарий (после US-1) — без элементов интерфейса (кнопок, меню, попапов), читаемая на листе A4.
- [ ] AC-3: Строки в печатной версии отсортированы по времени начала (а не сгруппированы по ресурсу), чтобы читаться как журнал за день.
- [ ] AC-4: По умолчанию отменённые брони в печатную версию не попадают; есть явная опция включить их.
- [ ] AC-5: Поведение идентично для беседок и Плей Парка.

**Приоритет (MoSCoW): Should have.** Обоснование: прямая замена конкретного бумажного процесса, явно названного в исходном плане перезапуска целью миграции; данные уже есть в дневном timeline-запросе, реализация в основном фронтенд + печатные стили — недорого относительно ценности.

**Метрики успеха:**
- Базовое: 0% смен используют печатную версию (функции нет).
- Целевое: через 4 недели после запуска — фиксируем факт использования (клик «Печать» как прокси-метрика) и подтверждаем опросом операторов, что печатный лист используется вместо/наравне с бумажным журналом хотя бы частью смен.

### US-5: Недельный вид расписания

- **Как** менеджер или владелец
- **Я хочу** видеть расписание сразу на неделю вперёд
- **Чтобы** оценить загрузку и спланировать смены/закупки, не пролистывая по одному дню

**Acceptance Criteria:**
- [ ] AC-1: На странице расписания появляется переключатель «День / Неделя».
- [ ] AC-2: В недельном виде (десктоп) видно 7 дней и их брони по каждому ресурсу за один экран.
- [ ] AC-3: Клик по брони в недельном виде открывает ту же карточку брони, что и в дневном виде — переиспользуется существующий компонент, не создаётся вторая версия карточки.
- [ ] AC-4: Переключение недель вперёд/назад — по аналогии с сегодняшней навигацией по дням.
- [ ] AC-5: Поведение идентично для беседок и Плей Парка.
- [ ] AC-6: Быстрое создание брони кликом по свободному слоту в недельном виде — необязательно для первой итерации; минимально допустимо, что клик по свободному времени в недельном виде переводит в дневной вид на нужный день/ресурс для создания (см. «Вне скоупа»).

**Приоритет (MoSCoW): Should have — с оговоркой по готовности.** Явный, прямо озвученный запрос операторов («бумажный журнал давал неделю сразу»), но это архитектурно самая тяжёлая позиция эпика: и бэкенд (`getTimeline` принимает одну дату), и сама сетка (`timeline-grid.tsx`, абсолютное позиционирование в процентах от границ одного дня) рассчитаны на один день, не на диапазон. По готовности к немедленной разработке эта story идёт после US-1/US-2/US-3/US-4 — требует предварительного архитектурного решения (см. «Открытые вопросы»).

**Метрики успеха:**
- Базовое: операторы просматривают расписание только по одному дню за раз (переключателя нет).
- Целевое: ≥30% визитов на страницу расписания используют недельный вид в течение 4 недель после запуска — сигнал реального использования, а не просто наличия кнопки.

### US-6: Drag-and-drop перенос и растяжение брони

- **Как** менеджер, работающий с сеткой расписания на десктопе
- **Я хочу** перетащить бронь на другое время/ресурс или растянуть её край мышью
- **Чтобы** менять время брони быстрее, чем через форму редактирования (открыть карточку → «Изменить» → выбрать новое время → сохранить)

**Acceptance Criteria:**
- [ ] AC-1: В дневном виде сетки (десктоп, мышь) бронь можно перетащить в другую ячейку — другое время и/или другой ресурс в пределах того же модуля.
- [ ] AC-2: Растягивание правого края брони меняет время окончания.
- [ ] AC-3: Перенос, создающий конфликт с уже существующей активной бронью на новом месте, блокируется с понятным сообщением о причине — переиспользуется существующая серверная проверка конфликтов (`rescheduleBooking`), а не создаётся отдельная клиентская проверка, которой можно доверять меньше.
- [ ] AC-4: После успешного переноса срабатывают те же побочные эффекты, что и при переносе через форму (обновление события Google Calendar, уведомление гостю/каналу) — без дублирования этой логики отдельно для drag-and-drop.
- [ ] AC-5: Перенос между ресурсами возможен только внутри одного модуля (нельзя перетащить бронь беседки на стол Плей Парка).
- [ ] AC-6: В первой итерации drag-and-drop работает только в десктопной (мышь) сетке. Мобильный/сенсорный таймлайн (`mobile-timeline.tsx`) в этой итерации не меняется — перенос там остаётся через форму редактирования. Обоснование — задокументированный профиль операторов («часто на телефоне», PRD 2026-08-13): жест перетаскивания на мелкой сенсорной временной сетке менее надёжен, чем контролируемая форма, и риск случайного переноса выше пользы.
- [ ] AC-7: Первая итерация — только беседки; распространение на Плей Парк — отдельная задача после подтверждения ценности на беседках.

**Приоритет (MoSCoW): Could have.** Обоснование: ценность реальна (быстрее правки на десктопе), но ниже, чем у остальных пунктов эпика, для преимущественно мобильной аудитории операторов; безопасность данных не под риском (перенос уже защищён существующей серверной проверкой конфликтов), риск — стоимость реализации (интеграция `@dnd-kit` с сеткой на абсолютном процентном позиционировании — не тривиальная, оценка сложности за Architect) и вероятность случайных срабатываний на touch-экранах, которые эта итерация явно исключает.

**Метрики успеха:**
- Базовое: 0 переносов через drag (функции нет), 100% переносов — через форму редактирования.
- Целевое: ≥20% переносов брони в десктопной сетке беседок за первые 4 недели выполняются через drag-and-drop; 0 инцидентов двойного бронирования, вызванных переносом (гарантируется переиспользованием существующего конфликт-чека, а не новой логикой).

## Вне скоупа

- **Месячный вид расписания.** В тексте issue «недельный/месячный» перечислены через слэш как альтернативы, а не как двойное требование. Месяц физически нечитаем на часовом уровне детализации текущей сетки и отдельно не запрошен — не входит в v1. Отдельный PRD можно поставить, если после недельного вида появится явный запрос.
- **Drag-and-drop на мобильном/сенсорном таймлайне и в Плей Парке.** V1 — только десктопная сетка беседок (US-6, AC-6/AC-7).
- **Быстрое создание брони кликом по свободному слоту в недельном виде.** Опционально; минимум v1 — переход в дневной вид на нужный день/ресурс.
- **Печать/экспорт за диапазон дат (неделя целиком).** V1 — только один день за раз.
- **Массовый (bulk) drag нескольких броней одновременно.** V1 — одна бронь за операцию.
- **Пересмотр модульного RBAC целиком** для решения задачи автокомплита (US-2) — только минимально необходимое расширение доступа к данным гостя для этой конкретной задачи, не полный редизайн `hasModuleAccess`/`requireAdminSection`.
- **Бэкфилл исторических бумажных записей задним числом.** Отдельный, уже существующий вопрос из P1 (пункт 11 плана перезапуска, «по решению владельца») — не часть этого PRD.
- **Причина отмены брони в админ-UI.** Не разрабатывается — уже полностью реализовано (см. «Что уже реализовано», пункт 6). Указано явно, чтобы шаг декомпозиции эпика не завёл по этому пункту дублирующую задачу.
- **Изменение самой модели `Booking`/жизненного цикла статусов** — все 6 story реализуются поверх существующей модели бронирования, без новых полей БД сверх минимально необходимых (если такие появятся — решение Architect).

## Открытые вопросы для Architect

1. **RBAC для автокомплита (US-2).** Два пути с разными компромиссами: (а) скорректировать доступ к `/api/admin/clients` так, чтобы MANAGER модуля `gazebos`/`ps-park` мог им пользоваться без отдельного назначения на модуль `clients` (даёт доступ к каноническим карточкам клиента, включая кросс-модульную историю, но требует пересмотра текущего RBAC-гейта и веса ответа — эндпоинт сейчас тянет полную CRM-агрегацию); (б) построить автокомплит поверх уже RBAC-чистого поиска каждого модуля по собственным броням (`GET /api/{module}/bookings?search=`, доступен MANAGER'у своего модуля уже сегодня), с дедупликацией по телефону на выдаче — не трогает CRM-доступ вовсе, но не даёт видимости кросс-модульной истории гостя внутри формы. PO не предписывает выбор, но требует, чтобы выбранный путь удовлетворял AC-4 (US-2): типичный оператор без доступа к разделу «Клиенты» должен получить работающую подсказку.
2. **Архитектура недельного вида (US-5).** Расширять `getTimeline(date)`/`timelineQuerySchema` до диапазона дат одним запросом, или делать с клиента несколько параллельных вызовов уже существующего дневного эндпоинта; и — можно ли переиспользовать текущий процентно-позиционированный `timeline-grid.tsx` (расширив на 7 колонок дней), или нужен принципиально другой макет с потерей части часовой детализации ради читаемости недели. Решение и его обоснование — за Architect.
3. **Общий календарный компонент или дублирование по модулю** (см. раздел «Общий архитектурный вопрос» выше) — Architect явно фиксирует решение, не оставляет по умолчанию/инерции, учитывая, что `TimelineBooking` у обоих модулей уже идентичен, а `TimelineData` идентичен по форме, но требует сначала свести Decimal-vs-number нормализацию `pricePerHour` между типами ресурсов.
4. **Технический подход к drag-and-drop (US-6)** поверх сетки с абсолютным процентным позиционированием (а не CSS Grid/Flex-ячейками) — `@dnd-kit` уже в зависимостях проекта, но может понадобиться дополнительный слой перевода координат drag-события в конкретную ячейку время/ресурс. Оценка сложности — за Architect.
5. **Порядок декомпозиции для `/plan-epic`.** PO-рекомендация (не жёсткое требование): US-1, US-2, US-3, US-4 — независимы друг от друга и не требуют предварительного архитектурного дизайна, готовы к немедленной нарезке на отдельные PR-задачи. У US-2 есть открытый вопрос №1 (RBAC-развилка для автокомплита) — в отличие от US-5/US-6, её AC не меняются от выбора пути, поэтому это не блокирует декомпозицию: решение принимается внутри штатного Architect-шага самой дочерней задачи US-2, а не заранее. US-5 и US-6 требуют архитектурного решения по вопросам 2–4 выше до того, как их AC можно довести до PR-размера — имеет смысл выделить их в отдельный architecture-spike перед декомпозицией на реализацию.
