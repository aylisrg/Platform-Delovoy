# PRD: Engagement Sprint — активация пользователей и аналитика воронки

**Дата:** 2026-04-30
**Автор:** Product Owner
**Статус:** Ready for Architect
**Источник:** `docs/analytics/2026-04-30-engagement-audit.md`, `docs/product/2026-04-30-engagement-hypotheses.md`

---

## Контекст и проблема

Платформа запущена 14 апреля 2026. Первый аудит после запуска выявил три системных проблемы, которые мешают пользователям самостоятельно взаимодействовать с платформой:

1. **67% броней создаёт администратор** вместо пользователя. Пользователь после регистрации оказывается в тупике — публичный личный кабинет `/profile` не реализован (Phase 2, технический долг).
2. **60% уведомлений не доходят** (39% SKIPPED, 21% FAILED). Ни один USER-аккаунт не привязал Telegram — флоу привязки не существует.
3. **Аналитика слепая**: нет поля `source` в `Booking` (web/bot/admin), `cancelReason` не собирается при отмене. Невозможно принимать data-driven решения о развитии каналов.

Все три проблемы решаемы в одном спринте. Решение H1 (профиль) разблокирует онбординг; H3 (Telegram-привязка) закрывает доставляемость уведомлений; H5+H4 (схемные фиксы) дают данные для следующей итерации.

## Фича 1: Публичный личный кабинет USER (`/profile`)

### Проблема

После sign-in пользователь оказывается на главной странице без контекста. Нет страницы "мои брони", "мои заказы", "мои данные". Единственная альтернатива — Telegram Mini App, которая требует отдельного действия (открыть бота). Это создаёт барьер активации: пользователь не видит ценности платформы после первой регистрации.

### Решение

Минималистичная страница `/profile` для авторизованного USER с тремя блоками: контактная информация, история бронирований (с возможностью отмены), быстрые ссылки на модули.

### Целевая аудитория

USER — арендаторы офисов, геймеры PS Park, компании, бронирующие беседки.

### User Stories

#### US-1: Просмотр истории бронирований

- **Как** зарегистрированный пользователь (USER)
- **Я хочу** зайти на страницу `/profile` после авторизации и увидеть список своих бронирований (беседки, PS Park)
- **Чтобы** убедиться, что моя бронь принята, и отменить её при необходимости без звонка менеджеру

**Acceptance Criteria:**
- [ ] AC-1: Страница `/profile` доступна только авторизованным пользователям; неавторизованный пользователь редиректируется на `/signin`
- [ ] AC-2: На странице отображается список всех бронирований USER, отсортированный по дате (новые первые)
- [ ] AC-3: Каждая строка содержит: модуль (беседка/PS Park), название ресурса, дату, время, статус (PENDING / CONFIRMED / CANCELLED / COMPLETED)
- [ ] AC-4: Бронирования со статусом PENDING или CONFIRMED имеют кнопку "Отменить"
- [ ] AC-5: При нажатии "Отменить" открывается диалог с обязательным выбором причины (dropdown: "Изменились планы", "Нашёл другое время", "Ошибся при бронировании", "Другое" + поле ввода)
- [ ] AC-6: После отмены статус бронирования в списке обновляется без перезагрузки страницы
- [ ] AC-7: Если бронирований нет — отображается пустое состояние с CTA "Забронировать беседку" и "Забронировать PS Park"

#### US-2: Просмотр и редактирование контактных данных

- **Как** зарегистрированный пользователь (USER)
- **Я хочу** видеть своё имя, email и телефон на странице профиля и иметь возможность их обновить
- **Чтобы** платформа знала, как со мной связаться, и уведомления доходили

**Acceptance Criteria:**
- [ ] AC-1: На странице профиля отображаются: имя, email (если есть), телефон (если есть)
- [ ] AC-2: Пользователь может отредактировать имя и телефон (email — только для отображения, не редактируется если это идентификатор входа)
- [ ] AC-3: При сохранении данные обновляются в `User` через `PATCH /api/profile`
- [ ] AC-4: Валидация: телефон — формат +7XXXXXXXXXX, имя — минимум 2 символа

#### US-3: Блок привязки Telegram

- **Как** зарегистрированный пользователь (USER)
- **Я хочу** видеть на странице профиля статус привязки Telegram и кнопку для привязки аккаунта
- **Чтобы** получать уведомления о бронированиях в Telegram, а не пропускать их

**Acceptance Criteria:**
- [ ] AC-1: Если Telegram не привязан — отображается блок "Подключить Telegram" с инструкцией и кнопкой/ссылкой
- [ ] AC-2: Клик на кнопку открывает ссылку на бота с одноразовым токеном (`t.me/DelovoyPark_bot?start=link_XXXXXXXX`)
- [ ] AC-3: После успешной привязки через бота страница `/profile` показывает "Telegram подключён: @username"
- [ ] AC-4: Привязка отображается без перезагрузки страницы (polling или WebSocket — решение на усмотрение архитектора)

### Приоритет (MoSCoW)

**Must have.** Без публичного профиля пользователь не видит ценности регистрации через веб. US-1 и US-3 закрывают два критических барьера активации. US-2 — should have внутри этой фичи.

**Зависимости:** модули `profile` (частично существует — `/api/profile/*`), `booking`, `auth`, `notifications` (для токена привязки Telegram).

### Метрики успеха

- Базовое: 33% бронирований создаются USER самостоятельно
- Целевое через 4 недели после деплоя: >60% бронирований создаются USER самостоятельно
- Базовое: 0% USER с привязанным Telegram
- Целевое через 4 недели: >30% USER с привязанным Telegram

### Вне скоупа

- История заказов кафе (отдельная итерация, зависит от кафе-модуля)
- Push-уведомления в браузере
- Удаление аккаунта
- Смена email / смена способа входа
- Программа лояльности (Phase 5.1)
- Публичный профиль для просмотра другими (нет такой потребности)

## Фича 2: Onboarding-флоу привязки Telegram к web-аккаунту

### Проблема

Telegram-бот (@DelovoyPark_bot) работает, но существует отдельно от web-аккаунтов. 0 из 12 USER-аккаунтов имеют привязанный `telegramId`. Архитектура channel-agnostic уведомлений реализована (Phase 5.4), но без привязанного канала 39% уведомлений уходят в SKIPPED. Пользователь не получает подтверждение брони — теряет уверенность в транзакции — отменяет.

Флоу привязки должен существовать на двух уровнях: в вебе (блок в профиле, описан в US-3 выше) и в боте (команда `/connect` или deep-link с одноразовым токеном).

### Решение

One-time token флоу: веб генерирует одноразовый токен (TTL 10 минут), встроенный в deep-link на бота. Пользователь переходит по ссылке в Telegram, бот активирует токен, и `telegramId` привязывается к web-аккаунту. Аналогичный механизм уже реализован в ветке `fix/bot-to-web-login-bot-side` для обратного направления (bot → web). Нужно реализовать web → bot направление.

### Целевая аудитория

USER — все, кто зарегистрирован в вебе.

### User Stories

#### US-4: Привязка Telegram из веб-профиля

- **Как** пользователь веб-платформы (USER)
- **Я хочу** нажать "Подключить Telegram" в профиле и за 3 шага связать свой Telegram-аккаунт
- **Чтобы** получать уведомления о бронированиях и не беспокоиться, дошло ли подтверждение

**Acceptance Criteria:**
- [ ] AC-1: API `POST /api/profile/telegram-link` генерирует одноразовый токен и возвращает deep-link вида `https://t.me/DelovoyPark_bot?start=link_<token>`
- [ ] AC-2: Токен действителен 10 минут; после использования — невалиден
- [ ] AC-3: При переходе по deep-link бот проверяет токен, связывает `telegramId` пользователя Telegram с `userId` в БД, отвечает: "Ваш Telegram привязан к аккаунту в системе бизнес-парка Деловой."
- [ ] AC-4: Если токен истёк — бот отвечает: "Ссылка устарела. Вернитесь в профиль и получите новую."
- [ ] AC-5: После привязки `User.telegramId` заполнен; `NotificationPreference` создаётся с `channel=TELEGRAM` как основным каналом
- [ ] AC-6: В `AuditLog` записывается действие `profile.telegram_linked` с `userId`

#### US-5: Защита от повторного использования токена и конфликтов

- **Как** система
- **Я хочу** гарантировать, что один токен привязывает только один аккаунт и не может быть использован повторно
- **Чтобы** исключить ситуацию, когда чужой Telegram привязывается к чужому профилю

**Acceptance Criteria:**
- [ ] AC-1: Токен — минимум 32 символа, cryptographically random
- [ ] AC-2: Попытка использовать уже использованный токен возвращает ошибку и не меняет `telegramId`
- [ ] AC-3: Если `telegramId` уже привязан к другому `userId` — операция отклоняется, бот сообщает: "Этот Telegram уже привязан к другому аккаунту. Обратитесь к администратору."
- [ ] AC-4: Rate limit на `POST /api/profile/telegram-link`: не более 3 токенов в 15 минут на пользователя

### Приоритет (MoSCoW)

**Must have.** Без привязки Telegram channel-agnostic архитектура Phase 5.4 не даёт результата. 39% SKIPPED уведомлений — прямое следствие отсутствия этого флоу. Фича разблокирует: уведомления о бронировании, снижение cancel rate, ретеншн через проактивные сообщения.

**Зависимости:** `notifications` (Phase 5.4 — реализован), `profile` (частично есть), `bot` (требует обработчика deep-link).

### Метрики успеха

- Базовое: 0% USER с привязанным Telegram, 39% уведомлений SKIPPED
- Целевое через 4 недели: >30% USER с привязанным Telegram, <10% уведомлений SKIPPED

### Вне скоупа

- Привязка WhatsApp, email как каналов (Phase 5.4 next iterations)
- Автоматическая привязка при регистрации через Telegram OAuth (другой флоу)
- Push web-уведомления
- Уведомления в SMS

## Фича 3: Поля `source` и `cancelReason` в бронированиях (Schema & UI fixes)

### Проблема

Два поля отсутствуют или не используются в схеме `Booking`:

1. **`source`** — нет поля, различающего web / bot / admin. Без него невозможно оценить эффективность каналов и обоснованно вкладывать усилия в развитие веб-воронки или бота.
2. **`cancelReason`** — поле в схеме есть, но ни один UI-компонент не запрашивает его при отмене. 100% отмен имеют пустую причину. Высокий cancel rate беседок (66.7%) невозможно диагностировать без этих данных.

### Решение

Два минимальных изменения: (a) добавить поле `source` в схему `Booking` с дефолтом `web`, заполнять при создании через бот значением `bot`, при ручном вводе менеджером — `admin`; (b) сделать обязательным выбор причины при отмене через UI (dropdown + опциональный текст).

### Целевая аудитория

Данные используются SUPERADMIN и MANAGER для анализа. UI изменения затрагивают USER при отмене.

### User Stories

#### US-6: Атрибуция канала создания бронирования

- **Как** суперадмин и менеджер
- **Я хочу** видеть, через какой канал создано каждое бронирование (веб, бот, ввод менеджером)
- **Чтобы** понять, какой канал конвертирует лучше, и приоритизировать инвестиции в UX

**Acceptance Criteria:**
- [ ] AC-1: Схема `Booking` содержит поле `source` с типом enum `BookingSource: WEB | BOT | ADMIN` и дефолтом `WEB`
- [ ] AC-2: При создании брони через веб (`POST /api/gazebos/book`, `/api/ps-park/book`) поле `source` = `WEB`
- [ ] AC-3: При создании брони через Telegram-бота поле `source` = `BOT`
- [ ] AC-4: При ручном создании менеджером или SUPERADMIN поле `source` = `ADMIN`
- [ ] AC-5: В панели менеджера список бронирований отображает столбец "Канал" (web/бот/вручную)
- [ ] AC-6: Миграция корректно проставляет `ADMIN` на существующие записи с `booking.admin_create` в AuditLog, `WEB` на остальные

#### US-7: Сбор причины отмены бронирования

- **Как** пользователь, который хочет отменить бронирование
- **Я хочу** указать причину отмены при нажатии "Отменить"
- **Чтобы** администрация могла улучшить сервис на основе реальных причин

**Acceptance Criteria:**
- [ ] AC-1: При отмене бронирования через веб (профиль или страницу модуля) открывается диалог с обязательным выбором причины
- [ ] AC-2: Варианты причин: "Изменились планы", "Нашёл другое время", "Ошибся при бронировании", "Слишком дорого", "Другое"
- [ ] AC-3: При выборе "Другое" отображается текстовое поле (необязательное, max 200 символов)
- [ ] AC-4: Кнопка "Подтвердить отмену" неактивна до выбора причины из списка
- [ ] AC-5: `cancelReason` сохраняется в БД при отмене; при отмене менеджером через панель — допустимо сохранять "Отменено администратором"
- [ ] AC-6: В панели менеджера для отменённых броней отображается причина отмены

### Приоритет (MoSCoW)

**Must have** (US-6 — `source`): одна миграция, минимальный effort, критичная аналитическая ценность. Без атрибуции канала все продуктовые решения — интуиция.

**Should have** (US-7 — `cancelReason`): небольшой UI-компонент, но открывает диагностику главной операционной проблемы (66.7% cancel rate беседок).

**Зависимости:** модули `booking`, `gazebos`, `ps-park`, `profile` (US-7 в контексте страницы профиля).

### Метрики успеха

- Базовое: 0% бронирований с заполненным `source`, 0% отмен с заполненным `cancelReason`
- Целевое через 2 недели после деплоя: 100% новых бронирований содержат `source`, 100% отмен через UI содержат `cancelReason`
- Аналитическая цель: через 4 недели — данные по каналам позволяют сделать вывод о приоритете (web vs bot)

### Вне скоупа

- Автоматический возврат средств при определённых причинах отмены
- Email пользователю с вопросом о причине отмены
- A/B тест вариантов причин
- Агрегированные отчёты по причинам (следующая итерация аналитики)

## PO — Ключевые решения

1. **Не берём H7 (funnel events) в этот спринт.** Добавление серверных funnel-событий — отдельная итерация. Yandex Metrika уже подключена server-side; если нужна когортная аналитика в БД, это PRD для Phase 5.3.

2. **F1 и F2 связаны:** US-3 (блок Telegram в профиле) — пересечение фич. Архитектору нужно убедиться, что они реализуются в одном PR или с явной зависимостью.

3. **Модуль `profile` уже частично существует** (`src/modules/profile/`, `/api/profile/*` — API контактов USER). F1 расширяет его, не создаёт заново. SUPERADMIN не затрагивается.

4. **Миграция `source`**: дефолт `WEB` для новых записей; для исторических — `ADMIN` если в AuditLog есть `booking.admin_create` для этого `bookingId`, иначе `WEB`. Архитектор уточняет механику.

5. **Бот-часть F2**: в текущей ветке `fix/bot-to-web-login-bot-side` уже есть механика one-time токенов для обратного направления. F2 использует аналогичную механику — архитектор может переиспользовать.
