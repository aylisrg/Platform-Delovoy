# PRD: Ролевой ребилд Telegram Mini App «Деловой»

**Версия:** 1.0
**Дата:** 2026-08-13
**RUN_ID:** 2026-08-13-miniapp-role-rebuild
**Статус:** Готов к передаче Architect
**Автор:** Product Owner

---

## Проблема

Владелец сформулировал три отдельные, но связанные боли по Telegram Mini App (`@DelovoyPark_bot`, `src/app/webapp/`):

### 1. Нет уровней доступа

Сегодня Mini App одинаковый для всех: обычный гость парка и сотрудник с админ-правами видят один и тот же набор разделов. Роль пользователя (`User.role`) технически уже доезжает до Mini App (в JWT и в контексте `TelegramProvider`), но используется только как текстовая подпись на экране профиля — ни один раздел, таб или экран не ветвится по роли. Административной поверхности в Mini App нет вообще.

Хуже того, единственный сегодняшний способ для сотрудника управлять уведомлениями — переключатель "🚀 Релизы" в команде `/settings` бота — пускает `SUPERADMIN`/`MANAGER`, но **не пускает `ADMIN`** (`bot/handlers/team-settings.ts`, `getTeamUser()`: `if (user.role !== "SUPERADMIN" && user.role !== "MANAGER") return null;`). Роль `ADMIN` в этой системе полноценно администрирует Барбекю Парк, Плей Парк и Склад (`ADMIN_EDITABLE_MODULES`) и может получать `AdminPermission` на любые другие разделы — но по уведомлениям остаётся "невидимкой".

Также в текущей навигации есть таб («Чаты» — Мессенджер), который виден всем, но фактически работает только при наличии NextAuth-веб-сессии, которой у чистого Mini App пользователя нет — тап ведёт в тупик привязки аккаунта (сама привязка тоже сломана: OTP-код только логируется в консоль, не отправляется).

### 2. Дубли системных сообщений о релизах

Владелец получает по несколько по-разному сформулированных сообщений об одном и том же деплое. Расследование подтвердило точный механизм (проверено чтением `.github/workflows/deploy.yml` и `src/modules/notifications/release-notify.ts`):

- Guard "не анонсировать уже анонсированную версию" (`deploy.yml:703`) проверяет наличие файла `docs/releases/<version>-*.md`, который должен закоммититься архивным пушем в защищённую ветку `main` — но такой пуш в защищённую ветку всегда молча отваливается (`git push origin HEAD || true` глотает ошибку). Файла никогда нет → **каждый обычный деплой, не только релизный, заново анонсирует "новый релиз"**.
- На один успешный деплой существует два независимых анонсера: групповое "✅ Deploy OK" (`deploy.yml:673`) и личное сообщение о релизе каждому подписчику (`deploy.yml:685` → `sendReleaseNotification()`). Владелец состоит в обоих адресных пространствах — получает 2 разных по тексту сообщения об одном событии в силу самой конструкции.
- `workflow_run` + `push` могут запустить `deploy.yml` дважды на один и тот же коммит; `cancel-in-progress: false` не отменяет второй запуск.
- `sendReleaseNotification()` шлёт напрямую по `user.telegramId`, минуя очередь/дедуп-стек уведомлений (`OutgoingNotification`, `dedupKey`) — у него нет серверной идемпотентности "версия X уже отправлена".

### 3. Дизайн

Текущий UI — захардкоженные градиентные карточки с эмодзи вперемешку с SVG-иконками, статичные CSS-переменные `--tg-*`, не привязанные к реальной теме Telegram пользователя (`themeParams`), нет поддержки тёмной темы. `TelegramProvider` уже частично умеет читать `themeParams`/`colorScheme`/haptics — но большинство экранов их не используют.

---

## Решение

Дать Mini App три уровня контента вместо одного: обычный гость парка видит простую ленту + сервисы + кафе; сотрудник (`MANAGER`/`ADMIN`/`SUPERADMIN`) дополнительно получает "Центр уведомлений" — экран выбора, какие типы событий по каким разделам приходят лично ему, ограниченный его реальными правами доступа. Устранить дубли релизных сообщений через серверную идемпотентность на уровне версии и единый источник правды для предпочтения "уведомления о релизах". Переработать визуальный слой на нативной теме Telegram.

Ничего из этого не требует нового модуля: используем существующий модуль `notifications` (таблицы `NotificationEventPreference`, `UserNotificationChannel`, `OutgoingNotification`, таксономию `EVENT_ROUTING`/`ROUTING_CATEGORIES`) и существующий слой `src/app/webapp/` + `src/app/api/webapp/`.

## Технический контекст: что переиспользуем и границы скоупа

**Уже есть, не изобретаем заново:**
- Роль в JWT Mini App (`/api/webapp/auth`, `TelegramProvider`) — фундамент ролевого рендера уже есть, просто не используется.
- `NotificationEventPreference` (userId + eventType, enabled, channelKinds, quiet hours) — точечные предпочтения по типу события. Именно на неё опирается Центр уведомлений, а не на legacy `NotificationPreference.notifyReleases`.
- `UserNotificationChannel` + `OutgoingNotification` (dedupKey) + `dispatch()` — очередь доставки с дедупом и ретраями уже существует и работает для booking/order-событий.
- `ROUTING_CATEGORIES` (`src/modules/notifications/routing-categories.ts`) — категория `system` уже объявлена, но нигде не используется; `EVENT_ROUTING` (`events.ts`) не содержит типов `system.deploy`/`system.release` — их предстоит ввести.
- `src/lib/permissions.ts` — `hasAdminSectionAccess`, `getUserAdminSections`, `ADMIN_SECTIONS`, `hasRole` — готовые хелперы для правила "категория видна, только если есть доступ к разделу".
- Существующий инструмент рассылок (`/admin/notifications/broadcast`, `BroadcastCampaign`) — источник контента для ленты новостей; новый инструмент создания контента не нужен.
- Публичные API `cafe`/`gazebos`/`ps-park` (меню, бронирование, гостевой QR-чекаут с оплатой) — переиспользуются как есть.

**Жёсткие границы скоупа (обязательны для Architect):**
1. Новый модуль в `src/modules/` не создаётся. "Новости" — это не модуль, а поверхность над `BroadcastCampaign`/`OutgoingNotification`. Центр уведомлений — поверхность существующего модуля `notifications`.
2. Затронутые области: `notifications` (модуль) + `src/app/webapp/` + `src/app/api/webapp/` + точечно `bot/handlers/team-settings.ts` (см. US-6) + `.github/workflows/deploy.yml`. Итого не более 4-5 поверхностей — держим PR под правилом "5+ модулей → NEEDS_CHANGES".
3. Модули `gazebos`, `ps-park`, `cafe` не трогаем на уровне `service.ts`/`validation.ts` — только их существующие публичные API.
4. Только аддитивные миграции БД (новые таблицы/колонки). Никаких `DROP`/удаления колонок — если что-то выводим из употребления (например, `NotificationPreference.notifyReleases`), колонка остаётся, просто перестаёт быть единственным источником правды.

## Персоны и уровни доступа

| Персона | Кто | Что видит в Mini App |
|---|---|---|
| **USER** | Гость парка, арендатор без админ-прав, геймер Плей Парка | Главная (лента), Кафе, Барбекю Парк, Плей Парк, Мои брони, Профиль с простыми уведомлениями (брони/заказы/напоминания). Ничего сотруднического. |
| **MANAGER** | Сотрудник, назначенный на конкретные модули/секции | Всё, что видит USER, **плюс** Центр уведомлений, ограниченный секциями, на которые у него есть `AdminPermission`/`ModuleAssignment`. |
| **ADMIN** | Сотрудник с расширенными правами (по роли — Барбекю Парк/Плей Парк/Склад, плюс выданные секции) | То же самое, что MANAGER — Центр уведомлений строится по тем же правилам доступа, **без исключения по роли**, которое есть сегодня в боте. |
| **SUPERADMIN** | Владелец/управляющий парка | Всё вышеперечисленное плюс категория "Системные" (деплой/релизы/мониторинг) по умолчанию доступна, плюс обязательные CRITICAL-алерты инфраструктуры (не отключаемые через Центр уведомлений). |

## User Stories

### US-1: Ролевая навигация и безопасный вход

**Как** пользователь Mini App любой роли, **я хочу** видеть только те разделы, которые мне доступны и реально работают, **чтобы** не натыкаться на тупики и не путать личный кабинет гостя с рабочим инструментом сотрудника.

**Acceptance Criteria:**
- [ ] AC-1.1: Состав разделов главной навигации однозначно определяется ролью пользователя (USER/MANAGER/ADMIN/SUPERADMIN), а не одинаков для всех.
- [ ] AC-1.2: USER может из навigации попасть ровно в: Главная, Кафе, Барбекю Парк, Плей Парк, Мои брони, Профиль — без пунктов, которые ему не нужны или не работают. Точная группировка разделов по табам/меню — решение дизайна (US-7), не фиксируется здесь.
- [ ] AC-1.3: MANAGER, ADMIN и SUPERADMIN дополнительно видят вход в Центр уведомлений (US-5) из Профиля — единообразно для всех трёх ролей, без исключения по роли.
- [ ] AC-1.4: Раздел «Чаты» (Мессенджер), сегодня ведущий в тупик привязки аккаунта для чистого Mini App пользователя, не показывается в навигации, пока переход не станет технически рабочим внутри Mini App-сессии (см. «Вне скоупа»).
- [ ] AC-1.5: Доступ к чувствительным разделам (Центр уведомлений и его сохранение) перепроверяет роль/права пользователя по базе данных при каждом обращении, а не доверяет исключительно роли из ранее выданного токена — понижение роли лишает доступа немедленно, не дожидаясь истечения токена.
- [ ] AC-1.6: Авторизация и определение роли завершаются до отрисовки ролезависимой навигации — недопустимо кратковременное отображение чужого/неопределённого состава разделов при загрузке.
- [ ] AC-1.7: Запросы аутентификации Mini App ограничены по частоте так же, как остальные публичные endpoint'ы платформы.
- [ ] AC-1.8: Если серверный секрет для подписи токена Mini App не настроен, аутентификация отказывает явной ошибкой — не работает "по умолчанию" на публично известном резервном значении.
- [ ] AC-1.9: Проверка подписи данных, присланных Telegram (initData), защищена от атак по времени сравнения.

**Приоритет:** Must have — без этого нет "разных уровней доступа", буквальное требование владельца.

### US-2: Главная — лента гостя парка

**Как** USER, **я хочу** на главном экране видеть новости парка и свои личные уведомления одним списком, **чтобы** не искать обновления по разным экранам.

**Acceptance Criteria:**
- [ ] AC-2.1: Главный экран показывает единую ленту из (а) объявлений парка, разосланных существующим инструментом рассылок, и (б) личных уведомлений пользователя (статусы броней/заказов), отсортированных по времени.
- [ ] AC-2.2: Источник новостей — тот же, что уже используется в `/admin/notifications/broadcast`; новый инструмент создания контента не создаётся.
- [ ] AC-2.3: При отсутствии рассылок/уведомлений (новый гость) экран показывает содержательное пустое состояние (информация о парке), а не пустую область.
- [ ] AC-2.4: Каждая запись ленты показывает относительное время публикации и достаточно текста для понимания сути без перехода на другой экран.
- [ ] AC-2.5: Быстрый доступ к Барбекю Парку, Плей Парку и Кафе остаётся на главном экране на видном месте.
- [ ] AC-2.6: Главный экран не показывает карточки/ссылки, к которым у текущего пользователя нет доступа.

**Приоритет:** Must have — буквально то, что просил владелец для обычного USER ("новости, уведомления").

---

### US-3: Кафе внутри Mini App

**Как** USER, **я хочу** видеть меню кафе и понятный путь к заказу прямо в Mini App, **чтобы** не выходить из Telegram, чтобы узнать что есть и как заказать.

**Acceptance Criteria:**
- [ ] AC-3.1: В навигации появляется раздел «Кафе», отсутствующий сегодня в Mini App.
- [ ] AC-3.2: Раздел показывает актуальное меню (категории, позиции, цены, фото) — те же данные, что на публичной странице кафе сайта; дублирующего меню не заводим.
- [ ] AC-3.3: Из раздела доступен понятный путь к оформлению заказа через существующий сценарий (гостевой QR-чекаут с онлайн-оплатой) — новый механизм заказа/оплаты не создаётся.
- [ ] AC-3.4: Раздел использует только существующий публичный интерфейс модуля `cafe`; правила самого модуля (меню, приёмка заказов, оплата) не меняются.
- [ ] AC-3.5: При недоступности меню (пусто/ошибка) пользователь видит понятное сообщение, а не пустой экран.

**Приоритет:** Must have — прямое требование владельца ("кофе" в базовой поверхности USER); сегодня кафе в Mini App нет вообще.

### US-4: Редизайн существующих сценариев USER (сервисы, брони, профиль)

**Как** USER, **я хочу**, чтобы экраны бронирования и профиля выглядели современно и понятно, **чтобы** пользоваться Mini App вместо звонка на ресепшн.

**Acceptance Criteria:**
- [ ] AC-4.1: Экраны Барбекю Парка, Плей Парка, «Мои брони» и «Профиль» получают новый визуальный вид в рамках единой дизайн-системы (US-7) — бизнес-правила бронирования (доступность, конфликты слотов, отмена, оплата) не меняются.
- [ ] AC-4.2: Существующие сценарии (просмотр доступности, создание брони, просмотр своих броней, отмена, оплата) проходят в переработанном виде без потери функциональности.
- [ ] AC-4.3: Переработанный экран отмены брони обрабатывает существующий ответ API о необходимости подтверждения штрафа при поздней отмене явным управляемым шагом (сообщение + понятное действие), а не тупиком без объяснения.
- [ ] AC-4.4: Профиль сотрудника (MANAGER/ADMIN/SUPERADMIN) содержит все элементы профиля обычного пользователя плюс отдельный, ясно подписанный вход в Центр уведомлений (US-5).

**Приоритет:** Must have — визуальный редизайн явно запрошен владельцем; сотрудник тоже пользуется этими экранами как гость парка.

### US-5: Центр уведомлений для сотрудника

**Как** сотрудник (MANAGER, ADMIN или SUPERADMIN), отвечающий за один или несколько разделов парка, **я хочу** выбрать, какие именно типы уведомлений приходят лично мне, **чтобы** не тонуть в чужих алертах и не пропускать свои.

**Acceptance Criteria:**
- [ ] AC-5.1: Сотрудник открывает Центр уведомлений из Профиля и видит уведомления, сгруппированные по категориям (Барбекю Парк, Плей Парк, Кафе, Аренда, Склад, Системные и т.д.) — но только те категории, к которым у него есть доступ в админ-панели. Недоступные категории не показываются вовсе.
- [ ] AC-5.2: Внутри доступной категории сотрудник включает/выключает конкретные типы событий по отдельности (например, для Барбекю Парка — "новая бронь" отдельно от "отмена брони").
- [ ] AC-5.3: Категория "Системные уведомления" (релизы, деплой, алерты мониторинга) видна и настраиваема только тем, у кого есть доступ к разделу «Мониторинг», либо роль SUPERADMIN.
- [ ] AC-5.4: ADMIN обладает точно теми же возможностями Центра уведомлений, что MANAGER/SUPERADMIN — набор категорий определяется правами доступа для всех ролей одинаково, без отдельного исключения по роли (в отличие от сегодняшнего поведения бот-команды `/settings`).
- [ ] AC-5.5: Выключение типа уведомления останавливает его доставку этому сотруднику для новых событий сразу после сохранения; включение — возобновляет.
- [ ] AC-5.6: При первом открытии Центра уведомлений сотрудником без ранее настроенного способа доставки система обеспечивает канал через Telegram автоматически (пользователь уже аутентифицирован в Mini App через Telegram) — экран работает сразу, без отдельного шага подтверждения кода.
- [ ] AC-5.7: Обязательные CRITICAL-оповещения об инфраструктурных сбоях для SUPERADMIN не могут быть отключены через Центр уведомлений — это защищённая категория; Центр управляет только информационными/рабочими типами.
- [ ] AC-5.8: Экран и сохранение настроек перепроверяют текущие права пользователя по базе данных, а не только по данным сессии.

**Приоритет:** Must have — буквальное требование владельца ("выбор типов уведомлений в зависимости от доступа"), включая явное требование не забыть ADMIN.

### US-6: Ровно одно сообщение о релизе на получателя

**Как** владелец (SUPERADMIN), **я хочу** получать ровно одно понятное сообщение на каждый продакшн-релиз, **чтобы** доверять тому, что читаю, а не сверять несколько по-разному сформулированных дублей.

**Acceptance Criteria:**
- [ ] AC-6.1: Повторный успешный прогон деплоя для уже анонсированной версии не порождает повторное объявление той же версии ни одному получателю — независимо от того, попал ли архивный коммит с release-notes в защищённую ветку.
- [ ] AC-6.2: Если деплой для одного и того же релиза технически запустился дважды, получатель всё равно получает не больше одного сообщения об этом релизе.
- [ ] AC-6.3: Получатель, состоящий одновременно в группе для команды и в списке персональных подписчиков на релизы, не получает два разных по формулировке сообщения об одном и том же релизе — это одно событие.
- [ ] AC-6.4: Управление тем, приходят ли сотруднику уведомления о релизах/деплое, происходит из одного места — Центра уведомлений (US-5, категория "Системные"). Прежний отдельный переключатель в боте для той же настройки убирается или явно ведёт в Центр уведомлений — не остаётся двух мест с независимым состоянием одной настройки.
- [ ] AC-6.5: При переходе на новую схему ни один сотрудник, ранее получавший уведомления о релизах, не перестаёт их получать, и ни один из отключивших их ранее — не начинает получать снова (перенос текущего состояния 1:1).
- [ ] AC-6.6: Если проверка "уже анонсировано или нет" технически не выполняется (сбой), система склоняется к тому, чтобы отправить уведомление о реальном релизе, а не молча его пропустить.
- [ ] AC-6.7: Каждое блокирование дублирующего/повторного сообщения оставляет след в системном логе платформы — можно проверить, что сработала именно дедупликация, а не что сообщение потерялось.

**Приоритет:** Must have — вторая явная жалоба владельца, с точно установленным механизмом (см. «Проблема»).

### US-7: Единая дизайн-система на теме Telegram

**Как** любой пользователь Mini App, **я хочу**, чтобы приложение выглядело как аккуратный нативный Telegram Mini App (светлый или тёмный — по моей теме Telegram), **чтобы** оно ощущалось современным и вызывающим доверие, а не недоделанным прототипом.

**Acceptance Criteria:**
- [ ] AC-7.1: Все экраны (существующие и новые) следуют цветам текущей темы Telegram пользователя и корректно выглядят в светлой и тёмной теме без перезагрузки приложения при переключении темы в Telegram.
- [ ] AC-7.2: На карточках сервисов и разделов не остаётся жёстко заданных фирменных градиентов/цветов, не связанных с темой пользователя.
- [ ] AC-7.3: Иконография единообразна по всему приложению — эмодзи и векторные иконки не смешиваются для однотипных элементов на одном экране.
- [ ] AC-7.4: Интерфейс уважает безопасные зоны экрана Telegram и последовательно использует тактильный отклик (haptics) для ключевых действий на всех переработанных и новых экранах.
- [ ] AC-7.5: Визуальная приёмка редизайна подтверждена владельцем платформы перед вливанием в основную ветку.

**Приоритет:** Must have — третья явная жалоба владельца.

## Риски

1. **Авто-выдача Telegram-канала доставки без OTP-цикла (US-5, AC-5.6).** Решение признать уже проверенную HMAC-подпись initData достаточным доказательством владения Telegram-аккаунтом — осознанное отступление от сегодняшнего flow верификации канала, требует явного согласования с Architect/Reviewer, а не тихого послабления.
2. **Миграция состояния "уведомления о релизах" (US-6, AC-6.5).** Ошибка переноса — часть сотрудников либо неожиданно начнёт получать уведомления, от которых отказалась, либо перестанет получать нужные.
3. **Риск регресса бронирования при "полном ребилде".** Большая переработка экранов создаёт риск задеть логику бронирования/оплаты, хотя это не требуется — явно зафиксировано в AC-4.1/4.2, QA обязан прогонять сценарии броней и оплаты, не только визуальную приёмку.
4. **Скрытие раздела «Чаты» (US-1, AC-1.4).** Для тех редких пользователей, у кого уже есть рабочая веб-сессия, раздел был функционален — его временное исчезновение из навигации требует подтверждения владельца как приемлемого до отдельной задачи по унификации авторизации.
5. **RU-мобильное окружение.** Платформа уже имеет отдельную архитектуру под нестабильные мобильные сети РФ (ADR `2026-07-23-ru-availability-edge-architecture`) — редизайн не должен увеличивать вес/время загрузки Mini App.
6. **Изменения в `deploy.yml`.** Ошибка здесь рискует не дублированием, а полным молчанием о реальном релизе — отсюда AC-6.6 (fail-open) и требование протестировать на дружественном прогоне перед вливанием в `main`.
7. **Scope creep.** Формулировка "полное переосмысление" приглашает добавить смежное (лояльность, PWA, OTP-фикс, unification auth) — список «Вне скоупа» обязателен к соблюдению Developer'ом и проверке Reviewer'ом.

## Вне скоупа / Follow-up

1. **Починка привязки Telegram-аккаунта по OTP** (код сегодня только логируется в консоль, не отправляется) — реальный баг, но не входит в три заявленные проблемы; отдельная задача.
2. **Унификация авторизации мессенджера** (NextAuth-cookie vs Mini App JWT) — из-за неё раздел «Чаты» временно скрыт (US-1, AC-1.4); самостоятельная задача авторизации.
3. **Полноценная административная панель** (создание/редактирование броней, меню, пользователей) внутри Mini App — управление остаётся в `/admin`; сотрудник в Mini App получает тот же функционал, что и гость, плюс Центр уведомлений.
4. **Выбор канала доставки и "тихих часов" по каждому типу события отдельно** в Центре уведомлений — данные в схеме уже есть, но не запрошено; можно добавить позже без миграций.
5. **Дедупликация и cooldown уведомлений watchdog'ов/инцидентов** (падение сайта, недоступность уведомлений, расхождение показаний мобильных сетей) — отдельная, более широкая проблема с собственной архитектурой (4 источника наблюдения), заслуживает своего PRD.
6. **Полная консолидация ~20 разрозненных прямых отправок системных сообщений** в единый стек — в этой итерации переводим только деплой/релизные объявления (жалоба владельца); остальное — технический долг на будущее.
7. **PWA/offline-режим** (регистрация service worker для `/webapp`, баннер установки) — компоненты уже есть в коде, но не подключены; не запрошено.
8. **Настройка меню-кнопки бота через Bot API** (`setChatMenuButton`/`setMyCommands`) — запуск Mini App остаётся как сегодня (кнопка в приветственном сообщении, ручная настройка в BotFather).
9. **Программа лояльности** — остаётся текущей заглушкой "Скоро!" в профиле.
10. **Устранение дублирования кода экранов Барбекю Парка/Плей Парка** (~95% совпадение) — техническая переработка, не продуктовое требование; можно сделать попутно на усмотрение Developer.
11. **Прочие мелкие технические дефекты** (наивная обработка часовых поясов и т.п.), не связанные напрямую с тремя заявленными задачами — фиксируются как отдельные issues по мере обнаружения QA.
