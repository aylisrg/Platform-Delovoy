# PRD: F7 — Автосписание абонемента + drill-down прошедшей сессии

> RUN_ID: `2026-05-04-subscription-debit-and-drilldown`
> Дата: 2026-05-04
> Модуль: `ps-park` + `subscriptions` (зависимость F6)
> Ветка: `claude/wave-3-subscriptions-impl`

---

## Проблема

Сегодня менеджер PS Park завершает сессию через модальное окно оплаты и вводит сумму наличными или картой. Два пробела:

1. **Абонемент не связан с кассой.** Если у гостя есть абонемент (F6), менеджер физически обнуляет часы в отдельном месте и всё равно вводит нулевую сумму вручную — риск ошибки и двойного учёта. Система не фиксирует, что сессия была оплачена абонементом.

2. **История сессий не даёт картины.** Менеджер видит список броней (дата, стол, клиент, статус), но не может «провалиться» и увидеть полный срез: сколько фактически играли, что заказали в кафе во время сессии, каким способом оплатили. Это мешает разборам спорных ситуаций и сверке кассы.

Целевые персоны: **MANAGER** (ежедневное использование), **SUPERADMIN** (аудит и сверка).

---

## Решение

**Часть А — Автосписание абонемента при завершении сессии**

В момент нажатия «Завершить» в модальном окне оплаты система проверяет, есть ли у гостя активный абонемент с достаточным балансом часов. Если да — менеджер видит переключатель «Оплатить из абонемента». При его включении денежные поля обнуляются и блокируются. Подтверждение фиксирует списание в финансовом журнале.

**Часть Б — Drill-down прошедшей сессии**

Новая страница детали сессии: гость, длительность, кафе-заказы за время сессии, способ оплаты. Из таблицы истории броней добавляется ссылка «Подробнее» на каждой строке COMPLETED.

---

## Целевая аудитория

- **MANAGER** (ps-park) — ежедневное завершение сессий и просмотр истории
- **SUPERADMIN** — аудит способов оплаты, сверка с абонементами

---

## User Stories

### US-1: Списание часов из абонемента при оплате сессии

- **Как** менеджер PS Park
- **Я хочу** видеть в окне закрытия сессии переключатель «Оплатить из абонемента», когда у гостя достаточно часов
- **Чтобы** не вводить нулевую сумму вручную и иметь автоматическое подтверждение того, что часы списаны корректно

**Acceptance Criteria:**

- [ ] AC-1 (happy path): При завершении сессии гостя с ACTIVE Subscription (`remainingHours >= billedHours`, `validTo >= now()`) в `session-bill-modal` появляется блок «Абонемент» с переключателем (по умолчанию выключен). Рядом — имя абонемента и остаток часов.

- [ ] AC-2 (toggle включён): После включения переключателя поля «Наличные» и «Безналичные» обнуляются и блокируются для ввода. Секция скидки также блокируется (скидка несовместима с абонементом). Кнопка «Завершить сессию» становится активной.

- [ ] AC-3 (toggle выключен снова): Выключение переключателя возвращает поля оплаты в редактируемый режим, секцию скидки — в доступный, значения сбрасываются до `effectiveTotal` (наличные) и `0` (карта).

- [ ] AC-4 (недостаточно часов): Если у гостя ACTIVE Subscription с `remainingHours < billedHours` — переключатель отображается, но заблокирован. Tooltip: «Не хватает X ч. (осталось Y ч.)».

- [ ] AC-5 (нет активного абонемента): Если активного абонемента нет — блок «Абонемент» не отображается вовсе. Поведение модала не меняется.

- [ ] AC-6 (атомарность): После подтверждения с включённым переключателем система в одной транзакции: (а) переводит бронь в COMPLETED, (б) уменьшает `Subscription.remainingHours` на `billedHours`, (в) создаёт `SubscriptionTransaction(type=DEBIT_SESSION, bookingId=…, hoursDebited=N)`, (г) создаёт `FinancialTransaction(totalAmount=0, cashAmount=0, cardAmount=0, type=SESSION_PAYMENT)`, (д) пишет AuditLog `subscription.debit_session` с `bookingId, hoursDebited, remainingAfter`.

- [ ] AC-7 (автодеплет): Если после списания `Subscription.remainingHours = 0`, статус подписки обновляется до `DEPLETED` в той же транзакции.

- [ ] AC-8 (race condition): Если два менеджера одновременно пытаются списать с одной подписки — второй получает ошибку `INSUFFICIENT_HOURS`. Это обеспечивается условием `updateMany WHERE remainingHours >= billedHours` или пессимистичной блокировкой строки подписки внутри транзакции.

- [ ] AC-9 (истёкший абонемент): Если с момента открытия модала `validTo` подписки стал прошедшим (`validTo < now()`) — при попытке подтверждения сервер возвращает ошибку «Абонемент истёк», переключатель деактивируется, менеджеру необходимо выбрать другой способ оплаты.

---

### US-2: Просмотр детальной карточки прошедшей сессии

- **Как** менеджер PS Park (или суперадмин)
- **Я хочу** открыть любую завершённую сессию и увидеть полную информацию: гость, длительность, кафе-заказы, оплата
- **Чтобы** разбирать спорные ситуации и сверять кассовые данные без поиска в разных журналах

**Acceptance Criteria:**

- [ ] AC-10 (доступ): Страница `/admin/ps-park/sessions/[id]` открывается для ролей MANAGER (с доступом к ps-park) и SUPERADMIN. USER и MANAGER других модулей получают 403. Soft-deleted брони (`deletedAt != null`) возвращают 404.

- [ ] AC-11 (данные сессии): Страница отображает секцию «Сессия» с: именем и телефоном гостя (с кликом в карточку гостя `/admin/ps-park/clients/[userId]` если userId привязан), названием стола, датой, временем начала / фактического окончания, тарифными и фактическими часами, стоимостью аренды.

- [ ] AC-12 (кафе-заказы): Если во время сессии были кафе-заказы (связаны через `Order.bookingId`), отображается секция «Заказы в кафе» со списком позиций каждого заказа (название, количество, цена, статус заказа). Если заказов нет — секция скрыта или показывает «Заказов не было».

- [ ] AC-13 (способ оплаты): Секция «Оплата» показывает итоговую сумму и детали: наличные, карта, или «Абонемент №X — списано N ч.» (данные из FinancialTransaction + SubscriptionTransaction по `bookingId`). Скидка (если была) отображается отдельной строкой.

- [ ] AC-14 (навигация): В таблице истории броней (`BookingHistoryTable`) у каждой строки со статусом COMPLETED присутствует ссылка «Подробнее» ведущая на `/admin/ps-park/sessions/[id]`. На странице детали есть кнопка «Назад» возвращающая на предыдущий экран истории.

- [ ] AC-15 (API): `GET /api/ps-park/sessions/[id]` возвращает объект: `booking` (основные поля), `orders` (массив заказов с `items`), `financialTransaction` (итоговая запись FT), `subscriptionTransaction` (ST с type=DEBIT_SESSION, если есть). Формат — стандартный `{ success: true, data: { … } }`.

## Edge Cases (зафиксированные решения)

| Ситуация | Решение |
|----------|---------|
| `validTo` абонемента истёк в процессе сессии | Lazy check на сервере в момент подтверждения; ошибка «Абонемент истёк» |
| Скидка + абонемент одновременно | Запрещено. Включение toggle блокирует секцию скидки в UI; сервер отклоняет запрос с обоими полями |
| Отмена / возврат COMPLETED сессии | Вне скоупа F7. Часы не возвращаются автоматически — требует отдельного workflow |
| Гость без привязанного userId (гостевая бронь) | Абонемент не может быть привязан к гостевой брони (нет userId для поиска подписки) — переключатель не отображается |

## Приоритет (MoSCoW)

**Категория: Must have**

Обоснование: это последняя нереализованная часть требования №4 заказчика («если человек пришёл играть — автоматически подтягивать карточку гостя, списывать часы»). F6 (Subscription) без F7 — незавершённый функционал, за который нет пути оплаты. Бизнес продаёт абонементы, но не имеет инструмента их учёта при закрытии кассы.

**Зависимости:**
- F1 (payment guard в `updateBookingStatus`) — в main, необходимо расширить сигнатуру для subscription credit
- F4 (userId на брони) — в main, обеспечивает поиск подписки по гостю
- F5 (`Order.bookingId`) — в main, обеспечивает кафе-заказы в drill-down
- F6 (`Subscription`, `SubscriptionTransaction` модели) — в этой же ветке wave-3

## Метрики успеха

| Метрика | Базовое значение | Целевое (через 2 недели) |
|---------|-----------------|--------------------------|
| % сессий с абонементом, закрытых через toggle | 0% (функционала нет) | 90%+ от сессий абонементных гостей |
| Время менеджера на закрытие абонементной сессии | ~3 мин (ручной учёт + поиск карточки) | < 30 сек |
| Ошибки двойного учёта часов (INSUFFICIENT_HOURS при race) | неизвестно | 0 дублей в AuditLog |
| Использование drill-down (просмотры страницы /sessions/[id]) | 0 (страницы нет) | > 5 просмотров в день к концу 2-й недели |

## Вне скоупа

- Возврат часов при отмене или рефанде COMPLETED сессии — отдельный feature
- Частичное покрытие абонементом (split: часть часов из абонемента, остаток — наличными) — упрощение, пока не нужно
- Групповые абонементы (несколько гостей на одну подписку)
- Automatic top-up (авто-пополнение при достижении нуля)
- Subscription bonuses / уровни (программа лояльности — Phase 5.1)
- UI drill-down для кафе-заказов вне контекста PS Park сессии
- Telegram-уведомление гостю о списании часов (может быть добавлено в V1.5)
- История просмотра абонемента в карточке гостя (покрывается F6 admin CRUD)

## Open Questions → для Architect

1. **Размещение `debitFromSession`**: рекомендация PO — helper в `src/modules/subscriptions/debit.ts`, вызываемый из `ps-park/service.ts` внутри `prisma.$transaction`. Решение о внутренней структуре — за Architect.

2. **Guard F1 при subscription payment**: текущий guard в `updateBookingStatus` требует `cashAmount + cardAmount >= totalBill`. При subscription debit эффективная сумма к оплате = 0. Рекомендация: передавать `subscriptionCredit: number` как дополнительный слагаемый guard-чека (`paid + subscriptionCredit >= totalBill`), не вводить флаг-обход. Решение — за Architect.

3. **Отдельная страница vs вкладка в карточке гостя**: рекомендация PO — отдельная страница `/admin/ps-park/sessions/[id]`, чтобы она имела постоянный URL для линковки из истории и потенциально из Telegram-алертов. Решение — за Architect.
