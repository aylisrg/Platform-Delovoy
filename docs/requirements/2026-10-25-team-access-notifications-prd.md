## Проблема

Владелец провёл ревью прав команды (`/admin/users`, таб «Команда») и упёрся в пять связанных проблем:

1. **Сотрудника нельзя убрать из команды.** Кнопка «Удалить» жёстко удаляет аккаунт, а на аккаунте всегда висит история (журнал входов, назначения на модули, задачи, переписка). Итог: ошибка 409 «на него ссылаются другие записи» во всплывающем окне без объяснения. Смена роли на «Пользователь» только меняет подпись: права, назначения, списки получателей, подписки и открытая сессия остаются. Конкретный случай — один из сотрудников, которого владелец хочет исключить (адрес указан в контекст-логе запуска).
2. **Нет карточки сотрудника и общей картины прав.** Страницы `/admin/users/[id]` не существует; чтобы понять, кто что может и получает, нужно открывать несколько окон и сверять вручную. Окно «Права» для суперадмина не сохраняется (ошибка «стандартные разделы можно настроить только для менеджеров»).
3. **Непонятно, кому какие уведомления приходят.** Получатель из списка получателей раздела в Mini App видит тумблер «выкл», хотя уведомления получает; лиды Авито идут по роли и тумблер на них не влияет; интерфейс обещает «суперадмины получают всегда», хотя это не так; ADMIN без явных разделов видит пустой Центр. Админ не может настроить уведомления сотрудника за него.
4. **Нет статистики уведомлений.** Не видно, сколько сообщений дошло, сколько упало и почему, читает ли их сотрудник и как быстро реагирует. Кликов и прочтений никто не записывает; пропуски доставки (нет канала, «не беспокоить») не оставляют следа.
5. **У человека два аккаунта вместо одного.** Бот создаёт отдельный аккаунт при входе через Telegram и отказывается дополнять аккаунты сотрудников; самопривязка Telegram к аккаунту с email не работает (одноразовый код только пишется в лог сервера и не отправляется), а при конфликте «Telegram уже привязан к другому аккаунту» человек упирается в тупик. Нет признака, запускал ли человек бота: без `Start` бот не может писать пользователю, и Telegram-доставка тихо падает.

## Решение

Пять блоков, все в существующих модулях:

- **A. Исключить из команды.** Одно действие суперадмина закрывает сотруднику доступ и уведомления и оставляет аккаунт клиентом с целой историей. «Удалить» вместо ошибки объясняет, что мешает. Починена модалка «Права».
- **B. Страница сотрудника и обновлённый таб «Команда».** Карточка `/admin/users/[id]` (профиль, идентичности, права, уведомления, статистика, действия); таб «Команда» превращается в экран ревью всей команды.
- **C. «Кто что получает» + управление.** Для каждого события — получает ли сотрудник, по какому пути, каким каналом и что блокирует. Админ и сам сотрудник управляют одной и той же подпиской; матрица «сотрудники × события»; Центр в Mini App показывает правду.
- **D. Статистика и реакции.** Отправлено / доставлено / ошибка / прочитано / клик / время до реакции с срезами; клики считаются через трекинг-ссылки.
- **E. Один аккаунт = email + Telegram.** Признак «бот запущен/заблокирован», объединение аккаунтов сотрудников, рабочая самопривязка по OTP, конфликт Telegram превращается в запрос на объединение вместо тупика.

## Решения владельца (окончательные, не пересматриваются)

1. **Удаление → только «Исключить из команды»** (аккаунт остаётся клиентом, история цела). Жёсткое удаление/обезличивание — вне скоупа. «Удалить» объясняет, что мешает, и предлагает исключение.
2. **Реакция → прочтение + клики** (трекинг-ссылки, время до реакции), в разрезе сотрудника и типа события.
3. **Управление → админ ставит, сотрудник может менять** (одна и та же персональная подписка, AuditLog с актором). Замка «обязательное» нет.
4. **Email + Telegram → объединение аккаунтов сотрудников + починка самопривязки**; галочка «бот запущен» с датой и признак «бот заблокирован».

## Аудитория и права доступа

Основная персона — **SUPERADMIN** (владелец/управляющий): ревью команды, исключение, настройка и статистика. Вторая — **сотрудник (MANAGER/ADMIN/SUPERADMIN)** как получатель: видит и меняет собственные уведомления. Через самопривязку Telegram проходит и **USER**, пришедший из бота.

| Действие | SUPERADMIN | ADMIN | MANAGER | USER | Без входа |
|---|---|---|---|---|---|
| Страница сотрудника, таб «Команда» со сводкой, матрица, общая статистика | да | 403 | 403 | 403 | вход / 401 |
| Исключить из команды, смена роли, объединение аккаунтов, очередь запросов на объединение | да | 403 | 403 | 403 | 401 |
| Менять уведомления **другого** сотрудника | да | нет | нет | нет | 401 |
| Менять **свои** уведомления (Центр Mini App) | да | да | да | Центра нет (403) | 401 |
| Привязать Telegram к своему аккаунту по OTP (Mini App/бот) | цель-аккаунт SUPERADMIN запрещена (AC-E3.7) | да | да | да | — |
| Трекинг-ссылка (переход) | публично, без входа; доступ к целевой странице проверяется как обычно | | | | |

Правило: даже при выданной секции «Пользователи» перечисленные выше админ-действия остаются только за SUPERADMIN (как сегодня все `/api/users/*`).

## Определения (глоссарий для Dev и QA)

- **Команда** — аккаунты с ролью SUPERADMIN, ADMIN или MANAGER (не влитые в другие, не системный пользователь).
- **Исключение из команды** — операция, не удаление: роль → «Пользователь», снятие всего «сотруднического», история остаётся.
- **Путь доставки** — откуда сотрудник получает событие: личная подписка / список получателей раздела / по роли (Авито) / лента Mini App (сводка звонков) / только общий чат (лично не приходит).
- **Получает** — маршрут есть. **Подписан, но не дойдёт** — маршрут есть, канал заблокирован (нет канала, бот не запущен/заблокирован, отключён канал, «не беспокоить»).
- **Статусы бота** (одно из четырёх): «Telegram не привязан»; «Бот не запущен» (Telegram привязан, обращений к боту не было); «Бот запущен ✓ <дата>» (дата первого `/start` или любого сообщения боту в личном чате); «Бот заблокирован» (Telegram сообщил об остановке/блокировке бота; снимается новым обращением к боту).
- **Отправлено** — система создала и пыталась отправить уведомление сотруднику (включая ушедшие в повтор). **Доставлено** — канал принял сообщение (Telegram вернул подтверждение, push-сервис принял, карточка появилась в ленте Mini App). **Ошибка** — не удалось после всех повторов (с причиной). **Пропущено** — отправка не пыталась (нет канала, «не беспокоить», отключено, дубль) с причиной.
- **Прочитано** — только лента Mini App (карточка открыта или помечена прочитанной). Telegram и Web Push отметок о прочтении не дают.
- **Клик** — переход по кнопке/ссылке из Telegram-сообщения, Web Push или карточки ленты через трекинг-ссылку.
- **Реакция** — первое из: прочтение (лента) или клик. Одно уведомление даёт не более одной реакции (чтение и клик по одной карточке — это одна реакция). **Время до реакции** — от доставки до первой реакции (показываем медиану и долю «без реакции за 24 часа»).
- **Измеримое уведомление** — доставленное уведомление, у которого реакцию можно измерить (есть кнопка/ссылка либо оно в ленте). Telegram-сообщение без ссылки не измеримо. **Доля реакции** = уведомления с реакцией / измеримые доставленные.

## User Stories

### Блок A. Исключить из команды (область: users, auth/сессии, notifications)

#### US-A1: Исключить сотрудника из команды одним действием — Must

- **Как** SUPERADMIN
- **Я хочу** одним подтверждённым действием убрать сотрудника из команды
- **Чтобы** немедленно закрыть доступ и поток рабочих уведомлений, не теряя историю (журнал, брони, заказы, задачи), и не ходить по пяти экранам вручную

**Acceptance Criteria:**
- [ ] AC-A1.1: Кнопка «Исключить из команды» есть в строке таба «Команда» и на странице сотрудника; видна только SUPERADMIN и только для аккаунтов с ролью SUPERADMIN/ADMIN/MANAGER.
- [ ] AC-A1.2: Перед выполнением окно подтверждения показывает: имя и текущую роль; что будет снято (числа: разделы, модули, списки получателей, личные подписки); что сохранится («Аккаунт останется клиентом. Брони, заказы, задачи, переписка и журнал действий не удаляются»). Справочно (Should): сколько открытых задач у него исполнителем — они остаются за ним, переназначать вручную.
- [ ] AC-A1.3: После подтверждения выполняется **«всё или ничего»**: (1) роль → «Пользователь»; (2) сняты все права на разделы; (3) сняты все назначения на модули; (4) убран из списков получателей уведомлений **всех** модулей (включая те, на которые не был назначен); (5) удалены личные подписки на события каталога, включая релизы и сводку звонков (зеркальный флаг «Релизы» выключен); (6) активные сессии прекращены. При сбое на любом шаге данные остаются как были.
- [ ] AC-A1.4: Клиентская часть не затронута: Telegram-канал доставки, клиентские уведомления (подтверждения собственных броней/заказов), брони, заказы, абонементы. Подписки снимаются удалением, а не выставлением «выкл», чтобы не заглушить человеку его клиентские уведомления того же типа события. Проверка: исключить сотрудника, у которого есть собственная бронь, — напоминания по ней продолжают приходить.
- [ ] AC-A1.5: Доступ закрыт без ожидания перелогина: открытая вкладка админки исключённого на следующем действии/обновлении получает «нет доступа», вызовы админ-API отклоняются; допустимая задержка — не более 60 секунд, цель — со следующего запроса. В Mini App Центр уведомлений отвечает «Доступ отозван»; staff-команды бота недоступны. Исключённый может заново войти как обычный клиент.
- [ ] AC-A1.6: Гарды (понятное сообщение в окне, без `alert()` и 5xx, данные не меняются): себя — «Нельзя исключить самого себя»; последнего суперадмина — «Нельзя исключить последнего суперадмина. Сначала назначьте другого»; аккаунт не в команде — «Пользователь не входит в команду». «Последний» = единственный действующий SUPERADMIN (не влитый, не системный).
- [ ] AC-A1.7: Сидированный суперадмин (аккаунт, чей Telegram ID задан в настройках сервера): окно показывает предупреждение «Этот аккаунт назначен суперадмином в настройках сервера. При ближайшем обновлении платформы роль вернётся автоматически. Чтобы исключение осталось, сначала смените настройку сервера» и требует отдельного подтверждения «Всё равно исключить». Сам Telegram ID в интерфейсе не показывается. Это предупреждение, а не запрет.
- [ ] AC-A1.8: Повторное исключение (уже исключённого, двойной клик, два админа одновременно): выполнение одно; остальные получают «Пользователь уже не входит в команду», без ошибки сервера и без повторной записи в журнал.
- [ ] AC-A1.9: Журнал: одна запись «исключение из команды» — актор, цель, прежняя роль, что снято (перечни: разделы, модули, списки получателей, подписки), время. Email/телефон в записи не дублируются.
- [ ] AC-A1.10: RBAC: SUPERADMIN выполняет; ADMIN/MANAGER/USER — 403; без входа — 401 (в том числе при выданной секции «Пользователи»).
- [ ] AC-A1.11: После исключения повторный прогон деплой-сидеров не возвращает роль, права и назначения (единственное исключение — сидированный суперадмин, AC-A1.7).
- [ ] AC-A1.12: Возврат в команду — обычным способом (создание/смена роли); ранее снятые права, подписки и списки автоматически не восстанавливаются.

#### US-A2: Смена роли через выпадающий список не оставляет хвостов — Must

- **Как** SUPERADMIN
- **Я хочу**, чтобы смена роли сотрудника на «Пользователь» в списке давала тот же результат, что «Исключить из команды»
- **Чтобы** не получилось «разжалованного» человека, который продолжает получать рабочие уведомления и сохраняет доступ

**Acceptance Criteria:**
- [ ] AC-A2.1: Выбор «Пользователь» у сотрудника открывает то же окно подтверждения и выполняет ту же операцию, что US-A1 (включая гарды и предупреждение о сидированном суперадмине). Прямой вызов API смены роли на USER даёт тот же результат.
- [ ] AC-A2.2: Любое **понижение** роли (SUPERADMIN → ADMIN/MANAGER, ADMIN → MANAGER) тоже прекращает действие старых сессий (AC-A1.5): человек не сохраняет прежний уровень до перелогина.
- [ ] AC-A2.3: После понижения до роли выше USER сотрудник не получает уведомлений тех категорий, к которым доступа больше нет; блок «Уведомления» (C1) показывает по ним «Нет доступа к разделу».
- [ ] AC-A2.4: Повышение до MANAGER/SUPERADMIN работает как сегодня (MANAGER получает «Дашборд», подписка на релизы по умолчанию) — регрессионный тест.
- [ ] AC-A2.5: Любая смена роли пишет запись в журнал с актором (было → стало).

#### US-A3: «Удалить» объясняет, что мешает — Must

- **Как** SUPERADMIN
- **Я хочу**, чтобы при невозможности удаления система показывала, какие именно связи мешают, и предлагала исключение
- **Чтобы** не гадать над «какие-то другие поля защищают» и сразу сделать правильное действие

**Acceptance Criteria:**
- [ ] AC-A3.1: Если удаление невозможно из-за связей, вместо `alert()` открывается окно «Удалить нельзя: у аккаунта есть история» со списком типов связей **и количеством** по каждому, по-русски, например: «Журнал действий — 214», «Назначения на модули — 5», «Задачи — 3», «Обратная связь — 1», «Абонементы Плей Парка — 2», «Чаты и сообщения — 17», «Доставленные уведомления — 40».
- [ ] AC-A3.2: Каждое число проверяемо запросом к данным; типы без записей не показываются; в списке учтены и косвенные блокеры (например, доставленные уведомления). Если причину определить не удалось — общий текст, но действие «Исключить из команды» всё равно предлагается.

### Блок C. «Кто что получает» + управление (область: notifications, users)

#### US-C1: Видеть, кто и как получает каждое событие — Must

- **Как** SUPERADMIN
- **Я хочу** видеть по каждому событию каталога у сотрудника: получает ли, по какому пути, каким каналом и что блокирует доставку
- **Чтобы** понять, почему человек получает лишнее или не получает нужное, не читая код и настройки пяти разделов

**Acceptance Criteria:**
- [ ] AC-C1.1: Блок показывает все 12 типов событий каталога по категориям. Категории без доступа — серым с причиной: «Нет доступа к разделу «Кафе»», «Только для суперадмина», «Нужен явный доступ к «НеДеловой»».
- [ ] AC-C1.2: Для каждого события: статус («Получает» / «Подписан, но не дойдёт» / «Не получает»), путь, каналы, блокировки.
- [ ] AC-C1.3: Формулировки путей: «Личная подписка»; «Список получателей раздела «Кафе»»; «По роли (Авито: суперадмины и менеджеры/администраторы, назначенные на модуль)»; «Лента Mini App (сводка звонков, суперадмины)»; «Только общий чат раздела — лично не приходит». Если путей несколько, перечисляются все; сообщение при этом одно (без дублей).
- [ ] AC-C1.4: Каналы — только реально настроенные и проверенные, в порядке реальной отправки (основной, затем запасной): Telegram / Web Push / лента Mini App / Email; «Нет канала», если нет ни одного.
- [ ] AC-C1.5: Блокировки: «Нет канала доставки», «Бот не запущен», «Бот заблокирован», «Канал отключён», «Не беспокоить до 18:00», «Тихие часы 22:00–08:00», «Отключено сотрудником». Любая блокировка меняет статус на «Подписан, но не дойдёт».
- [ ] AC-C1.6: **Экран говорит правду**: расчёт «получает/путь» использует ту же логику, что реальная рассылка. Проверка: для каждого события каталога автотест строит сотрудников во всех комбинациях путей и сверяет «получатели по экрану» с получателями реальной отправки тестового события — 0 расхождений.
- [ ] AC-C1.7: Для каждой категории отдельная справочная строка: получает ли событие общий чат раздела («Общий чат раздела получает это событие: да/нет») — чтобы было видно, что оно не пропадает при выключении личной подписки.
- [ ] AC-C1.8: Изменение подписки (в админке или в Mini App) отражается при следующем открытии блока без ручной очистки кэша.

#### US-C2: Админ включает и выключает уведомления сотрудника — Must

- **Как** SUPERADMIN
- **Я хочу** включать и выключать конкретные уведомления сотруднику прямо на его странице

- [ ] AC-C2.8: Тумблер «Релизы» (в таблице и в блоке) показывает одно и то же состояние.

### Блок D. Статистика уведомлений и реакции (область: notifications)

- **Чтобы** знать, реагирует ли сотрудник, когда у Telegram нет отметок о прочтении

**Acceptance Criteria:**
- [ ] AC-D3.1: Кнопки в Telegram-сообщениях, ссылки Web Push и кнопки карточек ленты ведут через ссылку на домене платформы с непредсказуемым кодом. Клик записывается (уведомление, сотрудник, время, канал); человек попадает на ту же страницу, что и раньше, без промежуточных экранов и без входа.
- [ ] AC-D3.2: Сбой записи клика не мешает переходу.
- [ ] AC-D3.3: **Открытый редирект исключён.** Конечный адрес определяется только значением, сохранённым при отправке уведомления; в самой ссылке адрес передать нельзя. Параметры вида `?url=`, `?to=`, значения `//evil.example`, `\\evil.example`, `javascript:`, `data:`, закодированные и двойно закодированные варианты не влияют на место перехода. Допустимые назначения — страницы платформы, адреса домена платформы и ссылки на нашего бота (t.me); прочее не оборачивается в трекинг-ссылку и не отправляется кликабельным.
- [ ] AC-D3.4: Неизвестный, повреждённый или удалённый код → безопасный переход на главную страницу платформы (без 5xx и без раскрытия, существует ли код).
- [ ] AC-D3.5: Код не раскрывает и не позволяет вывести идентификатор пользователя или уведомления; перебор ограничен лимитом запросов.
- [ ] AC-D3.6: Автоматические предпросмотры (Telegram link preview, почтовые/антивирусные сканеры, HEAD-запросы) не засчитываются кликом (в пределах возможного).
- [ ] AC-D3.7: Повторные клики: время до реакции считается по первому; общее число кликов хранится отдельно.
- [ ] AC-D3.8: Кнопки в старых сообщениях продолжают работать не менее 12 месяцев (после срока хранения статистики клик перестаёт записываться, но переход остаётся).
- [ ] AC-D3.9: Клик не даёт доступа: целевая страница требует вход и права как обычно; трекинг-ссылка сама никого не авторизует.
- [ ] AC-D3.10: Тап по карточке ленты фиксирует и прочтение, и переход как одну реакцию.
- [ ] AC-D3.11: Публичная ссылка защищена лимитом запросов; лимит не должен мешать мобильным пользователям за общим адресом оператора.

#### US-D4: Подсветка проблем доставки — Must (бот) / Should (остальное)

- **Как** SUPERADMIN
- **Я хочу**, чтобы статистика сама показывала, где ломается доставка
- **Чтобы** чинить причину, а не разбирать цифры вручную

**Acceptance Criteria:**
- [ ] AC-D4.1 (Must): Блок «Проблемы» на общей странице и на странице сотрудника: «Бот не запущен — 3 сотрудника, 17 неудачных доставок за 30 дней», «Бот заблокирован — 1 сотрудник, 4 неудачные доставки»; клик ведёт к списку этих сотрудников.
- [ ] AC-D4.2 (Should): «Подписаны, но нет рабочего канала — 2 сотрудника»; «События, которых лично не получает никто — 1».
- [ ] AC-D4.3 (Should): Пропуски доставки фиксируются с причиной («нет канала», «не беспокоить», «отключено сотрудником», «дубль»), чтобы вопрос «почему мне не пришло» имел ответ; в карточках статистики показываются отдельно от «Ошибок».
- [ ] AC-D4.4 (Could): Динамика по дням (график), выгрузка в CSV.

### Блок E. Один аккаунт = email + Telegram (область: telegram-link, clients, users, bot)

#### US-E1: Признак «бот запущен» и «заблокирован» — Must

- **Как** SUPERADMIN
- **Я хочу** видеть, начал ли человек пользоваться Delovoy Bot и не заблокировал ли его
- **Чтобы** знать, придёт ли ему сообщение в Telegram, до того как оно потерялось

**Acceptance Criteria:**
- [ ] AC-E1.1: Четыре состояния из глоссария показываются на странице сотрудника, в таблице «Команда», в причинах блокировок (C1), в матрице и в проблемах статистики (D4) — одной и той же логикой.
- [ ] AC-E1.2: «Запущен» ставится при первом `/start` или любом сообщении боту **в личном чате**; дата первого обращения не перезаписывается повторными `/start`; действия в групповых чатах не считаются.
- [ ] AC-E1.3: Если человек начал пользоваться ботом до привязки Telegram к аккаунту (или аккаунта ещё не было), дата сохраняется и подтягивается при привязке и объединении (при объединении берётся более ранняя).
- [ ] AC-E1.4: «Заблокирован» ставится, когда Telegram сообщает об остановке/блокировке бота пользователем либо отказом доставки с этой причиной; снимается новым обращением к боту; дата блокировки сохраняется.
- [ ] AC-E1.5: Существующие данные: у кого уже есть успешная доставка в Telegram или кто входил через бота — «Бот запущен ✓ (дата неизвестна)»; остальные с привязанным Telegram — «Бот не запущен» с подсказкой «Обращений к боту не зафиксировано с <дата начала учёта>».
- [ ] AC-E1.6: Для флага хранится только факт и дата, но не тексты сообщений пользователя боту.

#### US-E2: Объединение двух аккаунтов одного сотрудника — Must

- **Как** SUPERADMIN
- **Я хочу** объединить email-аккаунт сотрудника и аккаунт, созданный ботом, в один
- **Чтобы** у человека был один вход, одна история и одни настройки уведомлений, а права не потерялись и не размножились

**Acceptance Criteria:**
- [ ] AC-E2.1: Вход: «Объединить аккаунты» на странице любого аккаунта; поиск второго аккаунта по имени/email/телефону/Telegram и список «Возможные дубли» (совпадение телефона, запросы из US-E4).
- [ ] AC-E2.2: Шаг «Кого оставить»: админ выбирает основной аккаунт; по умолчанию — с более высокой ролью, при равенстве — у кого есть email. Нельзя выбрать один и тот же аккаунт. Нельзя вливать аккаунт, под которым вы вошли: «Нельзя объединить аккаунт, под которым вы вошли. Выберите его основным».
- [ ] AC-E2.3: **Превью обязательно и ничего не меняет.** Показаны: профиль (имя, фото, email, телефон, Telegram, VK — что остаётся, конфликты подсвечены); итоговая роль; разделы; модули; списки получателей; личные подписки и каналы доставки; счётчики переносимого (брони, заказы, абонементы, задачи, сообщения, записи журнала, уведомления); отдельным списком «Не будут перенесены: …».
- [ ] AC-E2.4: Безопасные правила: (а) итоговые роль и права = роль и права **основного** аккаунта, права вторичного автоматически не добавляются; (б) объединение не повышает права ни одной стороны сверх показанного в превью и не может оставить систему без суперадмина; (в) конфликт подписок по одному событию — побеждает основной, непересекающиеся переносятся; (г) конфликт контактов (разные email/телефон/Telegram) — остаётся значение основного, значение вторичного попадает в журнал и превью, конфликт Telegram требует отдельного явного подтверждения; (д) сидированный суперадмин (Telegram ID из настроек сервера) не может быть вторичным аккаунтом: «Этот аккаунт привязан к настройке сервера. Выберите его основным».
- [ ] AC-E2.5: Подтверждение — чекбокс «Я понимаю, что действие нельзя отменить в интерфейсе». Откат в интерфейсе не предусмотрен.
- [ ] AC-E2.6: Результат: вторичный аккаунт помечен как объединённый (не удаляется), не показывается в списках и не может войти, его контакты освобождены или перенесены; основной входит и по email, и по Telegram в один аккаунт. Брони, заказы, абонементы, задачи, переписка, журнал, доставки — на основном. **Списки получателей модулей**, где был вторичный, указывают на основной (без дублей). Дата первого запуска бота — более ранняя; состояние «заблокирован» — актуальное.
- [ ] AC-E2.7: Крайние случаи: уже объединённый аккаунт → «Этот аккаунт уже объединён с другим»; параллельное объединение → один результат, второе получает ошибку без частичных изменений; сбой на полпути → все изменения откатываются; совпадение email/телефона у основного и вторичного обрабатывается по правилу (г), а не 500.
- [ ] AC-E2.8: Журнал: актор, оба аккаунта, итоговая роль, перенесённые счётчики, разрешённые конфликты.
- [ ] AC-E2.9: Открытые сессии вторичного прекращаются; сессия основного не ломается.
- [ ] AC-E2.10: Работает для пар сотрудник ↔ клиент (бот), сотрудник ↔ сотрудник, клиент ↔ клиент (без регрессии по сегодняшнему поведению).
- [ ] AC-E2.11: RBAC: только SUPERADMIN; остальные 403, без входа 401.

#### US-E3: Самопривязка Telegram: код реально приходит на email — Must

- **Как** пользователь, пришедший через Telegram, у которого уже есть аккаунт с email
- **Я хочу** привязать Telegram к своему аккаунту по коду из письма
- **Чтобы** не получать второй аккаунт и видеть свои брони, заказы и права в одном месте

**Acceptance Criteria:**
- [ ] AC-E3.1: При запросе привязки по email код уходит письмом на адрес аккаунта; интерфейс показывает маскированный адрес («Код отправлен на ab***@mail.ru»). Письмо по-русски: код, срок действия 10 минут, «Если это были не вы — проигнорируйте письмо». Доставка в течение 60 секунд в 95% случаев.
- [ ] AC-E3.2: Код не пишется в логи сервера.
- [ ] AC-E3.3: Ответ не раскрывает, существует ли аккаунт: всегда «Если такой аккаунт есть, мы отправили код на его email».
- [ ] AC-E3.4: Защита от злоупотреблений: не более 3 запросов кода на один email в час; ограничения по Telegram; 3 неверных попытки блокируют на 15 минут (как сегодня); код одноразовый.
- [ ] AC-E3.5: Если письмо не отправилось, пользователь видит «Не удалось отправить код. Попробуйте позже или обратитесь к администратору», а не «Код отправлен»; сбой фиксируется в мониторинге.
- [ ] AC-E3.6: Вариант «по телефону» не предлагается, пока нет рабочей SMS-доставки.
- [ ] AC-E3.7: OTP-привязка к аккаунту с ролью SUPERADMIN запрещена: «Для этого аккаунта привязку выполняет суперадмин». (Предложение PO, подтвердить на этапе архитектуры, см. вопрос 9.)
- [ ] AC-E3.8: После успешной привязки у аккаунта есть Telegram, канал доставки и состояние бота (E1); запись в журнале.

#### US-E4: Конфликт «Telegram уже привязан» — не тупик — Must

- **Как** пользователь, чей Telegram уже привязан к другому аккаунту
- **Я хочу** получить понятный ответ и чтобы вопрос решился
- **Чтобы** не застрять в сообщении об ошибке и не остаться без своего аккаунта

**Acceptance Criteria:**
- [ ] AC-E4.1: В любом потоке (код по email, deep-link с сайта, Mini App) человек видит: «Этот Telegram уже используется в другом аккаунте. Мы передали запрос администратору — он объединит аккаунты. Пока вы можете пользоваться текущим аккаунтом». Данных другого аккаунта (имя, email) в сообщении нет.
- [ ] AC-E4.2: Создаётся запрос на объединение (пара аккаунтов, причина, дата) — не более одного открытого на пару; повтор дубликатов не плодит; лимит на число запросов с одного Telegram.
- [ ] AC-E4.3: SUPERADMIN видит запросы: счётчик «Запросы на объединение: N» на табе «Команда»/«Пользователи» и блок «Возможные дубли» на странице аккаунта. Действия: «Объединить» (открывает US-E2 с предзаполненной парой), «Это разные люди» (закрывает без объединения, пара не предлагается повторно).
- [ ] AC-E4.4: Запрос не создаётся, если аккаунты уже объединены или пара закрыта как «разные люди».

Повтор действия — «уже не входит в команду». Прогон сидеров права не возвращает. Те же шаги с гардами: себя, единственный SUPERADMIN, сидированный SUPERADMIN.

**Статистика (D).** Сотрудник за 30 дней, 13 уведомлений: Telegram 8 попыток (6 доставлено — 4 с кнопкой и 2 без; 2 ошибки — «бот не запущен» и «бот заблокирован»); Web Push 2 доставлено, обе со ссылкой, 1 клик; лента Mini App 3 карточки, 2 прочитаны (одна из них ещё и с переходом по кнопке); по 3 из 4 Telegram-сообщений с кнопкой кликнули (по одному — дважды). Ожидание: Отправлено 13; Доставлено 11; Ошибки 2; Прочитано (лента) 2 из 3; уникальных уведомлений с кликом 5, всего кликов 6; реакций 6 (Telegram 3, Push 1, лента 2); измеримых 9 (Telegram с кнопкой 4, Push 2, лента 3); доля реакции 67%; «реакцию измерить нельзя» 2; проблемы: «Бот не запущен — 1 неудачная доставка», «Бот заблокирован — 1».

**Объединение (E2).** Основной: MANAGER с email, 2 разделами, 1 модулем; вторичный: USER из бота с Telegram и 2 бронями. Итог: роль MANAGER, разделы и модуль без изменений, Telegram и 2 брони на основном, вторичный скрыт и не входит. Пара с разными email — конфликт в превью, значение основного остаётся. Вторичный = сидированный суперадмин — отказ. Вторичный = текущий пользователь — отказ. Две параллельные попытки — одна успешная. Списки получателей: id вторичного заменён на основной, без дублей.

**Крайние случаи (сводка).** Исключить себя (AC-A1.6); последнего суперадмина (A1.6); повторное исключение (A1.8); merge с конфликтом Telegram/email (E2.4–E2.7, E4); open redirect в трекинг-ссылке (D3.3–D3.5: `?url=`, `//host`, `\\host`, `javascript:`, двойное кодирование, неизвестный код); RBAC USER/MANAGER/ADMIN/SUPERADMIN по таблице выше; OTP без раскрытия существования аккаунта и без кода в логах (E3.2–E3.3).

## Риски

1. **Сессии не отзываются.** Вход построен на токене, который живёт сам по себе; требование «не позднее 60 секунд» зависит от решения Architect (вопрос 1).
2. **Сидер возвращает суперадмина.** Исключение сидированного аккаунта будет отменено следующим деплоем — отсюда предупреждение (A1.7). Отдельно: у сидера есть запасное значение Telegram ID, если настройка не задана.
3. **Столкновение ключей подписки.** Подписка сотрудника и клиентские уведомления одного типа события (`booking.*`, `order.*`) живут в одной записи на пользователя; «выкл» у сотрудника может заглушить ему клиентские. Поэтому при исключении подписки удаляются (AC-A1.4); вопрос 8 к Architect.
4. **Telegram не отдаёт прочтение.** Любая «доля прочтения» по Telegram была бы выдумкой; в продукте только клики и честные подписи.
5. **Ложные клики** от предпросмотра ссылок и сканеров; смягчено AC-D3.6.
6. **Трекинг-ссылка — новая точка отказа и вектор атаки.** Сбой записи не должен ломать переход (D3.2); open redirect закрыт AC-D3.3; доступ к данным ссылка не даёт (D3.9).
7. **Наблюдение за сотрудниками.** Статистика реакций — персональные данные сотрудников; смягчено заметкой в Центре (C3.6) и отсутствием текстов сообщений в списках (D2.2). Рекомендация PO: предупредить команду до релиза.
8. **Данные не восстановить задним числом.** Клики, пропуски и признак бота начнут копиться только после релиза записи.
9. **Радиус изменений.** Затронуты пять областей и бот; требует осмысленной нарезки на волны (см. ниже), не на микро-PR (Scope guard, п.3).
10. **Изменение видимых категорий.** После правок C3.3/C3.4 часть сотрудников увидит иной набор категорий в Центре — предупредить в релизе.

## Порядок поставки (рекомендация PO)

1. **Волна 1 — срочное (кейс владельца) + сбор данных.** Блок A целиком (исключение, смена роли, «Удалить» с объяснением, модалка «Права»). Параллельно, как можно раньше, начать **записывать** клики, пропуски и признак бота (E1) — данные нельзя восстановить задним числом, а стоят они недорого.

3. **Волна 3 — аналитика и единый аккаунт.** Блок D (страница, блок сотрудника, подсветка проблем) и E2–E4 (объединение, OTP, запросы на объединение).

Нарезку и границы PR определяет Architect по правилу батчей (CLAUDE.md, Scope guard п.3); при необходимости E2 можно сдвинуть в волну 2, если ревью владельца выявит дубли аккаунтов команды.

## Вне скоупа

- **Жёсткое удаление и обезличивание аккаунтов** (решение владельца №1), включая кнопку «Удалить» для клиентов.
- **«Обязательные» уведомления, которые нельзя отключить** (замок), решение №3. Критические инфраструктурные алерты по-прежнему идут мимо Центра и не управляются тумблерами.
- **Бизнес-реакция**: «бронь обработана», «лид взят в работу», «заявка закрыта» — только прочтение и клик.
- **Каналы и тихие часы по каждому событию** (данные в схеме есть, не запрашивалось). Существующие «не беспокоить»/тихие часы только отображаются как причина блокировки.
- **Новые модули**, новые типы событий, новые каналы доставки (SMS и др.).
- **Статистика клиентских уведомлений и рассылок** — только получатели из команды.
- **Уведомление исключённому** о факте исключения; кнопка «Вернуть в команду» с автоматическим восстановлением прав; автопереназначение его задач; массовое исключение/массовая смена подписок.
- **Откат объединения в интерфейсе.**
- **Прочтение в Telegram и Web Push** — технически недоступно.
- **Починка таба «Чаты»** (мессенджер Mini App) и общая унификация авторизации.
- **Смена сидера** (`SUPERADMIN_TELEGRAM_ID`): в рамках PRD только предупреждение; изменение механики — на усмотрение Architect, если предложит безопасный вариант.
- **Интеграции с BI и автоматические алерты по падению реакции** (график и CSV — только Could D4.4).

## Открытые вопросы для Architect

Решения не предрешены; PO описал требуемое поведение.

1. **Отзыв сессий.** Вход на JWT, роль/разделы обновляются при входе, в edge-прокси нет доступа к базе. Как обеспечить «не позднее 60 секунд» для веб-админки, Mini App и бота (версия сессии на пользователе, проверка роли из базы, короткий TTL и др.)? Что делать с токенами Mini App и токенами «вход из бота»?
2. **Атомарность исключения.** Списки получателей лежат в JSON настроек модулей (идентификаторы пользователей внутри). Как делать «всё или ничего» и не потерять конкурентную правку настроек модуля? Нужно ли вынести список в отдельную таблицу?
3. **Модель хранения кликов, прочтений и пропусков.** Отдельная таблица реакций или поля на уведомлении? Как покрыть три источника (исходящие, лента Mini App, групповые чаты)? Агрегация для срезов 7/30/90, сроки хранения (клики ≥ 90 дней; ссылки живут ≥ 12 месяцев, AC-D3.8), объём.
4. **Трекинг-ссылки.** Формат непредсказуемого кода, где хранится целевой адрес, белый список назначений, поведение при просрочке, обработка HEAD/предпросмотров, лимиты для мобильных сетей за общим адресом. Кнопки URL и кнопки Mini App (`web_app`): что менять для измерения.
5. **Признак бота.** Источники сигнала (команда `/start`, сообщения, события блокировки), хранение по Telegram-аккаунту отдельно от пользователя (до привязки), бэкфилл по истории, различение «не запускал» и «заблокировал» по ответам Telegram, влияние флага `allows_write_to_pm` при запуске Mini App.
6. **Правила объединения ролей, прав и подписок.** Расширение сегодняшнего объединения клиентов (только USER ↔ USER) на сотрудников: как реализовать правила из AC-E2.4; перепривязка идентификаторов в JSON списков получателей; сидер ищет суперадмина по Telegram ID (при вливании сидированного аккаунта вторичным он создал бы нового суперадмина) — менять сидер или оставить запрет AC-E2.4(д).
7. **Единый расчёт «кто получает».** Как сделать один источник правды для реальной рассылки и для экранов C1/C4/Центра: списки раздела, личные подписки, роль (Авито), лента суперадмина, общий чат. Как реализовать «явное выкл побеждает любой путь» (AC-C2.1) без ломки существующих настроек разделов.
8. **Ключ подписки.** Столкновение подписок сотрудника и клиентских уведомлений одного типа события (AC-A1.4, риск 3). Нужно ли разводить ключи?
9. **Самопривязка к аккаунтам сотрудников.** Бот сегодня намеренно не дополняет аккаунты сотрудников (admin-аккаунты входят только по паролю/ссылке). Согласовать политику: PO предлагает OTP запретить для SUPERADMIN и разрешить для ADMIN/MANAGER с записью в журнал; альтернатива — только deep-link из вошедшей сессии и объединение админом.
10. **Единый источник «какие разделы доступны ADMIN».** Часть разделов ADMIN получает по роли, часть явными правами; Центр и экран C1 должны показывать то же, что гейт админки (AC-C3.4, A4.5).
11. **Нагрузка и производительность** страницы статистики и таба «Команда» (AC-B2.6, D1.10); «последний вход» — из какого источника, поддерживается ли он для входа по email.
12. **Нарезка на поставки** с соблюдением CLAUDE.md (Scope guard п.3, п.4: синк таблицы модулей в том же PR — `users`, `notifications`, `telegram-link`, `clients`).
