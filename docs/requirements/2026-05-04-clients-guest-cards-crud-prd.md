# PRD: CRM Карточка гостя — справочник + автозаполнение из Booking

**Тикет**: F4  
**RUN_ID**: `2026-05-04-clients-guest-cards-crud`  
**Дата**: 2026-05-04  
**Модуль**: `clients`  
**Статус**: Ready for Architect

---

## Проблема

Менеджер Плей Парка принимает гостей «с улицы» каждый день. Он вводит имя и телефон при бронировании вручную, но этот гость нигде не сохраняется как полноценная карточка: нет истории визитов, нет заметок, нет возможности перезвонить или найти его через поиск.

Параллельно: когда гость бронирует стол и менеджер указывает его телефон при создании брони — система не привязывает бронь к карточке User. В итоге Booking.userId остаётся пустым, гость невидим в CRM, и при следующем визите вся история теряется.

Две конкретные боли:

1. **Нет списка гостей** — страница `/admin/clients` не существует. Менеджер не может найти гостя, посмотреть его историю или создать карточку вручную.
2. **Брони с телефоном не привязываются к User** — при создании брони через админку (`createAdminBooking`) код уже ищет или создаёт User по телефону, но логика неполная: `phone` используется в поиске, а не `phoneNormalized`, что ломается при разных форматах (+7 999..., 8999..., +7-999-...).

---

## Решение

Расширяем модуль `clients` (уже существует) без создания новых моделей:

- **Страница `/admin/clients`** — список всех пользователей с ролью USER: поиск, фильтры, пагинация, кнопка создания.
- **Форма создания/редактирования гостя** — по аналогии с формой поставщика (`suppliers-list.tsx`): телефон обязателен, имя/email/день рождения/теги/заметки опциональны.
- **API `POST /api/clients`** и **`PATCH /api/clients/:id`** — создание и редактирование гостя.
- **Нормализация телефона в `createAdminBooking`** — переключить поиск существующего User с `phone` на `phoneNormalized`, обеспечив upsert по нормализованному значению.

Решение зафиксировано заказчиком: новая модель `Guest` не создаётся. Карточка гостя = запись User с `role=USER`. Страница `/admin/clients/[id]` уже существует и работает.

---

## Целевая аудитория

- **MANAGER** (Плей Парк) — основной актор: создаёт карточки гостей при бронировании вручную, редактирует заметки после визита.
- **SUPERADMIN** — видит всех гостей, может редактировать любую карточку.

## User Stories

### US-1: Список гостей

- **Как** менеджер Плей Парка (MANAGER)
- **Я хочу** открыть страницу «Гости» в админке и увидеть список всех гостей с поиском
- **Чтобы** быстро найти нужного гостя, посмотреть когда он последний раз был и открыть его карточку

**Acceptance Criteria:**

- [ ] AC-1: Страница `/admin/clients` существует и доступна для ролей MANAGER и SUPERADMIN. Попытка открыть неавторизованным пользователем возвращает редирект на страницу входа.
- [ ] AC-2: На странице отображается таблица гостей (User с role=USER и mergedIntoUserId=null) с колонками: имя, телефон, email, дата последней активности, количество броней.
- [ ] AC-3: Поле поиска фильтрует список по имени, телефону и email (без учёта регистра). При пустом поиске отображаются все гости.
- [ ] AC-4: Список разбит на страницы по 50 записей. При >50 гостях отображается пагинация с навигацией вперёд/назад.
- [ ] AC-5: Нажатие на строку гостя открывает его карточку по маршруту `/admin/clients/[id]`.

### US-2: Создание карточки гостя вручную

- **Как** менеджер Плей Парка (MANAGER)
- **Я хочу** нажать «+ Создать гостя», ввести телефон и имя, сохранить
- **Чтобы** гость появился в базе до его первого бронирования (например, при записи по телефону)

**Acceptance Criteria:**

- [ ] AC-6: На странице `/admin/clients` есть кнопка «+ Создать гостя». Нажатие открывает форму с полями: телефон (обязательный), имя (опциональное), email (опциональное), день рождения (опциональное), заметки (опциональное).
- [ ] AC-7: При попытке сохранить форму без телефона — форма подсвечивает поле ошибкой «Телефон обязателен». Запрос на сервер не отправляется.
- [ ] AC-8: При вводе телефона, который уже зарегистрирован в системе (по `phoneNormalized`), сервер возвращает ошибку «Гость с таким телефоном уже существует» (HTTP 409). Форма отображает это сообщение.
- [ ] AC-9: При успешном создании новый гость появляется в списке на странице `/admin/clients` без перезагрузки всей страницы. Форма закрывается.
- [ ] AC-10: Новый гость создаётся с `role=USER` и `source="manual"`. Мутация фиксируется в AuditLog с action `client.create`.

### US-3: Редактирование карточки гостя

- **Как** менеджер Плей Парка (MANAGER)
- **Я хочу** открыть карточку гостя и отредактировать его заметки, теги или день рождения
- **Чтобы** сохранить важную информацию (предпочтения, особенности) для следующего визита

**Acceptance Criteria:**

- [ ] AC-11: На странице карточки `/admin/clients/[id]` есть кнопка «Редактировать». Нажатие открывает форму редактирования с текущими значениями полей: имя, телефон, email, день рождения, заметки.
- [ ] AC-12: Изменения сохраняются через `PATCH /api/clients/:id`. После сохранения карточка обновляется без перехода на другую страницу.
- [ ] AC-13: Поле телефон при редактировании изменять нельзя (поле заблокировано в UI). Смена телефона — операция мерджа (отдельный механизм, вне скоупа).
- [ ] AC-14: Мутация фиксируется в AuditLog с action `client.update` и метаданными «было/стало» для изменённых полей.

### US-4: Автоматическая привязка гостя при бронировании в Плей Парке

- **Как** менеджер Плей Парка (MANAGER)
- **Я хочу** чтобы при создании брони с телефоном гостя система автоматически находила или создавала карточку гостя и привязывала её к брони
- **Чтобы** история визитов гостя копилась автоматически без ручного создания карточек

**Acceptance Criteria:**

- [ ] AC-15: При создании брони через `createAdminBooking` с указанным `clientPhone` — поиск существующего User выполняется по полю `phoneNormalized` (нормализованное значение), а не по сырому `phone`. Телефоны `+79991234567`, `89991234567` и `+7 999 123-45-67` должны находить одну и ту же запись.
- [ ] AC-16: Если User с таким `phoneNormalized` не найден — создаётся новый User с `role=USER`, `source="ps_park_booking"`, `phone=clientPhone`, `phoneNormalized=<нормализованное>`. Бронирование привязывается к нему через `userId`.
- [ ] AC-17: Если User с таким `phoneNormalized` уже есть — `userId` брони указывает на него. Дубль User не создаётся.
- [ ] AC-18: Если `clientPhone` не указан или пустой — `Booking.userId` остаётся `null`. Логика идентична текущему поведению (без регрессии).
- [ ] AC-19: После релиза доля броней Плей Парка с непустым `clientPhone` и пустым `userId` снижается. Целевой показатель через 2 недели: менее 10% от таких броней (созданных после релиза) остаются с `userId=null`.

## Acceptance Criteria — сводный чеклист

1. Страница `/admin/clients` существует, требует авторизации MANAGER/SUPERADMIN.
2. Список гостей с поиском и пагинацией.
3. Форма создания гостя с обязательным телефоном.
4. Форма редактирования из карточки.
5. `POST /api/clients` создаёт User(role=USER, source="manual"), возвращает 409 при дубле по phoneNormalized.
6. `PATCH /api/clients/:id` обновляет name/email/birthday/notes, не позволяет менять phone.
7. `createAdminBooking` в ps-park использует phoneNormalized для поиска/upsert User.
8. Все мутации логируются в AuditLog.
9. API требует роль MANAGER или SUPERADMIN (не публичный).

## Приоритет (MoSCoW)

**Must have** — весь скоуп тикета F4.

Обоснование: без списка гостей менеджер работает вслепую. Каждый день в Плей Парке проходят десятки гостей, которые не накапливаются в CRM. Это блокирует любую персонализацию (программа лояльности, Phase 5.1) и делает аналитику неполной — сейчас значительная доля броней Плей Парка имеет `userId=null`.

Зависимости:
- `src/modules/clients/service.ts` — уже есть, расширяем.
- `src/modules/ps-park/service.ts` — точечное изменение в `createAdminBooking`.
- `prisma/schema.prisma` — схема достаточна (birthday, tags, notes, phoneNormalized уже есть). Миграция нужна только если Architect решит добавить UNIQUE-индекс на phoneNormalized (см. Open Questions).

```sql
SELECT COUNT(*) FROM "Booking"
WHERE "moduleSlug" = 'ps-park'
  AND "clientPhone" IS NOT NULL
  AND "userId" IS NULL
  AND "createdAt" > '<дата_релиза>';
```

Значение должно убывать со временем.

## Edge Cases

| Сценарий | Ожидаемое поведение |
|----------|---------------------|
| Разные форматы телефона при бронировании | Поиск по `phoneNormalized`. Architect подтверждает алгоритм нормализации (уже используется в схеме). |
| Телефон совпадает, email отличается | Не мержим автоматически. Возвращаем существующего User по phoneNormalized. |
| Телефон null / пустая строка при бронировании | Booking.userId остаётся null. Поведение не меняется. |
| Менеджер создаёт гостя без телефона | UI блокирует (client-side validation). Zod отклоняет на бэке (HTTP 400). |
| Два менеджера одновременно создают гостя с одним телефоном | Второй запрос получает HTTP 409 (phoneNormalized уникален — см. Open Questions). |
| Список >1000 гостей | Пагинация по 50 записей. `listClients()` уже поддерживает `limit`/`offset`. |

| Риск | Вероятность | Митигация |
|------|-------------|-----------|

## Open Questions для Architect

1. **phoneNormalized — UNIQUE сейчас?** В схеме есть `@@index([phoneNormalized])` и комментарий «уникальность только когда mergedIntoUserId IS NULL» (partial UNIQUE). Нужно ли добавить/подтвердить этот partial unique constraint для гарантии защиты от дублей при конкурентном создании? Если нет — нужна ли оптимистичная блокировка или `upsert`?

2. **Алгоритм нормализации телефона**: какая функция `normalizePhone` уже используется в кодовой базе? Нужно ли убедиться, что она покрывает форматы `+7`, `8`, `007`, пробелы и дефисы? Уточнить, прежде чем менять логику в `createAdminBooking`.

3. **Отдельная модель `ClientNote`?** Сейчас `notes` — одно текстовое поле в User. Для истории заметок (автор, время, текст) нужна отдельная модель `ClientNote`. Для данного тикета достаточно строкового `notes` или уже сейчас делаем нормальный audit trail заметок?

4. **Место upsert в `checkInBooking`**: сейчас upsert User реализован в `createAdminBooking`. Нужно ли добавлять аналогичный upsert в `checkInBooking` (когда менеджер делает check-in и только тогда знает телефон гостя)? Или это следующий тикет?

5. **`GET /api/clients` — уже частично существует?** Нужно уточнить у Developer: есть ли route handler `src/app/api/clients/route.ts` или директория `src/app/api/clients/` пустая? Это определяет, создавать ли с нуля или дописывать существующий обработчик.
