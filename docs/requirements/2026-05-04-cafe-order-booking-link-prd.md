# PRD: F5 — Cafe Order ↔ Booking link (backend миграция и API)

> RUN_ID: `2026-05-04-cafe-order-booking-link`
> Дата: 2026-05-04
> Размер: S
> Зависимости: модули `cafe`, `ps-park`, общая модель `Booking`

---

## Проблема

Менеджер PS Park видит сессии: кто играл, когда, сколько. Но не видит, что гость пил и ел во время игры — заказы кафе нигде не привязаны к сессии. В результате при разборе любой прошедшей сессии менеджер вынужден вручную сопоставлять время заказа с временем брони. Это невозможно делать системно.

Цель тикета F5 — создать структурную связь между кафе-заказом и конкретной игровой сессией (Booking). Без этой связи любой drill-down по сессии (F7) останется неполным: данные физически не соединены на уровне базы.

**Персона:** MANAGER PS Park.

---

## Решение

Добавить необязательную ссылку на бронирование к кафе-заказу. Когда менеджер создаёт кафе-заказ в контексте активной сессии, заказ автоматически получает привязку. Обычные заказы из кафе (без сессии) продолжают работать без изменений.

---

## Целевая аудитория

**MANAGER** — менеджер PS Park, который ведёт активную сессию и хочет видеть полную картину: брони, платежи, еда и напитки — в одном месте.

---

## User Stories

### US-1: Создание кафе-заказа в контексте активной сессии

- **Как** менеджер PS Park, ведущий активную сессию
- **Я хочу** добавить кафе-заказ прямо из карточки сессии
- **Чтобы** этот заказ был автоматически привязан к сессии и впоследствии (F7) отображался в истории сессии

**Acceptance Criteria:**

- [ ] AC-1.1: **Схема данных** — модель `Order` содержит поле `bookingId String?` (NULL по умолчанию), индекс `@@index([bookingId])`, FK с поведением `onDelete: SetNull` на модель `Booking`. Существующие записи `Order` сохраняются нетронутыми после миграции.

- [ ] AC-1.2: **Сервисный слой** — функция `createOrder` принимает необязательный параметр `bookingId`. Если `bookingId` передан и Booking с таким ID не существует в базе (включая мягко удалённые — `deletedAt IS NOT NULL`), сервис выбрасывает ошибку с кодом `BOOKING_NOT_FOUND`. Если `bookingId` не передан, поведение идентично текущему.

- [ ] AC-1.3: **API** — `POST /api/cafe/orders` принимает в теле запроса необязательное поле `bookingId: string`. Zod-схема `createOrderSchema` расширена: `bookingId: z.string().cuid().optional()`. При невалидном формате строки API возвращает `400` с понятным сообщением. При несуществующем `bookingId` API возвращает `404` с кодом `BOOKING_NOT_FOUND`.

- [ ] AC-1.4: **UI — PS Park** — в компоненте, открытом в контексте активной сессии PS Park, при создании кафе-заказа автоматически передаётся `bookingId` текущей сессии. Менеджер не вводит `bookingId` вручную. Компонент `add-items-button.tsx` сейчас отправляет запрос к `/api/ps-park/bookings/{bookingId}/add-items` (inventory-операция). Для кафе-заказа нужен отдельный путь: либо новая кнопка `CafeOrderButton`, либо расширение существующего модального окна — решение за Architect.

- [ ] AC-1.5: **Обратная совместимость** — все существующие вызовы `createOrder` без `bookingId` работают без изменений. Ни один существующий тест не должен упасть после изменения сигнатуры.

- [ ] AC-1.6: **Тесты** — в `src/modules/cafe/__tests__/service.test.ts` присутствуют тесты: (a) `createOrder` без `bookingId` — Order создаётся с `bookingId: null`; (b) `createOrder` с валидным `bookingId` — Order создаётся с заполненным `bookingId`; (c) `createOrder` с несуществующим `bookingId` — выбрасывается `OrderError` с кодом `BOOKING_NOT_FOUND`. Тесты мокируют Prisma через `vi.mock('@/lib/db')`.

### US-2: Заказ кафе без сессии (текущий сценарий)

- **Как** менеджер кафе или клиент
- **Я хочу** создавать кафе-заказы как сейчас, без указания сессии
- **Чтобы** обычный workflow кафе не изменился и не сломался

**Acceptance Criteria:**

- [ ] AC-2.1: `POST /api/cafe/orders` без поля `bookingId` в теле работает как сейчас, возвращает `201` с созданным Order, в котором `bookingId: null`.

- [ ] AC-2.2: После деплоя запрос `SELECT COUNT(*) FROM "Order" WHERE "bookingId" IS NOT NULL` возвращает `0` до первого создания привязанного заказа — подтверждает, что миграция не затронула исторические данные.

---

## Приоритет (MoSCoW)

**Must have.**

Без этой связи данные о сессии останутся неполными навсегда: исторические заказы нельзя будет backfill-ить (не известно, к какой сессии они принадлежат). F7 (drill-down по сессии) невозможен без F5. Связь нужно устанавливать с момента запуска, иначе теряем аналитическую ценность каждого нового заказа.

**Зависимости:**
- Блокирует: F7 (UI drill-down по сессии)
- Зависит от: ничего нового — `Booking` и `Order` уже существуют

## Метрики успеха

| Метрика | Базовое значение | Целевое (через 2 недели после деплоя) |
|---|---|---|
| Доля заказов, созданных из PS Park с `bookingId` | 0% (поле не существует) | 50% заказов из контекста сессии имеют `bookingId` |
| Ошибки при создании заказа (5xx) | 0 | 0 (регрессия недопустима) |
| Тест-покрытие `createOrder` | не измеряется | 3 новых теста, все зелёные |

---

## Вне скоупа

- **Backfill исторических заказов** — невозможен и не нужен: нельзя ретроспективно определить, к какой сессии принадлежал заказ.
- **UI drill-down прошедших сессий** — это F7, отдельный тикет.
- **Изменения в меню, корзине, самообслуживании** — текущий тикет касается только поля `bookingId` в заказе.
- **Telegram-бот заказов** — вне скоупа.
- **Беседки (gazebos)** — `bookingId` технически совместим с любым `moduleSlug`, но UI для газебо в этом тикете не делается.
- **Валидация статуса Booking** — намеренно не ограничиваем: заказ можно привязать к завершённой или отменённой брони (например, менеджер закрывает чек после завершения сессии и обнаруживает добавленный кофе). Это решение PO.

## Открытые вопросы для Architect

1. **Relation name** — добавить `booking Booking? @relation(...)` в `Order` или оставить только поле `bookingId` без явного relation на стороне `Booking`? Если relation двусторонний — нужно добавить `orders Order[]` в `Booking`. PO-предпочтение: добавить relation для type-safety в Prisma, решение за Architect.

2. **UI: новая кнопка vs расширение** — `add-items-button.tsx` сейчас создаёт inventory-транзакцию (через `/api/ps-park/bookings/{id}/add-items`), а не кафе-заказ. Нужен либо отдельный компонент `CafeOrderButton`, либо модальное окно с вкладками «Товары» / «Кафе». Architect выбирает минимальный вариант.

3. **Вызов `BOOKING_NOT_FOUND` при soft-deleted Booking** — PO-решение: разрешать привязку к `deletedAt IS NOT NULL` Booking (для аналитики, менеджер мог создать заказ сразу после закрытия). Если Architect считает иначе — обсудить до старта разработки.
