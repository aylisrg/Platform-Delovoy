# Независимая оценка бизнес-аналитики

Дата: 2026-10-31. Основание: архитектура `docs/architecture/2026-10-31-business-analytics.md`, код main `3ab30cdb`. Проверены модели и сервисы; производственные финансовые данные не запрашивались. Это оценка возможностей и расчётов, а не результат анализа реальных продаж.

## Вердикт

Предложенная архитектура годится для первой поставки после уточнений P0 ниже. Сильные решения: отделение денег от заказов и начисленной выручки, явное исключение офисов, разделение дат спроса/обслуживания/денежной записи, отказ от неподтверждённых ROAS/прибыли, проверка текущей роли перед показом и доставкой. Главный риск — создать впечатление полной кассы на основе неполного леджера.

## Уточнения расчётов и безопасности

1. Дедупликация ONLINE_PAYMENT по paymentId, REFUND по refundId; несколько реальных частичных возвратов одного платежа считаются отдельно. Каноническая первая запись должна выбираться глобально по ключу, иначе дубль в другом периоде попадёт в две разные сводки. Конфликтующие суммы не разрешать произвольным «первым» значением: показывать проблему качества.
2. Строгий allowlist применяется и к основному факту, и к связанной Payment/Booking/Order/Subscription. `Payment.subjectType=RENTAL_PAYMENT` исключён даже при ошибочном moduleSlug. Привязанные к офисам заказы не использовать для показателей офисной деятельности; заказы самого кафе можно считать только как факт кафе, без офисных сумм/измерений.
3. Денежная дата FinancialTransaction.createdAt — дата регистрации в книге; Payment.paidAt — дата оплаты у провайдера. В день позднего webhook они различаются. Подпись/CSV обязаны сохранять выбранную семантику. Деньги возвращаются в периоде возврата, даже если исходная оплата раньше.
4. Не рассчитывать «средний чек» как денежный приход окна / завершённые брони окна: аванс, абонемент, возврат и посещение принадлежат разным когортам. Допустимы отдельно средняя сумма заказов кафе и средняя сумма зарегистрированной транзакции, с точным названием.
5. Повторность: два отдельных показателя — несколько завершённых визитов в выбранном периоде и возвращение гостя с завершённым визитом до начала периода. Для первого достаточно окна, второй требует исторического запроса. На экране назвать реализованный вариант точно; долю считать только среди идентифицированных клиентов и показать покрытие идентификацией.
6. Cafe attach rate = число уникальных обслуженных Booking с ≥1 учитываемым связанным Order / число обслуженных Booking той же когорты. Количество заказов / количество броней — другая метрика и может превышать 100%. Заказы считаются один раз по id независимо от количества товарных строк.
7. Визуальный отчёт, CSV и Telegram используют один DTO и версию определения метрик. `generatedAt` плюс границы периода видны везде; в CSV должны остаться ограничения полноты и исключение офисов, иначе экспорт теряет смысл подписи.
8. `NotificationLog` с детерминированным id подходит как durable claim. При неопределённом сетевом исходе статус нельзя обозначать уверенным «не отправлено» и автоматически повторять. UI показывает «исход доставки неизвестен». Повтор теста должен быть защищён от двойного клика.
9. Для контакта Telegram использовать имеющийся `computeBotStatus`: `blockedAt` исторически сохраняется после разблокировки, проверять только его наличие неверно. Существующий gate положительного telegramId + свежая привязка пользователя исключает группы и подмену получателя.
10. Если в будущем отчёт кладётся в общий Mini App feed/OutgoingNotification, роль проверяется также при чтении старых записей, счётчиков и прямого id. Нельзя полагаться только на проверку при отправке. Первой поставке проще хранить там только безопасную ссылку, сами цифры получать через защищённый API.

## Что полезно добавить в рамках первой поставки

- Блок «Нужна проверка»: количество исключённых тестовых строк, несогласованных/дублированных записей и реальных оплат без записи. Отдельно отличать нормальное исключение тестов от ошибки.
- Плей Парк: посещения/отмены/NO_SHOW и потреблённые часы абонементов как натуральные величины; продажа абонемента и списание часов — две разные шкалы. Сумму услуг, покрытых абонементом, не называть новым денежным приходом.
- Кафе: число заказов, выданных без онлайн-подтверждения, и связанные заказы по паркам. Это даёт оператору список процессов, которые требуют сверки, без фиктивной «выручки».
- Сравнение с предыдущим равным окном: абсолютная разница и процент только при ненулевой сопоставимой базе. При изменившемся покрытии данных предупредить, что изменение не обязательно означает рост/падение бизнеса.
- Две очевидные вкладки «Бизнес» и «Сайт и реклама», один доступный вход. Цифры сайта не подмешивать в исключающие офисы бизнес-итоги.
- Telegram: компактный итог за завершённую неделю, три направления, сумма возвратов, предупреждение о неполном учёте и кнопка защищённого отчёта с тем же периодом. Не отправлять персональные данные гостей.

## Следующие возможности, без ложных обещаний текущей поставки

| Возможность | Что нужно для надёжного результата |
|---|---|
| Полная касса и сверка смен | Проводка ручных продаж абонементов, офлайн-заказов кафе и ручных авансов с уникальным источником, способом оплаты и отменой через обратную запись. |
| Загрузка ресурсов по часам | Пересечение интервалов брони с окном, календарь доступности/закрытий и историческая ёмкость. Количество броней / число часовых слотов — неверный процент загрузки. До календаря показывать занятые часы, не точный utilization. |
| Сквозной ROAS/CAC | Стабильная связь разрешённых campaign/lead/session→entity→Payment, модель атрибуции и окно, сумма рекламных расходов нужных кампаний. Общий доход всех клиентов / общий рекламный расход не доказывает отдачу рекламы. |
| Валовая прибыль и маржинальность | Датированные затраты, себестоимость списанных SKU, распределение скидки по строкам, эквайринг/налоги/расходы периода. Наличие Expense или текущей цены SKU само по себе недостаточно. |
| Когортное удержание/LTV | Канонический клиент после merge, известная доля гостей без идентификации, история повторных посещений; стабильные когорты и наблюдаемое окно. |
| Ранние сигналы владельцу | После накопления сопоставимой базы — пороги отмен, просадки оплаченных посещений и разрывов сверки. Сначала показать факты и покрытие, затем вводить алерты с проверенным baseline. |

## Приёмка для следующего этапа

Дизайнер должен видеть четыре разных состояния: значение 0, данные не подключены, учёт частичный, загрузка/ошибка. Ограничение полноты нельзя прятать только в tooltip. API/CSV/Telegram не содержат офисных чисел и не расходятся по формулам. Финансовые итоги не называются прибылью или начисленной выручкой. Перед выпуском QA проверяет пустой период, ручной абонемент, доставленный офлайн-заказ, доплату ADJUSTMENT, тестовую онлайн-оплату, возврат следующей недели, дубль в другом периоде, отсутствующую запись леджера, отзыв роли и повтор отправки.
