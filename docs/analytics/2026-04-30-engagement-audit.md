### Критические находки от Метрики

1. **Funnel start не инструментирован.** Цели «начал бронирование» по трём модулям имеют **0 reaches за 24 дня**. Либо событие не отправляется с фронта, либо триггер цели в Метрике настроен неверно. Без этого мы **слепы к самой важной точке воронки** — где пользователь решил, но передумал.
2. **Я.Директ: 126 визитов, 0 целей.** За 24 дня платный канал не дал ни одного целевого действия. Деньги уходят впустую — нужен либо stop рекламы, либо аудит лендингов под её аудиторию.
3. **Конверсия в бронь беседки = 0.95%, PS Park = 0.57%, Офис = 0.19%.** Для CTR с прямого канала это очень мало (бенчмарк B2C-бронирования: 2-5%). Подтверждает гипотезу H1: проблема не с трафиком, а с **продуктом** между «зашёл» и «забронировал». _(Кафе из расчётов исключено — модуль намеренно скрыт из навигации.)_
4. **Метрика валидирует данные dev-БД.** В Метрике 5 успешных броней беседки (since launch) — в dev-БД 6 (включая ручной admin-create). Расхождение в 1 — admin-create. То есть **dev-данные структурно корректны, не «случайные тестовые»** — гипотезы H1-H7 валидны.
5. **17 целей создано, 6 пустых.** Помимо «начал бронирование» нулём идут «клик по email», «соцсеть», «поиск по сайту». Часть может отсутствовать на сайте (нет email-ссылок) — норма. Но 3 funnel-start цели — это технический долг инструментации.

## Топ-3 проблемы

### Проблема 1: Пользователи не бронируют самостоятельно

67% всех бронирований создаёт администратор (`booking.admin_create`). Только 2 из 12 USER-аккаунтов воспользовались самостоятельным бронированием. Это означает либо отсутствие точек входа в веб-интерфейс, либо UX-барьер на этапе создания брони.

### Проблема 2: Беседки теряют клиентов — 66.7% отмен

4 из 6 бронирований беседок отменены. Для модуля с ограниченным числом ресурсов (5 беседок) это критично. Причины: нет данных о мотиве отмен (поле `cancelReason` не заполнено).

### Проблема 3: Каналы уведомлений не настроены — 39.4% SKIPPED

Статус SKIPPED говорит о том, что система пытается отправить уведомление, но не знает куда. У пользователей нет привязанного Telegram и не настроен `NotificationPreference`. Пользователь не получает подтверждение брони — лишается уверенности в транзакции.

## Топ-3 гипотезы "что не так"

### Гипотеза 1: Нет онбординга — пользователь не знает что делать после регистрации

Платформа запустилась 14 апреля, но публичный личный кабинет в вебе не реализован (Phase 2, "НЕ СДЕЛАН" по CLAUDE.md). Пользователь регистрируется через signin, но оказывается в тупике: некуда перейти, нет подсказки "забронируй беседку" или "посмотри меню". Без ясного следующего шага конверсия регистрация → первое действие падает.

**Проверка:** На prod посмотреть % пользователей, которые в рамках одной сессии после регистрации перешли на `/gazebos` или `/ps-park`.

### Гипотеза 2: Кафе недоступно пользователям или не продвигается

0 онлайн-заказов при 8 позициях меню может означать: (a) страница кафе не найдена / не связана с навигацией, (b) пользователь не видит кнопку "Заказать", (c) модуль работает только в офлайн-режиме через менеджера. При этом кафе потенциально высокочастотный модуль (ежедневные заказы).

**Проверка:** Добавить в AuditLog событие `cafe.menu_view` и замерить просмотры vs заказы.

### Гипотеза 3: Telegram-бот не привлекает аудиторию — не анонсирован или нет точки входа

0 пользователей с привязанным Telegram означает: либо бот не продвигается (нет QR-кода в офисе, нет ссылки на сайте), либо flow привязки Telegram-аккаунта к web-профилю сломан. При этом именно Telegram — основной канал уведомлений и обратной связи.

**Проверка:** На prod посмотреть количество `/start` в боте через `SystemEvent` с source='telegram-bot'.

## Ограничения анализа (слепые зоны)

### Отсутствует инструментация просмотров страниц

В БД нет событий типа `page.view`, `menu.view`, `resource.view`. AuditLog содержит только мутации (создание, изменение). Это означает:
- Невозможно посчитать воронку просмотр → бронирование.
- Нельзя замерить bounce rate.
- Неизвестно, сколько пользователей дошли до страницы бронирования, но не нажали кнопку.

**Рекомендация:** добавить серверные события просмотра в `SystemEvent` или подключить Yandex Metrika server-side (задача уже зафиксирована в `docs/analytics/2026-04-29-metrika-tracking-gap.md`).

### AuditLog не покрывает пассивное поведение

Все записи AuditLog — это мутации. Пользователь, который просматривал расписание PS Park но ничего не забронировал, не виден в данных вообще.

### Причины отмен бронирований неизвестны

Поле `cancelReason` в таблице `Booking` присутствует, но в 100% случаев не заполнено. Невозможно понять: пользователь передумал, нашёл другое время, или столкнулся с UX-проблемой.

**Рекомендация:** сделать `cancelReason` обязательным полем при отмене через UI (dropdown с вариантами + поле "другое").

### Telegram-бот не логирует сессии в БД

Взаимодействие с ботом не отражается в `AuditLog` (нет `booking.bot_create` или аналога). Если пользователь бронирует через бота, это видно только как `booking.create` без атрибуции к каналу.

**Рекомендация:** добавить поле `source` в `Booking` (`'web'|'bot'|'admin'`) или заполнять `metadata.source` при создании через бота.

## SQL-шаблоны для production

-- DAU по дням (только END-USER активность)
SELECT
  DATE(al."createdAt") AS day,
  COUNT(DISTINCT al."userId") AS dau
FROM "AuditLog" al
JOIN "User" u ON u.id = al."userId"
WHERE u.role = 'USER'
  AND al."createdAt" >= :period_start
  AND al."createdAt" < :period_end
GROUP BY DATE(al."createdAt")
ORDER BY day;

WITH user_funnel AS (

    u."createdAt" AS registered_at,
    MIN(b."createdAt") AS first_booking_at,
    MIN(o."createdAt") AS first_order_at
  FROM "User" u
  LEFT JOIN "Booking" b ON b."userId" = u.id AND b."deletedAt" IS NULL
  LEFT JOIN "Order" o ON o."userId" = u.id AND o."deletedAt" IS NULL
  WHERE u.role = 'USER'
    AND u."createdAt" >= :period_start
  GROUP BY u.id, u."createdAt"
)
SELECT
  COUNT(*) AS total_registered,
  COUNT(LEAST(first_booking_at, first_order_at)) AS activated,
  ROUND(COUNT(LEAST(first_booking_at, first_order_at))::numeric / NULLIF(COUNT(*), 0) * 100, 1) AS activation_rate_pct
FROM user_funnel;

-- W1→W2 Retention (Booking-based)
WITH week1 AS (
  SELECT DISTINCT "userId"
  FROM "Booking"
  WHERE "createdAt" >= :week1_start AND "createdAt" < :week1_end
    AND "deletedAt" IS NULL
),
week2 AS (
  SELECT DISTINCT "userId"
  FROM "Booking"
  WHERE "createdAt" >= :week2_start AND "createdAt" < :week2_end
    AND "deletedAt" IS NULL
)
SELECT
  COUNT(w1."userId") AS week1_cohort,
  COUNT(w2."userId") AS retained_in_week2,
  ROUND(COUNT(w2."userId")::numeric / NULLIF(COUNT(w1."userId"), 0) * 100, 1) AS retention_pct
FROM week1 w1
LEFT JOIN week2 w2 ON w1."userId" = w2."userId";

-- Cancellation rate по модулям
SELECT
  "moduleSlug",
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE status = 'CANCELLED') AS cancelled,
  ROUND(COUNT(*) FILTER (WHERE status = 'CANCELLED')::numeric / NULLIF(COUNT(*), 0) * 100, 1) AS cancel_rate_pct
FROM "Booking"
WHERE "deletedAt" IS NULL
  AND "createdAt" >= :period_start AND "createdAt" < :period_end
GROUP BY "moduleSlug";

-- Notification delivery health
SELECT
  status,
  channel,
  COUNT(*) AS cnt,
  ROUND(COUNT(*)::numeric / SUM(COUNT(*)) OVER () * 100, 1) AS pct
FROM "NotificationLog"
WHERE "createdAt" >= :period_start AND "createdAt" < :period_end
GROUP BY status, channel
ORDER BY cnt DESC;
