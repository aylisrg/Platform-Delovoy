## Проверка логики дедупликации (детально)

- **Семантика ключа по `lastHeartbeatAt`.** Пока heartbeat не обновился (эпизод молчания продолжается), `lastHeartbeatAt` неизменен → один и тот же Redis-ключ на весь эпизод → повторные опросы `site-watchdog` (раз в 5 мин) корректно гасятся `NX`. Как только приходит новый heartbeat (эпизод закончился), `ok=true` и функция возвращает `false` без обращения к Redis (`health.ts:245`) — новый будущий эпизод получит новый ключ автоматически. Корректно.
- **Гонки.** `SET NX EX` атомарен на стороне Redis — конкурентные вызовы (например, параллельные health-запросы от разных вантажных точек, `site-watchdog` + deploy-smoke) не могут оба получить `true`: ровно один вызывающий пройдёт. Совпадает с уже существующим паттерном троттлинга в `src/lib/logger.ts:72-78` (`critical-alert:<source>`), т.е. решение архитектурно согласовано с существующим кодом.
- **Повторное окно = TTL порога (6ч).** Совпадение `OWNER_DECISIONS_ALERT_REPEAT_SECONDS` и `OWNER_DECISIONS_STALE_MINUTES` (оба 6ч) осознанно и задокументировано отдельными комментариями с разным обоснованием — не копипаста бездумно.
- **Fail-open.** При `redisAvailable === false` или ошибке на `redis.set` функция возвращает `true` без исключения — не роняет вызывающий код (`route.ts`), сама возможная "штормовая" частота ограничена независимым троттлингом `log.critical()` (300с, `logger.ts:53-84`) — это явно и верно описано в комментарии `health.ts:236-241`. Двойная защита (6ч-дедуп + 300с-троттл) не противоречит друг другу: при недоступном Redis оба слоя фейлят открыто одновременно (тот же клиент `redis`), поэтому в худшем случае (Redis лежит **и** контур реально молчит) алерт будет уходить не чаще раза в 5 минут (частота опроса `site-watchdog`) — хуже, чем "раз в 6ч", но это результат сознательного компромисса "не потерять реальный инцидент", подтверждённого текстом задачи. Не считаю багом.
- **`ownerChatId` не настроен.** Ветка `ok:true` без heartbeat при отсутствующем `TELEGRAM_OWNER_CHAT_ID` не создаёт лишний Redis-ключ (`shouldAlertOwnerDecisionsSilence` даже не вызывается, т.к. `check.ok === true`) — соответствует намерению "не шуметь, пока контур не включён".
