## Независимая мутационная проверка (отдельно от двух мутаций code-reviewer'а)

Code-reviewer уже проверил две мутации: (1) убрать `confirmPenalty: true` из повторного
DELETE — тест #3 падает; (2) слать `confirmPenalty: true` безусловно в обеих ветках — тест #1
ловит. Я выбрал третью, независимую мутацию — порчу функцию чтения суммы штрафа, а не факт
отправки флага:

**Мутация A** — `readPenaltyAmount()` в `page.tsx` всегда возвращает `null`, независимо от
входных данных:
```diff
 function readPenaltyAmount(data: unknown): number | null {
-  if (!data || typeof data !== "object") return null;
-  const amount = (data as { penaltyAmount?: unknown }).penaltyAmount;
-  return typeof amount === "number" && Number.isFinite(amount) ? amount : null;
+  return null; // MUTATION
 }
```
Результат: `2 failed | 3 passed` — падают именно тест #2 (`показывает сумму штрафа`, ищет кнопку
`/Отменить с штрафом 500/`, которой больше нет) и тест #3 (`подтверждение штрафа`, ищет
`/Отменить с штрафом/` тем же текстом кнопки — с `null` рендерится `«Отменить со штрафом»` без
суммы, что не матчится регэкспом). Тесты #1, #4, #5 остались зелёными, как и должно —
затронутая логика их не касается. Мутацию откатил (`git checkout -- page.tsx`), полный набор
снова 5/5.

**Дополнительно — проверка на пробел покрытия (не блокирует, но стоит отметить)**: попробовал
мутацию (c) из наводки задания — убрать `Number.isFinite(amount)` из проверки типа:
```diff
-  return typeof amount === "number" && Number.isFinite(amount) ? amount : null;
+  return typeof amount === "number" ? amount : null; // MUTATION
```
Результат: **все 5 тестов остались зелёными** — эта мутация не поймана. Это реальный, но
некритичный пробел покрытия: ни один тест не отправляет `penaltyAmount: NaN` или
`penaltyAmount: Infinity` в metadata 402, поэтому regression на этой границе (сервер вернёт
`NaN`/`Infinity`, UI отрендерит `"NaN ₽"` или `"∞ ₽"`) тесты не заметят. Не блокирует вердикт —
входные данные приходят от собственного сервера (не от пользователя), а `basePrice`/`penaltyAmount`
в реализации сервера — обычные числа из БД, вероятность `NaN`/`Infinity` там низкая. Стоит
завести отдельный тикет на добавление такого кейса, но не является основанием для FAIL этого
PR (тест-only, узкий скоуп, issue #502 не про это).

Рабочее дерево после всех мутаций подтверждено чистым:
```
$ git status --short && git diff --stat
(пусто)
```

## Проверка мок-обвязки на маскировку реальной регрессии

Проверил, не может ли форма мока `useTelegram()` пройти тест против «фейкового» интерфейса,
не совпадающего с реальным `TelegramContextValue`:

- Мок возвращает: `ready, user, apiFetch, showBackButton, onBackButtonClick, haptic
  {impact, notification, selection}`.
- Реальный `TelegramContextValue` (`TelegramProvider.tsx:26-48`) шире — есть ещё `token`,
  `capabilities`, `needsLinking`, `setNeedsLinking`, `setUser`, `setToken`, `colorScheme`,
  `themeParams`, `close`, `expand`. Это отсутствует в моке.
- Проверил построчно, какие поля реально читает `BookingsPage` (только эти 6, `page.tsx:60-61`)
  и вложенный `BookingCard` (только `haptic`, `BookingCard.tsx:51`) — других компонентов,
  зовущих `useTelegram()` в дереве рендера этой страницы, нет. Так что мок покрывает ровно то,
  что используется — не шире фактического контракта компонента, но и не уже.
- `ApiFetchError` в тесте — **не** заглушка: `vi.mock` фабрика делает `...actual` спред через
  `vi.importActual`, так что `ApiFetchError`, которым тест бросает ошибку, и тот класс, который
  `page.tsx` проверяет через `instanceof` и `e.code` — буквально один и тот же импорт одного
  модуля. Несовпадения класса/типа при `instanceof` быть не может.
- Единственный теоретический риск: если в будущем `page.tsx` начнёт читать ещё одно поле
  контекста (например, `capabilities`), тест продолжит компилироваться (TS не проверяет форму
  замоканного возврата против интерфейса `TelegramContextValue` — фабрика `vi.mock` типизирована
  слабо) и тест-компонент получит `undefined` вместо реального значения молча. На сегодняшний
  день это не проявляется, т.к. используемые поля покрыты полностью, но это системный риск
  паттерна для всех подобных тестов в репозитории, не специфичный для этого PR — не блокирует.
