## Эмпирическая проверка тайминга cmdClaim (не только статический анализ)

Задание явно просило не ограничиваться чтением кода, а реально прогнать `cmdClaim`.
Скрипт делает живые HTTP-вызовы через `curl` (`scripts/lib/gh-api.ts`) — реальную issue
клеймить не стал. Вместо этого подставил в `PATH` перед реальными `sleep`/`curl`
поддельные исполняемые файлы (bash-скрипты в scratchpad), которые:
- пишут в лог `<timestamp> <SLEEP|CURL> args=...` при каждом вызове;
- `sleep` реально исполняет `/usr/bin/sleep` с теми же аргументами (не заглушка по времени);
- `curl` возвращает валидный fake-ответ в формате `ghApi()` (`<json-тело>\n<http-код>`,
  без лишних символов, чтобы `cmdClaim` реально прошёл до конца, включая PATCH).

Запустил `PATH="<fakebin>:$PATH" npx tsx scripts/issue-queue.ts claim 999999` (несуществующий
номер, без сети наружу) трижды подряд:

```
run 1: SLEEP args=0.246  →  +0.255s  → CURL GET
run 2: SLEEP args=0.941  →  +0.951s  → CURL GET
run 3: SLEEP args=0.567  →  +0.577s  → CURL GET
```

Во всех трёх прогонах: (а) `sleep` вызывается первым, с аргументом строго в `[0.2, 1.5)`;
(б) `curl GET` вызывается только после того, как процесс `sleep` реально завершился —
интервал между таймстампами в трейсе совпадает (с точностью до overhead запуска
процесса) с длительностью, переданной в `sleep`; (в) в развёрнутом прогоне до конца
(с валидным fake-ответом) видно и `PATCH` сразу вслед за `GET` — `cmdClaim` реально
доходит до `setLabels()` и завершается `claimed #999999`, exit 0. Это подтверждает
не только «джиттер вызывается раньше GET по тексту кода», а что в реальном процессе
подпроцесс `sleep` физически блокирует выполнение до своего завершения, и только
после этого стартует сетевой вызов — ровно то поведение, которое требуется для
эффекта митигации.

Дополнительно — статический трейс: между `execFileSync('sleep', ...)` (issue-queue.ts:312)
и `gh<RawIssue>(...)` (issue-queue.ts:314) нет ничего, кроме пустой строки и комментария —
ни `if`, ни `return`, ни другого вызова, который мог бы переставить порядок или создать
путь выполнения, минующий sleep. `execFileSync` синхронный (в отличие от `spawn`/`exec`
асинхронных) — рантайм не может продолжить до завершения дочернего процесса.

## Оценка: предотвратила бы эта митигация конкретный инцидент #564 → #626/#645?

Честная оценка, как и просило задание — не идеализирую результат:

- **Точных данных о таймингах исходного инцидента нет.** Известно только время
  создания PR #626 и #645 (~55 минут друг от друга, по вводным задания) — это
  время создания PR, которое наступает уже **после** `claim()` (в начале сессии)
  и после всей реализации/тестов/коммита (внутри сессии). 55-минутный разрыв между
  PR ничего не говорит о разрыве между самими вызовами `claim()` — если одна сессия
  писала код/тесты на 55 минут дольше другой, оба `claim()` вполне могли произойти
  в пределах секунд друг от друга. Телеметрии с точными таймстампами именно
  `claim()`-вызовов исходного инцидента не существует — проверить post-hoc,
  «спас бы джиттер именно этот случай», объективно нельзя.
- **Порядок величины джиттера правдоподобен для целевого класса гонки.**
  Измерил вживую реальную задержку одного вызова `curl` к `api.github.com`
  из этого окружения (агент-прокси): ~0.3–1.2с на вызов (первый — холодное TLS-соединение,
  ~1.2с; последующие — ~0.3с). `cmdClaim` делает **два** последовательных вызова
  (GET, затем PATCH) — то есть реальное окно гонки (от старта GET до применения PATCH)
  того же порядка величины, что и сам джиттер (0.2–1.5с), а не на порядок меньше.
  Средняя разница между двумя независимыми `Uniform[0.2, 1.5)` — `(MAX−MIN)/3 ≈ 0.43с»
  (посчитано аналитически) — сопоставима с длительностью одного сетевого вызова.
- **Вывод: джиттер сдвигает вероятность в пользу победителя, но не гарантирует
  разведение по времени.** Если исходная гонка была вызвана буквально одновременным
  пробуждением обеих сессий одним Routine-триггером и обе сразу (без задержки на
  триаж непричёсанных issues, шаг 0 `/next-issue`) доходили до `claim()`, то
  джиттер, скорее всего, помог бы в большинстве случаев, но не во всех: при
  небольшой (например, <0.1–0.2с) разнице между двумя независимыми джиттер-выборками
  второй GET всё ещё может успеть прочитать `auto:ready` до применения первого PATCH,
  особенно с учётом продакшен-latency GitHub Actions (которое может отличаться от
  измеренного здесь через агент-прокси, но не равно нулю). Это ровно то, что честно
  признано и в issue, и в комментариях кода — не преувеличение эффекта.
- Это соответствует рамке самой issue #647: «jitter-delay + recheck» — одно из
  **приемлемых направлений митигации**, а не мандат на полностью пуленепробиваемый
  фикс (GitHub Issues API объективно не даёт CAS/ETag на PATCH labels, `gh-api.ts` —
  голая curl-обёртка без conditional-request поддержки). По этой рамке митигация
  **достаточна** — она обоснованно (не произвольно) сужает вероятность повторения,
  и это именно то, что было запрошено.
- Отдельное наблюдение (не блокер): формулировка issue — «jitter-delay + recheck» —
  предполагает потенциально два шага (задержка, а затем повторная проверка перед
  записью). Реализация делает задержку **до** единственного read-check-write, а не
  задержку + повторное чтение после неё. По сути это эквивалентно по цели (развести
  во времени конкурирующие `GET`), но не буквальная «recheck» семантика. Не считаю
  это дефектом: при однократном чтении после задержки экономится один лишний
  сетевой вызов, а цель («развести конкурентов во времени») достигается тем же
  способом. Отмечаю для полноты, не блокирует вердикт.
