# Аудит: нативный GitHub auto-merge обходит гейт двойного вердикта (issue #745)

## 1. Кто/что включает `auto_merge_enabled` на PR `claude/**`

Проверено:
- `grep -rn "enablePullRequestAutoMerge|auto_merge|--auto\b" .github/ scripts/ src/` —
  ни один workflow, скрипт или composite action в текущем HEAD репозитория не
  вызывает нативную GitHub-мутацию/флаг auto-merge. Единственное упоминание
  `gh pr merge --auto` — в комментарии `.github/workflows/dependabot-automerge.yml`,
  описывающем УЖЕ УДАЛЁННЫЙ код (см. коммент в файле); реального вызова там нет.
- Весь мерж в этом репозитории идёт через прямой `PUT /pulls/{n}/merge`
  (`scripts/issue-queue.ts`, `attemptMerge`) — включая путь owner-decisions
  (аппрув владельца), который тоже не трогает auto-merge API.
- `GET /repos/aylisrg/platform-delovoy` → `"allow_auto_merge": true`. Это
  репозиторная настройка, разрешающая **любому** с write-доступом (человеку
  или боту/токену) включить нативный auto-merge на любом PR — источник
  возможности, а не конкретный виновник.
- `GET /repos/.../branches/main/protection` → `403 Resource not accessible by
  integration` — токен сессии не видит branch protection/список установленных
  GitHub Apps; средствами репозитория дальше это не расследовать.

**Вывод:** ни один файл в репозитории не включает auto-merge — источник
внешний (ручной клик через GitHub UI/mobile, стороннее GitHub App с
permissions на репозиторий, либо личный скрипт владельца под
`AUTOMATION_TOKEN`, не живущий в этом репо). Во всех обнаруженных случаях
actor — `aylisrg` (type `User`), но это **не доказательство ручного клика**:
CLAUDE.md сам документирует, что действия под PAT атрибутируются человеку
(«Пуш под PAT приписывается человеку»), и тот же паттерн виден у легитимных
машинных вызовов этого репозитория (например, `pr-ready` через GraphQL
`markPullRequestReadyForReview` под `AUTOMATION_TOKEN` тоже атрибутируется
`aylisrg`). На PR #710 события `ready_for_review` (сигнатура ровно этого
`pr-ready`) и `auto_squash_enabled` разделены 6 секундами — слишком быстро для
многошагового ручного клика по UI, что скорее говорит в пользу какой-то
автоматики вне репозитория, а не подтверждённого решения владельца.

Поскольку источник не устанавливается кодом репозитория, фикс закрывает
**последствие** безусловно (см. `block-native-automerge.yml`), не дожидаясь
атрибуции причины.

## 2. Фикс

- `.github/workflows/block-native-automerge.yml` — на событие
  `pull_request: auto_merge_enabled` для веток `claude/**` немедленно вызывает
  `gh pr merge --disable-auto` и комментирует PR почему. Код-only, работает
  сразу после мержа этого PR, никаких repo-настроек не требует.
- `.github/workflows/merge-gate-check.yml` — вторая линия защиты: публикует
  `classifyMergeGate` (issue #580, тот же код что `issue-queue.ts gate <PR>`)
  как commit status `merge-gate/verdicts` на каждый claude/** PR (по
  `pull_request` и по `issue_comment`, чтобы ловить вердикты, которые
  публикуются комментарием без нового коммита). **Требует ручного шага
  владельца**, чтобы стать настоящей защитой: Settings → Branches → main →
  Require status checks to pass → добавить `merge-gate/verdicts`. Без этого шага
  джоба просто публикует статус и ни на что не влияет — это ожидаемо и
  безопасно, отключить её нельзя случайно нажатием.
  ⚠️ У этого шага есть последствие, которое должен проверить тот, кто его
  включает: `pr-merge`/`automerge`/decisions-sync мержают hold-PR (в т.ч.
  needs-owner после аппрува владельца) через прямой `PUT /pulls/{n}/merge` под
  `AUTOMATION_TOKEN` — для таких PR этот чек тоже красный (гейт вернул hold по
  построению). Branch protection required checks блокируют **любой** мерж,
  включая API, если у актора нет прав обхода — нужно либо дать
  `AUTOMATION_TOKEN`/его актору bypass в branch protection, либо легитимный
  путь мержа needs-owner PR сломается вместе с обходом, который он должен
  исполнять.
- `HOLD_PATTERNS` (`scripts/lib/issue-queue.ts`) расширен обоими новыми
  workflow-файлами — иначе защита циклична: агент мог бы тем же прогоном
  ослабить их и автомержем закатить ослабление.

## 3. Ретроспективный аудит: смержились ли так другие PR

Проверены 36 последних смерженных в `main` PR (16–24 августа 2026,
`GET /issues/{n}/events` + `/comments`, скрипт использован разово, не в
поставке). Критерий бай-пасса: событие `auto_squash_enabled`/`auto_merge_enabled`
в таймлайне PR **до** мержа.

Нативный auto-merge был включён (`auto_squash_enabled`) на **10 из 36**
проверенных PR: #755, #743, #742, #710, #677, #659, #654, #653, #652, #634.

Из них **смержились без хотя бы одного из двух вердикт-маркеров** (то есть
`classifyMergeGate` при реальном вызове вернул бы `hold`, а мерж прошёл мимо
него):

| PR | Смержен | Вердикты | Что менял |
|----|---------|----------|-----------|
| #743 | 2026-08-23 | оба отсутствовали на момент мержа | 2 markdown/jsonl файла (docs), уже описан в issue #745 |
| #634 | 2026-08-16 | оба отсутствовали | 27 файлов, 4+ модуля (avito, monitoring, tasks, waitlist) |
| #677 | 2026-08-17 | оба отсутствовали | 12 файлов, модули `booking`+`gazebos`+`ps-park` |
| #710 | 2026-08-20 | оба отсутствовали | **45 файлов, включая
  `.claude/commands/next-issue.md`, `.github/issue-queue.json`,
  `.github/workflows/issue-queue-merge.yml`, `.github/workflows/auto-rebase.yml`
  — файлы из `HOLD_PATTERNS`, то есть правку рубильников самой автоматики** |

Остальные шесть PR с включённым auto-merge (#755, #742, #653, #652, #659,
#654) на момент мержа уже несли оба вердикт-маркера — по счастливому
совпадению таймингов, не по устройству защиты: `classifyMergeGate` для них
тоже не вызывался.

Все семь PR с `auto_squash_enabled`, для которых проверялись лейблы (#634,
#677, #710, #743 и др.), либо не несли `needs-owner`, либо несли его и
**всё равно смержились обходом** — то есть контур owner-decisions (grace-окно
15 минут, пин к SHA, аудит решения) для #634/#677/#710 не исполнялся вовсе,
хотя гейт должен был увести их именно туда.

**Вывод:** #743 — не единичный инцидент, а систематическая дыра, реализованная
минимум 4 раза за 9 дней, включая один случай (#710) с прямой правкой
рубильников самой автоматики. Содержимое #634/#677 при беглой проверке diff'ов
выглядит доменной работой без явных признаков RBAC-дыр/секретов (не проводился
полный ревью постфактум — вне рамок этой задачи), но сам факт, что
классификатор их не видел, означает, что доверять текущей истории `main` в
вопросе «вердикты стояли на всём» нельзя без ретроактивной проверки, которую
эта таблица и есть.
