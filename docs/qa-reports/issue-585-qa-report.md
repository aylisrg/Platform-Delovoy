## Живая проверка CI-скрипта (`eval/traceability-report.ts`) — 4 сценария

Запускал напрямую (`npx tsx eval/traceability-report.ts`) с реальными `PR_BODY`/`BASE_REF`, не
только читал код:

**A. PR ссылается на реальный PRD с несколькими AC** (`docs/requirements/2026-07-09-payments-module-prd.md`, `BASE_REF=main`):
```
## AC-трассируемость (`docs/requirements/2026-07-09-payments-module-prd.md`)

| AC | Covered | Tests |
|----|---------|-------|
| AC-1 | ❌ | — |
...
| AC-7 | ❌ | — |

⚠️ 7 AC без покрытия тестами (см. таблицу выше). Проверка пока в режиме отчёта и не блокирует мерж.

> ℹ️ PRD reuses AC-1, AC-2, ..., AC-7 across multiple User Stories — coverage is tracked per identifier, not per User Story.
```
exit code 0. Таблица корректно сформирована (все AC не покрыты, т.к. этот PR не трогает тестов
фичи из этого PRD) — но см. **BUG-1** ниже: этот же прогон обнажает реальный дефект экстрактора.

**B. PR без ссылки на PRD в теле** (`PR_BODY="Just a regular bugfix, no PRD here."`) →
`ℹ️ AC-трассируемость: PR не ссылается на PRD (...) — проверка пропущена.` exit 0. Корректно.

**C. PR ссылается на несуществующий PRD** (`docs/requirements/2099-01-01-nonexistent-feature-prd.md`) →
`⚠️ AC-трассируемость: PR ссылается на \`...\`, но файл не найден в репозитории.` exit 0. Корректно.

**D. PRD существует, но AC-чек-листа нет** (скретч-файл с секциями Проблема/Решение, без `- [ ] AC-N`) →
```
_No AC-N items found in PRD._

⚠️ 1 AC без покрытия тестами (см. таблицу выше). Проверка пока в режиме отчёта и не блокирует мерж.
```
exit 0, не падает. **Минорный косметический баг**: текст "1 AC без покрытия тестами" вводит в
заблуждение — реальных AC ноль, `issues.length === 1` здесь — это одна объяснительная строка
(`"PRD has no AC-N checklist items to trace..."`), а не счётчик непокрытых AC. `traceability-report.ts`
безусловно интерполирует `result.issues.length` в шаблон "N AC без покрытия", не различая этот
случай. Не покрыто юнит-тестами (тестируется только `result.issues` как массив, не итоговый
markdown-текст). Не блокирует ни один AC issue — чисто формулировка в редком edge-case.

### BUG-1 (Major, найден самостоятельно, не в существующих тестах) — сворачивание `AC-N.M` в `AC-N`

`AC_CHECKLIST_RE = /^-\s*\[\s?\]\s*(AC-\d+)/gm` берёт только `AC-` + цифры **до точки**. Реальные
PRD в репозитории массово используют вложенную нумерацию `AC-1.1`, `AC-1.2`, `AC-1.3`, ... (это не
редкий случай — 14 из 34 `*-prd.md`, включая **самый свежий** `2026-08-13-miniapp-role-rebuild-prd.md`
от того же дня, что и постановка issue #585). `extractAcIds` на таком PRD режет `AC-1.1`..`AC-1.5`
до одного и того же `"AC-1"` и репортит их как "PRD reuses AC-1 across multiple User Stories" —
хотя на самом деле это пять разных требований в одной US, а не переиспользование одного и того же
ID в разных US (для которого и задумывалась заметка `duplicates`).

**Шаги воспроизведения:**
```ts
const prd = `
- [ ] AC-1.1: first sub-criterion
- [ ] AC-1.2: second sub-criterion
- [ ] AC-1.3: third sub-criterion
`;
const testFile = `it("covers the first sub-criterion (AC-1.1)", () => {});`;
checkTraceability(prd, { "f.ts": testFile });
```
**Ожидаемый результат:** три отдельных AC (`AC-1.1` не покрыт тестом только частично — `AC-1.2` и
`AC-1.3` без теста вообще), `pass: false`.
**Фактический результат:**
```
| AC | Covered | Tests |
|----|---------|-------|
| AC-1 | ✅ | f.ts |
pass: true, issues: []
```
Один маркер `AC-1.1` в тесте гасит весь ряд `AC-1`, включая непокрытые `AC-1.2`/`AC-1.3` — чекер
рапортует **полное покрытие там, где реально покрыт только один AC из трёх**. Живьём воспроизвёл
тем же прогоном на реальном `2026-07-09-payments-module-prd.md` (сценарий A выше) — там же видно
`AC-1`..`AC-7` вместо настоящих `AC-1.1`..`AC-4.x`.

Так как проверка сейчас в режиме отчёта (не блокирует мерж) и explicit-scope issue #585 в качестве
формата примера везде использует простой `AC-N` (без вложенной нумерации — сверено с шаблоном
`agents/po.md`, который тоже учит `AC-1`/`AC-2`, без точек), это не нарушает ни один из 3 явных AC
из issue. Но по сути это ложноположительный результат в самом частом (41% файлов, включая последний
по дате) реальном формате PRD в этом репозитории — прямо противоречит цели issue #585 ("механическая
проверка" вместо "доверия дисциплине QA-агента"). **Рекомендую завести fast-follow issue и закрыть
до перевода проверки в блокирующий режим** — иначе блокирующий режим будет либо ложно пропускать
недотестированные под-AC, либо (если разработчики узнают про дыру) обесценит доверие к тулу.

### BUG-2 (Minor/Moderate, найден самостоятельно) — `.test(` как member-access ложно матчится как тайтл-маркер

`hasTitleMarker` требует `\b` перед `(?:it|test)`, но не запрещает, чтобы этому слову предшествовала
точка (member access). `someRegex.test("... AC-1 ...")` — идиоматичный JS (`RegExp.prototype.test`),
а не объявление теста — тоже матчится:

```ts
const acPattern = /AC-\d+/;
export function hasAcReference(x: string) {
  return acPattern.test("example containing AC-1 text");
}
```
→ `checkTraceability` засчитывает `AC-1` как покрытый по этому файлу (`pass: true`). В реальном CI
это ограничено файлами из `listChangedTestFiles` (только `*.test.ts`/`__tests__/`), но внутри
тестового файла эта конструкция абсолютно реалистична — например, тест на regex-валидатор:
`expect(slugPattern.test("...AC-1...")).toBe(true)` в теле `it(...)`, не относящемся по смыслу к
AC-1, ложно засчитает AC-1 как покрытый. Менее вероятен и менее внятен, чем BUG-1, но той же
природы (regex видит текстовое совпадение `AC-N` рядом с `test(`, не различая объявление теста и
вызов метода) — стоит закрыть вместе с BUG-1 в том же фолоу-апе.
