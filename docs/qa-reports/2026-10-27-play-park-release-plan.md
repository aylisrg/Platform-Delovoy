## Результат реализации

Посетитель выбирает стол и время, вводит имя/телефон/email для чека и согласие, сразу получает форму существующей ЮKassa. Цена считается сервером по сохранённым длительности, тарифу и товарам; менеджерский расчёт фактически сыгранного времени для предоплаты не используется. Бронь PENDING подтверждается автоматически только после проверенного платежа. Ручное подтверждение неоплаченной online reservation запрещено.

Используется общий Payment/BOOKING и существующая сверка с ЮKassa. Для Play Park reservation добавлены устойчивый ключ запроса, восстановление после timeout/раннего webhook, проверка суммы/валюты/назначения, атомарный учёт денег и повторной доставки. Отмена/отказ платежа освобождают неоплаченный слот; поздний success учитывает деньги, но не занимает освобождённое время. Менеджерский session bill получает только оставшуюся к оплате сумму. Поведение оплаты беседок сохранено.

Перенос выполняется администратором через `POST /api/ps-park/bookings/[id]/reschedule` и кнопку в расписании/истории. Разрешён только оплаченный, ещё не использованный период на том же ресурсе. Сохраняются длительность, тариф и предоплата; проверяются рабочие часы, слот, роль и доступ к Play Park. Блокировка строки и проверка исходного времени защищают от устаревшей формы; условные записи защищают перенос от запоздавших check-in/no-show/extend/complete/cancel. Изменённый после оплаты период или товары требуют сверки перед переносом; повтор того же запроса не создаёт новую оплату или аудит. Отменённую оплаченную бронь можно перенести после сверки; начатую/завершённую нельзя.

Новые reservation не используют старый клиентский штраф 50%: клиенту предложен контакт администратора для переноса/обращения по оплате. Автоматические возвраты не добавлены. Подготовлены `content/legal/ps-park-offer/v1.md` и запись `scripts/seeds/legal.ts`; документы ещё не опубликованы. Обязательные права потребителя и ручное рассмотрение законных требований сохранены, без обещания безусловного удержания всей оплаты. Бизнес-решение о переносах получено; отдельной юридической экспертизы текста не было.

## Технический блокер QA

Prisma/Client 6.19.3, target `debian-openssl-3.0.x`, engine commit `c2990dca591cba766e3b7ef5d9e8a84796e47ab7`. Штатный download получил HTTP 403 на:

`https://binaries.prisma.sh/all_commits/c2990dca591cba766e3b7ef5d9e8a84796e47ab7/debian-openssl-3.0.x/libquery_engine.so.node.gz.sha256`

No-engine клиент пригоден для типов/моков, но прямой `$queryRaw` с обычным PostgreSQL URL даёт P6001. Новых оснований повторять отказавший download не появилось; обходов/checksum-ignore/новых credentials не было.

Минимальное изменение среды: разрешить обычное HTTPS-чтение официальных query/schema engines и checksum этого commit/target. После подтверждения изменения — один `npm run db:generate`. Альтернатива со стороны администратора среды: заранее установленный стандартный Prisma 6.19.3 с этими проверенными движками. Ни production DB, ни Accelerate credentials для этого не нужны.

После восстановления стандартного клиента на выделенной synthetic DB/локальном Redis:

```sh
npm run db:generate
npx prisma migrate deploy
DEV_OVERLAY=1 npx tsx scripts/seed.ts
npm run build:e2e
npx playwright test e2e/ps-park-booking.spec.ts --project=chromium
```

Этот штатный spec проверяет fail-closed гостевого checkout на обычном seed. Далее нужен сквозной платный сценарий в тестовом магазине или разрешённом локальном provider fixture с настоящими Next/Prisma/DB: success, cancel, повторы и ранний webhook; проверка Booking/Payment/FinancialTransaction. Реальный магазин не использовать.

## Точный блокер деплоя

Production путь — `.github/workflows/deploy.yml`: hosted Actions строит образ и выкатывает через существующий VPS-доступ. CLI read `gh api repos/aylisrg/Platform-Delovoy/commits/main` получил `Forbidden`; последующий запрос runners не выполнялся. Это отказ доступа, не автоматический approval review. Отказ не обходился.

Подключённый GitHub connector умеет читать/менять репозиторий, но инструментов dispatch workflow и VPS shell в текущем списке нет. SSH agent не подключён. Нельзя заменить это произвольным push: он способен запустить запрещённые hosted Actions, а актуальность main не сверена. Активный staging с безопасной тестовой БД также не подтверждён; compose-файл сам по себе не даёт доступа.

Минимально требуется один рабочий канал: существующий авторизованный SSH/VPS executor без расхода hosted Actions, либо подключённый github-actions с разрешённым запуском deploy и явным решением о расходе Actions. Новые ключи, банковские доступы или отключение защит не требуются. Разрешение пользователя на сам деплой уже есть, повторно его спрашивать не нужно.

## Откат

```sh
npx tsx scripts/ps-park-online-booking.ts disable <existing-superadmin-id>
```

Это закрывает создание новых reservation, сохраняет обработку уже созданных платежей, сверку и страницу результата. Не удалять Booking/Payment/OfferVersion и не трогать беседки. Старый payment handler не умеет подтверждать новые Play Park reservation: полный откат образа возможен только после сверки незавершённых платежей либо с сохранением совместимого обработчика. Обратная миграция не нужна.

## Сравнение прежних правил

- Старый Play Park: 2 часа / 50% базовой аренды, запись штрафа в metadata; автоматического банковского возврата нет.
- Беседки online: 24 часа / 100%, автоматический возврат при отмене строго раньше порога. В оферте §7 — фактические документально подтверждённые расходы; `cancellation-summary.ts` уже признаёт расхождение. Правила беседок в этой задаче не менялись.
- Новая Play Park reservation: перенос неиспользованного оплаченного времени через администратора, без повторной оплаты и без автоматического возврата; законные обращения рассматриваются вручную. Старые 50% или gazebo 100% на новую предоплату не перенесены.

Публичная проверка ранее показывала старые тексты «Оплата по факту». Локальный Chromium к сайту получил `ERR_TUNNEL_CONNECTION_FAILED`, HTTP GET из shell — 403; повторов после отказа не было. Поэтому исправность актуального production API не подтверждена. Локальная готовность не означает, что посетитель уже может оплатить на сайте.
