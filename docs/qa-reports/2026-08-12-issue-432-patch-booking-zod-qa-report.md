## Скоуп

`4765805`). Проверка функционального фикса P0-бага: PATCH-эндпоинты

- тесты: `src/modules/booking/__tests__/validation.test.ts`, оба `route.test.ts`

Code-reviewer уже дал PASS; отдельного `docs/qa-reports/*-review.md` для

## Acceptance criteria

### AC-1: отрицательный `cashAmount`/`cardAmount` → 422, сервис не вызывается (оба модуля)

**PASS.** Проверено на трёх уровнях:
- Unit `validation.test.ts`: `it.each` с ровно тем сценарием из репорта бага
  (`cashAmount: 2000, cardAmount: -1000` при `status: COMPLETED`) и с
  отрицательным `cashAmount` — оба `safeParse().success === false`.
- Route-тесты обоих модулей: тот же payload → `res.status === 422`,
  `body.error.code === "VALIDATION_ERROR"`, `mockUpdateBookingStatus`
  **не вызван**.
- Сквозная проверка корня бага: `paidByOperator = (cashAmount ?? 0) + (cardAmount ?? 0)`
  в `gazebos/service.ts:884` и `ps-park/service.ts` (аналог) теперь физически
  не может получить отрицательное слагаемое — Zod отсекает его до вызова
  сервиса, эксплойт из issue закрыт на границе, а не патчем самого гейта.

Границы проверены: `min(0)` включительно (0 разрешён — тест с
`cardAmount: 0` в связке со скидкой 0 проходит 200), верхний потолок
`max(10_000_000)` — `10_000_001` отклоняется (граничное значение ровно
`10_000_000` отдельным тестом не покрыто — см. дефект QA-432-1, не блокер).

### AC-2: `status` вне enum → 422

**PASS.** `updateBookingStatusSchema` — `z.enum(BOOKING_STATUSES)`. Тесты
покрывают: строку не из enum (`"PAID"`), число (`42`), нижний регистр
(`"completed"` — только в validation.test.ts), пустую строку, `null`,
`undefined`. Все 6 валидных статусов enum'а (`PENDING/CONFIRMED/CHECKED_IN/
COMPLETED/CANCELLED/NO_SHOW`) явно проверены как принимаемые — не тавтология
"схема есть — верим", а честный перебор всех значений enum'а.

Нюанс (не баг, но важно для понимания порядка): в `gazebos/route.ts` есть
более ранняя ветка `if (!status) { … режим редактирования брони … }` —
она отфильтровывает **falsy** значения (`undefined`, `null`, `""`, `0`,
`false`) ДО того, как тело попадёт в `updateBookingStatusSchema`, и уводит
запрос в `rescheduleBookingSchema` (для менеджеров) вместо 422. Для `status:
false`/`status: 0` итог тот же 422 или 403 через другую схему — это не
регрессия (ветка существовала до фикса в точности так же), просто
`updateBookingStatusSchema` не единственный источник 422 для "falsy" статусов
в gazebos. `ps-park` эквивалента не имеет — там правильно возвращает 422
"Укажите статус" на `undefined/null/""` до Zod. Расхождение между модулями
уже было до фикса, вне скоупа issue #432.

### AC-3: `reason` > 500 символов → 422

**PASS.** `.max(500)`. Тесты: 500 символов → success, 501 → 422 (граница
проверена с обеих сторон, не только "слишком длинное отклоняется").

### AC-4: валидные сценарии не сломаны

**PASS**, проверено по каждому пункту:

- Завершение брони с кассовой разбивкой (`cashAmount`/`cardAmount` как
  числа) → 200, `updateBookingStatus` вызван с корректными числовыми
  аргументами (тест на `600/400`).
- Отмена пользователем своей брони (`status: CANCELLED`, non-MANAGER) →
  `cancelBooking` вызван с `session.user.id`, а не с чем-либо из body —
  прямая подмена `userId` невозможна (не изменилось этим PR, но не
  сломано).
- Режим правки брони gazebos (PATCH без `status`) → по-прежнему уходит в
  `rescheduleBooking`, `updateBookingStatus` не вызывается.
- Скидка при `COMPLETED`: `discountPercent: 0` корректно трактуется как
  "без скидки" (не как невалидное значение) — предмет отдельного бага в
  прошлом, здесь не регрессировал.
- Абонемент в ps-park: непустой `subscriptionId` доходит до сервиса,
  пустая строка → `undefined` ("без абонемента"), длина ограничена 64 —
  не была явно упомянута в issue, но добавлена в схему консистентно и
  протестирована.
- `null` в `cashAmount`/`cardAmount`/`reason`/`subscriptionId` (реальный
  паттерн фронта — пропуск поля и `null` смешиваются) корректно
  превращается в `undefined`, а не в 422. Хороший edge case — без него
  чекаут с пустыми полями формы сломался бы.
- Невалидный JSON в теле → 422 (не 500) в обоих модулях — proper edge
  case для устойчивости эндпоинта, не входил явно в AC, но правильно
  добавлен.
