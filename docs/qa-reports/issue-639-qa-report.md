## Мутационное тестирование двух защитных добавлений (не доверяю зелёным тестам на слово)

### (a) `escapeRegExp()` — откатил вызов, использовал сырой `ac` в `idBoundaryPattern`
Временно заменил `idBoundaryPattern` на `` `\\b${ac}\\b(?!\\.\\d)` `` (без `escapeRegExp`). Написал
и прогнал одноразовый scratch-тест (`eval/__tests__/tmp-mutation-escape.test.ts`, удалён сразу после
использования, не попал в коммит): PRD с единственным `AC-1.1`, тестовый файл с текстом
`it("false positive via AC-1x1 wildcard", () => {})` — **не содержит** буквальной подстроки
`AC-1.1`, только "decoy" `AC-1x1` (символ на месте точки — `x`, не `.`).
- **Без экранирования**: тест упал — `AC-1.1` ложно засчитан `covered: true` (необэкранированная
  `.` в regex работает как wildcard, `x` вместо `.` тоже матчится).
- **Восстановил `escapeRegExp()`**: тот же тест зелёный — `covered: false`, как и должно быть.
Это подтверждает, что `escapeRegExp()` — не декоративная защита, а закрывает реальный
wildcard-injection баг, который иначе внёс бы сам факт добавления точек в `AC-N.M`-идентификаторы
(до этого PR `ac` всегда был чистым числом без спецсимволов regex, экранирование было не нужно).

### (b) `(?!\.\d)` в `idBoundaryPattern` — откатил лукахед
Временно вернул `idBoundaryPattern` к `` `\\b${escapeRegExp(ac)}\\b` `` (без `(?!\.\d)`). Прогнал
уже существующий в PR тест напрямую (`npx vitest run eval/__tests__/traceability.test.ts -t "does
not let a marker for a dotted sub-criterion"`):
```
AssertionError: expected true to be false
- Expected: false
+ Received: true
```
Без лукахеда `AC-1` (голый parent-id) ложно засчитывается `covered: true`, когда в тестовом файле
есть только маркер для `AC-1.2` (dotted sibling) — ровно тот баг, который лукахед призван
предотвращать. Восстановил `(?!\.\d)` — тот же тест снова зелёный.

**После обоих экспериментов**: `git status --short` и `git diff --stat` — пусто, дерево идентично
закоммиченному состоянию (`traceability.ts` побайтово восстановлен из `git show HEAD:...` перед
началом экспериментов и сверен после). Временный scratch-тестовый файл удалён, не входит ни в один
коммит. `npx vitest run eval` после восстановления — снова 29/29.

## Судим `(?!\.\d)` (item 3 из описания PR) — обосновано или overengineering?

Это добавление **не входит** ни в один явный пункт "Что сделать" issue #639 (только `AC_CHECKLIST_RE`,
`(?<!\.)` перед `it|test`, регрессионные тесты, опциональный п.4 про сообщение). Проверил
самостоятельно, действительно ли это активная защита от несуществующей проблемы:

- `for f in docs/requirements/*-prd.md` — ни один из 34 реальных PRD сегодня не смешивает голый
  `AC-N` и `AC-N.x` для одного и того же `N` (проверил скриптом, 0 совпадений), и ни один вообще не
  смешивает голую и точечную нумерацию AC в одном файле (тоже 0 из 34). То есть сегодня этот код
  — мёртвый путь на реальных данных репозитория.
- Но: расширение `AC_CHECKLIST_RE` этим же PR-ом (item 1) — первый случай, когда `ac`-строки,
  передаваемые в `hasCommentMarker`/`hasTitleMarker`, стали неоднородны по длине/вложенности
  (`"AC-1"` и `"AC-1.2"` в одном пространстве совпадений). Раньше `\b`-границы было достаточно,
  потому что все id были чистыми числами без общих префиксов длиной с точку. Теперь, без
  `(?!\.\d)`, сам факт добавления dotted-id **создал бы новую** дыру точности — маркер для дочернего
  `AC-1.2` ложно засчитывал бы родительский `AC-1` как покрытый — то есть баг того же типа
  (ложноположительное покрытие), что и BUG-1, только развёрнутый в другую сторону и открытый самим
  же этим PR, а не унаследованный со старого кода.
- Блок изменения хирургический: один новый helper (`idBoundaryPattern`), 6 строк, свой
  комментарий, свой регрессионный тест, не трогает другие файлы/модули/API — не подпадает под
  scope-guard CLAUDE.md ("новый модуль", "фича вне роадмапа"), это тот же файл и та же функция
  matching-логики, которую issue и так просит менять.
- Мутационное тестирование (раздел выше) подтвердило: это не decorative-код — реально предотвращает
  конкретный воспроизводимый ложноположительный результат.

**Вывод: обосновано, не overengineering.** Риск для сегодняшних 34 PRD нулевой (проверено), но это
не "гипотетическая фича вне скоупа", а закрытие дыры точности, которую сам этот PR открыл бы своим
основным изменением (item 1), если бы её не закрыл. Для инструмента, чья единственная цель —
не врать про покрытие AC (как явно сформулировано в issue #585, породившем #639), считаю
правильным закрыть и симметричный случай сразу, а не заводить третий fast-follow issue на то же
самое regex-поле через неделю. Не блокирует вердикт ни в одну сторону — все явные AC проходят
и без этой строчки, но она делает диф строго более, а не менее корректным, ценой 6 строк в уже
изменяемом файле.

## Проверка `(?<!\.)` на реальных `it`/`test` паттернах репозитория (п.6 задания)

`(?<!\.)` отклоняет только случаи, где символу непосредственно перед `it`/`test` предшествует
буквальная точка (member access). Проверил, не ловит ли это ложно легитимные объявления тестов:
- `grep -rn '^\s*(it|test)\.(skip|only|each|todo|concurrent)\('` по всему репо → десятки реальных
  `it.each([...])`, `it.each(["SUPERADMIN", ...])(...)` и т.п. (`bot/__tests__/index-wiring.test.ts`,
  `scripts/__tests__/issue-queue.test.ts`, `src/lib/__tests__/chunk-reload.test.ts` и др.) — во всех
  случаях символ перед `it`/`test` — начало строки/пробел, **не точка** (суффиксы `.each`/`.skip`
  идут ПОСЛЕ `it`/`test`, лукахед проверяет символ ДО). Ни один не был бы ложно отклонён.
- `grep -rn '\w\.(it|test)\('` по всему репо → единственные реальные совпадения на конструкцию
  "что-то.test(" или "что-то.it(" — это исключительно вызовы `RegExp.prototype.test`
  (`pattern.test(...)`, `regex.test(...)`, `verdictRegex.test(...)` в `eval/checks/{qa-report,
  prd}.ts`, `scripts/lib/issue-queue.ts`, `scripts/lib/feedback-bridge.ts`) — то есть ровно тот
  класс конструкций, который `(?<!\.)` и должен отсеивать. Легитимного `objectName.it(...)`/
  `objectName.test(...)` как объявления теста в кодовой базе не встретилось ни разу (это и
  структурно невозможно для vitest/jest API — `it`/`test` вызываются как голые глобальные функции).

Лукахед логически и эмпирически не создаёт ложных срабатываний на реальных паттернах этого репо.
