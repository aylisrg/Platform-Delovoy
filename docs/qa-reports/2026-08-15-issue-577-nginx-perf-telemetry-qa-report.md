## 6. Целенаправленный поиск того, что могли пропустить два прошлых ревью

### 6.1. Обработка невалидного/отсутствующего `perf-aggregate.json` в `analyze-perf.ts`

```
Missing file  → "❌ ENOENT: no such file or directory, open '...'" , exit 1
Truncated JSON → "❌ Expected ',' or ']' after array element in JSON at position 66..." , exit 1
{"current":"oops","baseline":[]} → "❌ Некорректный формат ...: ожидался {current: [], baseline: []}" , exit 1
{} → тот же понятный формат-error, exit 1
```

Ни разу нет сырого unhandled-исключения/стектрейса в stdout — внешний `try { main() } catch`
ловит всё и печатает короткое сообщение через `console.error`. Это ровно то, что нужно для
CI-шага (видно в summary, не роняет весь workflow непонятной портянкой).

### 6.2. Деление на ноль / нулевые total

`percentile()` явно возвращает `0` при пустом массиве (не бросает и не делит на `sortedAsc.length`
без проверки). `RouteStats.total = 0` в принципе не может возникнуть из `summarizeRoutes()`, т.к.
`Map` создаётся только для роутов, у которых есть ≥1 сэмпл — по построению нет пути, которым в
`current`/`baseline` попадёт роут с `total: 0`. `base.p95 > 0` — отдельная явная проверка перед
умножением на `p95Factor`, значит и здесь никакого скрытого деления/NaN. Не нашёл ни одного
реального пути к делению на 0.

### 6.3. Разрешительная модель `$SUDO` в `local-watchdog.sh` — не поверил утверждению фикса, разобрал сам и воспроизвёл эмпирически

Это была основная цель прохода. Вопрос из задания: не течёт ли дыра, которую нашёл первый
раунд ревью (алерт молча гаснет после ротации), **уже с самого первого, ещё не ротированного
файла** — то есть нужен ли `sudo` с минуты 0, а не только после первой ротации.

Разобрал по фактам из репозитория:
- `scripts/setup-vps.sh:42`: `useradd -m -s /bin/bash -G docker deploy` — пользователь `deploy`
  состоит **только** в группе `docker` (плюс собственная primary-группа `deploy`), не в `www-data`,
  не в `adm`.
- `infra/nginx/delovoy-nginx-perf.logrotate:15`: `create 0640 www-data adm` — но это применяется
  **logrotate'ом** только к файлу, который logrotate сам создаёт при ротации, а не к файлу самой
  первой записи, который создаёт nginx.
- `scripts/apply-nginx-vhost.sh:58-59`: `mkdir -p "$PERF_LOG_DIR"; chown www-data:adm
  "$PERF_LOG_DIR"` — это chown **директории**, не будущего файла внутри неё.

Дальше не поверил рассуждению на слово, а воспроизвёл эмпирически (в песочнице, где `id -u` = 0,
как и продовый systemd, стартующий nginx без `User=` в юните — проверил
`/usr/lib/systemd/system/nginx.service`, там нет `User=`/`Group=`, то есть master стартует как
root; `user www-data;` в `/etc/nginx/nginx.conf` относится только к воркерам после fork+setuid —
подтверждено `ps aux`: `root ... nginx: master process`, `www-data ... nginx: worker process`):

1. Создал `/var/log/delovoy-park` строго как это делает `apply-nginx-vhost.sh` (`mkdir -p` +
   `chown www-data:adm` **только на директорию**, файла ещё нет).
2. Запустил nginx (root master / www-data worker), сделал один HTTP-запрос — `access_log`
   создался **автоматически самим nginx** (в момент открытия лог-файла при чтении конфига).
3. `stat` на свежесозданный файл:
   ```
   Access: (0644/-rw-r--r--)  Uid: (0/root)  Gid: (0/root)
   ```

**Вывод: самый первый, ещё не ротированный файл создаётся мастер-процессом nginx (root) с
режимом 0644 — это MIRE-readable (бит `r--` у "other"), а не 0640 www-data:adm.** Значит
`deploy` **МОЖЕТ** прочитать его без `sudo` на день 0 — вопреки буквальной формулировке
комментария в коде («`$SUDO` обязателен: logrotate ставит ротированным файлам 0640...»), который
объясняет только пост-ротационный случай и не уточняет, что до первой ротации файл и так
общедоступен на чтение. Дыра **после** первой ротации при этом реальна и корректно закрыта:
logrotate (root, вне nginx) сам создаёт НОВЫЙ пустой файл с `create 0640 www-data adm`
**до** отправки `postrotate`-сигнала (`kill -USR1`) — нового `open()` с `O_CREAT` на уже
существующий путь режим не меняет, значит все ротированные/пост-ротационные live-файлы остаются
`0640 www-data:adm` — недоступны `deploy` (только группа `docker`) без sudo, что и было
первоначальной находкой.

**Итог по разрешительной модели:** фикс (`$SUDO` безусловно перед `stat`/`tail`) — не строго
необходим для дня 0 (файл и так world-readable), но **обязателен и достаточен** начиная с первой
же ротации, что и было целью фикса. Использование `sudo`, когда оно не строго нужно (день 0),
не создаёт регрессии: тот же `SUDO=""; [ "$(id -u)" != "0" ] && SUDO="sudo"` идиома уже
эксплуатируется в проде `watchdog-remediate.sh`/`deploy-bluegreen.sh`/`apply-nginx-vhost.sh` —
это установленный проектный контракт (passwordless sudo для `deploy` на конкретные операции,
конфигурируется вне репозитория на самом VPS), а не новое допущение, которое вводит этот PR.
Единственное, что можно было бы улучшить — комментарий в коде чуть точнее описывает мотивацию
(упоминает только пост-ротационный случай), но это не влияет на корректность самого фикса и не
является функциональным багом. Не блокирует вердикт.

### 6.4. Дополнительно проверенное (не запрошено явно, но напрашивается рядом)

  больше текущего размера файла (ротация уменьшила файл) — код это явно обрабатывает

  ключ `"status":` в самом тексте паттерна делает совпадение уникальным (у `upstream_time`/
  `request_time` в JSON другие имена ключей).
- `scripts/apply-nginx-vhost.sh` теперь копирует и `delovoy-nginx-perf.logrotate` в
  `/etc/logrotate.d/delovoy-nginx-perf`, и `.github/workflows/ops-nginx.yml` действительно
  добавил этот файл в scp `source:` list (проверил diff обоих файлов) — без этого шага фикс
