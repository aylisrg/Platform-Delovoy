## Debounce+AbortController race — подтверждено, добавлен недостающий тест

Проверил все 4 компонента: эффект возвращает
`() => { clearTimeout(timer); controller.abort(); }`. Каждое изменение
`clientPhone` перезапускает эффект, чей cleanup срабатывает **до** тела
нового эффекта — отменяя и незавершённый таймер, и незавершённый fetch.

Просмотрел все 4 тест-файла на набор `fireEvent.change` — ни один не делает
несколько **быстрых последовательных** изменений телефона до истечения
300мс debounce (каждый существующий тест меняет значение поля один раз).
Это ровно тот сценарий гонки, который просил проверить QA-запрос. Написал и
добавил недостающий тест в
`src/components/admin/gazebos/__tests__/quick-booking-popover.test.tsx`:

```ts
it("быстрый ввод отменяет промежуточные запросы — летит только один fetch, с последним значением", async () => {
  vi.mocked(fetch).mockResolvedValue(jsonResponse({ success: true, data: [] }));
  renderPopover(2);

  const phoneInput = screen.getByPlaceholderText("Телефон *");
  fireEvent.focus(phoneInput);
  fireEvent.change(phoneInput, { target: { value: "999" } });
  fireEvent.change(phoneInput, { target: { value: "9991" } });
  fireEvent.change(phoneInput, { target: { value: "99912" } });

  await new Promise((r) => setTimeout(r, 350));

  expect(fetch).toHaveBeenCalledTimes(1);
  expect(fetch).toHaveBeenCalledWith(
    expect.stringContaining("/api/gazebos/guests/search?phone=99912"),
    expect.anything()
  );
});
```

Осознанное отклонение от буквальных значений из запроса ("1"→"12"→"123"):
при `min(3)` первые два значения (длина 1 и 2) вообще не попадают в ветку,
планирующую таймер (`if (query.length < 3) { ...; return; }`), поэтому тест
на буквальных "1"/"12"/"123" проверял бы debounce слабее — по сути только
подтверждал бы, что единственный запланированный таймер (для "123")
действительно сработал один раз, не тестируя отмену уже запланированных
предыдущих таймеров. Взял три значения по 3+ символа (`"999"` → `"9991"` →
`"99912"`), каждое из которых само по себе планирует таймер/fetch — так тест
реально проверяет, что debounce отменяет предыдущие запланированные вызовы,
а не просто что короткие значения не долетают до fetch (это уже отдельно
покрыто существующим тестом "не запрашивает подсказки при вводе короче 3
символов").

Прогон — зелёный (10/10 в файле, см. «Регрессия» выше, обновлённые
289 test files / 4021→4022 в общем прогоне). Чтобы подтвердить, что новый
тест не тавтологичен, замутировал cleanup в самом компоненте (убрал
`clearTimeout(timer);` из `return () => { ... }`, оставив только
`controller.abort();`):
```
FAIL > быстрый ввод отменяет промежуточные запросы — летит только один fetch, с последним значением
AssertionError: expected "vi.fn()" to be called 1 times, but got 3 times
Tests  1 failed | 9 passed (10)
```
Упал ровно новый тест — все остальные 9 остались зелёными (в частности,
`AbortController.abort()` сам по себе не мешает *запланировать* устаревшие
таймеры, только отменяет уже улетевший fetch — без `clearTimeout` все три
таймера долетают до `fetch`, что и поймал новый тест). Восстановил
`git checkout -- src/components/admin/gazebos/quick-booking-popover.tsx` —
`git diff` пусто. **Тест-файл с добавленным тестом сохранён** в этой ветке
(единственное production-затрагивающее изменение этого QA-прохода — не
исправление бага, а добавление недостающего регрессионного покрытия
поведения, которое уже корректно работает в проде и уже описано в review
как debounce+abort «textbook-correct»).

## RBAC — независимая перепроверка (не на веру от ревьюера)

Прочитал сам `requireAdminSection` (`src/lib/api-response.ts:76-100`) и
`hasAdminSectionAccess` (`src/lib/permissions.ts:155-176`):
- Анонимная сессия (`session === null`) → `apiUnauthorized()` внутри самого
  `requireAdminSection`; но оба новых роута уже отсекают это раньше —
  `if (!session?.user?.id) return apiUnauthorized();` — до вызова
  `requireAdminSection` вообще. Подтверждено тестом "требует авторизацию — 401".
- `role === "USER"` → `apiForbidden()`; в роутах отдельно отсекается ещё раньше
  явным `hasRole(session.user, "MANAGER")`. Подтверждено тестом "не пускает
  роль USER — 403".
- MANAGER без гранта на конкретную секцию → `hasAdminSectionAccess` вернёт
  `false` → `apiForbidden("Нет доступа к этому разделу")`. В `permissions.ts`
  это `prisma.adminPermission.findUnique({ where: { userId_section: { userId, section } } })`
  — уникальный ключ **на пару** (не на `userId` целиком), так что грант на
  одну секцию физически не запрашивается и не влияет на проверку другой.
  Косвенно подтверждено существующими независимыми кейсами
  `permissions.test.ts` ("returns true for MANAGER with matching permission"
  на `cafe`, "returns false for MANAGER without permission" на `architect")
  — тот же механизм композитного ключа, не буквально пара `gazebos`/`clients`,
  но идентичный по устройству; `userId_section` — не зависящий от секции
  композитный уникальный индекс, так что вывод переносится без потери
  строгости.
- Оба новых роута гейтятся `requireAdminSection(session, "gazebos"\|"ps-park")`
  — литерал, не параметр запроса, значит атакующий не может подменить секцию
  через query/body. Явный тест `route.test.ts`: `"гейтится через
  requireAdminSection('gazebos'), не через 'clients'"` пинит именно этот выбор.

**AC-4 подтверждаю как выполненное без оговорок.**

## Rate limiting — уточнение наблюдения ревьюера (не блокирует PASS, но точнее)

Ревьюер отметил (Рекомендация 1): новые роуты не рейт-лимитятся, что
формально соответствует политике CLAUDE.md «Admin: no limit», но два похожих
debounced-keystroke эндпоинта (`inventory/sku/search`, `messenger/users/search`)
рейт-лимитятся — и предложил follow-up, не блокируя PASS.

Проверил сам, не только по двум приведённым примерам:

1. **`messenger/users/search` — не показательный прецедент.** Прочитал роут:
   он доступен **и роли `USER`** (`isAdmin = session.user.role !== "USER"` —
   т.е. USER тоже может его вызывать, просто получает неадминский срез
   результатов). Это не admin-only эндпоинт, значит по самой политике
   CLAUDE.md он обязан быть на тир `authenticated` (240/мин), а не
   `admin: no limit` — это не контр-пример, а корректное применение
   политики к другому классу эндпоинта.

2. **`inventory/sku/search` — действительно admin-only И рейт-лимитится.**
   Роут явно проверяет `role !== SUPERADMIN/ADMIN/MANAGER → 403` — то есть
   это ровно тот же класс эндпоинта (роль-гейтед, debounced-keystroke), что и
   новый `guests/search`, но всё равно вызывает `rateLimit(request,
   "authenticated")` с явным комментарием в коде: «endpoint is fired on every
   debounced keystroke». Это прямое противоречие буквальной формулировке
   «Admin: no limit» для этого конкретного под-класса эндпоинтов.

3. **Пошёл дальше двух примеров ревьюера — посчитал по всей кодовой базе.**
   `grep -rl requireAdminSection src/app/api --include=route.ts` даёт 107
   файлов; из них 17 всё же вызывают `rateLimit(request, ...)` (в основном
   email/Telegram-рассылки и финансовые мутации — `send-email`,
   `notification-settings`, `broadcast`, `subscriptions/[id]/adjust` — где
   рейт-лимит защищает не от чтения данных, а от дорогого/абузящегося
   побочного эффекта). Но нашёл и два примера **внутри самого `ps-park`**,
   в том же модуле, что и новая фича: `GET /api/ps-park/sessions/[id]/route.ts`
   и `POST /api/ps-park/session-ending-alert/route.ts` — оба гейтятся тем же
   `requireAdminSection(session, "ps-park")`, оба всё равно вызывают
   `rateLimit(request, "authenticated")`. `session-ending-alert` — с явным
   security-обоснованием в комментарии (был публичным, ловил
   Telegram-HTML-инъекцию, поэтому получил всё сразу: auth + rate-limit +
   Zod + экранирование) — не показательно как «общая admin-политика».
   Но `sessions/[id]` — обычный read-only GET без такой предыстории,
   рейт-лимитится без явного обоснования в коде — реальный, пусть и
   единичный, прецедент рейт-лимита на чисто admin-gated GET того же модуля.

**Вывод, уточняющий рекомендацию ревьюера**: буквальная формулировка «Admin:
no limit» в CLAUDE.md — не строго соблюдаемая машинная политика (нет
отдельного `"admin"`-тира в `rateLimit()`, только `"public"`/`"authenticated"`
плюс статические спец-конфиги — admin-роуты просто *не вызывают* `rateLimit`
по умолчанию), а скорее конвенция по умолчанию с реальными исключениями,
включая debounced-keystroke-эндпоинты (наиболее прямое сходство с
`guests/search`) и один прецедент в том же самом `ps-park`. Это не basis для
NEEDS_CHANGES/FAIL — согласно `agents/qa.md`, обязательный security-кейс для
QA — «Rate limiting работает на публичных эндпоинтах», а эти роуты не
публичные (role-gated). Но отмечаю точнее, чем «genuinely non-issue,
policy-compliant»: это реальная, пусть и мелкая, непоследовательность,
заслуживающая follow-up issue (а не просто рекомендации на усмотрение) —
добавить `rateLimit(request, "authenticated", session.user.id)` в оба новых
роута, по прецеденту `inventory/sku/search` и `ps-park/sessions/[id]`.

пред-существующая характеристика поиска по броням в этой кодовой базе, не
новый недостаток этой ветки. Деградирует мягко (гость просто не появится в
подсказке — fallback на ручной ввод, AC-3), не даёт ошибок. **Согласен: не

## Edge cases

- Пустой `phone` / отсутствие параметра в query — `guestSearchQuerySchema`
  требует `string`, `Object.fromEntries` на пустом query даёт `{}` →
  Zod "invalid_type" → 422 (проверено лично через `tsx`-скрипт вне тестов).
- `phone` из одних пробелов (`"   "`) — `.trim()` схлопывает до `""`, длина
  0 < 3 → срабатывает именно кастомное сообщение `.min(3, "Минимум 3 символа
  для поиска")`, не generic Zod-ошибка (проверено лично).
- Гость без `clientPhone` или `clientName` в БД (историческая бронь без
  контакта) — `searchGuestsByPhone` явно пропускает такие записи (`if
  (!b.clientPhone || !b.clientName) continue`), тест "пропускает записи без
  clientPhone или clientName" подтверждает.
- Больше 8 совпадений — обрезается `MAX_RESULTS = 8`, тест "ограничивает
  выдачу 8 гостями" подтверждает.
- Нет совпадений вовсе — пустой массив, AC-3 fallback на ручной ввод
  (см. таблицу AC выше).
- Rapid typing (гонка debounce) — подтверждено собственным тестом (см. выше),
  только последнее значение долетает до fetch, промежуточные отменяются.
- Cross-module изоляция — `moduleSlug` хардкожен на уровне роута (не из
  запроса), плюс юнит-тест сервиса ловит регрессию в фильтре `where` (см.
  mutation (a) выше).
