## 5. БАГ-1 (Major, блокирующий) — P0-issue лжёт про авто-откат, когда предыдущего SHA нет

**Модуль:** `error-budget-watch` (`scripts/lib/error-budget.ts`)

**Шаги воспроизведения:**
1. `PREVIOUS_SHA` пуст (реальный кейс: самый первый деплой после мержа этой фичи — `DEPLOYED_SHA_PREVIOUS` ещё ни разу не был записан, см. п.3) и одновременно `after`/`before` дают `action=rollback` (например before=5, after=30).
2. Вызвать `errorBudgetIssue({ action: 'rollback', previousSha: null, ... })` (или прогнать `error-budget-watch.ts` целиком — воспроизвёл оба раза, см. сценарий 5 выше).

**Ожидаемый результат:** issue должен ясно сообщать, что авто-откат **не выполнен** (ровно как это делает соседний шаг Telegram-алерта — строки 162-168 `deploy-error-budget.yml`: `"Предыдущего успешного деплоя не найдено — откат пропущен, нужна ручная проверка."`).

**Фактический результат:** тело issue безусловно содержит:
```
🔴 **Авто-откат запущен** — деплой `cafe0005` откатывается на предыдущий успешный `?`.
```
(`error-budget.ts:89-92`, `rollbackLine` строится по `i.action === 'rollback'` без проверки `i.previousSha`; `(i.previousSha ?? '?')` подставляет буквальный символ `?` вместо SHA). При этом шаг диспатча в `deploy-error-budget.yml` (`if: steps.decide.outputs.action == 'rollback' && steps.decide.outputs.previous_sha != ''`) в этом случае реального отката **не запускает** — issue и реальность расходятся.

**Почему это блокер, а не косметика:** это единственный постоянный (не-Telegram, не теряется в чате) артефакт инцидента с меткой `prio:P0`, который читает дежурный при разборе последствий регрессии. Он утверждает, что необратимое действие (откат прода) уже выполняется, когда на самом деле откат пропущен и требуется ручное вмешательство — прямая противоположность тому, что нужно знать дежурному в момент реального инцидента. Это ровно "худший вариант" уже описанного в задаче остаточного ограничения, а не то же самое: там PREVIOUS указывает на не тот (но существующий) коммит, здесь issue заявляет о действии, которого не было, с явно битой подстановкой `?`.

Ни один из 19 существующих тестов не покрывает комбинацию `action: 'rollback'` + `previousSha: null` — тест "rollback issue упоминает предыдущий SHA и авто-откат" (`error-budget.test.ts:114-128`) всегда передаёт непустой `previousSha`.

**Рекомендация Developer'у:** сделать `rollbackLine` в `errorBudgetIssue()` (`scripts/lib/error-budget.ts:89-92`) условным по `i.previousSha`, зеркально Telegram-шагу:
- `previousSha` есть → текущий текст ("Авто-откат запущен... на `X`");
- `previousSha` пуст → явно "Авто-откат пропущен — предыдущий успешный SHA не найден, нужна ручная проверка" (без `?`).

## 6. Finding-2 (Minor, не блокирует) — неэкранированное сообщение коммита в markdown-ссылке issue

`errorBudgetIssue()` (`error-budget.ts:87`): `` `- \`${sha}\` [${message.split('\n')[0].slice(0,100)}](${url})` ``. Сообщение коммита не экранируется. Собранным PoC подтвердил: сообщение коммита вида `` fix: `](evil)[click me](https://evil.example.com) ``` injected `` ломает разметку и вставляет отдельную кликабельную ссылку на произвольный внешний URL внутрь автоматически создаваемого P0-issue (`agents/SECURITY.md` §1 явно перечисляет markdown injection как класс атаки, требующий экранирования). Пустое/whitespace-only сообщение коммита рендерится как `[](url)`/`[   ](url)` — косметически не страшно, не ломает структуру.

Не считаю блокером: эксплуатация требует коммита, уже смерженного в `main` (уже высокий уровень доверия — CLAUDE.md запрещает прямой push в `main`, только через PR с ревью), т.е. атакующий с таким доступом может нанести куда больший вред напрямую. Рекомендую отдельным тикетом на усиление (экранировать `[`, `]`, `` ` `` в сообщении коммита перед вставкой), не требую блокировать этот PR.

## Вердикт: FAIL

Причина — **БАГ-1** (раздел 5): при срабатывании `action=rollback` без доступного `previousSha` (реальный, не гипотетический путь — самый первый деплой после появления этой фичи, либо любая последующая потеря repo-переменной `DEPLOYED_SHA_PREVIOUS`) создаваемый P0-issue безусловно заявляет "Авто-откат запущен" с битым placeholder'ом `?` вместо SHA, хотя шаг диспатча в `deploy-error-budget.yml` в этом случае реальный откат **не** выполняет. Telegram-алерт для этого же случая сформулирован верно ("откат пропущен, нужна ручная проверка") — расхождение именно между двумя каналами оповещения означает, что постоянный, более авторитетный артефакт инцидента (GitHub issue) может ввести дежурного в заблуждение ровно в момент, когда точность важнее всего. Это тот самый "худший вариант" уже описанной проблемы, который просила найти задача, воспроизведён и напрямую (`errorBudgetIssue()`), и end-to-end (`error-budget-watch.ts` против самодельного fake-GitHub-API, сценарий 5).

Всё остальное — SHA-ротация (фикс 1-го прохода ревью), 6 сценариев `error-budget-watch.ts`, YAML/shell/SQL (включая живой psql с fixture-данными на границах окон), `HOLD_PATTERNS`/тир авто-мержа, регрессия — подтверждено эмпирически и соответствует заявленному. Finding-2 (неэкранированное сообщение коммита в markdown-ссылке) зафиксирован для трекинга, не блокирует сам по себе.

**К повторной проверке после фикса БАГ-1** — предлагаемое исправление в разделе 5 небольшое (условная ветка в `rollbackLine`, зеркальная уже существующей логике Telegram-шага), не требует архитектурных изменений.
