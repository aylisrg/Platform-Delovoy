## Findings

Серьёзности: blocker / major / minor / nit. Blocker и major — нет.

### Minor

1. **minor** — `src/app/r/[code]/route.ts:39`. При превышении лимита `public` роут отвечает `302` на главную до разбора кода. ADR §Q4 обещает «в худшем случае теряла запись клика, а не переход», AC-D3.11 — «лимит не должен мешать мобильным пользователям за общим адресом». Бакет `rate-limit:public:ip:{ip}` общий для всех публичных API, а отклонённые запросы всё равно добавляются в окно (`zadd` до проверки), поэтому за CGNAT насыщенный IP остаётся насыщенным, и тап по кнопке «Открыть задачу» уводит на главную. Исправление: отдельный (более высокий) тир для `/r`, либо при превышении всё равно читать сохранённую цель и редиректить на неё, пропуская только запись клика.
2. **minor** — `src/modules/notifications/dispatch/channels/web-push/index.ts:94` + `public/sw.js` (`notificationclick`). Раньше `url` в push всегда был `/admin/dashboard`, и Service Worker искал окно админки. Теперь `url` — `https://…/r/<код>`, в нём нет подстрок `/admin` и `/webapp`, `matchAny` становится `true`, и SW навигирует первое попавшееся окно сайта (в том числе публичную страницу или Mini App) на трекинг-ссылку. Исправление: в SW считать `/r/` отдельным случаем (всегда `openWindow` или предпочитать админ-окно), либо слать в `data.url` итоговый путь, а трекинг — отдельным полем.
3. **minor** (hardening) — `src/modules/telegram-link/service.ts` (`attachTelegram`, ветка «оболочка → `mergeAccounts(self_link)`», вызывается из `processDeepLink`). Раньше конфликт «Telegram уже привязан» защищал владельца Telegram: любой, кто один раз открыл Mini App (оболочка создаётся автоматически), получал 409. Теперь тот, кто нажал Start по чужой ссылке `t.me/…?start=link_<token>`, молча вливает свою пустую оболочку в аккаунт автора ссылки: его Telegram и будущая активность в Mini App оказываются в чужом аккаунте. Требует социальной инженерии, но поверхность шире, чем до PR. Исправление: перед вызовом `deep-link` бот показывает имя аккаунта и просит подтвердить («Привязать / Отмена»), либо автослияние только для оболочек моложе N минут без активности в Mini App.
4. **minor** — `src/modules/notifications/audience.ts:73-79` (кандидаты Авито). Старый запрос получателей лидов фильтровал `module: { slug, isActive: true }`; в резолвере (и в `StaffSnapshot.assignments`) `isActive` потерян — назначенные на деактивированный модуль теперь получают лиды. Исправление: вернуть условие `isActive` либо явно зафиксировать смену поведения в release notes.
5. **minor** — `src/modules/clients/merge.ts:725-741` (шаг 11). Строки списков получателей вторичного переносятся на основной без проверки допуска. Если основной — USER, строки инертны, но считаются в `listRowCount` и подавляют общий чат раздела: событие не получает никто. Исправление: переносить только строки, где основной допущен (SUPERADMIN/ADMIN, либо MANAGER с назначением на модуль), остальные удалять и показывать в «Не будут перенесены».
6. **minor** — `src/components/admin/notifications/matrix-table.tsx:~105` (`categories`). Опции фильтра «Категория» строятся из уже отфильтрованного `data.events`, поэтому после выбора категории остальные пропадают из списка — переключиться напрямую нельзя, только через «Все категории». Исправление: строить опции из статического `NOTIFICATION_CATALOG`.
7. **minor** — `src/components/admin/users/team-review-table.tsx:80-101`, `matrix-table.tsx:~35-52`, `profile/notifications-block.tsx`: загрузки без отмены/счётчика запросов. При быстрой смене фильтров ответ более раннего запроса может прийти позже и перезаписать результат нового; индикатора загрузки при смене фильтра нет. Исправление: `AbortController` или номер запроса (как в `use-stats-fetch.ts`, где это сделано правильно).

## Security

- **Secrets leakage: OK.** В ответах нет `passwordHash`, токенов, `externalId`, `payload`, `targetUrl`, кодов трекинга и Telegram ID (только флаги `hasTelegram`/`isSeededSuperadmin`/`telegramLinked`); тексты уведомлений в «последних» не отдаются; OTP не пишется в логи (`sensitive` не логирует тело, в Redis лежит `sha256(code+telegramId)`, сравнение `timingSafeEqual`); в AuditLog Telegram ID маскируется (`maskChatId`), email/телефон в записи исключения отсутствуют. Хардкода секретов нет; `.env*` не добавлены.
- **RBAC: OK.** Все новые/изменённые `/api/users/**` и `/api/admin/{permissions,notifications/matrix,notifications/stats,modules/[slug]/recipients}` проверяют `SUPERADMIN` до Zod и бизнес-логики (в т.ч. при выданной секции «Пользователи»/«Уведомления»); страницы `/admin/users/[id]`, `/admin/notifications/matrix|stats` гейтятся на сервере (`redirect`); Mini App-роуты используют `verifyWebAppToken` (+ `loadWebAppStaff` для Центра), `userId` берётся из токена, не из тела; `deep-link` сверяет `x-bot-token` через `safeCompare` (`timingSafeEqual`).
- **Injection: OK.** Raw SQL — только тегированные шаблоны `$queryRaw`/`$executeRaw` и `Prisma.sql` с привязанными параметрами (в т.ч. массивы `ANY($ids)`); `$executeRawUnsafe`, `dangerouslySetInnerHTML`, `innerHTML` в добавленном коде нет.
- **Open redirect: OK.** Цель только из БД, нормализуется при записи и повторно при редиректе; query-параметры не читаются; всегда `302`; `no-store`, `no-referrer`, `noindex`; HEAD/боты/prefetch не считаются кликом; код 128 бит. Фактически проверено (см. таблицу выше).
- **OTP не раскрывает существование аккаунта: OK** (общий ответ во всех ветках, SMTP-проверка до поиска аккаунта). Единственный оракул — 502 при отказе SMTP именно на этом адресе; задокументирован и ограничен лимитами. Код одноразовый (`DEL` как захват права), счётчики попыток/адресов, SUPERADMIN никогда не получает код.
- **Слияние атомарно и защищено: OK.** Себя, последний суперадмин, сидированный суперадмин, уже влитый, конфликт Telegram с отдельным подтверждением, два ACTIVE-абонемента — все проверены внутри транзакции после блокировки строк; повышения прав нет (роль и права основного).
- **Отзыв сессий: OK.** `sv` ставится при входе, полный `jwt`-callback сверяет с состоянием (Redis 60 с → БД), несовпадение перечитывает роль/разделы, влитый/удалённый → `null` (проверено по исходникам `@auth/core`: `null` чистит cookie, `auth()` → `null`), при сбое перечитывания разделов — понижение до USER, fail-open только при недоступности и Redis, и БД; прокси не менялся; `SessionWatcher` перепроверяет каждые 30 с и на focus; Mini App-токен несёт `sv`, расхождение → 401 → один повторный выпуск токена клиентом. Токены без `sv` трактуются как 0 — массового разлогина нет (у ADMIN после миграции версия 1: токен обновится на следующем запросе).
- **Supply chain: OK.** Зависимости не добавлялись, `package.json`/lock не менялись.
- **Dangerous ops: OK.** Миграция только аддитивная (`ADD COLUMN`, `CREATE TABLE/INDEX`, бэкфилл `INSERT … ON CONFLICT DO NOTHING`, `UPDATE` новых полей), ключ `Module.config.notificationRecipients` сохранён для blue-green; `rm -rf`/`push --force` в скриптах нет.
- Единственное замечание по безопасности — finding 3 (hardening, не инцидент).
