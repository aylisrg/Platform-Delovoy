## Метод верификации (шаг 5 задания) — почему тест не выдуман

Это конфиг-файл GitHub, не тестируемая бизнес-логика — `agents/qa.md`/CLAUDE.md не предполагают
Vitest-теста на содержимое `.github/CODEOWNERS`, и придумывать фиктивный `it(...)` вокруг чтения
текстового файла было бы имитацией проверки, а не проверкой. Фактическое соблюдение branch
protection (GitHub реально запросит ревью `@aylisrg` при PR на `src/proxy.ts`) — эффект,
наблюдаемый только на стороне GitHub API/UI при открытии PR, недоступен для локальной
детерминированной проверки в рамках этой сессии.

Вместо этого использован метод, достаточный для доказательства корректности фикса:
1. Прочитан фактический файл `.github/CODEOWNERS` целиком (не полагаясь на diff) — подтверждает
   итоговое состояние, не только направление изменения.
2. Независимо (не по тексту issue) подтверждено существование `src/proxy.ts` и отсутствие
   `src/middleware.ts` через `ls` — ровно тот факт, который делает старую строку CODEOWNERS
   мёртвой, а новую — живой.
3. Синтаксис новой строки посимвольно сверен с соседними, заведомо рабочими строками того же
   файла (`/src/lib/auth.ts @aylisrg` — тот же паттерн: security-critical single-file path с
   ведущим `/`) — GitHub уже применяет это правило к `auth.ts`, значит применит и к `proxy.ts`.
4. Полнотекстовый grep репозитория на `src/middleware\.ts` (см. ниже) исключает, что где-то ещё
   в живых (не исторических) конфигах/workflow'ах остался тот же мёртвый путь, требующий
   аналогичного фикса в рамках этого же PR.

Совокупность (существование целевого файла + отсутствие исходного + синтаксическое соответствие
работающему прецеденту в том же файле) — достаточное доказательство корректности точечного
однострочного конфиг-фикса; дальше идёт уже не QA, а верификация поведения самой платформы
GitHub, вне периметра репозитория.
