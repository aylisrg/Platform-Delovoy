# Блокировка IP у потребительских операторов (ТСПУ) — 2026-07-20

**Статус:** дополнительный IP `85.193.89.242` заказан, поднят на сервере и проверен; ожидает переключения DNS (reg.ru, вручную владельцем).

## Симптом

«Сайт отвечает, но грузится вечно» / вечный спиннер **на всех устройствах владельца во всех его сетях** (домашний провайдер + чистый LTE Мегафон/Yota, Safari и Chrome, комп и телефон), при этом:
- 200 OK за 0.08–0.3с из 5 стран и 3 российских дата-центров (check-host: Москва×2, СПб);
- SSLLabs A+, chain issues 0, все современные клиенты проходят симуляцию;
- DNS чистый: единственный A `91.222.236.239`, AAAA нет, RU-резолверы отдают то же.

## Решающий тест

Заход с поражённого устройства по **голому IP** `https://91.222.236.239` (мимо DNS и SNI) → тоже вечный спиннер = **TCP-коннект не устанавливается**. VPN не помогает (типовые VPN не туннелируют .ru-домены — split tunneling).

## Диагноз

**IP `91.222.236.239` (Timeweb) дропается на ТСПУ у потребительских операторов** — фильтры стоят у consumer-провайдеров и мобильных операторов, дата-центровые маршруты идут мимо. Вероятно «за соседа» по переиспользуемой подсети. Волновой характер блокировок объясняет и прежние «циклические» жалобы, не коррелировавшие с деплоями.

### Сигнатура для будущих инцидентов
`у пользователя вечный спиннер по голому IP` + `200 OK из дата-центров` = блокировка пути (ТСПУ), сайт и сервер ни при чём. Не тратить время на приложение.

## Лечение (выполнено)

1. **Дополнительный IPv4 через Timeweb API** (иная подсеть):
   `timeweb-manage.yml → custom-api`, `POST /api/v1/servers/7548623/ips` body `{"type":"ipv4","ptr":"delovoy-park.ru"}` → выдан `85.193.89.242`.
2. **Поднятие IP в ОС** — новая операция `timeweb-manage.yml → ops-add-ip` (этот PR): рантайм `ip addr add IP/32 dev eth0` + systemd-юнит `secondary-ip.service` для персистентности. **Сознательно не через netplan**: `netplan apply` рвёт сеть живого сервера, а drop-in со списком `addresses` при merge заменяет (а не дополняет) адреса и может снести основной IP на ребуте.
3. **Проверка**: локально nginx на новом IP — 200; `curl --resolve delovoy-park.ru:443:85.193.89.242` — 200/1.4с; TCP с RU-узлов — 2–10мс; с устройства владельца из поражённой сети — по чек-листу ниже.

## Переключение DNS (владелец, панель reg.ru — NS домена ns1/ns2.reg.ru)

1. Проверить с телефона `https://85.193.89.242` — **предупреждение о сертификате = коннект есть, IP чист** (если снова вечный спиннер — IP тоже блокирован, заказать другой: `timeweb-manage → custom-api POST /api/v1/servers/7548623/ips`, повторить `ops-add-ip`).
2. reg.ru → Домены → delovoy-park.ru → DNS-серверы и зона → изменить **обе A-записи** (`@` и `www`): `91.222.236.239` → `85.193.89.242`. TTL, если поле доступно, — 300.
3. Старый IP остаётся на сервере (основной у Timeweb) — клиенты с кэшированным DNS продолжают попадать на сайт из незаблокированных сетей до истечения TTL (2ч).
4. Проверка после переключения: `dig +short delovoy-park.ru` → `85.193.89.242`; сайт открывается с телефона владельца; из DC — по-прежнему 200.

## Дальнейшие шаги

- Тикет в поддержку Timeweb: «IP 91.222.236.239 недоступен из потребительских сетей (Мегафон/Yota, домашние провайдеры), предположительно ТСПУ; выдайте информацию/замените основной IP или подайте на исключение» — Timeweb сталкивается с этим регулярно.
- `secrets.VPS_HOST` в GitHub указывает на старый IP — деплой работает (GitHub-раннеры не фильтруются ТСПУ), но при отказе от старого IP секрет нужно обновить на `85.193.89.242`.
- Опционально: вторая A-запись как горячий резерв не рекомендована (браузерный фолбэк при молчаливом дропе медленный); лучше держать процедуру смены IP наготове (этот док).
