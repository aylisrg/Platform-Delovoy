# Инцидент: ложный CRITICAL «Контур решений владельца молчит»

**Дата:** 2026-09-03
**Статус:** закрыт — причина установлена, порог и дедупликация алерта исправлены
**Сигнал:** личное Telegram-сообщение владельцу в 05:31 UTC:
«🚨 [CRITICAL] owner-decisions — Контур решений владельца молчит 49 мин — секрет не задан или сайт недоступен для свипера»

## TL;DR

Контур **не ломался**. `OWNER_DECISIONS_SECRET` задан, сайт из Actions
доступен, все 799 прогонов свипера за 12 дней зелёные, heartbeat пишется.
Молчал не контур, а планировщик GitHub Actions: cron `*/15` у
`issue-queue-merge.yml` ночью шёл с дырами 68, 96 и 49 минут при пороге
тухлости 40 минут. Порог был взят из расчёта «2–3 тика по 15 минут», а cron в
GitHub — best-effort и таких гарантий не даёт.

Второй дефект того же алерта — частота: пока heartbeat считался протухшим,
каждый опрос `/api/notifications/health` (site-watchdog раз в 5 минут) рождал
новый CRITICAL, а троттлинг `log.critical()` — всего 300 секунд. За две ночные
дыры владелец мог получить до дюжины одинаковых сообщений.

## Данные

Прогоны `issue-queue-merge.yml` 2026-08-22 23:04 → 2026-09-03 05:57 (799 шт.,
все `success`, кроме одного `cancelled` по concurrency 23 августа):

| Дыра между прогонами | Сколько раз |
|----------------------|-------------|
| ≥ 40 мин (старый порог) | 41 |
| ≥ 60 мин | 21 |
| ≥ 120 мин | 11 |
| ≥ 180 мин | 7 |
| максимум | 261 мин (28 августа, 12:01 → 16:22) |

27–28 августа тики шли раз в 3–4 часа весь день. `site-watchdog.yml`
(cron `*/5`) молчал в те же ночные окна (03:11 → 04:42 — 91 мин), то есть
задерживается планировщик GitHub для всего репозитория, а не наш workflow:
ни падений, ни отмен, ни задержки в очереди раннеров.

Следствие: **любой** порог в десятках минут даёт ложные срабатывания почти
каждую ночь. Ложных CRITICAL в личку владельца с момента появления проверки
(ADR 2026-08-24) было, вероятно, не один десяток.

## Что починено

1. **Порог** `OWNER_DECISIONS_STALE_MINUTES`: 40 → 360 минут
   (`src/modules/notifications/health.ts`). Худшая наблюдавшаяся дыра ×1.4.
   Реальная поломка контура (секрет не задан, сайт недоступен из Actions)
   длится днями, пока её не починят — обнаружение за 6 часов ничего не
   теряет, а инцидент 2026-08-24 (4 дня незамеченного молчания) по-прежнему
   ловится.
2. **Один алерт на эпизод молчания** — `shouldAlertOwnerDecisionsSilence()`:
   Redis `SET NX EX` с ключом по последнему heartbeat, повтор того же эпизода
   не чаще раза в 6 часов. Redis недоступен — fail-open (лучше лишний алерт,
   чем потерянный инцидент), шторм тогда ограничен троттлингом
   `log.critical()`.
3. **Текст алерта** теперь содержит порог и время последнего heartbeat, а
   причины перечислены честно: секрет не задан, сайт недоступен из Actions
   **или workflow не запускается** — по этим данным отличить задержку cron
   от поломки можно без захода в GitHub.

## Что не трогали и почему

- **Cron-расписание свипера** — сдвиг минут (`7,22,37,52`) помогает от
  толчеи в `:00`, но не от задержек в часы; менять расписание hold-класса
  ради этого не стоит.
- **Второй heartbeat из другого workflow** (`issue-queue.yml`, ежечасно) —
  задержки планировщика коррелированы для всех workflow репозитория, второй
  источник ничего не добавит.
- **503 от health при стейле** — семантика ADR 2026-08-24 сохранена; с новым
  порогом ложные 503 по этой причине исчезают.

## Побочная находка — для #708 (`notifications-down`, 37 циклов за 7 дней)

Живая выборка `/api/notifications/health` во время разбора: 44 запроса с
интервалом 2–4 с, в 6 из них одна-две из трёх Telegram-проб (`getMe`,
`getChat` админ-группы, `getChat` владельца — каждый раз разные) вернули

```
configured: Timeout after 2667ms connecting to https://api.telegram.org;
direct: fetch failed (UND_ERR_CONNECT_TIMEOUT)
```

при том, что owner-decisions всё это время был здоров. То есть дневные
инциденты `notifications-down` (2 сентября — девять штук при дырах свипера не
больше 46 минут) — это кратковременные обрывы соединения VPS → api.telegram.org,
которые здоровая проба ловит с вероятностью ~14 % на запрос; site-watchdog
пробует дважды с паузой 10 с и всё равно регулярно попадает в окно. Данные
переданы в #708; решение (гистерезис по нескольким подряд неудачным пробам,
повтор пробы внутри запроса или мягкая деградация одной из трёх) — задача
#708, а не этого инцидента.
