# /next-issue — взять следующую задачу из автоочереди и довести до мержа

Ты — воркер автономной разгрузки бэклога. Тебя разбудил Routine по расписанию;
пользователя рядом нет и не будет. Работай до конца или до честного блокера.

Полное описание системы — `docs/architecture/2026-08-10-autonomous-issue-cleanup-adr.md`.

**Одна сессия = одна issue = один PR.** Не бери вторую, даже если первая оказалась мелкой.

---

## 1. Выбрать задачу

```bash
npx tsx scripts/issue-queue.ts next
```

- `picked: null` → прочитай `reason` и **закончи сессию**. Это не ошибка: очередь
  выключена, упёрлась в backpressure или уже занята. Ничего не чини, просто выйди.
- Есть номер → это твоя задача. Дальше по тексту `$ISSUE`.

Взять лок (до единой строчки кода — иначе параллельная сессия возьмёт то же самое):

```bash
npx tsx scripts/issue-queue.ts claim $ISSUE
```

## 2. Понять задачу

Прочитай тело issue целиком и всё, на что оно ссылается: QA-отчёты в
`docs/qa-reports/`, ADR в `docs/architecture/`, инцидент-доки в `docs/incidents/`.
В issues этого проекта обычно уже указаны конкретные файлы и строки — доверяй им,
но проверяй: код мог уехать.

Отдельно прочитай `CLAUDE.md`. Он источник правды по архитектуре, и его правила
(RBAC, `apiResponse()`/`apiError()`, Zod на входах, бизнес-логика в `service.ts`,
никакого `any`) — не рекомендации.

Если задача требует нового модуля, которого нет в таблице модулей CLAUDE.md, —
это scope creep. Верни задачу и выйди:

```bash
npx tsx scripts/issue-queue.ts release $ISSUE "нужен новый модуль без PRD — scope guard"
```

## 3. Ветка

```bash
git checkout main && git pull origin main
git checkout -b claude/issue-$ISSUE-<короткий-slug>
```

Префикс `claude/issue-<номер>-` обязателен: по нему очередь связывает PR с issue,
даже если тело PR перепишут.

## 4. Реализовать

- Правь ровно то, что описано в issue. Заметил рядом второй баг — **не чини**,
  заведи отдельную issue с `prio:*` + `auto:ready`, очередь до неё дойдёт.
- Тесты пишутся в том же коммите, что и код (правило CLAUDE.md). Новая функция
  в `service.ts` → тест в `__tests__/service.test.ts`. Баг-фикс → тест, который
  падал до фикса. Без теста PR не считается сделанным.
- Прогони перед коммитом:

```bash
npm test && npx tsc --noEmit && npm run lint
```

Всё три должны быть зелёными локально. Красный CI на PR — это твоя работа,
не проблема ревьюера.

## 5. Проверка своей работы

Запусти двух субагентов (`Agent`), последовательно:

1. `code-reviewer` — соответствие issue/ADR, RBAC-дыры, утечки секретов, scope creep.
2. `qa-engineer` — только после вердикта PASS от первого.

Вердикт `NEEDS_CHANGES` — чини и запускай заново, до трёх кругов. После третьего
круга останови работу: закоммить что есть, открой PR черновиком, опиши в теле, на
чём застрял, и оставь issue в `auto:wip`. Дальше разберётся владелец.

## 6. PR

> Тебя разбудил Routine, а такие сессии стартуют **без MCP-инструментов**:
> `mcp__github__*` недоступны, есть только Bash. Весь цикл PR поэтому идёт через
> тот же CLI — он ходит в GitHub через curl и работает всегда.

```bash
git push -u origin claude/issue-$ISSUE-<slug>
npx tsx scripts/issue-queue.ts pr-open $ISSUE claude/issue-$ISSUE-<slug>
```

Команда создаёт **черновик** с готовой строкой `Closes #$ISSUE` и печатает номер
PR (повторный вызов не плодит дубли). Перепиши тело PR: что было сломано, что
изменено, как проверено, что осталось за кадром.

Дальше дождись CI — одним вызовом, без ручного опроса:

```bash
npx tsx scripts/issue-queue.ts pr-wait $PR 30
```

- `state: green` → шаг 7.
- `state: red` → чини сам, пушь, снова `pr-wait`. Красный CI на своём PR — твоя
  работа, а не проблема ревьюера. Круг за кругом, пока не позеленеет.
- `state: timeout` → CI завис. Оставь PR черновиком, опиши в теле, что видел.

## 7. Мерж

```bash
npx tsx scripts/issue-queue.ts gate $PR
```

- `tier: "auto"` → сними черновик и мержи:

  ```bash
  npx tsx scripts/issue-queue.ts pr-ready $PR   # если нужно снять draft вручную
  npx tsx scripts/issue-queue.ts pr-merge $PR
  ```

  `pr-merge` — последний предохранитель: он сам перепроверяет и гейт, и зелёный
  CI, и отказывается мержить черновик. Верит только себе, не тебе. После мержа
  issue закроется по `Closes #`.

- `tier: "hold"` → **не мержи**. Оставь черновиком, повесь на PR лейбл
  `needs-owner`, комментарием перечисли причины из вывода гейта. Так бывает,
  когда PR трогает миграции, `infra/`, деплой-workflow или 5+ модулей: мерж в
  `main` запускает деплой в прод, и такие изменения владелец смотрит глазами.

- `pr-merge` ответил «GitHub отказал в мерже» → почти наверняка branch
  protection требует ревью. Не обходи: лейбл `needs-owner` и объяснение в
  комментарии.

## 8. Конец

Сессия заканчивается, когда PR замержен, либо когда PR висит на `hold`/блокере и
всё нужное написано в его теле. Промежуточных состояний не оставляй: очередь
должна быть либо пустой, либо занятой чем-то живым.

Не пиши владельцу отчётов в личку и не заводи «итоговых» issues — дашборд
`auto:dashboard` обновляется сам и уже всё показывает.
